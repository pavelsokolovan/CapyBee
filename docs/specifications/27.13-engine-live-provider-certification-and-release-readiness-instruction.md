# Spec 27.13 — Live Provider Certification and Full-Game Release Readiness

**Type:** Release, certification, packaging, and operations specification  
**Parent:** Spec 27.12 — Rich Reference Full Generated Game  
**Depends on:** Specs 25, 26.1, and 27.1–27.12  
**Baseline:** repository commit `32ce630`, plus the approved designs and implementation delivered by Specs 27.4–27.12. The current Anthropic adapter/configuration, structured generation result and error contracts, generation execution summaries, session-backed CLI, legacy live-smoke path, shaded CLI JAR, developer launcher, CI workflow, and `lanterns-of-willow-marsh` reference pack were inspected while writing this specification. The build was not run. Existing work was not modified.  
**Status:** Ready for implementation after Spec 27.12  
**Primary outcome:** A release candidate can be built once, verified offline, launched from an unpacked distribution, and optionally certified against one explicitly pinned live provider model by completing the frozen reference game through its success, partial-success, and responsible-postponement routes. Certification is cost-bounded, produces privacy-safe machine-readable evidence, detects compatibility and quality drift, and never makes ordinary tests or provider-free play depend on network access.

---

## 1. Purpose

Specs 27.4–27.12 make a full generated game playable and provide one rich reference adventure. They do not yet answer the release question:

> Can the exact CLI artifact that will be distributed start, save, resume, and finish a full generated game with the selected live model, within declared quality, call, time, and cost limits, while still completing safely when that provider is absent?

The current `--live-smoke` option is useful but too narrow for this proof. It runs the classic, non-session console, checks only a subset of stages, has no frozen certification suite, has no monetary admission limit, and does not create a release evidence bundle. It also cannot prove package layout, persistent resume, all three result classes, or operational rollback.

Spec 27.13 closes the full generated CLI milestone by defining:

- deterministic offline gates for every change;
- a distributable CLI release bundle;
- a one-command package verification flow;
- a separate, explicit, paid live-provider certification flow;
- objective compatibility, quality, latency, call, and cost gates;
- privacy-safe evidence and release approval;
- provider-disable, rollback, and incident procedures.

The provider remains optional at runtime. A certification failure blocks the **live-certified** release label; it must not make the reviewed authored fallback game unplayable.

## 2. Current implementation findings

| ID | Finding | Consequence |
|---|---|---|
| F1 | `PlayMain` creates the Anthropic adapter only when `--generated` or `--live-smoke` is present. Missing provider configuration becomes a null generator and therefore authored fallback. | Preserve provider-free completion and make provider choice explicit in certification. |

| F4 | Current defaults are a five-second connection timeout and a 25-second response timeout. | Treat these as the v1 certified adapter configuration and record them in evidence. |
| F5 | The adapter sends structured-output requests with Anthropic API version `2023-06-01`, caps responses at 1 MiB, caps output text at 256,000 characters, and caps combined structured input at 64,000 code points. | Certification must lock these protocol values and prove boundary/error behavior offline. |
| F6 | The adapter maps authentication, permission, rate-limit, timeout, billing, structured-output support, invalid-response, and availability failures to stable codes. | Evidence and operator guidance use stable codes, never raw response bodies. |
| F7 | The adapter reports returned model ID and token usage. | F8 | The generation pipeline permits at most the pack-defined repair count and falls back safely after provider or validation failure. | Runtime resilience remains unchanged. Live certification may accept a bounded repair but must reject fallback. |
| F9 | Session play is the normal `play` entry point, saves automatically, and supports quit/resume. | Certification must exercise session play, not only the legacy classic console. |
| F10 | `--live-smoke` cannot be combined with session mode and checks SCENARIO, CAST, QUEST, and two scenes, but not the complete five-stage/full-route contract. | Replace it as release evidence with a dedicated `certify` command; keep it temporarily for compatibility. |
| F11 | The CLI Maven module already creates an executable shaded JAR with `PlayMain`. | Build a release archive around that exact JAR rather than creating a second runtime. |
| F12 | `dev.ps1 game` builds and launches the shaded JAR, but there is no release archive, checksum manifest, SBOM, or certification action. | Add convenience actions while keeping direct `java -jar` commands authoritative. |
| F13 | Standard CI runs `mvn -B -f app/engine/pom.xml clean verify` on Java 25 without credentials. | Keep all pull-request and normal branch CI offline and secret-free. |
| F14 | `lanterns-of-willow-marsh` has stable success, partial, and responsible-postponement routes and complete English fallbacks. | Freeze it as the v1 certification workload and run all three routes. |
| F15 | Provider prices, model availability, and supported features can change outside this repository. | Never hard-code a current commercial price or silently select a model. Require reviewed certification inputs with effective dates. |

## 3. Goals and non-goals

### 3.1 Goals

1. Produce one versioned, portable CLI distribution from the Maven reactor.
2. Prove that the distribution launches using Java 25 and contains the exact frozen reference pack.
3. Prove complete generated play without credentials through reviewed authored fallbacks.
4. Certify one explicit provider/model/protocol tuple with real structured-output calls.
5. Complete success, partial-success, and responsible-postponement routes through normal session-backed CLI behavior.
6. Exercise THEME, SCENARIO, CAST, QUEST, every visited SCENE, and all three ending variants.
7. Prove automatic save, process-level quit, fresh-process resume, and no regeneration of accepted artifacts.
8. Bound live provider calls before execution and estimated provider cost during execution.
9. Apply clear compatibility, quality, repair, fallback, latency, and completion gates.
10. Create a schema-validated evidence bundle that contains no prompts, generated prose, setup free text, credentials, or raw provider bodies.
11. Keep all ordinary tests deterministic, offline, fast, and free of provider cost.
12. Provide operators with preflight, troubleshooting, disable, rollback, and incident procedures.
13. Make live-certification status visible without claiming that provider output is deterministic.
14. Leave the engine/provider boundary usable by future adapters without weakening Anthropic-specific certification.

### 3.2 Non-goals

- Making live provider calls during pull requests, normal pushes, Maven verification, or local package builds.
- Guaranteeing provider uptime, price, latency, or output beyond the recorded certification sample.
- Comparing providers or automatically choosing the cheapest/latest model.
- Fetching current model catalogs or prices from the Internet during build or play.
- Logging or retaining full prompts, provider responses, player free text, or API keys for certification.
- Using generated prose as a golden-text assertion.
- Changing trusted routes, mechanics, choices, effects, objectives, or outcomes in the reference pack.
- Adding a graphical client, server deployment, account system, remote save service, or gameplay telemetry.
- Treating a chat-product subscription as proof of API access or credit.
- Automatically retrying paid provider calls after ambiguous transport failure.
- Claiming formal reproducible builds across all operating systems in v1.
- Requiring signing keys on developer machines. Official releases require CI provenance and checksums; local builds are clearly labeled development builds.

## 4. Decisions

| ID | Decision |
|---|---|
| D1 | Add a top-level `certify` command. Do not overload normal `play` with release-only policy. |
| D2 | Certification has `offline` and `live` modes. Offline mode is safe for CI; live mode is always explicit and paid. |
| D3 | The authoritative certification target is the already-built release archive, unpacked into a clean temporary directory. |
| D4 | `lanterns-of-willow-marsh` version 1.0.0, or a later explicitly reviewed version, is the only v1 full-game certification pack. |
| D5 | The full suite runs success, partial-success, and responsible-postponement routes exactly once each with prefetch disabled. |
| D6 | Live certification uses no optional free-text setup. Preset setup values are fixed by versioned suite files. |
| D7 | Every visited artifact must come from the configured live provider or its one allowed repair. Any authored fallback makes the live suite fail. |
| D8 | A live certification failure never disables fallback play or invalidates existing saves. It only denies/withdraws the live-certified status for that tuple. |
| D9 | There are no automatic network retries below the generation pipeline. A repair is a semantic repair request, not a transport retry. |
| D10 | Provider/model IDs, protocol version, adapter configuration, pack digest, prompt/template/quality digests, distribution digest, and thresholds are immutable inputs to one certification run. |
| D11 | Pricing is supplied in a reviewed local JSON file. Repository code never embeds a vendor price and never downloads one. |
| D12 | `--max-cost-usd` and `--max-provider-calls` are mandatory for live mode. The smaller of CLI and suite/pack limits wins. |
| D13 | Certification evidence stores counts, durations, hashes, stable codes, and bounded identifiers only. It never stores content-bearing request or response fields. |
| D14 | A model alias that returns a different model ID fails exact-model certification. Release approval uses a pinned provider model ID, not a moving alias. |
| D15 | Standard CI proves adapter behavior with a loopback stub. Live CI is a separate protected manual workflow with scoped secrets and concurrency one. |
| D16 | The current `--live-smoke` remains available for one compatibility release, is documented as diagnostic-only, and cannot satisfy the release gate. |
| D17 | The release bundle includes a CycloneDX SBOM, SHA-256 checksums, license/notice files, reference pack, certification suite, and operator documentation. |
| D18 | Official release artifacts are created by CI from a clean tagged commit. Local archives say `development` in their build metadata. |
| D19 | Provider output drift is judged by schema, engine quality, repair/fallback, trusted truth, and operational metrics—not by prose equality. |
| D20 | Spec 27.13 closes the engine-side full generated CLI milestone. Spec 28 may consume the stable results in a client but must not redefine certification. |

## 5. Certification model

### 5.1 Four assurance levels

| Level | Name | Network | Cost | Trigger | Release meaning |
|---|---|---:|---:|---|---|
| L0 | Static and deterministic verification | No | None | Every normal build | Source, schemas, fixtures, rules, privacy, and adapter contracts are valid. |
| L1 | Packaged offline smoke | No | None | Every release candidate | The distributed JAR and pack start, save, resume, and finish using fallbacks. |
| L2 | Live canary | Yes | Bounded | Manual troubleshooting or scheduled observation | The selected tuple can complete initial generation plus two lazy scenes. Diagnostic only. |
| L3 | Full live certification | Yes | Bounded | Protected pre-release/manual workflow | All three complete reference routes pass the live gates. Required for `live-certified`. |

L0 and L1 are mandatory for every release. L3 is mandatory only when the release is advertised as live-provider certified. L2 never substitutes for L3.

### 5.2 Release capability labels

Every distribution metadata file declares exactly one capability label:

- `offline-ready`: L0 and L1 passed. Generated packs finish using authored fallbacks; live provider support is not claimed.
- `live-certified`: L0, L1, and a still-valid L3 certificate passed for the exact distribution/provider/model/pack tuple.
- `development`: built outside the official release workflow; no production certification claim.

The executable must not refuse normal play merely because a bundled live certificate is missing or expired. It may display a concise warning when live generation is explicitly requested with an uncertified tuple.

### 5.3 Certificate validity

A live certificate is valid only when all these values match:

- distribution SHA-256;
- engine version and Git commit;
- adapter ID and adapter protocol version;
- configured provider ID;
- requested and returned model IDs;
- reference pack ID, semantic version, and content digest;
- generation catalog, templates, system prompt, setup, fallback, and quality-profile digests;
- certification suite version and route-script digests;
- timeout and size-limit profile;
- threshold profile;
- pricing-input digest.

It expires after 14 calendar days by default. A protected workflow may select a shorter period but never more than 30 days. Any tuple change invalidates it immediately.

Certificate expiry means “retest required,” not “existing saves are unsafe.”

## 6. Command-line contract

### 6.1 Top-level dispatch

The executable supports:

```text
java -jar engine-cli.jar play ...
java -jar engine-cli.jar certify ...
java -jar engine-cli.jar --help
```

Legacy invocation without `play` remains compatible for the period already promised by Spec 27.9. New certification options are accepted only after `certify`.

### 6.2 Offline command

Authoritative form:

```sh
java -jar bin/engine-cli.jar certify \
  --mode offline \
  --pack-dir packs/lanterns-of-willow-marsh \
  --suite certification/willow-marsh-v1/suite.json \
  --evidence-dir evidence/offline
```

Offline mode:

- rejects configured network use;
- does not require a key, model ID, or pricing file;
- forces the provider boundary unavailable even if credentials exist in the parent environment;
- runs all three routes through authored fallbacks;
- performs the required quit/restart/resume checkpoint;
- validates package files and checksums;
- exits non-zero if any provider call is attempted.

### 6.3 Live command

Authoritative form:

```sh
java -jar bin/engine-cli.jar certify \
  --mode live \
  --pack-dir packs/lanterns-of-willow-marsh \
  --suite certification/willow-marsh-v1/suite.json \
  --pricing-file certification/provider-pricing.json \
  --max-provider-calls 48 \
  --max-cost-usd 10.00 \
  --evidence-dir evidence/live \
  --confirm-live-provider-cost
```

The example values are illustrative operator choices, not hard-coded product defaults. The suite computes its own required and maximum calls and rejects a CLI ceiling that is too low to start safely.

Live mode requires:

- `GENERATION_MODEL_ID`;
- `ANTHROPIC_API_KEY` for the v1 adapter;
- `--pricing-file`;
- `--max-provider-calls`;
- `--max-cost-usd`;
- `--confirm-live-provider-cost` in non-interactive use.

Interactive use may instead show a redacted preflight summary and require the operator to type the exact phrase `CERTIFY LIVE`. A simple `y` is insufficient. The confirmation occurs only after validation and before the first network call.

### 6.4 Canary command

```sh
java -jar bin/engine-cli.jar certify \
  --mode live --scope canary \
  --pack-dir packs/lanterns-of-willow-marsh \
  --suite certification/willow-marsh-v1/suite.json \
  --pricing-file certification/provider-pricing.json \
  --max-provider-calls <reviewed-limit> \
  --max-cost-usd <reviewed-limit> \
  --evidence-dir evidence/canary \
  --confirm-live-provider-cost
```

Canary scope completes initial THEME, SCENARIO, CAST, QUEST, opening SCENE, and two later SCENEs on the success route. It writes `scope: CANARY` and can never emit a full certificate.

### 6.5 Developer convenience commands

Extend `dev.ps1` with additive actions:

```powershell
./dev.ps1 game-package
./dev.ps1 game-certify-offline
./dev.ps1 game-certify-live -- <certification arguments>
```

The live action must forward explicit limits and confirmation; it must not invent them. `game` remains the normal human-play entry point.

### 6.6 Exit codes

| Code | Meaning |
|---:|---|
| 0 | Requested verification passed and evidence was committed atomically. |
| 2 | Invalid or incomplete command/configuration; no provider call was made. |
| 3 | Local package, pack, store, script, or runtime failure. |
| 4 | Provider could not be evaluated: authentication, permission, billing, rate limit, timeout, availability, or unsupported capability. |
| 5 | Provider responded, but a compatibility, quality, repair, fallback, latency, model, cost, or route gate failed. |
| 6 | Evidence could not be written, validated, checksummed, or finalized. |

Exit 4 is `INCONCLUSIVE`, not a pass. A release cannot reuse an older certificate unless that certificate is still valid for the exact tuple.

## 7. Certification suite asset

### 7.1 Location

Create:

```text
app/engine/certification/willow-marsh-v1/
  suite.json
  routes/
    success.script
    partial.script
    postponed.script
  checkpoints/
    resume.json
  schemas/
    certification-evidence-v1.schema.json
    certification-manifest-v1.schema.json
    provider-pricing-v1.schema.json
```

The release bundle copies this directory to `certification/willow-marsh-v1/` unchanged.

### 7.2 Suite manifest

`suite.json` contains trusted, reviewable data only:

```json
{
  "schemaVersion": 1,
  "suiteId": "willow-marsh-v1",
  "pack": {"id": "lanterns-of-willow-marsh", "version": "1.0.0"},
  "locale": "en",
  "prefetch": false,
  "freeText": "FORBIDDEN",
  "routes": [
    {"id": "success", "script": "routes/success.script", "expectedResult": "SUCCESS"},
    {"id": "partial", "script": "routes/partial.script", "expectedResult": "PARTIAL_SUCCESS"},
    {"id": "postponed", "script": "routes/postponed.script", "expectedResult": "FAILURE"}
  ],
  "resumeCheckpoint": {"route": "partial", "afterAcceptedChoice": 4},
  "requiredStages": ["THEME", "SCENARIO", "CAST", "QUEST", "SCENE"]
}
```

The actual expected result enum must match the trusted result contract from Spec 27.7. The suite parser rejects unknown properties, duplicate keys, path traversal, absolute paths, symlinks escaping the suite, and files above the shared pack/script size limits.

### 7.3 Route scripts

Scripts use the strict normal-CLI script grammar from Spec 27.9. They contain:

- exact setup preset IDs;
- exact authored choice IDs from the reference pack README;
- permitted utility commands such as `/status`, `/objectives`, and `/characters`;
- `/save` and `/quit` at the declared checkpoint;
- an explicit resume assertion;
- expected scene IDs, phase IDs, objective states, and result class;
- no generated prose assertions;
- no free text.

The partial route is divided at its checkpoint. The runner closes the first host/store cleanly, creates a fresh host instance over the same temporary store, selects the saved run, and completes the second half. A dedicated process-level package test additionally launches two JVM processes to prove real restart behavior.

### 7.4 Workload calculation

Before execution, the runner derives from the frozen pack and scripts:

- unique initial generation stages;
- visited scene slots per route;
- maximum semantic repairs per artifact;
- maximum demand calls;
- maximum prefetch calls, which must be zero;
- maximum total provider calls;
- expected trusted route length and result.

No call count is copied manually into Java. A suite/pack change that changes the derived count invalidates prior evidence and requires review.

## 8. Provider configuration and identity

### 8.1 V1 provider tuple

The v1 tuple is:

```text
providerId: anthropic
endpoint: https://api.anthropic.com/v1/messages
apiVersion: 2023-06-01
requestedModelId: value of GENERATION_MODEL_ID
connectTimeout: PT5S
responseTimeout: PT25S
maximumResponseBytes: 1048576
maximumInputCodePoints: 64000
maximumOutputCharacters: 256000
automaticTransportRetries: 0
```

These values are recorded, not inferred later. Changing one creates a different tuple and requires new L0 adapter tests and L3 certification.

### 8.2 Exact returned model

For every successful response:

- `result.modelId` must be present and syntactically safe;
- it must equal `GENERATION_MODEL_ID` exactly for v1 certification;
- all calls in a suite must return the same ID.

If a provider intentionally returns a canonical ID for an accepted alias, the operator must certify that canonical ID explicitly in a future reviewed mapping. V1 does not guess alias equivalence.

### 8.3 Secret handling

The API key:

- is read from environment only;
- is never accepted as a CLI argument, suite value, pricing value, pack file, or stdin response;
- is never included in exception messages, debug text, process command lines, evidence, transcripts, checksums, or archives;
- is scoped to the live-certification workflow/environment only;
- is masked by CI before any command runs;
- is rotated immediately if exposure is suspected.

`ANTHROPIC_DEBUG=true` is forbidden in certification and official release workflows because the current debug mode can print full request and response JSON. Preflight must fail before network access if it is enabled.

### 8.4 Provider preflight

Preflight is local and makes no network call. It checks:

1. provider adapter is present;
2. key exists and is nonblank without printing its length or prefix;
3. model ID passes validation;
4. endpoint is the exact production endpoint;
5. timeout and size limits match the suite-approved tuple;
6. debug logging is disabled;
7. pack, suite, pricing, and distribution hashes are stable;
8. call and cost ceilings are valid;
9. evidence and temporary store directories are writable and empty/new;
10. system wall clock is usable for timestamps and certificate expiry;
11. no free-text input exists in a route;
12. prefetch is off;
13. all routes validate offline before live execution.

The first provider call is the capability probe. No separate vendor model-list call is required.

## 9. Pricing and cost admission

### 9.1 Pricing file

The operator supplies a schema-validated file such as:

```json
{
  "schemaVersion": 1,
  "providerId": "anthropic",
  "modelId": "operator-pinned-model-id",
  "currency": "USD",
  "effectiveAt": "2026-10-22T00:00:00Z",
  "reviewedAt": "2026-10-22T00:00:00Z",
  "inputUsdPerMillionTokens": "0.000000",
  "outputUsdPerMillionTokens": "0.000000",
  "cacheReadUsdPerMillionTokens": "0.000000",
  "cacheWriteUsdPerMillionTokens": "0.000000",
  "reservedMaximumUsdPerCall": "0.000000",
  "sourceLabel": "operator-reviewed provider price page"
}
```

Zeros above are schema examples only and must be rejected for live certification unless the operator explicitly records a valid free tier. Monetary values are decimal strings, parsed with exact decimal arithmetic, nonnegative, bounded to six fractional digits, and never represented by binary floating point.

The file must be no older than seven days at certification time. The model/provider must exactly match the requested tuple. `sourceLabel` is descriptive text, not a fetched URL and not proof by itself; the release approver owns verification.

### 9.2 Cost estimate

For each successful response:

```text
estimatedCost =
  inputTokens      × inputRate      / 1,000,000 +
  outputTokens     × outputRate     / 1,000,000 +
  cacheReadTokens  × cacheReadRate  / 1,000,000 +
  cacheWriteTokens × cacheWriteRate / 1,000,000
```

Round only the displayed value. Admission arithmetic retains exact decimal precision.

If token usage is absent or invalid, the artifact may still fall back during ordinary play, but live certification fails because cost cannot be measured.

### 9.3 Before-call admission

Before each paid call, require:

```text
completedCalls + 1 <= effectiveCallCeiling
accruedEstimatedCost + reservedMaximumUsdPerCall <= maxCostUsd
```

The reserved maximum is an operator-reviewed conservative amount for one request under the adapter and catalog bounds. This controls certification admission; it is not a promise about the provider invoice.

If the next call cannot be admitted:

- do not send it;
- stop live execution;
- write `COST_LIMIT_REACHED` or `CALL_LIMIT_REACHED`;
- finalize evidence as `FAIL`;
- keep any temporary run only until evidence finalization, then remove it according to retention rules.

### 9.4 Cost reporting

Evidence includes per route and total:

- admitted call ceiling;
- actual attempted and successful calls;
- provider-reported token categories;
- estimated cost by category;
- reserved amount at stop time;
- operator maximum;
- pricing file digest and effective/review timestamps.

It says `estimated`, never `billed` or `invoice`.

## 10. Live certification scenarios

### 10.1 Scenario A — Success

- Use the documented `success` route.
- Use the suite’s first preset combination.
- Exercise reed-bank investigation.
- Reach the radiant/success ending.
- Assert trusted objectives and result facts match the route matrix.

### 10.2 Scenario B — Partial success with restart

- Use the documented `partial` route.
- Use a different allowed preset combination.
- Exercise orchard-path investigation.
- After accepted choice four, issue `/save` and `/quit`.
- Destroy the in-memory host and create a fresh host over the same store.
- Resume the exact run without `--generated` start arguments.
- Assert all accepted artifacts before the checkpoint are reused and produce zero additional calls.
- Reach the gentle/partial-success ending.

### 10.3 Scenario C — Responsible postponement

- Use either suite-selected investigation route.
- Use a third allowed preset combination if available.
- Select `postpone-with-plan` at the trusted ending decision.
- Reach the postponed/failure result without unsafe, blaming, or contradictory generated text.
- Assert postponement is represented as a responsible outcome.

### 10.4 Ordering and isolation

- Run routes in suite order.
- Use a new run ID and isolated store per route.
- Disable prefetch to make demand-call accounting exact.
- Do not share generated artifacts between routes.
- Do not seed or alter provider output.
- Record the engine seed only where it affects trusted deterministic behavior; never treat it as provider determinism.
- A failed route stops the suite by default. `--continue-after-failure` is allowed only for diagnostics and forces overall `FAIL`.

## 11. Hard certification gates

### 11.1 Compatibility gates

Every call must satisfy:

- HTTP response is accepted by the adapter;
- response is within the byte/character caps;
- response type and stop reason are recognized;
- structured JSON parses and validates against the requested schema;
- returned model ID is exact and stable;
- usage values are present, integral, and nonnegative;
- no unsupported structured-output error occurs;
- no authentication, permission, billing, rate-limit, timeout, or unavailable error occurs.

### 11.2 Content and quality gates

Across the full suite:

- all required stages appear;
- every visited scene has an accepted generation execution;
- every artifact passes structural validation, safety, trusted-reference validation, and the Spec 27.11 quality profile;
- all three trusted results are reached;
- no generated statement contradicts trusted state or ending truth;
- blocking quality findings equal zero after the allowed repair;
- authored fallback count equals zero;
- invalid accepted artifact count equals zero;
- missing quality stamp count equals zero;
- stale artifact reuse count equals zero.

Advisory findings are recorded by stable rule ID. The initial v1 live gate allows at most one advisory artifact per route and at most two advisory artifacts across the suite. A later threshold change is versioned and requires new certification.

### 11.3 Repair gates

- The engine retains its one-repair-per-artifact maximum.
- No artifact may use more than one repair call.
- At most three artifacts across the three-route suite may require repair.
- No more than one repaired artifact may occur in a single route’s initial THEME/SCENARIO/CAST/QUEST group.
- Any fallback after repair fails certification.
- A repair caused by a blocking safety/truth finding is recorded separately from syntax/schema repair.

These gates detect drift without demanding exact prose. A suite that passes only because nearly every response is repaired is not healthy.

### 11.4 Call gates

- Attempted calls must not exceed the derived suite maximum, CLI ceiling, pack run budget, profile daily budget, or global daily budget.
- Prefetch calls must equal zero.
- A resume must not repeat a previously completed stage/scene call.
- A provider failure must not trigger an adapter retry.
- A manual rerun is a new certification ID and evidence directory; results are never merged.

### 11.5 Latency gates

Add a content-free observation at the adapter boundary for each attempt. It records monotonic elapsed milliseconds separately from stage elapsed time.

V1 gates:

| Metric | Gate |
|---|---:|
| Connection timeout configuration | exactly 5 seconds |
| Response timeout configuration | exactly 25 seconds |
| Maximum single attempt elapsed | 27 seconds |
| Provider-attempt p95 across full suite | at most 25 seconds |
| Initial four stages plus opening scene per route | at most 150 seconds |
| One complete route provider wall time | at most 360 seconds |
| Complete three-route suite wall time | at most 20 minutes |

Percentiles use nearest-rank over all attempts in the suite and the evidence states sample size. No p99 claim is made for this small sample.

Time spent by a human at prompts is excluded. The automated scripts make suite wall time reproducible. Local packaging/checksum time is reported separately.

### 11.6 Cost gate

Actual estimated cost must be less than or equal to `--max-cost-usd`, and every call must pass before-call admission. Crossing the limit after a provider’s usage report is still a failure and prevents further calls.

### 11.7 Completion gate

Each route must:

- start from a new run;
- visit exactly the trusted expected scenes;
- accept exactly eight story choices;
- end in the expected trusted result class;
- have no active generation job at completion;
- persist a valid terminal snapshot;
- reload that terminal snapshot without network access;
- render the final result and generation disclosure through the normal CLI.

## 12. Provider drift classification

| Drift class | Example | Result | Operator action |
|---|---|---|---|
| Identity | Returned model differs from requested ID | Fail | Pin the canonical supported ID and recertify; never auto-accept. |
| Protocol | Structured output rejected or response envelope changes | Inconclusive/fail | Disable live-certified claim; update adapter behind offline tests. |
| Syntax | JSON/schema errors increase | Repair may run; threshold decides | Review evidence and provider compatibility. |
| Semantic | Trusted-reference or truth checks fail | Repair may run; fallback in play; certification fails if unresolved | Keep provider disabled for certification until fixed. |
| Quality | Blocking/advisory findings exceed gates | Fail | Review prompts/profile/model; do not weaken rules silently. |
| Operational | Timeout, rate limit, 5xx, or high latency | Inconclusive or latency fail | Retry certification later as a new run; runtime fallback remains available. |
| Cost | Usage or current reviewed price exceeds ceiling | Fail before next call | Raise ceiling only with explicit release approval or reduce workload/model cost. |
| Privacy | Secret/content appears in logs or evidence | Critical fail | Stop release, isolate evidence, rotate key, fix redaction, rerun from clean state. |

Certification compares metrics to gates, not to the wording of a previous response. A previous certificate may be shown as a trend input, but it cannot relax the current hard gates.

## 13. Offline adapter and failure certification

The loopback HTTP test suite remains the authoritative proof for failures that should not be induced against a paid provider.

Required cases:

1. valid structured response and exact request headers;
2. exact requested/returned model capture;
3. token usage with and without cache fields;
4. malformed JSON and wrong envelope type;
5. missing text block and excessive response bytes;
6. output-limit and refusal finish reasons;
7. 400 invalid request;
8. 400 insufficient-credit classification;
9. 400 structured-output-unsupported classification;
10. 401 authentication failure;
11. 403 permission failure;
12. 404 resource/model not found;
13. 408 and 504 timeout;
14. 429 rate limit;
15. 5xx unavailable;
16. interrupted request preserves thread interruption;
17. response timeout;
18. no automatic retry for any error;
19. production endpoint and loopback-only test endpoint validation;
20. endpoint user-info/query/fragment/path rejection;
21. request and response size bounds;
22. key redaction from config, exceptions, logs, and evidence;
23. debug-mode rejection by certification preflight;
24. content-free per-attempt observation;
25. cost admission stops before the next request;
26. evidence never contains sentinel secrets, setup text, prompt text, or generated text.

Use a counting local server to prove exactly one HTTP request for each attempted provider call. Network retry tests do not contact the Internet.

## 14. Evidence bundle

### 14.1 Directory layout

Write to a new temporary sibling and atomically rename it only after all files validate:

```text
evidence/<certification-id>/
  manifest.json
  summary.json
  routes/
    success.json
    partial.json
    postponed.json
  observations.ndjson
  checksums.sha256
  console.txt
```

For canary scope, only the executed route file exists. Partial/incomplete directories retain a `.incomplete` suffix and can never be consumed as certificates.

### 14.2 Manifest fields

`manifest.json` includes:

- evidence schema version;
- random certification UUID;
- scope and mode;
- start/end UTC instants;
- result: `PASS`, `FAIL`, or `INCONCLUSIVE`;
- stable failure/gate codes;
- engine semantic version and Git commit;
- clean/dirty build marker;
- Java runtime vendor/version and normalized OS/architecture;
- distribution filename, size, and SHA-256;
- provider ID, requested model ID, returned model IDs;
- API/protocol version;
- timeout and size-limit profile;
- pack ID/version/content digest;
- catalog/template/prompt/setup/fallback/quality digests;
- suite ID/version and script digests;
- pricing digest and timestamps;
- threshold profile version;
- certificate issue/expiry instants when passed;
- official/development provenance marker.

### 14.3 Route fields

Each route evidence file includes:

- route ID and expected/actual result class;
- generated run ID represented as a one-way evidence-local digest, not the local store path;
- expected/actual scene and phase IDs;
- accepted story-choice count;
- restart checkpoint reached/resumed;
- artifact counts by stage and outcome;
- provider and repair call counts;
- fallback count;
- quality decisions and finding rule IDs;
- aggregated token usage;
- estimated cost;
- minimum/median/p95/maximum attempt latency;
- route wall time;
- completion and terminal-reload booleans;
- gate results by stable ID.

### 14.4 Attempt observations

`observations.ndjson` contains one object per provider attempt:

```json
{
  "sequence": 1,
  "routeId": "success",
  "stage": "THEME",
  "slotId": null,
  "attemptKind": "PRIMARY",
  "elapsedMillis": 1234,
  "outcomeCode": "COMPLETE",
  "modelId": "safe-bounded-model-id",
  "inputTokens": 100,
  "outputTokens": 50,
  "cacheReadTokens": 0,
  "cacheWriteTokens": 0
}
```

Allowed values are bounded enums and safe identifiers. Do not add request IDs if the provider may encode account information; v1 omits them.

### 14.5 Console transcript

`console.txt` is the certification runner’s content-free progress output, not the game transcript. It may contain:

- route/stage/slot identifiers;
- pass/fail state;
- counts, durations, usage, and estimated cost;
- stable errors and remediation category;
- redacted model/config summary.

It must not contain scene titles/body, choices, cast names generated by the provider, prompts, schemas, request/response JSON, player input, free text, store paths containing user names, or environment values.

### 14.6 Integrity and retention

- `checksums.sha256` covers every evidence file except itself.
- Official CI uploads the evidence bundle with restricted access and the release retention policy.
- Default retention is 90 days; security incidents may require a restricted legal/security hold.
- Local evidence is not auto-uploaded.
- Certification temporary stores are deleted after finalized evidence unless `--retain-temp-store` is used in local diagnostic mode.
- `--retain-temp-store` is forbidden in official live certification.

## 20. Provider disable and rollback

### 20.1 Runtime provider mode

Add a host configuration boundary with modes:

```text
disabled | enabled | certification
```

- `disabled`: never construct/call a provider; generated play uses fallbacks.
- `enabled`: normal explicit `--generated` play may call the configured provider.
- `certification`: accepted only by the `certify --mode live` command and enables evidence/cost admission.

The CLI exposes a safe player override `--offline` for `play`. It wins over environment configuration and credentials. `--offline --generated` means “use the full generated-game contract with authored fallbacks and no network.”

The environment variable name, if added, must be provider-neutral, for example `GENERATION_PROVIDER_MODE`, with `disabled` as the safe value. Invalid values fail closed to disabled for normal play and fail preflight for certification.

### 20.2 Disable procedure

When live generation must be stopped:

1. set provider mode to disabled in the host/release environment;
2. confirm a new play run reports authored fallback and makes zero calls;
3. do not delete or mutate existing saves;
4. allow active local CLI calls to reach their existing timeout; do not corrupt the snapshot;
5. withdraw the live-certified label/certificate from current operational documentation;
6. record the stable incident reason and time;
7. preserve privacy-safe evidence.

### 20.3 Rollback order

Use the least disruptive action:

1. disable provider and keep current engine/pack;
2. restore the last certified exact model/config tuple if still supported and approved;
3. roll back the CLI distribution to the previous compatible version;
4. roll back the reference pack only if save compatibility is proven.

Never silently change `GENERATION_MODEL_ID` to an uncertified alias. Never downgrade or rewrite a player save to make rollback easier.

### 20.4 Re-enable procedure

Re-enable only after:

- root cause is understood or external service recovered;
- L0 remains green;
- a fresh L2 canary passes;
- a fresh L3 passes for a live-certified claim;
- certificate tuple and expiry are current;
- incident owner approves re-enable.

## 21. Troubleshooting matrix

| Code/category | Meaning | Safe action |
|---|---|---|
| `LIVE_PROVIDER_NOT_CONFIGURED` | Key/model/adapter missing | Check environment presence privately; use `--offline` to play now. |
| `PROVIDER_AUTHENTICATION_FAILED` | Key rejected | Rotate/replace secret through secret storage; never print it. |
| `PROVIDER_PERMISSION_DENIED` | Account/model access denied | Verify account/model permission outside logs. |
| `PROVIDER_BILLING_UNAVAILABLE` | API credit unavailable | Review API billing; a chat subscription is not proof of API credit. |
| `PROVIDER_STRUCTURED_OUTPUT_UNSUPPORTED` | Model rejects required feature | Select an explicitly supported pinned model and recertify. |
| `PROVIDER_RESOURCE_NOT_FOUND` | Model/resource unavailable | Verify exact pinned model; do not fall forward to latest. |
| `PROVIDER_RATE_LIMITED` | Provider refused due to rate | Keep fallback enabled; wait and run a new certification later. |
| `PROVIDER_TIMEOUT` | Adapter deadline reached | Inspect latency evidence; do not add blind retries. |
| `PROVIDER_UNAVAILABLE` | Network/provider 5xx/I/O | Release offline-ready or retry later as a new run. |
| `PROVIDER_INVALID_RESPONSE` | Envelope/size/content invalid | Keep provider uncertified; use loopback fixtures to reproduce shape. |
| `MODEL_ID_MISMATCH` | Returned model differs | Pin returned canonical ID only after review; recertify. |
| `QUALITY_GATE_FAILED` | Blocking/advisory/repair threshold failed | Review stable findings and prompts/profile; preserve fallback. |
| `COST_LIMIT_REACHED` | Next call or measured total exceeds cap | Stop; approve a new cap explicitly or reduce workload. |
| `CALL_LIMIT_REACHED` | Derived/explicit call budget exhausted | Investigate duplicate calls/repairs; do not raise blindly. |
| `PACKAGE_INTEGRITY_FAILED` | File/checksum mismatch | Discard candidate and rebuild from clean tag. |
| `EVIDENCE_PRIVACY_FAILED` | Forbidden content detected | Isolate evidence, rotate exposed secret if needed, block release. |

Troubleshooting documentation uses these codes and never asks the operator to attach raw provider JSON.

## 22. Incident response

### 22.1 Severity

| Severity | Condition | Immediate response |
|---|---|---|
| SEV-1 | Credential or private content exposed; unsafe generated content accepted as valid | Disable provider, stop release, restrict evidence, rotate key, preserve audit trail. |
| SEV-2 | Trusted contradiction escapes quality gates; saves corrupt; repeated uncontrolled cost/calls | Disable provider, stop certification, keep fallback play, investigate. |
| SEV-3 | Provider outage, rate limits, model drift, high repair/fallback/latency | Withdraw live-certified status as needed; operate offline-ready. |
| SEV-4 | Documentation, cosmetic evidence, or non-blocking advisory issue | Track and fix without misrepresenting certificate state. |

### 22.2 First response checklist

1. Record UTC detection time and stable symptom code.
2. Stop new live certification runs.
3. Set provider mode disabled where controlled.
4. Verify fallback completion with the packaged offline smoke.
5. Protect evidence; do not copy raw provider content into tickets/chat.
6. Rotate key if exposure is possible.
7. Identify exact distribution/model/pack/certificate tuple.
8. Assess existing saves without changing them.
9. Publish a concise operational status: live generation unavailable, fallback play available/unavailable.
10. Fix behind deterministic regression tests and recertify before re-enable.

### 22.3 Post-incident

Add:

- stable failure fixture where reproducible;
- regression test;
- root-cause summary without secrets/content;
- affected certificate IDs and withdrawal times;
- cost impact estimate;
- recovery and re-certification evidence;
- documentation change if operator action was unclear.

## 24. Failure semantics

1. Validation/configuration failure occurs before any provider call.
2. Package/checksum mismatch stops immediately.
3. Provider errors map to stable existing codes and overall `INCONCLUSIVE` unless a completed hard gate clearly failed.
4. Model mismatch, invalid accepted data, fallback, excessive repair/advisory/latency/cost, or wrong result is `FAIL`.
5. Evidence write/privacy/checksum failure overrides an apparent pass and returns exit 6.
6. A live failure may leave generated artifacts in the isolated temporary store, but they are never promoted to release assets.
7. Certification does not modify the reference pack, suite, pricing file, distribution, or user saves.
8. Ordinary play continues to fall back and may finish even when the same provider condition would fail certification.
9. A certificate is created only after terminal reload, evidence validation, privacy scan, and checksum creation.
10. Cancellation/interrupt stops scheduling calls, preserves thread interruption, finalizes safe incomplete evidence when possible, and never reports pass.

## 25. Security requirements

- Use production HTTPS endpoint validation already enforced by the adapter.
- Permit loopback HTTP only in tests and never in live certification.
- Do not add a general endpoint environment override.
- Reject archive/suite/pack traversal, absolute paths, duplicate JSON keys, oversized files, and escaping symlinks.
- Create temporary stores/evidence with owner-only permissions where the OS supports them.
- Do not execute pack/suite content as shell commands.
- Launch child JVMs with argument arrays, not concatenated shell text.
- Forward only allow-listed environment values to child processes.
- Clear provider credentials explicitly for offline child processes.
- Do not load plugins or provider adapters from untrusted archive paths.
- Bound every evidence string, list, and file.
- Escape/sanitize all terminal text according to the existing CLI renderer.
- Use cryptographic SHA-256 from the JDK for integrity; checksums are integrity evidence, not signatures.
- Official CI provenance/attestation binds the archive to the repository workflow. Signing-key lifecycle is not invented in application code.

| Quality | Decision/finding/repair/fallback counts |
| Persistence | Restart checkpoint and zero duplicate calls |

No requirement is complete only because a human says it worked when deterministic evidence can be produced.

## 30. Definition of done

Spec 27.13 is complete when:

- the CLI has distinct `play` and `certify` entry points;
- offline and live certification modes are implemented with stable exit codes;
- the frozen Willow Marsh suite covers success, partial-success, and responsible postponement;
- the partial route proves real save/quit/fresh-host resume;
- normal play can always be forced offline with zero provider calls;
- every standard build/test remains network-free and credential-free;
- the Anthropic adapter contract covers all required status, timeout, size, refusal, usage, and no-retry cases;
- live mode requires an explicit model, key, pricing file, call cap, cost cap, and strong confirmation;
- debug request/response logging is rejected in certification;
- the exact returned model ID is verified on every live response;
- all live route artifacts pass schema, safety, trusted-reference, truth, and quality checks;
- live fallback count is zero and repair/advisory thresholds pass;
- latency, call, token, and estimated-cost gates pass;
- accepted artifacts are not regenerated after resume;
- evidence is schema-valid, content-free, checksummed, and finalized atomically;
- sentinel tests prove secrets, prompts, free text, provider prose, and raw paths do not leak;
- a versioned release archive contains the executable JAR, reference pack, suite, docs, legal material, build info, SBOM, and checksums;
- the unpacked archive passes offline certification on Linux and Windows;
- official releases certify and publish the same archive digest without rebuilding;
- protected live CI is manual, approved, cost-bounded, secret-scoped, and single-concurrency;
- release labels distinguish development, offline-ready, and live-certified artifacts honestly;
- provider disable, rollback, incident, and re-enable procedures are documented and dry-run;
- the first approved live certificate is attached to the exact release tuple or the release is explicitly marked offline-ready;
- a clean-machine player can launch the packaged CLI and normally play the reference generated game from setup through a trusted ending.

## 31. Final handoff

This specification completes the engine-side path from generated content configuration to a normally playable, packaged, certified full game in the CLI.

After Spec 27.13:

- Spec 28 may render the stable run, generation disclosure, progress, result, and recovery contracts in a graphical client;
- Spec 29 may build its product pack on the certified engine contracts;
- new providers/models must add their own adapter contract and obtain a certificate for an exact tuple;
- new reference-pack versions must rerun L0, L1, and any claimed L3 certification;
- ongoing re-certification and incident response are operational work, not a reason to weaken frozen engine rules.

Future work must preserve provider-free completion, trusted mechanics, bounded generation, transient setup privacy, durable recovery, honest provenance, and the rule that generated prose never owns game truth.
