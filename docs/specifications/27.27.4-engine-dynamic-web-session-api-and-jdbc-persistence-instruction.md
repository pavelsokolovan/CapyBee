# Spec 27.27.4 — Dynamic Web Session API and JDBC Persistence

**Type:** Implementation instruction
**Parent:** Dynamic-game release completion after Spec 27.27.3
**Depends on:** Specs 27 and 27.17–27.27.3, especially `GeneratorProfile`, `PreparationPresetResolver`, `ConfirmedDynamicPreparation`, `DynamicStartCoordinator`, atomic dynamic activation/replacement, dynamic snapshot v2, source-neutral session identity, `RunSessionService`, `JdbcSessionStore`, `GameRunController`, Spring Security and the existing wait-then-poll HTTP contract
**Baseline:** Inspected clean local `main` at commit `51b1f34` on 2026-10-29. The engine and CLI can safely prepare, start, persist, resume, certify and finish dynamic games. The Spring web host remains Pack-only: `POST /api/game/runs` requires `packId`; `RunSummaryDto`, `GameRunController.summary(...)` and `gameApi.ts` require Pack identity; `game_runs.pack_id` and `pack_version` are non-null; `JdbcSessionStore` constructs `PackId` unconditionally and does not implement `activateDynamic` or `replaceWithDynamic`; and the server has no generator-profile catalog or dynamic-start operation. A dynamic snapshot stored through another adapter would therefore fail in the web host. No build, migration or provider call was run while preparing this document.
**Status:** Implemented
**Primary outcome:** A signed-in family can discover an allowlisted generator profile, submit one explicitly confirmed dynamic-game preparation, poll its bounded operation, and then read, command, resume and finish the resulting run through the existing `/api/game` session API, with atomic PostgreSQL persistence and no Pack fabrication, provider-call duplication or persistence of private setup text.
**Repository location:** `docs/specifications/27.27.4-engine-dynamic-web-session-api-and-jdbc-persistence-instruction.md`

## 1. Purpose

The current dynamic capability ends at the local CLI. This slice makes the existing server a real host for that same capability:

```text
authenticated web request
  -> allowlisted validated generator profile
  -> local preset resolution and explicit provider disclosure
  -> server-owned idempotent dynamic-start operation
  -> trusted DynamicStartCoordinator
  -> complete validated/compiled dynamic snapshot
  -> atomic JdbcSessionStore activation or replacement
  -> existing RunSessionService command/view/event lifecycle
  -> process restart and exact dynamic resume
```

The HTTP adapter must remain thin. It does not parse model output, compile mechanics, build snapshots, infer profile constraints or implement gameplay. Those responsibilities stay in the engine/session boundaries already certified by 27.27.3.

## 2. Scope

### 2.1 In scope

- Make session wire summaries source-neutral while preserving Pack-client compatibility.
- Add an allowlisted, bounded server generator-profile catalog loaded at startup.
- Expose authenticated profile/setup discovery endpoints containing display-safe public metadata only.
- Add an explicit dynamic-start operation with confirmation, idempotency, polling and cancellation.
- Route starts through `DynamicStartCoordinator` and existing session metering/atomic activation.
- Implement PostgreSQL `activateDynamic` and `replaceWithDynamic` transactions in `JdbcSessionStore`.
- Migrate `game_runs` from Pack-only identity to a constrained Pack-or-dynamic identity.
- Resume and command dynamic runs after server/JVM restart without the original profile or provider.
- Add cost-bearing endpoint protection, owner isolation, request limits and content-free observability.
- Add controller, service, JDBC, migration and fresh-context recovery tests.
- Preserve Pack starts, commands, prefetch, migrations and offline queue behavior.

### 2.2 Out of scope

- React screens, setup forms, game rendering, client routing or visual design; Spec 28 consumes this API.
- A public profile marketplace, profile upload, arbitrary filesystem paths, remote URLs or user-authored profiles.
- Persisting wizard drafts, free-text suggestions, prompts, model responses or rejected blueprints.
- New mechanics, blueprint fields, compiler behavior, provider adapters or snapshot formats.
- Offline creation or offline command execution in the browser.
- Multiplayer, shared/public runs, WebSockets, SSE, push notifications or cross-device operation handoff.
- Automatic Pack fallback start after dynamic generation fails.
- Running a real paid provider call in automated tests or during implementation without separate authorization.

## 3. Source-neutral run wire contract

Replace Pack-only assumptions with a versioned source discriminator. Conceptually:

```json
{
  "runId": "uuid",
  "status": "ACTIVE",
  "revision": 0,
  "source": {
    "kind": "DYNAMIC",
    "profileId": "generic-adventure",
    "profileVersion": "1.0.0",
    "gameFingerprint": "sha256:..."
  },
  "packId": null,
  "packVersion": null,
  "locale": "en",
  "viewSchema": 2,
  "view": {},
  "updatedAt": "..."
}
```

For Pack runs, `source.kind=PACK`, Pack identity is present and dynamic fields are absent. Retain `packId` and `packVersion` as nullable compatibility aliases for existing clients during this API version; they must agree with `source` when present. Never place a fake Pack ID in a dynamic response.

Update the engine-session wire DTO rather than creating a server-only competing summary. `GameRunController.summary(...)` must handle either source without dereferencing a nullable Pack. Keep `viewSchema` and the existing engine `View` unchanged so Spec 28 can render one source-neutral view contract.

The API may return a shortened fingerprint suffix in list/detail display metadata, but durable/internal DTOs and owner-authenticated support responses may carry the complete fingerprint. Never expose canonical blueprints, definitions or snapshots.

## 4. Server generator-profile catalog

At application startup, load only explicitly configured profiles from one bounded deployment root or classpath catalog. Clients select a profile ID; they never provide a path.

Configuration is conceptually:

```yaml
capybee.game.dynamic:
  enabled: false
  profile-root: <deployment-controlled path>
  profile-ids: generic-adventure
  max-concurrent-starts: 1
  operation-timeout-seconds: 180
```

Requirements:

- `enabled` defaults to false independently of Pack play and dynamic resume.
- Enabling new dynamic starts requires generation to be enabled and at least one valid profile.
- Resume/read/command of an already stored dynamic run remains possible when new dynamic starts or the provider are disabled.
- Resolve configured paths once with containment, symlink, file-count and byte-size checks.
- Load through `GeneratorProfileLoader`; do not duplicate schema validation in Spring code.
- Fail application startup when dynamic start is enabled and an allowlisted profile is invalid, duplicated or missing required localized setup/quality resources.
- Expose only validated profile identity, fingerprint, supported locales, policy-safe title/description, public setup questions/options, defaults and preset metadata.
- Sanitize terminal/HTML control content and enforce the profile's existing bounds before serializing metadata.

The Docker/release build must copy the same canonical packaged profile resources used by CLI certification. Do not fork a second web-only profile copy that can drift unnoticed; add a build-time digest/parity check.

## 5. HTTP API

### 5.1 Discovery

Add owner-authenticated endpoints:

```text
GET /api/game/generator-profiles
GET /api/game/generator-profiles/{profileId}
```

The list is small and allowlisted. Detail returns safe setup metadata and the exact profile identity/fingerprint needed for optimistic configuration compatibility. It does not return prompts, quality instructions, fallback bindings, provider budgets, local paths or internal capability ceilings that are not player choices.

When dynamic start is disabled, discovery returns a stable unavailable response or an empty capability result according to one documented contract; it must not reveal deployment paths or provider configuration.

### 5.2 Submit a confirmed start

Add:

```text
POST /api/game/dynamic-starts
```

The bounded request contains:

- client-generated `requestId` UUID;
- profile ID, version and fingerprint observed during setup;
- locale, length preset, challenge preset and public setup selections by validated option ID;
- optional suggestion within the profile/host code-point limit;
- explicit disclosure revision and `confirmed=true`;
- optional `expectedCurrentRunId` only for an explicitly confirmed replacement;
- seed only when the existing server test/operator seed switch is enabled.

Reject unknown fields, unknown option IDs, stale profile fingerprints, inconsistent locale/presets, oversized maps/text, unconfirmed disclosure and ambiguous replacement requests before provider construction. Resolve all preferences through `PreparationPresetResolver`; the controller must not manufacture `EffectiveGenerationConstraints`.

The request itself is the final confirmation. Construct `ConfirmedDynamicPreparation` in memory and submit it immediately to the server-owned operation service. Do not write the request body, suggestion or resolved private preparation to a session, database, queue, event or trace.

### 5.3 Operation response and polling

Use wait-then-poll because blueprint generation can exceed an HTTP request timeout:

```text
POST /api/game/dynamic-starts                  -> 200 terminal or 202 processing
GET  /api/game/dynamic-starts/{requestId}      -> owner-scoped status
DELETE /api/game/dynamic-starts/{requestId}    -> best-effort cancellation
```

Responses are a bounded discriminated contract:

- `PROCESSING` with retry delay and no generated content;
- `STARTED` with source-neutral run summary;
- `NEEDS_INPUT` with a stable correction code;
- `FALLBACK_OFFERED` with safe reviewed Pack metadata only, never auto-started;
- `CANCELLED`;
- `FAILED` with a stable content-free code.

Never return prompts, raw provider errors, generated blueprint fields or the submitted suggestion. Polling makes no provider calls and must not wait by joining an unbounded future.

## 6. Idempotency, lifecycle and crash behavior

Within one server process, `(owner, requestId)` is single-flight. Replaying the same confirmed preparation returns the same operation/result; reusing the ID with different safe selections, replacement target or seed returns `DYNAMIC_REQUEST_CONFLICT` without a call.

Use the coordinator's deterministic run identity and check existing ownership/publication before generation. A retry after a successfully published run returns that run without another provider call, including after server restart.

Raw suggestion material remains memory-only. If the process dies before atomic publication:

- do not persist or reconstruct the preparation;
- do not silently restart generation;
- status reports `DYNAMIC_RECONFIRMATION_REQUIRED` or not-found under one documented owner-safe contract;
- the player must review again and use a new request ID before another paid attempt.

Persist only minimal terminal operation identity when necessary to prevent duplicate calls: owner, request ID, derived run ID, safe status/code and timestamps. Do not persist setup selections or hashes of suggestion text unless a separate privacy review explicitly approves them. Expire non-run terminal operation metadata under a short documented retention period.

Cancellation stops future work and propagates through `BlueprintCancellation`; it cannot retract an already submitted provider request or guaranteed charge. Cancellation before publication leaves the previous current run untouched.

## 7. Security and privacy boundary

Dynamic start is authenticated, owner-scoped and cost-bearing. In addition to OAuth/session authentication:

- protect submit/cancel with standard Spring CSRF tokens or an equivalently reviewed same-origin mechanism;
- do not rely on client-provided owner/profile IDs;
- apply a separate per-owner start-attempt rate limit and the existing global/concurrent generation limits;
- enforce request byte limits before JSON binding and code-point limits after binding;
- reject cross-site origins and unsafe content types;
- mark responses `Cache-Control: no-store` where preparation/operation state is present;
- ensure access/error logs, traces, metrics and exception renderers never capture request bodies or suggestions;
- use only content-free metrics: outcome code, latency bucket, provider-call count, profile identity and source kind;
- make other-owner request/run IDs indistinguishable from not found.

The optional suggestion traverses the existing input guard/scrubber and approved disclosure boundary exactly once. It must not enter `pending_start`, `RunSnapshot.startInputs`, JDBC JSON, Spring Session, outbox events or application logs.

## 8. PostgreSQL schema migration

Add a forward-only Flyway migration after V12. Existing Pack rows must migrate without rewriting their snapshot JSON.

The run identity becomes an explicit exclusive union:

```text
source_kind = PACK
  => pack_id + pack_version present; dynamic identity absent

source_kind = DYNAMIC
  => pack identity absent; profile_id + profile_version + game_fingerprint present
```

Migration requirements:

- backfill existing rows as `PACK` before adding the non-null discriminator;
- make `pack_id` and `pack_version` nullable only after backfill;
- add bounded profile ID/version/fingerprint columns;
- add a database CHECK enforcing exactly one valid source identity;
- expand the status constraint only as required for session lifecycle states used by atomic replacement, including `SUSPENDED`;
- preserve the one-open-run-per-owner partial unique index for `PREPARING`/`ACTIVE`;
- preserve command, event, usage and prefetch foreign keys and ordering;
- keep Pack snapshot v1 bytes logically unchanged;
- determine the snapshot size limit from a generated maximum-profile dynamic fixture. Retain 256 KiB if proven sufficient; otherwise introduce one explicit bounded limit no greater than 1 MiB and align application validation with it.

Do not store a separate blueprint/definition column. The verified canonical dynamic bundle remains inside snapshot v2 as specified by 27.26.

## 9. JDBC dynamic transaction contract

Implement `RunRepository.activateDynamic(...)` and `replaceWithDynamic(...)` in `JdbcSessionStore` with the exact semantics already tested for local/in-memory stores.

Before mutation, verify:

- dynamic snapshot v2 and matching run ID;
- canonical bundle/definition/game fingerprints;
- profile identity agreement with the row identity;
- snapshot locale/status and provider-call count bounds;
- successful fresh-engine resume performed by `RunSessionService`.

Activation runs in one short transaction and either inserts the complete run/identity/snapshot/current eligibility/counters or inserts nothing.

Replacement runs in one short transaction with owner rows locked in deterministic order. It must:

1. verify an exact expected current ACTIVE run;
2. reject ownership/status/revision conflicts without mutation;
3. suspend that run;
4. insert the complete dynamic replacement;
5. commit both changes atomically.

On unique-index races, re-read and map to existing bounded `CreateOutcome` semantics. Same-owner replay is idempotent only when immutable dynamic identity agrees and never resets revision, timestamps, usage or snapshot. Other-owner collisions reveal no data.

`row(...)` must decode Pack and dynamic rows source-neutrally, reject impossible mixed identities as store corruption and never call `new PackId(null)`. Dynamic generation-call totals must round-trip through `generation_calls` and the run ledger exactly.

No database transaction or connection may remain open while input safety or provider generation is running.

## 10. Server wiring

Add beans for the validated profile catalog, `SessionGenerators`, output reviewer, input guard, ID source and `DynamicStartCoordinator`/operation service. Reuse the existing `TextGenerator`, generation ledger, owner scopes, clock, limits and bounded worker executor.

Important boundaries:

- normal Pack starts continue through `RunSessionService.start(...)`;
- dynamic starts go only through the trusted coordinator;
- dynamic resume goes through the existing source-neutral engine factory and does not require profile catalog/provider availability;
- provider-disabled mode may render future unresolved scenes through accepted definition fallbacks but never regenerates a blueprint;
- dynamic start feature disablement does not make existing dynamic runs unreadable;
- fallback offers are returned explicitly and do not invoke Pack start automatically.

Separate properties should distinguish game API enabled, Pack generation enabled and new dynamic starts enabled. Validate unsafe combinations at startup with stable configuration errors.

## 11. Existing API and offline queue compatibility

Preserve existing Pack endpoints and status/error meanings. The source-neutral summary is an additive wire evolution except for making legacy Pack fields nullable for dynamic rows.

The browser offline queue may enqueue the final confirmed start request only under the existing idempotency rules, but it must not persist an optional suggestion. Therefore, until Spec 28 provides a reviewed client policy, suggestion-bearing dynamic starts are online-only and never written to IndexedDB. Commands against an already active dynamic run use the same one-pending-command and optimistic-revision rules as Pack runs.

Do not change rendering or add React setup screens in this specification. Update TypeScript contract declarations only if required to keep the repository build type-safe; visual consumption belongs to Spec 28.

## 12. Error mapping

Map bounded engine/session results to the existing error envelope and appropriate HTTP semantics:

- invalid/stale setup or disclosure: `400`/`422` with stable code;
- other-owner/unknown operation or run: `404`;
- active-run/replacement/revision/request-ID conflict: `409`;
- rate/call budget denial: `429` with bounded retry metadata when meaningful;
- processing: `202`;
- generation/provider unavailable: `503` without provider body;
- durable storage failure: `503 SERVICE_UNAVAILABLE`, never `RUN_UNRECOVERABLE`;
- invalid/tampered accepted snapshot: fail closed and publish no row.

Never turn `FallbackOffered` into HTTP success containing a fake dynamic run. Never expose compiler, validator, SQL or provider exception text.

## 13. Test matrix

### 13.1 Controller and operation tests

- profile discovery is authenticated, allowlisted, localized and redacted;
- disabled capability and invalid profile/fingerprint/options make zero calls;
- final confirmation, CSRF, request size and suggestion limits;
- same-request single-flight, conflict and terminal replay;
- processing poll and cancellation without duplicate calls;
- successful start and explicit replacement;
- fallback/correctable/failure result mapping;
- owner isolation for operations and runs;
- no suggestion in responses, logs, session state, events or persistence captures.

### 13.2 JDBC and migration tests

- V12 Pack rows migrate to valid `PACK` identity unchanged;
- dynamic activation success, replay, owner collision and active-run conflict;
- atomic replacement success and injected rollback;
- concurrent activation/replacement race leaves one current run;
- dynamic snapshot, identity, revision, counters and status survive application-context restart;
- ended and suspended dynamic rows decode correctly;
- mixed/missing identity and tampered snapshot are rejected;
- Pack v1 and dynamic v2 rows coexist and remain commandable;
- snapshot cap accepts the maximum valid fixture and rejects oversized data before partial write.

Exercise PostgreSQL-specific CHECK constraints, partial indexes, JSONB and row locking against PostgreSQL 16 in CI. H2 unit tests alone are not sufficient for these cases. Reuse the existing CI PostgreSQL service or add a dedicated bounded integration profile; keep the normal documented local gate deterministic.

### 13.3 End-to-end recovery

With a deterministic provider double:

1. start a dynamic game through HTTP;
2. poll to `STARTED`;
3. apply accepted commands through HTTP;
4. stop the Spring application context;
5. restart with provider and profile catalog unavailable for new starts;
6. read and continue the exact run from PostgreSQL;
7. finish with unchanged game/definition fingerprints and no blueprint calls.

Also rerun Pack controller/session flows and verify dynamic rows cannot break `/runs/current`, `/runs/{id}`, commands, events or deletion.

## 14. Observability and operations

Add content-free metrics for dynamic start submitted/started/failed/cancelled, operation latency, provider attempts, budget denial, activation conflict and resume failure. Tag only bounded values such as result code, source kind and allowlisted profile ID; never tag run/request IDs, suggestion presence/content, fingerprints or user IDs.

Document:

- required feature flags and profile deployment;
- provider-disabled resume behavior;
- worker/concurrency/call limits;
- operation expiry and reconfirmation after crash;
- migration/rollback procedure (application rollback must continue reading migrated Pack rows; database migration itself is forward-only);
- how to disable new paid starts without disabling existing gameplay.

## 17. Acceptance criteria

27.27.4 is complete when:

1. The HTTP run summary represents Pack and dynamic sources without fake Pack identity or null dereference.
2. Clients can discover only validated, allowlisted public profile/setup metadata; they cannot submit paths or profiles.
3. A confirmed authenticated dynamic start traverses the production coordinator and returns wait-then-poll outcomes with no model-output leakage.
4. Same-request replay is single-flight and a published run is recovered without duplicate provider calls after restart.
5. Suggestions are bounded, guarded, memory-only and absent from JDBC, Spring Session, queue, logs, traces, events and responses.
6. Cost-bearing submit/cancel endpoints have CSRF/same-origin, rate, size, owner and concurrency protection.
7. PostgreSQL enforces exactly one Pack-or-dynamic identity and migrates existing Pack rows without snapshot rewrite.
8. JDBC activation/replacement is atomic, ownership-safe, idempotent and preserves the previous current run on failure.
9. Dynamic snapshots, fingerprints, revisions, statuses and provider counters survive a real Spring/PostgreSQL restart.
10. Existing dynamic runs remain readable/playable with new starts, profiles and provider disabled.
11. Existing Pack API, commands, prefetch, migrations and offline queue behavior remain compatible.
12. PostgreSQL-specific migration/concurrency tests, full engine/backend gates, packaging and offline certifications pass.
13. No React game/setup UI or alternate gameplay engine is introduced in this slice.
