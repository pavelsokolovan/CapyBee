# Spec 30.2 — Public Presentation Contracts

**Type:** Implementation instruction
**Intent:** [Illustrated Honeycomb RPG](intent/03-illustrated-honeycomb-rpg.md)
**Depends on:** [30.1](30.1-visual-design-and-svg-catalog-instruction.md), 28.1–28.4, 29.1–29.3
**Baseline:** `996c537`, inspected 2026-11-15
**Status:** Implemented — Pack 1.2.0, 2026-11-15; [acceptance evidence](../game-presentation-contracts-acceptance.md)

## Deliverable and boundaries

Expose trusted artwork references, localized character traits/needs and accepted
recruited companions through the existing public view. React must consume these
without inspecting flags, snapshots, generated blueprints, Pack IDs or prose.
Keep the universal engine headless and source-neutral. The optional capability
must leave text-first games and older views/saves usable.

This part does not render the new board, portraits, party or encounters, change
MOVE behavior, generate artwork metadata, enable providers or add prefetch.
Those belong to 30.3–30.6. Reuse existing recruitment flags; no new command,
affection/health mechanic, API endpoint, cache or client-owned recruitment state.

## Public contract

Keep public `viewSchema` 2 and add optional `View.presentation`. Advertise
`presentation-v1` in the existing capabilities `viewFeatures`. Older consumers
ignore this additive field; v1/v2 views with absent/null metadata remain valid.
The independently versioned envelope has this shape:

```ts
interface GamePresentation {
  schemaVersion: 1;
  catalogVersion: number;
  playerAssetId: string | null;
  backdropAssetId: string | null;
  places: Array<{placeId: string; terrainAssetId: string}>;
  characters: Array<{
    id: string; assetId: string; trait: string | null; need: string | null;
    expression: 'neutral' | 'attentive' | 'pleased'; recruited: boolean;
  }>;
  party: string[];
}
```

Names/descriptions and current-scene presence stay in `View.characters`, keyed
by the same public ID. The envelope only enriches these discovered characters;
party IDs reference enriched characters whose accepted recruitment flag is true.
Absent trait/need means unspecified, never an inferred emotional score.

Return only the accepted scene's backdrop, art for already-public places and
discovered character metadata. Discovery depends on entered scene history,
not geometric proximity, MOVE, scene inspection or a prefetched future scene.
Do not serialize the entire asset catalog, unseen heroes, scene-to-cast map,
recruitment flag names, reveal conditions or future encounter IDs. Completed
views may retain known companions; abandoned views preserve the existing
cleared narrative behavior.

## Authored metadata and universal projection

Support optional `presentation.json` with `ASSETS` plus a local
`assets/catalog.json`, both explicitly indexed in the Pack manifest. Preserve
legacy `ASSETS` Packs that never declared presentation metadata. The catalog is
a bounded list of qualified logical IDs and universal kinds (`CHARACTER`,
`TERRAIN`, `BACKDROP`) with a positive catalog version; it contains no URL, file
path or SVG. The presentation file has schema version 1, an optional player
asset, character definitions, scene/backdrop bindings and place/terrain bindings.

Characters declare an ID, an optional declared generated cast slot, localized name/description keys, optional trait/need
keys, asset ID, scenes in which they appear and an optional existing recruited
flag. Limit characters to 32, scenes/places to 128, asset entries to 256,
appearance scenes per character to 128 and identifiers/keys to 128 characters.
Reject unknown/duplicate fields, duplicate IDs/bindings, unsupported schemas,
invalid/remote/path-like asset IDs, missing required fields, wrong asset kinds
and dangling scene/place/flag/string references in every declared locale.
Name/description strings are nonblank, with trait/need at most 512 code points.
Diagnostics contain stable codes/locations, not raw child/provider content.

Compile/parse the validated definition once per run. Use immutable defensive
copies and the existing reference-validation conventions. Projection reads
current/entered scenes and flag values without mutating them. A discovered
authored character gets a normal public `CharacterItem`; an existing generated
cast member bound through its validated slot retains its accepted engine-owned
ID and name/description; do not duplicate it using an authored actor ID. Optional
metadata cannot change options, routes, legal moves, outcomes, results or RNG.
The dynamic runtime continues with no envelope until a later specification
provides validated presentation metadata; do not invent a dynamic fallback cast.

## React boundary and degradation

Add TypeScript types and a bounded whitelist decoder for `presentation` in the
existing source-neutral decoder. Do not spread arbitrary presentation fields
into the returned object. Enforce array/string/identifier/boolean bounds,
unique IDs and references to public characters/places. Discard unseen character
metadata and unknown party members. Party membership additionally requires the
public metadata's `recruited === true`; no client inference from options or text.

Malformed or unsupported presentation schemas degrade to null independently
of valid story/actions. Unknown/missing/wrong-family artwork resolves through
30.1's fixed catalog fallbacks. Unknown catalog versions retain safe textual
traits/needs and recruited IDs but use neutral local art. Unknown expressions
use neutral. Raw markup/URLs/paths and extra fields are never handed to a
renderer. Older v1 views ignore any presentation field. Keep core view/command
validation strict; this degradation applies only to optional presentation.

## Pack/version and persistence compatibility

Create `capybee-new-hive` **1.2.0** from the existing 1.1.0 resources, adding
reviewed metadata for Capy, Mela, Borys, Luna and all seven public places.
Traits/needs use reviewed Polish strings and the existing `*-joined` flags.
Bind artwork only to IDs in catalog v1; validate canonical manifest parity
against 30.1 so frontend and Pack catalogs cannot silently diverge.

Keep 1.0.0 and 1.1.0 resources byte-for-byte unchanged, retaining both in server
and CLI packaging. New runs select 1.2.0; existing runs stay pinned to their
saved version and fingerprint. Version-bound completion policies may accept
the unchanged reviewed endings in 1.2.0 with the existing semantics. Do not
enable a production/generation flag or alter old resources to retrofit art.

Explicit CLI Pack directories must resolve their identity through the bounded,
validated manifest, including retained directories whose basename is a version.
Keep the host's existing expected-ID loader API strict; directory discovery
must not weaken allowlisted host ID checking.

Metadata is immutable Pack content covered by its fingerprint. Derive the
public envelope from the pinned Pack and saved mechanical state; do not add
an independent presentation save/cache or change snapshot/store schemas.
Publish identical metadata through start/read/command/replay/resume/rejection
paths. Short-reply views preserve accepted metadata. Resume never regenerates
the presentation or changes party membership.

## Acceptance and verification

- Validate all schemas, bounds, duplicate/dangling/wrong-kind references and
  locales using generic engine fixtures; keep product asset vocabulary in Pack
  data, not engine implementation or generic tests.
- Prove hidden cast/flags never enter the public view; MOVE alone does not
  reveal a hero; entering an encounter reveals trait/need; helping recruits
  exactly once; declining/revisiting/rejected commands do not fabricate members.
  Snapshot/resume reproduces exact metadata with providers disabled.
- Round-trip the optional field through session wire JSON and HTTP fixtures.
  Older snapshots/Packs and dynamic/text-only views remain usable. All returned
  collections are immutable; projections do not modify gameplay state.
- Test React old/missing/unknown/malformed/hostile/overlarge metadata, catalog
  mismatch, wrong families, duplicate IDs, hidden metadata filtering, party
  reference filtering and accepted public-state consumption. Story/actions
  remain available when optional art is discarded.
- Verify authored and generated-fallback 1.2.0 routes, retained 1.0.0/1.1.0 saves,
  packaged server/CLI resources, catalog parity and source-neutral public
  contracts. Run standalone engine `clean verify`, the exact backend Maven gate,
  frontend tests/coverage and official UI static sync. Run the existing
  Spring/PostgreSQL browser suite with deterministic providers, including a
  presentation-contract assertion on an actual encounter/recruitment response.
- Record implementation, compatibility checks, Pack fingerprint and limits in
  `docs/game-presentation-contracts-acceptance.md`, and update the specifications
  index. Commit on `main` after gates pass, using the repository's spec format.
