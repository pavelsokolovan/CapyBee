# Spec 28.1 — Game Client Contracts and Transport

**Type:** Implementation instruction
**Parent:** [Spec 28 — Web RPG Client](28-client-rendering-contract-instruction.md)
**Depends on:** Specs 27, 27.27.4 and 27.27.5
**Baseline:** `48bb38b`, inspected 2026-11-14; see the parent for evidence and verification limits.
**Status:** Draft
**Primary outcome:** React consumes a bounded, localized, source-neutral game API through one privacy-aware mutation and recovery layer, without inventing setup rules or replaying paid starts.

## 1. Scope and implementation locations

Extend `app/ui/src/game/gameApi.ts` and add small focused modules under
`app/ui/src/game/` for decoding, requests, mutation policy and operation state.
Reuse `src/offline/queueStore.ts`, `syncEngine.ts` and existing auth restoration;
do not introduce a second independent write/retry engine.

Server changes belong in `app/server/.../game/`, existing wire DTOs and narrowly
scoped engine view production. Do not change snapshot formats, gameplay rules,
generation schemas or database identity for a rendering need.

## 2. Source-neutral browser contract

Model `source` as a discriminated union:

```typescript
type GameSource =
  | { kind: 'PACK'; packId: string; packVersion: string }
  | { kind: 'DYNAMIC'; profileId: string; profileVersion: string;
      gameFingerprint: string };
```

Summary `packId`/`packVersion` are nullable compatibility aliases, never a
dynamic identity. Include all current run statuses (`PREPARING`, `ACTIVE`,
`SUSPENDED`, `ENDED`, `FAILED`, `CANCELLING`, `CANCELLED`) and every actual command,
processing and operation response. Distinguish Pack start `id` from dynamic
`requestId`; do not send a queue-injected `id` in place of `requestId`.

Replace `places: unknown` with the actual `PlacesView`, `PlaceView` and
`PlaceLinkView` fields. Type story, characters, objectives and result from the
current `View`, not an independently invented client schema. Keep v1 block
normalization (`actorId`/`tags`) separate from v2 (`speaker`/`refs`).

Add bounded runtime decoders at the HTTP boundary. They must check known schema
versions, discriminators, required fields, non-negative safe-integer revisions,
collection/text limits and identity consistency. Ignore additive unknown fields;
reject unsupported view/source versions with a localized update/retry state.
Never turn an invalid payload into an empty playable scene. A source-less
legacy summary is accepted only when it has a complete valid Pack identity.
Invalid or mixed identity fails closed. HTML/login pages are not JSON success.

Freeze representative real JSON fixtures for Pack v1/v2, dynamic v2, start,
processing, outcomes, profile metadata and errors. Contract tests must serialize
production Java DTOs and validate the matching TypeScript fixtures so changes
cannot silently drift on either side.

## 3. Public capability discovery

Add authenticated `GET /api/game/capabilities`, available even when new play is
disabled, with `Cache-Control: no-store`:

```json
{
  "schemaVersion": 1,
  "clientEnabled": false,
  "gameEnabled": true,
  "packStartEnabled": true,
  "packGenerationEnabled": false,
  "dynamicStartEnabled": false,
  "supportedViewSchemas": [1, 2],
  "viewFeatures": ["canAdvance"],
  "disclosureRevision": 1,
  "dynamicCancelMode": "BEST_EFFORT"
}
```

These are public behavior flags, not credentials, model names, pricing or
internal budgets. Derive them from effective host configuration and eligibility;
never expose start enabled when its prerequisite service is unavailable. Add
`capybee.game.web-client-enabled` default false for staged client rollout. Keep
API/read capability distinct from discovery of new starts. Profile/Pack lists
remain authoritative for selectable IDs; an empty list is a supported state.

Apply host-side audience eligibility to profile listing, detail and start. Use
the existing child birth year and server clock, never request another birth
date or send age to the generator. Birth-year-only age is an interval; admit
only if the entire possible age interval lies inside the profile audience.
Unknown age fails closed for new generated starts. Revalidate on submit so a
direct API request cannot bypass discovery. Return a stable generic unavailable
code without disclosing age. Do not prevent reading an already accepted run.
Do not alter or silently relabel the detective profile's 15–17 audience.

## 4. Localized setup metadata

Additively extend the profile DTO with `setupSchemaVersion: 1`, effective
`metadataLocale`, ordered `steps` and complete public `inputs`. Preserve existing
profile fields/questions for compatibility:

```json
{
  "steps": [{"id":"feel","title":"The feeling","inputIds":["tone"]}],
  "inputs": [{
    "id":"tone", "kind":"ENUM", "label":"Tone", "help":"Choose a tone",
    "required":false, "maxItems":1, "maxCodePoints":null,
    "defaults":["curious"],
    "options":[{"id":"curious","label":"Curious"}], "notice":null
  }]
}
```

Derive fields from validated `ProfileSetup`, `StartInputDef` and localized
strings. `ENUM_SET` carries its real selection ceiling; `FREE_TEXT` has no
options/default text and carries the effective code-point ceiling and notice.
Do not return prompt/quality resources, raw rule capabilities or filesystem
paths. Do not infer controls from IDs, option counts or translated help text.
Preserve ordered steps and distinguish an absent answer from explicit clearing.
Normalize `Accept-Language` to a supported base tag before the documented
default fallback; return the actual resolved metadata locale.

Add the same display-safe metadata as an additive `setup` field on Pack
discovery entries, including localized title/description, start input labels,
options and defaults when present. Resolve through existing Pack strings and
generation setup, with a single logical step if there is no step resource.
An authored Pack with no inputs needs no invented wizard. `generated=true` in
Pack metadata means support, not a requirement or permission to call a provider.
Generated Pack play requires the corresponding capability and disclosure.

The baseline Pack session host strips free-text start inputs before scheduling
the start, so it cannot honestly offer that personalization. For this series,
Pack setup advertises `transientTextSupported: false`: omit optional free-text
start controls with a short unavailable notice, and disable starting a Pack
that requires one. Do not send a text field that the server silently ignores.
Dynamic `suggestion` and gameplay `SUBMIT_TEXT` remain supported through their
existing guarded paths. Adding transient Pack-start text delivery/recovery is
deferred rather than persisting it in `pending_start`.

Keep the host allowlist and existing resolver authoritative. Metadata and
submit validation must agree, including the global request ceilings. A stale
fingerprint requires rediscovery and review, never silent selection remapping.

## 5. Explicit advance affordance

Add additive `canAdvance: boolean` to the engine-produced current `View` and
update all view mapping/constructors and client fixtures. It is true only if an
active, non-ended scene has no options and a legal next transition under the
existing `RunImpl` rules. The calculation is pure and makes no provider call.
Do not expose scene internals or implement this inference in React.

Preserve old constructors with a safe false default. Keep view schema 2 because
this is additive; advertise the new field through `viewFeatures`. New clients
require that feature before enabling full play. A legacy view without it still
renders text/choices but never guesses that an empty options array means Next.
Test scenes with choices, text-only input, automatic advance, ending and no
legal successor. Authored and dynamic views must use the same producer.

## 6. Unified mutation policy

This specification explicitly refines the generic offline-write guidance for
privacy-sensitive engine operations. Implement two modes within the existing
sync/mutation boundary, and update its scoped guidance when implementing:

| Operation | Storage and dispatch policy |
|---|---|
| Pack or dynamic start | Online, final-confirmed, memory-only body; never background-enqueued |
| `SUBMIT_TEXT` | Online, memory-only body; never persisted or auto-recreated |
| `CHOOSE`, `ADVANCE`, `MOVE`, confirmed `ABANDON` | Durable owner/run-scoped queue, one unresolved command per run |
| Cancel dynamic start | Explicit online action; retain only an operation marker |
| Reads and status polls | Network-only; cannot trigger writes/provider generation |

All writes go through this shared dispatcher; components do not invent fetch
retry loops. Do not apply optimistic gameplay effects: only a pending indicator
is optimistic. Non-game queue semantics must remain compatible.

Durable game records include owner namespace, run ID, UUID, expected revision,
the bounded command payload and retry/poll metadata. Never include a View,
story, profile draft or free text. On `202`, transition to GET polling using the
same command ID rather than repeatedly POSTing. A lost POST response first
polls that identity. An exact retained non-text command may be re-POSTed only
after an authenticated not-found result and authoritative revision/status
reconciliation. Never generate a replacement UUID as an automatic retry.

For memory-only writes persist at most an owner-scoped marker containing
operation/request/command ID, run ID if known, expected revision and timestamp.
Do not persist the body or its hash. On reload, recover by GET; if the operation
cannot be established, require explicit review/confirmation for a new start,
or freshly typed text. Never reconstruct the body from UI history.

Handle error envelopes separately from dynamic terminal operation DTOs; a
`503` with `status=FAILED` is a terminal result, not an automatic paid retry.
Decode response bodies on non-2xx results too. Preserve stable codes privately
for mapping; never display raw backend/provider messages.

## 7. Polling, ordering and authentication

- Use same-origin relative paths, `credentials: include`, JSON content type,
  `cache: no-store`, bounded request timeouts and `AbortController`.
- The browser supplies `Origin`; do not spoof or set it in JavaScript. Preserve
  server same-origin checks; do not enable wildcard CORS or disable protections.
- Honor bounded `retryAfterMs` and numeric/date `Retry-After`, with a minimum
  polling delay of 1 second and a 60-second ceiling. Use bounded exponential
  backoff for transport failures. Do not tight-loop on invalid values.
- One in-flight poll per operation. Pause hidden/offline polling and reconcile
  once on visibility/reconnect. After five visible minutes without a terminal
  result, pause automatic polling and offer Check status/Leave; this is not a
  declaration that the operation failed or permission to resubmit.
- Cancel timers/subscriptions on unmount. A browser abort detaches the request;
  it is not server cancellation or proof that no provider charge occurred.
- Associate every response with owner, run and operation generation. Ignore
  stale responses after account/run changes and never replace a higher run
  revision with a lower one. Same-revision conflicting payloads force a fresh GET.
- On 401, pause writes/polls and invoke existing session restoration once.
  Resume only after confirming the same owner. Never replay under a new owner.

## 8. Backend operation prerequisites

Before exposing the client to paid dynamic starts, fix the inspected scheduling
race in `DynamicStartOperationService`: reserve the owner/request slot before
scheduling any work. Conflicting/repeated requests must not schedule discarded
workers. Compare the existing safe preparation signature, not logged content.
Bound terminal operation retention and remove references to completed private
preparations. A process restart still requires the documented recovery policy;
do not persist raw setup to make an operation durable.

Cancellation is explicitly best effort. Do not claim that
`CompletableFuture.cancel(true)` prevents publication. Wire an operation-owned
cancellation signal through the existing engine cancellation boundary and check
it at the atomic activation/replacement boundary. Publication and cancellation
must have one ordered winner: cancellation wins before activation with the
previous run untouched, or publication wins and the response identifies the
saved run. A provider request already in flight may finish or be charged.
Retain/read a terminal cancellation status rather than converting a cancelled
future into a generic failure. Add only the narrow coordinator/session adapter
changes needed; no new generation engine or persistence format.

## 9. Tests and acceptance

Use Vitest/happy-dom and fake clocks for decoding, sequencing, backoff,
202-to-GET transitions, lost responses, owner switch, malformed JSON/HTML,
unknown schema and non-2xx terminal results. Inspect storage writes and prove
that private sentinel strings never enter them. Test transient operations under
React remount/double invocation and repeated confirmation events.

Server tests must cover localized metadata/cardinality/default agreement,
audience boundaries, no new calls on duplicate/conflicting submits, cancellation
versus activation races, owner isolation and disabled-start saved-run access.
Core tests cover `canAdvance` without changing accepted-command semantics.

This part is complete when matching DTO fixtures pass on both sides, writes use
the declared storage modes, processing uses status polls, private text remains
memory-only, and repeated submits cannot schedule duplicate generation work.

Run focused tests, frontend coverage/build/static sync, the exact backend gate
`mvn -B -f app/pom.xml -pl server -am verify`, and
`mvn -f app/engine/pom.xml clean verify` for the engine/session changes. Fix and
rerun implementation failures. Preserve coverage thresholds. Mark only 28.1
implemented, then commit using the repository implementation-message convention.
