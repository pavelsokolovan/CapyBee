# Spec 27.18 — Generator Profile and Capability Contract

**Type:** Implementation specification  
**Parent:** Spec 27.17 — Dynamic Game Generation Architecture and Preparation Wizard  
**Depends on:** 27.17 architecture, existing input/safety contracts from 25/27.8, and the existing pack/rules validation infrastructure  
**Baseline:** Local CapyBee checkout at `bbc66e8fd55e9c3ca1390705614bf0bba4d4b07c`; Spec 27.17 read in full from its current saved version. Existing unrelated `SceneOption.java` modification is outside scope. No build or live-provider request was run while preparing this document. Reinspect current implementation before coding.  
**Status:** Implemented  
**Primary outcome:** The engine can load and validate an authored, scenario-neutral generator profile, expose localized wizard metadata, and deterministically resolve preset answers into bounded generation constraints without creating a game, invoking a provider, or persisting free text.  
**Repository destination:** `docs/specifications/27.18-engine-generator-profile-and-capability-contract-instruction.md`

---

## 1. Purpose

Dynamic generation needs a trusted description of what the engine can generate before a particular scenario exists. An ordinary playable Pack cannot serve that purpose: current generation catalogs require already-authored scenes, choices and rules.

Introduce **GeneratorProfile**, separate from Pack. It describes supported setup options, structural/mechanical capabilities, safety constraints, budgets, prompts, quality resources and reviewed offline alternatives. It never declares the new game's actual scene IDs, actor slots, objective IDs, routes or endings.

The preparation wizard obtains its labels, defaults and allowed values from the profile. It must not hardcode a hidden Willow Marsh scenario or require players to know internal IDs.

## 2. Scope and non-goals

### In scope

- Versioned profile resources and strict parsing.
- Immutable Java domain contracts and collected validation issues.
- Capability bounds and closed mechanic vocabulary identifiers.
- Preset setup definitions and localized wizard presentation.
- Deterministic preset-to-constraint resolution.
- Clear separation of persistent preset values and optional transient suggestion.
- Resource integrity, fingerprints and explicit reviewed-fallback references.
- Positive, negative, localization, privacy and compatibility tests.

### Out of scope

- GAME_BLUEPRINT provider requests, generated blueprint parser or repair loop (27.19/27.20).
- Graph/state-space proof, rule compilation or runtime integration (27.21–27.24).
- Scene prose generation or runtime fallback composition (27.25).
- Session migration, profile archival or durable game resume (27.26).
- Rendering the CLI wizard or a public dynamic-generation command (27.27).
- Web screens, HTTP APIs, database tables or preference-history storage.
- New effects/conditions or changes to their interpreter.

Do not add an inactive CLI flag or advertise dynamic games as playable when only profile loading is complete.

## 4. Resource layout and identity

Use a dedicated bundle, for example:

```text
generator-profiles/generic-adventure-v1/
  profile.json
  setup.json
  strings/en.json
  strings/pl.json
  prompts/en/blueprint.md
  prompts/pl/blueprint.md
  quality/en.json
  quality/pl.json
```

This layout is not a new playable Pack format. Author reviewed fallback packs separately and reference their immutable identity.

### 4.1 Identity

- `schemaVersion`: exact supported profile format version, initially 1.
- `id`: stable lowercase ASCII ID, matching `[a-z][a-z0-9-]{0,63}`.
- `version`: existing semantic PackVersion syntax, reused where compatible.
- `files`: exact allowlist of profile-relative resource files, excluding `profile.json` itself.
- Same identity/version must resolve to identical normalized content fingerprint. Changed instructions, defaults, strings, capabilities, budgets or fallback references require a version bump.
- Reject duplicate bundle registration by ID/version when fingerprints differ.

### 4.2 Resource safety

No absolute paths, empty segments, `..`, backslashes, URL schemes, query strings, fragments or symbolic-link escape. Reject duplicate paths, missing indexed files, unused indexed files and references to non-indexed files. Access only supplied bundle contents; core does not fetch a URL, walk a filesystem or resolve a host path.

Recommended loader boundary: supplied UTF-8 resource map or existing provider-neutral resource accessor. A filesystem adapter may build that map outside the domain. Reuse an existing adequate abstraction rather than adding a speculative future port.

Hard load bounds: 64 files, 1 MiB combined UTF-8 bytes, 64 KiB per JSON file, 16 KiB per prompt, JSON nesting 24. Fail before parsing oversized input. Prohibit duplicate JSON object keys, trailing content, unknown fields and coercion of strings/floats into integers/booleans.

## 6. Capability validation

### 6.1 Supported v1 envelope

These are engine-wide maxima, not values the player can raise:

| Field | Valid range / restriction |
| --- | --- |
| Supported locales | 1–8 unique valid LocaleTags; default included; no implicit locale fallback |
| Phases | All five current PhaseKind values exactly once in their existing order |
| Graph | FORWARD_DAG only; no backward phase edges or cycles; exact graph validation deferred |
| Places | false only in v1; true is unsupported, not silently ignored |
| Scenes | `6 <= minScenes <= maxScenes <= 24`, including endings |
| Choices per nonterminal scene | Profile maximum 2–4; a particular scene may have fewer; at least one meaningful choice required by later graph validation |
| Actors | `1 <= minActors <= maxActors <= 12` |
| Objectives | `1 <= minObjectives <= maxObjectives <= 8` |
| Endings | `2 <= minEndings <= maxEndings <= 4` |
| State declarations | Counters 0–4; flags 0–12; sets 0–2; values per set 1–8 |
| Counter values | `0 <= counterMin < counterMax <= 20`; delta 1–5, no greater than interval width |
| Conditions | Depth 1–4; nodes 1–32, counted per expression tree |
| Effects | 0–6 per choice |
| Explored states | 1–100000; exhausting the limit is inconclusive/rejected, never proof of playability |
| Suggestion | When enabled, 1–300 Unicode code points; when disabled, limit 0 and no FREE_TEXT field |

Exact blueprint expression semantics and state exploration remain owned by 27.21/27.22. Profile acceptance means configuration is internally valid, not that any future blueprint is automatically playable.

### 6.2 Closed mechanic subset

Profile v1 may allow only these existing discriminators:

- Conditions: COUNTER_AT_LEAST, COUNTER_AT_MOST, COUNTER_EQUALS, FLAG_IS, SET_CONTAINS, SET_SIZE_AT_LEAST, VISITED_SCENE, ALL, ANY, NOT.
- Effects: COUNTER_ADD, COUNTER_SET, FLAG_SET, SET_ADD, SET_REMOVE.

Reject GO_TO, AT_PLACE, VISITED_PLACE, STEP_AT_LEAST, EMIT_EVENT and END_RUN in this dynamic profile format. They may exist in authored games; this spec does not remove them there. Ending outcomes use declared terminal scene mappings, not arbitrary END_RUN effects.

Use exhaustive engine-owned capability registration or enum mappings; do not reflectively instantiate a class from a JSON string. New discriminator support requires explicit implementation, tests and a compatible format decision. Unknown entries fail closed.

Detect incoherent configurations: counter predicates/effects require positive counter capacity, set operations require positive set capacity, flag predicates/effects require positive flag capacity. NOT/ALL/ANY count toward depth/node limits. Profiles and challenge subsets cannot claim a feature with its needed capacity zero. Unused capacity is permitted.

### 6.3 Length presets

Require 1–4 unique length presets; `4 <= minStoryTransitions <= maxStoryTransitions <= 16`. Count story transitions as graph edges from start to ending, excluding pure utility UI actions. Scene count includes all generated branches/endings, not only a selected route.

Each preset's maxScenes is at most the global maximum and at least the global minimum. Necessary feasibility check for the longest declared route plus alternative terminal scenes: `maxScenes >= maxStoryTransitions + minEndings`. This is a conservative profile check; exact path coverage belongs to the blueprint validator. A graph may not exploit an unreachable extra ending to satisfy bounds.

Preset definitions do not contain scene IDs, phase membership assignments or a sample plot. Do not promise minutes of play based only on transitions.

### 6.4 Challenge presets

Require 1–4 unique presets. The exact schema is the challenge shape in §5; every numeric maximum must be no larger than its profile maximum, and every allowlist must be a subset of profile capabilities. A selected preset narrows capabilities; it never expands them.

This version defines challenge as **mechanical complexity**, not measured human puzzle difficulty. Expose that honestly in help copy. Each preset must differ in at least one effective bound/allowlist from another; labels alone are not a functional difference. Reject unusable zero-node/depth configurations or unbound state references. A profile with no state-changing effects can still be valid if its objectives use VISITED_SCENE and its branching does not require state mutation.

### 6.5 Generation budget

- totalCallsPerRun: 1–64.
- blueprintMaxAttempts: 1 or 2; includes the initial request and at most one repair.
- blueprintMaxOutputTokens: 512–12000.
- sceneMaxAttempts: 1 or 2.
- sceneMaxOutputTokens: 128–1500.
- maxInputCharacters: 1024–32000, measured as Java UTF-16 code units consistently with current request limits; suggestion uses Unicode code points separately.
- No API key, vendor/model identifier, price, endpoint, raw prompt history or player-controlled budget field.
- Profile budgets are ceilings; host/global/user budgets may narrow them and cannot be overridden by setup.
- For each offered length, require `totalCallsPerRun >= 1 + maxStoryTransitions + 1`: one initial blueprint attempt plus each scene on the longest route. Repairs/prefetch may exhaust the remainder; validated narrative fallbacks are required later. This does not reserve calls for every alternative scene.
- Do not add independent THEME/SCENARIO/CAST/QUEST calls to that minimum implicitly. Dynamic bootstrap planning is one blueprint operation; 27.20/27.25 must reconcile any additional stages and revalidate budgets explicitly.

### 7.2 Fixed semantic bindings

Profile v1 recognizes only these input IDs: genre, setting, tone, interests, length, challenge, game-locale, story-wish. Values of creative fields are authored identifiers, not engine-hardcoded genre vocabulary; the example is neutral reference data. Length/challenge values must exactly equal their preset IDs in order. Locale values exactly equal supportedLocales.

Length, challenge and game-locale are required, present once, and have one valid default. Other fields may be omitted entirely from a profile. At most one optional FREE_TEXT input, story-wish, is permitted; its maximum equals policy.maxSuggestionCodePoints. No FREE_TEXT routing/stages field is accepted: the dynamic mode's only allowed consumer is future GAME_BLUEPRINT, including its bounded repair within the same start operation.

Do not add GAME_BLUEPRINT to the historical catalog enum solely to parse this setup file. 27.20 owns its production stage integration.

### 7.3 Wizard validation

- At most six nonempty steps; at most eight total inputs. Each input belongs to exactly one step; no duplicates or unknown references.
- Questions exactly cover the input definitions once and in input order. Step traversal order must yield that same flattened input order.
- Option values exactly match enum definitions, in order; max 16 options per input.
- ENUM_SET has maxItems 1–4, not exceeding available values. No duplicate values/defaults.
- FREE_TEXT is optional, no defaults/options; freeTextNoticeKey required and forbidden on other kinds.
- For optional ENUM/ENUM_SET, empty default means no preference. The host offers skip/clear or “Surprise me” as an operation; do not persist a fake `surprise` value.
- Required presets cannot be cleared or randomized without a defined supported result.
- No arbitrary input mapping expressions, dynamic visibility scripts or URLs.
- A question's selected value must reach a documented constraint field (§8); no decorative no-op controls.

## 8. Deterministic resolution of preset selections

Implement a pure `PreparationPresetResolver` (or equivalent nearby name). It takes a validated profile, declared preset answer map, and optional explicit requested game locale. It returns either collected issues or immutable `ResolvedGamePreferences` plus `EffectiveGenerationConstraints`.

This resolver accepts **presets only**. Receiving story-wish in its map returns PREPARATION_TRANSIENT_INPUT_REQUIRED without including the value in diagnostics. It neither approves nor stores text. The later start-operation boundary combines resolved presets with transient approved text through the existing safety pipeline.

### 8.1 Resolution order

1. Reject unknown input IDs/values, duplicate ENUM_SET selections, missing required configuration and wrong types.
2. Apply defaults only to absent fields, never over explicit selections. For optional inputs, an explicit clear must remain clear; represent edit intent in the host draft, and pass a resolved explicit-empty marker or typed omitted/default choice to the resolver. Do not collapse clear and absence into the same map entry.
3. For game locale: conflict between explicit requested locale and explicit wizard selection is PREPARATION_LOCALE_CONFLICT; otherwise use either explicit value, then the configured default. Never guess based on OS locale in core.
4. Canonicalize ENUM_SET selections into authored declaration order; retain immutable collections.
5. Resolve selected length/challenge IDs. Required defaults must exist; unknown IDs fail.
6. Produce hard constraints by intersecting profile bounds, selected length/challenge and optional trusted host ceilings. If host ceilings make a selection impossible, fail; do not change the selection silently.
7. Produce creative preference fields from explicit selected values, or absence. Do not infer content from labels or use a provider to classify choices.

Use a typed input representation when a plain map cannot distinguish ABSENT, SELECTED and CLEARED. These three states are mandatory; exact Java naming may follow project conventions. Do not alter existing Pack start-map semantics to impose the new draft representation on historical callers.

### 8.2 Result fields and precedence

| Field | Output and enforcement |
| --- | --- |
| Profile identity | ID, version, fingerprint; bound to this resolved result |
| gameLocale | Hard constraint; output accepted only in this supported locale |
| lengthPresetId | Exact min/max transition bounds and maxScenes intersected with profile bounds |
| challengePresetId | Effective mechanic capacities and allowlists; never more permissive than profile |
| genre / setting / tone | Optional creative preferences, not executable mechanics |
| interests | Ordered unique creative preference IDs |
| Audience, forbidden tags | Hard policy independent of child choices |
| Suggestion | No field in persistable result; only transient later capability |
| Budgets | Authored ceilings narrowed by trusted host limits, never player data |

The preset resolver cannot prove natural-language compliance. Later requests must transmit explicit creative preferences alongside the approved suggestion, instructing that it adds detail without silently overriding them. Structural/hard constraints are checked deterministically by later validators. Unsupported wishes are adapted or rejected honestly; never treated as permission for new rule types.

## 9. Localization, prompts and quality resources

Require string, blueprint-prompt and quality resource maps with keys exactly equal to supportedLocales. No silent language fallback.

- String resources use the existing locale-string conventions where possible; all title, description, step, question, help, option and notice keys must resolve to nonblank plain text.
- Limits in Unicode code points: title/question/option 120; description/help/notice 600. Reject active markup and unresolved placeholder syntax. Do not interpolate user text into labels.
- Provide actual EN and PL strings in the neutral example bundle. Future profiles may support different locales; no EN/PL branching in engine code.
- Disclosure/navigation host copy is owned by 27.27, not repeated as hardcoded domain strings. Free-text help must warn against real names, contacts, exact location, schools, secrets and that saved story content can reflect the idea.
- Blueprint prompts are authored instruction resources, not scenario templates with prefilled actors/objectives/routes. No player data substitution during load. 27.20 supplies bounded structured context separately.
- Validate quality resources through applicable existing parser/rules. Where the current parser requires a Pack or rules-derived truth references, extract a resource-level parse boundary without inventing dummy scenes. Reject dangling profile-specific references; generated-definition-dependent truth bindings belong to 27.25.
- A loaded quality resource is not evidence a future model response passed quality evaluation.

## 10. Reviewed offline fallback contract

Each fallback entry is exactly a PackId/PackVersion, supported locale and length/challenge preset IDs; no path or endpoint. Entries are unique for that locale/length/challenge tuple.

Profile parsing validates reference shape. A separate local binding check against supplied already-validated fallback Packs is required before a profile is exposed as offline-capable. This is local lookup, not network resolution; do not introduce future remote catalogs in this spec.

Binding validation must establish that the actual pack supports that locale, advertises a validated full-game contract, and has path bounds within the referenced length plus no mechanics outside the selected challenge/profile subset. Derive declarations and used condition/effect types from real pack data; do not trust fallback labels. A fallback outside supported dynamic mechanics remains playable through its old Pack path but cannot be advertised as honoring these settings.

Keep original Pack identity/version for a reviewed fallback; do not stamp it as generated or assign the profile's identity to it. No custom idea, genre/setting/interest preference is promised in offline mode. The future host hides/disables unsupported customization and explains the actual fallback before confirmation. No matching tuple means FALLBACK_UNAVAILABLE for those settings, not a locale/length substitution.

Cross-profile mechanics and fallback bindings must not depend on Willow Marsh constants. Neutral test fixtures belong in test resources and may be reused as offline examples only after full validation.

## 11. Java and validation boundaries

Suggested package: `com.capybee.engine.generation.profile`, with JSON parsing in its `json` subpackage. Follow actual repository boundaries before selecting final names.

Introduce only immediately used types: GeneratorProfile, ProfileCapabilities, LengthPreset, ChallengePreset, ProfileGenerationBudget, ProfileSetup, ValidatedGeneratorProfile, ProfileIdentity, ResolvedGamePreferences and EffectiveGenerationConstraints, with supporting immutable records as needed. Avoid duplicate versions of existing IDs, LocaleTag, Issue and StartInputDef.

`ValidatedGeneratorProfile` must not be publicly constructible from unchecked arbitrary data; a loader/validator establishes it. Resolved preferences must retain profile identity so callers cannot mix defaults/bounds from another version.

All collections are defensive immutable copies, preserving declared ordering for presentation. No JSON library imports outside `json`/adapter boundaries. No IO, provider SDK or host framework dependencies in domain/resolver code. Strings in profile resources are data; never executed.

Loader result collects deterministic bounded issues with code, resource and JSON pointer. No exception messages derived from user data. Proposed codes:

- PROFILE_SCHEMA_UNSUPPORTED / PROFILE_JSON_INVALID / PROFILE_UNKNOWN_FIELD
- PROFILE_RESOURCE_INVALID / PROFILE_RESOURCE_MISSING / PROFILE_LIMIT_EXCEEDED
- PROFILE_LOCALE_INVALID / PROFILE_STRING_MISSING
- PROFILE_CAPABILITY_UNSUPPORTED / PROFILE_CAPABILITY_INCONSISTENT
- PROFILE_PRESET_INVALID / PROFILE_SETUP_INVALID / PROFILE_BUDGET_INSUFFICIENT
- PROFILE_FALLBACK_INVALID / PROFILE_IDENTITY_CONFLICT
- PREPARATION_INPUT_INVALID / PREPARATION_LOCALE_CONFLICT
- PREPARATION_TRANSIENT_INPUT_REQUIRED / PREPARATION_CONSTRAINTS_UNSATISFIABLE

Never include submitted values or full prompt/resource content in issue messages. Cap accumulated findings at 100 and report an explicit truncation code rather than unbounded amplification.

### Fingerprint

Compute SHA-256 over a versioned canonical representation of the validated profile configuration and every indexed resource, ordered by path; canonicalize JSON objects by key, retain array order, and normalize text line endings to LF. Define the exact canonical encoding in code tests (including UTF-8 and length-delimited paths/content) to avoid concatenation ambiguity. No suggestion or player answer enters this fingerprint. A changed meaningful resource changes the fingerprint; equivalent JSON whitespace/key order does not. Reject malformed Unicode rather than hashing replacement characters.

## 14. Definition of done and downstream handoff
