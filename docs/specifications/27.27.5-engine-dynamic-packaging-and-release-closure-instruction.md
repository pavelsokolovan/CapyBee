# Spec 27.27.5 — Dynamic Packaging and Release Closure

**Type:** Implementation instruction
**Parent:** Dynamic-game release completion after Spec 27.27.4
**Depends on:** Specs 27 and 27.17–27.27.4, especially the trusted dynamic CLI start, atomic local recovery, offline and live certification, source-neutral web sessions, PostgreSQL persistence, the canonical `generic-adventure` generator profile, `package-engine.ps1`, `dev.ps1`, Docker packaging and the engine release-certification workflow
**Baseline:** Inspected local `main` at commit `f7da56b` on 2026-10-29. The engine CLI and Spring host can start, persist, resume and certify bounded dynamic games. The current portable package script hard-codes `0.1.0-SNAPSHOT`, emits a hand-maintained partial SBOM, accepts dirty source trees, includes nondeterministic metadata, and certifies only the already-unpacked staging directory. There is no independent clean-room archive verifier or promotion manifest. The release workflow rebuilds candidates per job/operating system; its optional live job builds another artifact and currently invokes Pack live certification rather than the dynamic live suite. The server image does not yet have one explicit parity-checked release contract for the canonical generator profile. No build, package, provider call or release action was run while preparing this document.
**Status:** Implemented
**Primary outcome:** Produce one immutable, independently verifiable dynamic-game release candidate whose CLI archive and server image contain the intended canonical resources, pass credential-free clean-room certification, can be optionally bound to current live-provider evidence, and can be promoted without rebuilding or overstating what was certified.
**Repository location:** `docs/specifications/27.27.5-engine-dynamic-packaging-and-release-closure-instruction.md`

---

## 1. Purpose

Specs 27.17–27.27.4 establish the dynamic-game trust, runtime, persistence, certification and web-host boundaries. This final slice closes the difference between "the code works in a checkout" and "this exact artifact is safe to publish":

```text
clean immutable source revision
  -> one versioned candidate build
  -> canonical CLI + server resource assembly
  -> generated SBOM, inventory and digests
  -> independent extracted-archive/image verification
  -> deterministic Pack + dynamic offline certification
  -> backend/PostgreSQL restart certification
  -> optional paid dynamic live certificate for the same digest
  -> promotion manifest and immutable release artifacts
```

No release label may be inferred from a successful compile alone. The release statement must describe the exact evidence available for the exact bytes being promoted.

## 2. Scope

### 2.1 In scope

- Replace hard-coded development packaging identity with a single validated release-version and source-revision contract.
- Build the CLI archive once and promote the same bytes through verification and optional live certification.
- Package the canonical validated generator profile, certification suites, schemas, reviewed fallback Pack, documentation and legal material.
- Give the server JAR/container an explicit allowlisted generator-profile resource contract with digest parity against the CLI package.
- Generate a complete machine-derived CycloneDX SBOM and a strict bounded artifact inventory.
- Add an independent package verifier that validates an extracted archive without trusting the packaging script.
- Run offline Pack and dynamic certification from a fresh extraction of the finished archive.
- Add a packaged Spring/PostgreSQL dynamic start, restart and resume release gate using deterministic providers.
- Correct and harden CI so optional paid dynamic certification consumes the exact offline-approved candidate.
- Produce a source-discriminated release manifest/attestation that records artifact and evidence digests without generated content or secrets.
- Define immutable promotion, retention, rollback and release-status language.
- Add cross-platform packaging/verifier tests and update release/operator documentation.

### 2.2 Out of scope

- React setup, rendering or gameplay UI; Spec 28 consumes the completed web API.
- New blueprint fields, mechanics, profiles, provider adapters, session semantics or persistence formats.
- A public profile marketplace, arbitrary profile upload or runtime download.
- Making a real paid provider call during normal builds, tests or offline certification.
- Publishing to Maven Central, an app store or another registry not already selected by the repository.
- Designing a custom signing authority, key-management service or certificate transparency system.
- Claiming story quality, novelty or a particular ending from structural certification.
- Bundling operator pricing, credentials, private setup text, generated live evidence or database contents in public artifacts.

## 3. Release identity and candidate immutability

Introduce one release input contract consumed by Maven, PowerShell, Docker metadata and CI. At minimum it contains:

- semantic product version, with `-SNAPSHOT` allowed only for development candidates;
- full Git commit and optional source tag;
- clean/dirty state;
- build timestamp supplied through `SOURCE_DATE_EPOCH` or another documented deterministic input;
- Java/toolchain and repository policy/schema versions;
- candidate ID derived from version, commit and primary artifact digest.

Do not infer the version independently in `package-engine.ps1`, `dev.ps1`, workflow paths and documentation. Read it from one authoritative build source or pass one validated release parameter through every layer.

A promotable candidate must:

1. come from the exact recorded commit;
2. have a clean tracked and untracked release input tree, excluding only bounded documented build outputs;
3. use a non-snapshot semantic version and an expected matching tag when producing a public release;
4. be built once;
5. retain the same archive/JAR/image digests through every later gate.

Dirty or snapshot builds remain useful development artifacts but are marked `development` and cannot produce a promotion manifest. Never silently clean, reset or mutate the checkout to satisfy this rule.

## 4. Canonical release contents

### 4.1 CLI distribution

The portable archive must contain exactly the allowlisted layout declared by a versioned distribution manifest:

```text
bin/engine-cli.jar
packs/<reviewed-fallback-pack>/...
profiles/generic-adventure/...
certification/willow-marsh-v1/...
certification/dynamic-v1/...
certification/dynamic-live-v1/...
docs/CERTIFICATION.md
docs/OPERATIONS.md
LICENSE.txt
NOTICE.txt
build-info.json
distribution-manifest.json
sbom.cdx.json
checksums.sha256
```

The manifest declares every allowed path class, size ceiling, media/type expectation and whether it is executable input, documentation or evidence support. Reject unexpected files, duplicate normalized paths, case-colliding paths, absolute paths, traversal segments, links/reparse points and archive expansion beyond the declared file/byte limits.

Profiles, suites, schemas and fallback bindings are copied from their canonical repository sources. The build must load and validate the bundled profile and Pack through production loaders before archive creation. Do not maintain a second hand-copied release profile.

### 4.2 Server artifact and image

The Spring release artifact must include or receive through one documented immutable deployment layer:

- the exact canonical generator-profile files enabled for dynamic start;
- the reviewed Pack resources required by configured fallback/Pack play;
- startup configuration that identifies allowlisted profile IDs, not arbitrary paths;
- build metadata exposing version, commit and profile fingerprint to authenticated operational diagnostics without revealing prompts or filesystem paths.

Prefer embedding the release profile as bounded classpath resources or copying it into a read-only container path owned by the image. If external mounting remains supported, it is an operator override and must pass the same digest/loader validation before new starts are enabled.

The CLI and server copies of `generic-adventure` must produce the same `GeneratorProfile` identity and canonical fingerprint. Add a build-time parity test; byte-for-byte parity is preferred, but canonical-loader fingerprint parity is authoritative where archive metadata differs.

Resume/read/command of already persisted dynamic runs remains possible when profile resources or new-start configuration are disabled, as required by 27.27.4.

## 5. Reproducible and bounded assembly

Refactor packaging into explicit assemble, verify, certify and promote phases. Packaging must be non-interactive, fail-fast and safe on Windows and Linux.

For identical source revision, release inputs and supported toolchain, two builds on the same platform must produce identical logical contents and identical per-file digests. Normalize:

- archive entry ordering and separators;
- timestamps from the declared build epoch;
- UTF-8 encoding and line endings for generated JSON/text;
- file permissions and executable bits;
- JSON key ordering and decimal formatting;
- locale/time-zone-dependent values;
- SBOM serial/metadata inputs.

If byte-identical ZIP output cannot be guaranteed across the supported Windows/Linux implementations, require identical extracted inventory and per-file digests and document the platform-specific outer-container digest. One canonical CI platform builds the promotable archive; other platforms verify and certify those downloaded bytes rather than rebuilding a competing release candidate.

Never include local absolute paths, user names, environment dumps, credentials, provider request bodies, generated game content, `.git`, Maven caches, temporary stores or prior evidence directories.

## 6. SBOM, legal and dependency inventory

Replace the hand-written SBOM component array with Maven/CycloneDX output derived from the resolved runtime dependency graph of the shaded CLI and server application. Requirements:

- CycloneDX JSON validates against the selected schema version;
- direct and transitive runtime components include package coordinates, versions, hashes and dependency relationships when available;
- the CLI application and server application are distinct top-level components or separately identified compositions;
- test/build-only dependencies are not misrepresented as shipped runtime components;
- shaded/relocated components remain discoverable;
- license identifiers/evidence are included when supplied by dependencies;
- SBOM generation is deterministic for fixed release inputs;
- SBOM digest is recorded in the distribution/release manifest.

Verify `LICENSE.txt`, `NOTICE.txt` and any dependency notices required by the shipped graph. A missing required notice, unknown disallowed license or mismatch between packaged JAR dependencies and SBOM is release-blocking under one documented policy. Do not invent license conclusions when metadata is absent; report a bounded review-required result.

## 7. Independent package verifier

Add a verifier entry point that is separate from `package-engine.ps1` and operates on either a ZIP path or an extracted distribution root. It must not trust filenames supplied only by the archive.

Before executing the CLI, the verifier:

1. validates archive safety and bounded extraction;
2. parses the strict distribution manifest with duplicate-key/trailing-data rejection;
3. verifies every SHA-256 entry and proves there are no unchecked unexpected files;
4. verifies build identity, candidate capability and source revision consistency;
5. validates the CycloneDX document and legal-file presence;
6. opens the shaded JAR and checks its version/main-class and required service metadata;
7. loads every bundled Pack/profile/suite/schema through the applicable production or certification parser;
8. verifies fallback bindings and CLI/server profile fingerprint parity;
9. rejects evidence, pricing, secrets and other forbidden content patterns;
10. emits a content-free structured result with stable failure codes.

The verifier must fail closed for tampering, truncation, duplicate archive entries, zip slip, symlinks, case collisions, checksum omission, manifest drift, unexpected executable content, invalid JSON/schema or fingerprint mismatch. Tests mutate each protected class independently and prove rejection.

Verification must not make provider/network calls, write outside a fresh bounded workspace or execute untrusted scripts from the archive.

## 8. Clean-room offline certification

`./dev.ps1 game-certify-offline` becomes an archive-level release gate:

1. receive or build one candidate archive;
2. verify its outer digest;
3. extract into a new temporary directory with the independent verifier;
4. run the Pack offline suite using only extracted paths;
5. run the dynamic offline suite, including real second-JVM provider-disabled resume, using only extracted paths;
6. finalize redacted evidence outside the immutable extracted candidate;
7. verify evidence schemas/checksums and bind evidence to the archive, JAR, profile and suite digests;
8. delete successful temporary stores and retain bounded failure diagnostics.

The gate must prove credentials are unnecessary and must explicitly clear or override provider environment variables. It must fail if certification resolves resources from the checkout, Maven target directories outside the extraction, user home, network or an ambient server.

Offline evidence is not added back into the candidate ZIP. It is a sibling release artifact, because changing the candidate after certification would invalidate its digest.

## 9. Packaged server and PostgreSQL release gate

Add a credential-free release integration suite for the packaged server artifact/container using PostgreSQL 16 and a deterministic provider fixture. It must exercise production HTTP and persistence boundaries, not instantiate only controller objects:

1. start PostgreSQL from a clean database and apply all Flyway migrations;
2. start the packaged server with the canonical allowlisted profile and deterministic provider;
3. authenticate through an approved test-only boundary and discover the profile;
4. submit one confirmed dynamic start, poll it and apply accepted commands;
5. record only run identity, source kind, revisions and fingerprints;
6. stop the server process/container;
7. restart the same packaged server bytes with new starts/profile/provider disabled;
8. read, command and finish the exact stored dynamic run without a provider call;
9. verify an existing Pack route and historical Pack row remain compatible;
10. verify database constraints and migration history are unchanged after restart.

Use bounded startup/process timeouts and always collect sanitized logs. Generated prose, suggestions, snapshots, database dumps and credentials must not appear in public release evidence. H2 does not satisfy this release gate.

The server gate records the server JAR/image digest, database image digest, migration version, profile fingerprint, run fingerprint, restart count and stable results in versioned checksummed evidence.

## 10. CI candidate flow

Refactor `.github/workflows/engine-release-certification.yml` or its successor around one candidate:

```text
source validation
  -> canonical build job
  -> archive + server artifact/image + manifests
  -> Windows/Linux verifier jobs download the same artifacts
  -> offline CLI certification
  -> packaged server/PostgreSQL certification
  -> optional protected live dynamic certification
  -> promotion manifest
```

Requirements:

- pin third-party actions to reviewed immutable commit SHAs under repository policy;
- use least-privilege job permissions and protected environments for paid/live or publishing steps;
- upload artifacts by digest and verify after every download;
- prevent a successful job from substituting a rebuilt artifact;
- use bounded retention and distinguish public offline evidence from restricted live evidence;
- make tag/release promotion depend on every required credential-free gate;
- preserve useful sanitized diagnostics when a gate fails;
- cancel no already-running paid provider request merely because another workflow starts.

Windows and Linux jobs verify launcher/path/encoding behavior against the same logical candidate. The canonical promoted archive is produced only once.

## 11. Optional live dynamic certification

Fix the protected live workflow to call the dynamic contract from 27.27.3:

```text
certify --mode live --dynamic --scope full
  --profile-dir <extracted-candidate>/profiles/generic-adventure
  --suite <extracted-candidate>/certification/dynamic-live-v1/suite.json
  ... explicit pricing/call/cost/confirmation arguments ...
```

It must download the already offline-approved candidate, verify its digest and certify those exact bytes. It must not rebuild, invoke the Willow Marsh Pack live suite, accept an unpinned model or infer cost confirmation from workflow dispatch alone.

The protected job retains all 27.27.3 preflight, secret, debug-logging, call, cost, timeout, redaction and expiry rules. The operator pricing document and raw restricted evidence are never copied into the public distribution.

A failed, missing, canary or expired live certificate does not invalidate offline readiness; it only prevents the stronger `live-certified` claim. A new candidate digest always requires a new full live certificate.

## 12. Release manifest and status vocabulary

After required gates, generate a canonical `release-manifest.json` as a sibling artifact. It binds:

- schema version, product version, commit/tag and candidate ID;
- CLI ZIP/JAR, server JAR/image, SBOM, distribution manifest and profile digests;
- Pack and certification-suite digests;
- offline Pack, offline dynamic and server/PostgreSQL evidence digests/results;
- supported OS/JDK/database matrix actually tested;
- optional live certificate ID, digest, provider/model tuple and expiry;
- creation time, repository/workflow identity and release status.

Use only these claims:

- `development`: dirty, snapshot or incomplete local candidate;
- `verified`: package structure/checksums/SBOM passed, but required certification is incomplete;
- `offline-ready`: all credential-free CLI and server release gates passed for the exact candidate;
- `live-certified`: `offline-ready` plus an unexpired full dynamic live certificate for the exact bound tuple;
- `revoked`: a previously promoted candidate was withdrawn with a content-free reason code and timestamp.

Do not describe checksum integrity as cryptographic publisher identity. If the release platform provides managed provenance/attestation signing, bind it to the finalized artifact digests through that platform; otherwise publish checksums and workflow provenance without claiming a signature.

## 13. Promotion, rollback and retention

Promotion copies or references already verified immutable artifacts. It never reruns packaging, edits an archive, injects evidence into it or retags different bytes under the same version.

Before promotion:

- verify version/tag/commit consistency and clean source identity;
- verify every referenced digest and evidence result;
- ensure required evidence is complete and not expired where a live claim is requested;
- perform a final secret/generated-content scan;
- require an explicit operator action for public publication.

Retain the release manifest, checksums, SBOM and public credential-free evidence for the release lifetime. Keep paid live evidence restricted and follow its documented retention. Preserve the immediately previous approved artifacts and database compatibility notes for rollback.

Rollback disables new dynamic starts/provider access first when safety or provider behavior is implicated, then deploys the prior exact server/CLI candidate. Persisted dynamic snapshots remain readable under the compatibility promises already established; never delete or rewrite user runs as a release rollback shortcut.

## 14. Tests and failure injection

Add deterministic automated coverage for at least:

- authoritative version propagation and invalid/tag/snapshot/dirty promotion rejection;
- deterministic logical package contents across repeated builds;
- manifest/checksum completeness and stable ordering;
- ZIP traversal, duplicate entry, case collision, symlink, oversized expansion and unexpected-file rejection;
- corrupted JAR, Pack, profile, suite, schema, SBOM and legal metadata rejection;
- CLI/server profile fingerprint equality and mismatch failure;
- no checkout-resource leakage during extracted offline certification;
- Pack plus dynamic offline certification from a fresh extracted archive;
- real second-process dynamic resume from the extracted CLI;
- packaged server/PostgreSQL start, restart, provider-disabled resume and Pack compatibility;
- same artifact digest across build, verifier, server gate and optional live job handoffs;
- live workflow command selects `--dynamic` and the dynamic-live suite;
- release status derivation for development, verified, offline-ready, live-certified, expired and revoked cases;
- exhaustive redaction/forbidden-content scans of artifacts, logs and evidence;
- failure-safe cleanup and bounded diagnostic retention.

No required automated test uses the network or a real provider credential. Test doubles fail if an unexpected provider call occurs.

- exact development package, verify, offline-certify and promotion commands;
- the one-build/same-digest rule;
- canonical archive/server contents and supported runtime versions;
- profile enablement and CLI/server fingerprint parity;
- how to inspect checksums, SBOM, manifest and offline evidence;
- optional live dynamic command, protected inputs, costs, expiry and limitations;
- status vocabulary and what each claim does not prove;
- server/PostgreSQL backup, restart, disable-new-starts and rollback procedures;
- privacy statement for setup suggestions, generated content and evidence;
- the unchanged trust boundary: AI configures only the engine's bounded mechanics vocabulary and supplies no executable code.

Do not mark the dynamic web product as end-user complete before Spec 28 supplies and verifies the client UI. This spec closes engine/server packaging and release readiness only.

## 17. Required verification

Follow `.github/instructions/build-workflow.instructions.md`. During implementation, run focused packaging, verifier, manifest, workflow-contract, CLI certification and server/PostgreSQL tests first.

Then run from the repository root:

```powershell
mvn -f app/engine/pom.xml clean verify

./dev.ps1 game-package
./dev.ps1 game-certify-offline -SkipBuild
```

Also run the packaged PostgreSQL 16 restart/certification action introduced by this specification and the independent verifier against a fresh extraction of the produced archive. Run the credential-free workflow path on both supported Windows and Linux environments, using the same downloaded candidate bytes.

For application/container changes, build the production Docker image and manually verify:

- the server starts with the canonical allowlisted profile;
- authenticated profile discovery returns the expected identity/fingerprint;
- a deterministic dynamic run can be started and persisted;
- restart with new starts/provider disabled resumes that exact run;
- Pack play remains available according to configured resources.

The paid command remains optional and requires a separate explicit operator authorization with reviewed pricing, positive limits, protected credentials and an approved environment:

```powershell
./dev.ps1 game-certify-live -- --dynamic --scope full <reviewed arguments>
```

Do not run it merely to implement this specification. Guidance-only preparation of this document requires only link/index/format and working-tree validation.

## 18. Acceptance criteria

27.27.5 is complete when all of the following are true:

1. One authoritative version/revision contract drives Maven, package scripts, launchers, Docker metadata, manifests and workflow paths.
2. A promotable candidate is clean, non-snapshot, immutable and built once; every later gate proves it consumed the same artifact digests.
3. The CLI archive has a strict allowlisted inventory, canonical dynamic resources, complete checksums, production-loader validation and bounded safe extraction.
4. The packaged server contains or mounts the canonical allowlisted profile under an immutable validated contract, and its fingerprint equals the CLI profile fingerprint.
5. CLI and server CycloneDX SBOMs are machine-derived from shipped runtime graphs and pass schema, composition and legal-policy checks.
6. An independent verifier detects tampering, omission, unexpected files, unsafe archive entries, invalid resources, SBOM drift and forbidden content without network/provider access.
7. Pack and dynamic offline certification execute only from a fresh extraction of the finalized archive and include the real second-JVM resume proof.
8. The packaged Spring/PostgreSQL gate proves HTTP dynamic start, durable restart/resume with new starts/provider disabled, and Pack compatibility.
9. Windows and Linux verify the same logical candidate; only one canonical job produces promotable release bytes.
10. Optional live CI invokes the dynamic live suite from the already offline-approved candidate and preserves every 27.27.3 cost/privacy/expiry boundary.
11. The release manifest binds exact artifact, resource and evidence digests and derives only the documented development/verified/offline-ready/live-certified/revoked claims.
12. Promotion never rebuilds or mutates artifacts, and rollback preserves existing dynamic snapshots and historical Pack compatibility.
13. Artifacts, logs and public evidence contain no credentials, private setup text, prompts, provider bodies, generated prose, raw snapshots, database dumps or local absolute paths.
14. Full engine/backend gates, independent archive verification, offline CLI certification, packaged PostgreSQL restart certification and production-image manual acceptance pass.
15. Documentation accurately limits closure to the dynamic engine/server release; end-user web UI completion remains Spec 28.

## 19. Completion

After implementation and all required credential-free verification pass, update this specification and the index to `Implemented` and commit directly to `main` with:

```text
spec 27.27.5 is implemented - close dynamic packaging and release
```

Do not commit generated archives, paid live evidence, pricing documents, credentials, database contents, temporary stores or unrelated changes unless an existing repository policy explicitly versions that artifact class.

Spec 27.27.5 closes the dynamic-game engine/server release sequence. Spec 28 may then provide the web client experience over the already released source-neutral APIs without weakening the profile, confirmation, privacy, deterministic-engine, persistence, certification or artifact-integrity boundaries established here.
