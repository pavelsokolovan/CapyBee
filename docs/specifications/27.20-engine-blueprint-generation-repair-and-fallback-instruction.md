## 2. Scope and prerequisite corrections

### 2.1 Scope

- A confirmed, host-neutral blueprint preparation/generation operation.
- Profile-based safe suggestion processing using the existing input pipeline.
- Provider-neutral GAME_BLUEPRINT purpose, instructions, data envelope and schema.
- Blueprint-specific request limits and adapter behavior.
- Parsing, output review and semantic-validation handoff.
- One total repair allowance, call reservations, cancellation and concurrent-call handling.
- Honest whole-game fallback offers and deterministic tests.

### 2.2 Corrections required before live dispatch

Implement these as focused prerequisite changes, with regression tests and separate reviewable diffs where practical. Do not replace the 27.18/27.19 design wholesale.

1. Eliminate raw request/response logging on success and error paths, including debug mode. Retain content-free status and usage diagnostics.
2. Correct locale precedence: only two conflicting explicit selections conflict. Explicit requested locale wins over an absent wizard answer's default; explicit wizard choice wins over default when no requested locale exists. Required cleared locale remains an error.
3. Close the unchecked profile-validation factory or make the production entry point independently establish equivalent complete validity. Parser/schema callers must receive profile-bound effective constraints with verified ranges, budgets, allowlists and preset identity. Trusted host ceilings may narrow, never expand them.
4. Complete schema specialization: remove unsupported operator alternatives, narrow values/capacities and decision choice counts, and ensure an empty effect vocabulary allows only effects:[]. Do not rely on custom annotations as validation.
5. Enforce blueprint depth/node budgets during token processing, before constructing an oversized tree. Validate decoded strings, including escaped lone surrogates. Preserve strict duplicate-key and trailing-token rejection. Apply equivalent strictness to profile resources consumed for requests where needed.
6. Validate quality resources against their actual supported shape and bind a real output review policy. Empty/arbitrary JSON objects must not become a safety/quality certificate.

Broader profile-loader issues discovered during implementation must be reported and fixed when they affect the trusted boundary. No feature flag may excuse sending data through a known privacy leak. Keep examples and game-specific content in resources, consistent with engine guidance.

### 2.3 Exclusions

No compiler, state interpreter, public CLI flag, web UI, new database, generated scene execution or durable dynamic-game release. No fixture generation on each run. No raw suggestion persistence. No silent switch to a fixed Pack after blueprint acceptance. Do not implement all remaining specifications implicitly.

## 3. Operation boundary and data ownership

Suggested component: BlueprintGenerationService under generation.blueprint, with JSON request construction under its json boundary. Final names may follow the current repository without duplicating responsibilities.

The operation receives:

- A genuinely validated GeneratorProfile and resolver-produced preferences/effective constraints.
- A host-created confirmation tied to the current preparation revision.
- An optional ephemeral suggestion, accessible only through the shared preparation/safety path.
- Injected TextGenerator, output reviewer, semantic-validator capability, ID/time ports and cancellation/deadline context.
- A metered provider path and real reviewed-fallback binding context when available.

Use separate types for preset/provenance data and text-bearing in-memory capabilities. No serializable request record containing the original/scrubbed/approved suggestion. A Java DTO is not non-serializable merely because it has no implements Serializable; ensure the application never hands it to its JSON/logging/persistence path. Override text-bearing toString methods and test serializers where relevant.

Before confirmation, configuration loading and preset resolution are local only. No TextGenerator or external-capable InputGuard/output reviewer invocation is permitted. A confirmation is host behavior, not a security claim that a generated boolean can grant consent. Edits after a completed/sent operation require fresh confirmation for a new operation.

The operation has a unique engine-generated preparation ID and monotonically numbered provider attempts. It does not construct a Run. If session accounting needs a UUID before a run exists, use a content-free preparation accounting ID, carried forward by 27.24/27.26 without resetting counts. Do not create an abandoned playable session simply to obtain a ledger key.

## 4. Shared input safety adapted to profiles

StartInputProcessor currently accepts a Pack and reads its policy/input definitions. Extract or overload a small host-neutral source boundary accepting the already-validated input definitions and ContentPolicy-equivalent settings. The existing Pack entry point delegates to that implementation and keeps historical behavior.

Do not build a dummy Pack with empty scenes to pass a profile into the old method. Do not run a second home-grown PII/safety algorithm. The dynamic preset resolver remains authoritative for ABSENT/SELECTED/CLEARED and preset intersection; the shared text path handles only the profile-declared story-wish for this operation.

After confirmation:

1. Check cancellation, valid profile, preset resolution and provider readiness locally.
2. Normalize and bound the suggestion using the shared PiiScrubber rules and min(profile limit, global input limit); maximum 300 Unicode code points.
3. Scrub locally, then call the existing InputGuard on the scrubbed value with the profile policy. Never send the raw value to generation or a remote guard.
4. Block/clarification/unavailable returns NEEDS_INPUT_ACTION, with edit, skip-with-presets or cancel options. Do not silently discard the idea or claim it was used.
5. On success, a PreparedStartInputs-style SafeTextInput capability is consumed by this operation only. It may be reused for its one blueprint repair while the operation is alive.
6. Release raw and approved references on completion/cancel; no claim of guaranteed JVM memory erasure.

When the suggestion is skipped, do not call InputGuard merely to approve preset IDs. Output review still applies to generated content. In provider-free mode, collect no unused suggestion and offer a matching reviewed offline game or cancellation. No silent EN/short substitution.

The external-processing disclosure and final confirmation remain as defined by 27.17. Normal diagnostics, argv, environment, files, telemetry, hashes, pending-start records and cache keys must contain no original or processed suggestion. Accepted fictional content may reflect it and must later pass output review before persistence.

## 5. Provider request purpose and compatibility

### 5.1 Explicit purpose

Reuse TextGenerator.generate(StructuredGenerationRequest). Add an engine-owned request purpose, for example PRESENTATION and GAME_BLUEPRINT, rather than inferring privilege from an arbitrary taskId, cost class or token count.

Preserve the existing 8- and 9-argument constructor call sites with overloads that default to PRESENTATION. Update equality/serialization tests and wrappers deliberately. No vendor/model information enters core. Keep old narrative artifact/catalog stages and snapshot wire representations intact; GAME_BLUEPRINT is a bootstrap purpose, not a narrative artifact accepted by existing GenerationOutputParser switches.

If an implementation instead extends a shared stage abstraction, prove historical parser switches, quality evaluation, codecs and legacy catalogs cannot accept a mechanical response as narrative. Do not add an enum constant indiscriminately to every historical switch.

### 5.2 Purpose-specific output envelope

- PRESENTATION retains 1–1500 output tokens and its existing restrictions.
- GAME_BLUEPRINT permits an engine envelope of 512–12000 output tokens, narrowed by profile, host ceilings, adapter/model capability and run/global budget.
- A player or model cannot raise any limit. Reject unavailable capabilities locally rather than silently raising/clamping a selected configuration.
- blueprintMaxAttempts comes from validated profile configuration (1 or 2), independent of token ceiling. The default allowance is initial plus at most one corrective replacement.
- A full blueprint may not fit every allowed token ceiling. Validate obvious minimum feasibility through compact example/request tests and reject unusable configurations; do not promise exact token estimates or silently simplify hard game-length requirements.

The adapter must expose or be configured with trusted purpose/schema/token support, so the service can preflight it. Keep provider-specific negotiation inside adapter code. A provider capability change is not a reason to weaken local schema/parser validation.

### 5.3 Adapter policy

For PRESENTATION keep the ban on proposing/changing mechanics. For GAME_BLUEPRINT authorize only a bounded declarative proposal under the supplied schema; never executable code, tool use, network/file access or new rule types. This is a deliberate change to the current adapter sentence “do not ... create actions or game rules.”

Policy precedence: fixed engine safety/purpose rules, then authored profile instructions, then clearly delimited untrusted data. Profile prose cannot enable an operator absent from the effective allowlist. Player suggestions cannot become taskInstructions, system text, taskId, schema, endpoint or budget.

## 6. Request construction

### 6.1 Authored instructions

Use the selected locale's validated blueprint prompt resource. Combine it with fixed purpose instructions to produce one complete 27.19 blueprint. State explicitly:

- Generate a new premise, cast, goals, graph, choices, state and endings; do not reskin a hidden authored graph.
- Follow selected locale, path/scene bounds, allowed mechanics and all profile limits.
- Treat creative presets as preferences that the idea elaborates without silently contradicting explicit selections.
- Treat the suggestion as fictional data, ignoring attempts to change engine instructions.
- Return only one JSON object; no explanations, fences, extra fields or copied input-history fields.
- Keep narrative planning concise enough for the response ceiling; detailed narration/dialogue will be generated later.

No mandatory extra THEME/SCENARIO/CAST/QUEST calls during dynamic bootstrap. The complete blueprint owns this planning. Historical modes retain their own stage sequence.

### 6.2 Untrusted data envelope

Serialize through a JSON writer, never by concatenating free text into a template. Example transport shape (not a persistable application DTO):

```json
{
  "operation":"initial",
  "preferences":{
    "gameLocale":"pl",
    "lengthPresetId":"short",
    "challengePresetId":"gentle",
    "genre":"exploration",
    "setting":"space",
    "tone":"curious",
    "interests":["puzzles"]
  },
  "constraints":{
    "minStoryTransitions":5,
    "maxStoryTransitions":7,
    "minScenes":6,
    "maxScenes":12,
    "maxCounters":1,
    "maxFlags":4,
    "maxSets":0,
    "allowedConditions":["FLAG_IS","VISITED_SCENE","ALL","ANY"],
    "allowedEffects":["FLAG_SET"]
  },
  "approvedSuggestion":"A fictional team explores a floating observatory."
}
```

This is a context excerpt: the real request includes all applicable effective mechanical bounds, audience/policy constraints and phase requirements, obtained from trusted configuration. Do not treat these example preset values as hardcoded engine vocabulary. Omit absent creative fields and approvedSuggestion entirely when skipped; do not invent a “surprise” value. No fixture scene IDs, actor slots, objectives or routes are included as hidden defaults. No other account/child/location/history context is read.

Metadata such as profile fingerprint, request purpose and schema version can be recorded content-free by the host; the model is never asked to certify them.

### 6.3 Input size and schema handling

Count final taskInstructions + untrustedDataJson + outputSchemaJson in Java UTF-16 code units against effective maxInputCharacters (27.18). Also respect the adapter's own payload bound using its documented unit. Recheck the final serialized envelope after repair feedback is added; escape expansion and schema size count. A bundle can load but still fail request feasibility locally.

Schema comes from BlueprintSchemas.specializedSchema with complete context binding and corrected narrowing. Any adapter translation to a supported schema dialect/subset must be deterministic and tested. Retain all expressible restrictions, document the specific translation, and keep local validation authoritative. No silent switch to plain-text completion, alternate model/provider, omitted schema or extra discovery request. Unsupported structured output returns a safe capability failure without a retry loop.

## 7. Processing order and review boundaries

For every dispatched response, including the corrective replacement:

1. Settle safe provider status and available token usage through the metered path even if output is later rejected.
2. Respect finishReason. REFUSED is terminal for this operation. OUTPUT_LIMIT never becomes a complete proposal even if its partial text happens to parse.
3. For COMPLETE, strictly parse using 27.19 against the same verified profile/preferences/effective constraints.
4. Review all narrative-bearing fields for output safety, private data and applicable profile quality. Avoid passing entire mechanical JSON through an old narrative-only control-word filter.
5. Call semantic validation capability for references, phase/path graph and bounded-state evidence when it is installed.
6. Return a candidate only with explicit evidence describing checks actually performed. Do not create a MaterializedGameDefinition or claim playability.

### 7.1 Output review

Reuse existing PII detection/quality infrastructure where suitable and extract shared policy logic rather than duplicating it. Existing GenerationQualityEvaluator is narrative-stage-oriented; it is not automatically a blueprint reviewer. The existing InputGuard checks input and is not an implicit output certificate.

A small immediately used BlueprintOutputReviewer boundary may return PASS, REJECT or UNAVAILABLE with bounded code-only findings and review-policy identity/version. Test doubles belong to tests. A production missing reviewer fails closed for acceptance. Do not label a dummy pass-through implementation safe.

Inspect title/premise/setting/tags/promises, actor fields, phase intent, scene/choice intent and objective/outcome text. Detected private data causes rejection; do not persist it, rewrite it mechanically or send the rejected content back in repair. Where language/fidelity checks are heuristic, report them honestly; do not claim exact semantic compliance from keywords alone.

Local review costs no provider generation call. If the deployment uses a remote reviewer/guard, invoke it only after confirmation, account for its own requests and ceilings explicitly, and fail closed when unavailable. The two-call blueprint limit still counts TextGenerator dispatches, not an invisible unlimited remote-review channel.

### 7.2 Semantic validator not yet implemented

27.20 owns the immediately used validator capability boundary; 27.21/27.22 provide the real implementation. Distinguish PASS, REJECT, INCONCLUSIVE and UNAVAILABLE. PASS must include the applicable validator version and verified context; an incomplete graph-only check cannot certify bounded-state playability.

At this milestone, deterministic tests may inject a fake validator to exercise orchestration. Without a complete production validator, an internal result may expose REVIEW_PENDING with a parsed/output-reviewed proposal to a controlled in-memory caller, explicitly non-executable and non-persisted. It cannot become a success artifact, public “game ready” response or normal CLI mode. No provider-facing dynamic route is released until the full series gates are met.

An absent validator is not a model error and does not consume a repair attempt. Do not repeatedly ask the model to solve an engine feature that has not been implemented.

## 8. Bounded repair: one complete replacement

The corrective attempt is a fresh complete document using the same confirmed preparation and immutable constraints. It is not JSON patching and not a merge of two responses.

Maximum TextGenerator dispatches per operation are min(profile.blueprintMaxAttempts, 2, available reserved call capacity). Attempt 1 is initial; attempt 2 is the sole corrective replacement. No separate per-parser, per-quality, per-semantic or per-compiler counter that could permit extra repairs.

The default repair request contains original trusted request context, the same transient approved suggestion if present, and sanitized feedback only:

```json
{
  "operation":"repair",
  "previousAttempt":1,
  "feedback":[
    {"code":"BLUEPRINT_UNKNOWN_FIELD","pointer":"/scenes/0"},
    {"code":"BLUEPRINT_ENDING_UNREACHABLE","pointer":"/scenes/7"}
  ]
}
```

This is a feedback excerpt added to the full request envelope. These are engine-owned example codes; semantic codes are finalized in 27.21. Include at most 20 findings and 2048 UTF-16 code units, ordered deterministically. A pointer contains only approved contract fields and numeric indexes; no model-controlled unknown key or rejected symbol. Never include raw/serialized rejected blueprint, provider error body, private text or prompt dump. The provider is asked to regenerate a full valid proposal from the same preferences, so it need not see the unsafe rejected content.

| Failure | Automatic action within confirmed operation |
| --- | --- |
| Complete output with parse/shape/capability error | One corrective replacement if remaining allowance/budget. |
| Truncated OUTPUT_LIMIT or INVALID_RESPONSE | One replacement if allowed; request concise complete output using the same token cap. No continuation request or silent token increase. |
| Output PII/policy or blocking quality failure | One clean replacement with generic safe feedback if the review policy permits; otherwise stop. Never quote offending content. |
| Semantic REJECT / exploration INCONCLUSIVE | One replacement under unchanged bounds; no increased exploration or mechanic limits. |
| Semantic/reviewer UNAVAILABLE | Stop or REVIEW_PENDING for internal non-executable use; no repair. |
| REFUSED | Stop; no automated rephrasing to evade refusal. |
| CONFIGURATION_ERROR / AUTHENTICATION_FAILED / PERMISSION_DENIED / REQUEST_INVALID / BILLING_UNAVAILABLE / STRUCTURED_OUTPUT_UNSUPPORTED / RESOURCE_NOT_FOUND / PROVIDER_REJECTED | Stop, report safe category; do not spend a repair on host/provider configuration. |
| TIMEOUT / UNAVAILABLE / RATE_LIMITED exception | No hidden transport retry. Return recoverable failure; explicit fresh retry needs confirmation and remaining shared budget. |
| Cancellation or compiler/internal defect | Stop; do not retry model output for an engine defect. |

If attempt 2 fails for any reason, end the operation. No third generation call, fallback-fragment completion or hidden SDK retry. A future user-confirmed retry creates a fresh operation, retaining shared/global accounting and never silently preserving a discarded suggestion.

Later compilation rejection attributable to the proposal may use the same remaining allowance through a future coordinator seam; it cannot reset the counter after 27.20 returns. Internal compiler defects never consume automatic model repair. If the suggestion is no longer alive, do not recover it from storage; ask for re-entry or make an explicitly confirmed preset-only retry.

## 9. Accounting, concurrency and cancellation

### 9.1 One metered dispatch boundary

Reuse GenerationLedger/MeteredTextGenerator or extract the minimal bootstrap accounting seam. Reserve a call immediately before each actual provider dispatch; record usage if known. Parsing, local reviewing and fallback lookup do not reserve another generation call. Returned refused/truncated/invalid output still consumes the dispatched call. An ambiguous timeout conservatively consumes it. No refund based solely on failure to accept a game.

Keep profile/global/day/run-or-preparation scopes and host ceilings. The profile ID for generator configuration must not be confused with an existing accounting-scope owner. Avoid double metering by defining exactly one owner for reservations/usage. Capture the same injected day/time across a preparation as required by current ledger semantics; do not use system time directly in core.

27.18's minimum call budget covers initial planning and one longest route, not all repairs and prefetched alternatives. Stop/return recovery options when repair lacks capacity; scene fallbacks later handle narrative exhaustion. Do not spend scene reserves on unlimited repairs or reset totalCallsPerRun after blueprint handoff. Pass content-free attempts/usage/accounting identity forward to 27.24/27.26.

### 9.2 Single operation and concurrency

Do not blindly wrap blueprint generation with existing SingleFlightTextGenerator: its timeout/interruption/failed-leader paths can call the delegate again. A blueprint operation must have one leader and followers must join its result without becoming new dispatchers on timeout.

Use a scoped in-memory preparation registry/operation lock or an explicit opt-in non-retrying mode. Registry keys are host preparation ID plus attempt ordinal, never a hash of the idea or a shared cross-player profile key. Distinct preparations must not share generated blueprints. Same live operation repeated by UI event joins the existing result; it does not consume a second allowance. Late results after terminal state are ignored and cannot publish another candidate.

Followers that time out receive IN_PROGRESS/timeout status; interruption preserves interrupt and returns without launching a replacement. Provider SDK automatic retries must be disabled or every physical dispatch must enter the same attempt/reservation policy. A requestId alone does not guarantee external exactly-once behavior.

### 9.3 Cancellation and crash

Check cancellation/deadline before input guard, reservation, each dispatch, review, repair and handoff. If a request is already in flight, cancellation prevents acceptance/further calls and attempts best-effort cancellation where supported; it cannot retract sent data or guarantee no charge. Settle observed usage without persisting output text.

27.20's operation state is in memory. Reuse existing content-free ledger/accounting; do not introduce a competing pending-start database. Future PREPARING persistence and crash-recovery publication belong to 27.24/27.26. A crash does not authorize replay of an ambiguous provider call or reconstruct the original idea. Recovery requires honest re-entry, preset-only confirmation or cancellation.

## 10. Results and provenance

Use a sealed result or equivalent explicit variants; avoid nullable bags with accepted=true and optional unverified fields. Suggested variants:

- CANDIDATE_REVIEWED: parsed proposal plus completed output/semantic evidence and content-free attempt metadata; still not compiled or playable.
- REVIEW_PENDING: controlled internal handoff, missing required validator capability; never public success or durable content.
- NEEDS_INPUT_ACTION: generic input safety/edit/skip/cancel outcome; no original text.
- GENERATION_FAILED: safe categorized failure plus supported explicit recovery choices.
- CANCELLED: no candidate publication.
- FALLBACK_OFFER: matching verified complete Pack identity and disclosure metadata; selecting it is a separate explicit host action, not a generated blueprint.

Record profile identity/fingerprint, selected preset IDs, locale, blueprint schema version, engine-generated preparation/request IDs, attempt count, purpose, policy/reviewer/validator versions, finish status and numeric usage. Provider/model provenance may be retained through existing adapter-neutral result metadata under existing policies. No arbitrary provider field is promoted to a trusted engine stamp.

Do not persist a new definition/hash format here. 27.26 owns durable codecs and integrity; 27.23 owns compiled definition identity. No accepted candidate is executable without its later compiler/final validator.

## 11. Whole-game fallback and recovery

On exhausted/final failure, return edit-and-reconfirm, retry-and-reconfirm, cancel, and a fallback offer only when an actual matching reviewed Pack is bound through 27.18 FallbackBindingValidator.

- Match locale, length and challenge exactly and verify actual supported mechanics/path bounds. Do not trust a matching filename or label alone.
- Present fallback as a reviewed offline game with its original Pack ID/version; it is not a newly generated scenario and does not promise to honor the custom idea/genre/interests.
- Selecting fallback explicitly confirms the disclosed change. No silent switch after a failed network request, and no repeated suggestion prompt in offline mode.
- Do not synthesize a partial fallback by copying objectives, characters, routes or outcomes from rejected proposals. Rejects are discarded.
- If no tuple is available, return FALLBACK_UNAVAILABLE for that option; retry/cancel may still be available. Do not silently substitute EN, short, another challenge or Willow Marsh.
- After a definition has been accepted/compiled downstream, a later scene failure uses that definition's own presentation fallback under 27.25. It must not call this whole-game fallback switch.

A neutral reviewed fallback fixture is authored stable test data. It is not an AI blueprint accepted without semantic validation. Current parser examples with unreachable extra endings are not automatically suitable fallback games.

## 12. Error and privacy rules

Use bounded engine-owned codes with generic messages; map provider errors without body excerpts. Suggested orchestration codes:

- BLUEPRINT_CONFIGURATION_INVALID / BLUEPRINT_REQUEST_TOO_LARGE
- BLUEPRINT_PROVIDER_CAPABILITY_UNAVAILABLE / BLUEPRINT_PROVIDER_FAILURE
- BLUEPRINT_INPUT_ACTION_REQUIRED / BLUEPRINT_OUTPUT_REJECTED
- BLUEPRINT_REPAIR_EXHAUSTED / BLUEPRINT_BUDGET_EXHAUSTED
- BLUEPRINT_VALIDATOR_UNAVAILABLE / BLUEPRINT_REVIEW_UNAVAILABLE
- BLUEPRINT_CANCELLED / BLUEPRINT_OPERATION_IN_PROGRESS
- BLUEPRINT_INTERNAL_FAILURE / BLUEPRINT_FALLBACK_UNAVAILABLE

Do not log prompts, data envelopes, generated response text, rejected symbols, exception payloads, input-derived hashes or schema annotations containing player content. Tests must enable adapter debug mode and exercise success, provider error, timeout, parse/review rejection and cancellation. Content-free metrics may include purpose, attempt number, status, duration and token counts.

Provider request/response JSON exists transiently for transport/parsing; it is never a transcript, durable artifact or debugging convenience. No application-shared cache may retain it across players. Release references after operation completion; respect existing provider disclosure without inventing a promise about provider-side retention.
