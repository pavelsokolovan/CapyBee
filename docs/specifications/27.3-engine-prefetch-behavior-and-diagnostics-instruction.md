# Spec 27.3 — Scene Prefetch Behavior and Diagnostics

**Type:** Implementation specification
**Parent:** Spec 27 — Engine API Contract (§8.7 diagnostics, §10.1 scene prefetch, §14.1 `--debug`, §15 tests 21–27)
**Depends on:** Spec 27.1 and Spec 27.2 (both implemented on `main`)
**Baseline:** repo `main` at commit `f623f50` ("engine - spec 27.2 implemented"). All findings below were read from that commit's source. The build and tests were **not** run while writing this spec; step 0 of the sequence does that.
**Status:** Ready for implementation. All open questions from the earlier draft are resolved (§3).
**Primary outcome:** Prefetch behaves as Spec 27 §10.1 promises and can be measured. A scene is generated once and reused. A prefetch never delays or blocks an unrelated player turn, never takes a player's generation slot, and never spends the calls held back for the player. Every provider call is counted. A lost prefetch is rebuilt on the next read. `--debug` and `diagnostics()` report, per turn, whether the scene was prefetched, joined or generated on demand, with latency and remaining budget.

This is the last spec of the 27 series. It changes no story content, no authored-pack behavior and no HTTP API.

## 2. Goals and non-goals

**Goals**
1. All prefetch knobs live in `SessionLimits`; hosts and the console no longer hard-code reserves or fan-out.
2. Prefetch never occupies a player slot, never delays an unrelated turn.
3. One provider call per scene when a turn needs a scene whose prefetch is in flight (single-flight).
4. Every reserved provider call is counted; per-run prefetch calls are known.
5. Each completed command records `latencyMillis` and `sceneSource`.
6. `diagnostics()` and `--debug` report the §6 shape, without resuming the snapshot.
7. §15 items 21–27 are proven by deterministic tests (call-counting fake provider, controllable clock, no sleeping).

**Non-goals**
- The prefetch candidate rule (depth 1: options, `next`, branches). It is correct.
- Cross-machine single-flight. The in-flight registry is per process (Spec 27 §10.1). Residual duplicate risk is listed in §11.
- Console flags for reserves or fan-out (defaults only; see §5.1).
- HTTP exposure of diagnostics (stays in-process).
- Anything in `FileRunRepository` / `ConsoleApp` structure noted above.

## 3. Decisions (all resolved)

| ID | Decision |
|---|---|
| D1 | `SessionLimits` gains `prefetchMaxFanout` (1..3, default 3), `prefetchMaxConcurrent` (≥1, default 1), `prefetchProfileReserve` (8), `prefetchGlobalReserve` (100), `prefetchRunReserve` (4). Defaults equal today's literals, so default behavior does not change. |
| D2 | Prefetch gets its own semaphore (`prefetchMaxConcurrent`). It never takes a `generationSlots` permit. Maximum concurrent provider calls therefore becomes `maxConcurrentGeneration + prefetchMaxConcurrent` (default 2 + 1 = 3); state this in the console doc. |
| D3 | **Single-flight at the text-generator level**, keyed by a new request field `slotKey`. The single-flight wrapper sits **outside** the metering wrapper, so a call that joins an in-flight one is neither reserved nor counted again. |
| D4 | The prefetch counters are driven by **reservation**, not usage. `tryReserveCall` (granted, priority `PREFETCH`) increments the day `prefetchCalls` and a new per-run `runPrefetchCalls`. `recordUsage` only adds tokens. |
| D5 | `awaitInFlightPrefetch` is **deleted**. A turn that needs an in-flight scene joins it through D3; a turn that does not, never waits (fixes F6 and F7). |
| D6 | `sceneSource` is derived after `apply` by one pure function (§6.3). `latencyMillis` is measured with the injected `SessionClock` (so tests control it). |
| D7 | `wastedCalls = max(0, prefetchCalls − hits)`. It is an upper bound (a repaired scene spends two calls for one scene). Documented as such; no extra counters. |
| D8 | `latencyMillis` includes time spent joining an in-flight scene. That is what the player feels. |
| D9 | `generationCalls` in diagnostics comes from the store (`StoredRun.generationCalls`, i.e. the run reservation count), not from resuming the snapshot. Per-stage detail (`stages`) is kept **in memory** from the last command and is empty after a restart until the next command. |
| D10 | Reserve semantics stay clamped, not validated: effective prefetch ceiling is `max(0, cap − reserve)` (existing store behavior). `--calls-per-day 5` with a global reserve of 100 therefore means prefetch never runs. `SessionLimits` must **not** reject reserves larger than caps. The debug `budget` fields and the console doc make this visible. |
| D11 | Format moves to `version = 2` with a read-time migration from 1 (§7). |
| D12 | Join marking uses a per-thread flag (`SingleFlightRegistry.consumeJoined()`), because `Run.apply` executes synchronously on the worker thread. |

## 5. Session changes

### 5.1 `SessionLimits`

```java
public record SessionLimits(Duration leaseDuration, Duration startTtl, int runCalls,
    int globalCallsPerDay, int maxConcurrentGeneration, int profileCallsPerDay, boolean prefetchEnabled,
    int prefetchMaxFanout, int prefetchMaxConcurrent,
    int prefetchProfileReserve, int prefetchGlobalReserve, int prefetchRunReserve) {}
```

Validation (adds to the existing checks): `1 ≤ prefetchMaxFanout ≤ 3`, `prefetchMaxConcurrent ≥ 1`, each reserve `≥ 0`. **No** comparison with caps (D10). Keep the existing 5-argument and 7-argument constructors, filling defaults; update `defaults()`.

Config names for the future web host (documentation only here): `capybee.game.prefetch.max-fanout`, `max-concurrent`, `profile-reserve`, `global-reserve`, `run-reserve`.

### 5.2 `SessionGenerators` and `SingleFlightTextGenerator` (new, package `engine.session`)

`SessionGenerators` builds the generator chain for one engine instance so hosts stop assembling metering by hand:

```java
public final class SessionGenerators {
    public SessionGenerators(TextGenerator provider, SessionPorts.GenerationLedger ledger, SessionLimits limits);
    public TextGenerator forRun(SessionTypes.LedgerScope profile, LocalDate day,
                                UUID runId, MeteredTextGenerator.Priority priority);
    public SingleFlightRegistry registry();
}
```

`forRun` returns `SingleFlightTextGenerator(MeteredTextGenerator(provider …, reserves from limits), registry, runId)`. The global scope is `new LedgerScope("global", limits.globalCallsPerDay())`. `ConsoleApp`'s engine factory calls `forRun` instead of constructing `MeteredTextGenerator` with `8, 100, 4`; the `StructuredInputInterpreter` uses the same generator.

`SingleFlightTextGenerator.generate(request)`:
- `slotKey == null` ⇒ call the delegate directly.
- Else `key = runId + ":" + slotKey`. If `registry.inFlight.putIfAbsent(key, future)` returns `null`, this call is the **leader**: call the delegate, complete the future with the result or the exception, and `remove(key, future)` in `finally`.
- Otherwise this call is a **follower**: wait for the leader's future (hard safety cap 120 s) and return the **same** `TextGenerationResult` (immutable). Mark the thread as "joined" (D12). If the leader failed or the cap passes, the follower becomes a leader and makes its own call (one retry only, through the delegate, so it is reserved and counted normally).
- Repair attempts are separate calls (the first attempt's entry is already removed), so a repair is single-flighted on its own. The follower never receives a result that is older than its own request.

Accepted residual window: between the leader's `generate` returning and the prefetch row being inserted (parse and validation, milliseconds), a turn can still start its own call. Worst case: one extra **counted** call, never a wrong result. Documented in §11.

### 5.3 Prefetch job (`RunSessionService.ensurePrefetch`)

```
if !limits.prefetchEnabled: return
stored = requireRun; if not ACTIVE or no snapshot: return
run = engines.create(owner, runId, PREFETCH).resume(mergePrefetched(snapshot, prefetch.load(runId)))
candidates = run.prefetchCandidates() (already ordered) minus keys in prefetchJobs
for scene in candidates.limit(limits.prefetchMaxFanout):
    if !prefetchSlots.tryAcquire(): break                 // never queue; next trigger continues
    key = runId:scene; if putIfAbsent(key, future) != null: release slot; continue
    workers.execute:
        try:
            artifact = run.prefetch(scene).orElse(null)   // metered as PREFETCH; if refused (RATE_LIMITED) the engine falls back ⇒ FALLBACK ⇒ discarded
            if artifact != null and outcome != FALLBACK:
                if prefetch.insertIfAbsent(runId, scene, stored.revision(), artifact):
                    // F12 guard: if the scene was entered meanwhile, drop the row again
                    cur = runs.find(runId, owner); if cur present and visitedGeneratedScenes(cur.snapshot) contains scene:
                        prefetch.deleteForScenes(runId, [scene])
            future.complete(artifact)
        catch RuntimeException e: future.completeExceptionally(e)
        finally: prefetchJobs.remove(key, future); prefetchSlots.release()
```

Rules: no lease, no transaction, no revision change, no write to the run record while the provider is called; never throws into the caller (the existing `catch (RuntimeException ignored)` stays); triggers unchanged (start becomes ACTIVE, accepted command that leaves the run ACTIVE, every `get` of an ACTIVE run). Nothing about in-flight jobs is persisted (a lost job is rebuilt by the next trigger, Spec 27 §10.1).

### 5.4 Command processing (`processCommand`)

- Delete the `awaitInFlightPrefetch(…)` call and method (D5).
- Before `run.apply`: `rows = prefetch.load(runId)` (already loaded for the merge), `previousScene = stored.snapshot().state().sceneId()`, `registry.consumeJoined()` to reset the flag, `startedAt = clock.now()`.
- After `apply`: compute `sceneSource` (§6.3), `latencyMillis = clock.now() − startedAt` (taken at the same place as `commands.complete`).
- Call the extended `commands.complete(runId, commandId, accepted, revisionAfter, events, latencyMillis, sceneSource)`. The existing 5-argument method stays as a default method passing `null, null`.
- Keep `lastStages[runId] = summaryOf(run.generationSummary())` in an in-memory `ConcurrentHashMap` (cleared on delete).
- Everything else (lease, revision check, `generationSlots`, transactions) is unchanged.

## 6. Accounting, command log, diagnostics

### 6.1 Ledger port

```java
public interface GenerationLedger {
    // existing: tryReserveCall, recordUsage, releaseCall
    DayUsage dayUsage(LedgerScope scope, LocalDate day);     // reservedCalls, inputTokens, outputTokens, prefetchCalls

}
```

- `tryReserveCall`: on a **granted** reservation with `PREFETCH`, increment `usage[profileKey][2]`, `usage[globalKey][2]` and the per-run prefetch counter. `recordUsage` no longer touches index 2 (tokens only, both priorities).
- The per-run prefetch counter is a new map `runPrefetchCalls` (run id → int), removed on `delete(run)` like `runReservations`. Daily usage is **not** touched by delete.
- A failed or usage-less provider call keeps its reservation and its prefetch count (conservative, unchanged policy).
- Implement in `InMemorySessionStore` and `LocalSessionStore`; add both to the contract tests.

### 6.3 `sceneSource` (pure function, unit-tested)

```
entered = next.state.sceneId if next.state.sceneId != previousScene else none
if entered is none: NONE
artifact = scene artifact in next.generationArtifacts with ScenePayload.sceneId == entered
if artifact is null: NONE                                  // authored scene
if entered ∈ rowsBeforeApply.sceneId: PREFETCHED
else if artifact.outcome == FALLBACK: FALLBACK
else if artifact.outcome == REPAIRED: INLINE_REPAIRED
else if joined: JOINED_PREFETCH
else: INLINE_GENERATED
```

Counting: `hits = PREFETCHED + JOINED_PREFETCH`; `misses = INLINE_GENERATED + INLINE_REPAIRED + FALLBACK`; `NONE` and null are ignored.

## 7. Format v2 and migration (`LocalSessionStore`)

Changes to the file (`version` becomes `2`; `format` string unchanged):
- Each command entry gains nullable `latencyMillis` and `sceneSource`.
- `Document` gains `runPrefetchCalls` (map run id → int).
- Ledger semantics change for index 2 of `usage[key]` as in §6.1 (same array, now counted at reservation).

Migration rules:
- **Read:** accept `version` 1 and 2. A v1 document decodes with the new fields `null`/empty (additive, nullable record components) and is held as v2 in memory. Add a small package-private `StoreMigrations.toCurrent(Document)` called in `decode` right after the version gate; today it only normalizes nulls (empty `runPrefetchCalls`), but it is the single place for future migrations.
- **Write:** always `version = 2`. The file is rewritten on the next commit. Opening the store does not write. (`execute` with no changes also commits when the re-encoded bytes differ, so the first transaction upgrades the file; that is intended.)
- Pre-v2 data: command rows keep `null` latency/source; the per-run prefetch count starts at `0`; existing day `usage[…][2]` values are kept as they are (they counted prefetch calls that reported usage, a documented small undercount).
- Versions `> 2` ⇒ `STORE_VERSION_UNSUPPORTED` (`found`, `supported = 2`); `< 1` or non-integer ⇒ `STORE_CORRUPT`.
- Validator additions: command rows in state `DONE` may have null `latencyMillis`/`sceneSource`; `IN_PROGRESS`/`FAILED` rows must have both null; `latencyMillis ≥ 0`; `runPrefetchCalls` keys must be known run ids and values `≥ 0`.
- **Compatibility note (F14):** a build from before this spec cannot read a v2 store; because the JSON mapper is strict it reports `STORE_CORRUPT`, not `STORE_VERSION_UNSUPPORTED`. Say so in the docs, and tell developers to upgrade all consoles that share a `--store-dir` together.

## 11. Definition of done

- Every prefetch/budget number comes from `SessionLimits`; no literal `8, 100, 4` or `.limit(3)` remains.
- Prefetch never takes a `generationSlots` permit (P6) and no command waits for a prefetch it does not need (P10).
- A scene in flight is generated once (P3); `awaitInFlightPrefetch` no longer exists.
- Every reserved prefetch call is counted, with or without usage data (P13, U4).
- Every completed command has `latencyMillis` and `sceneSource`; `--debug` and `diagnostics()` match §6.4/§6.5 and do not resume the snapshot (P16).
- A v1 store opens and upgrades without data loss (M1); the format and its compatibility note are documented.
- Spec 27 §15 items 21–27 each map to a passing test (§12).
- No test sleeps for real or uses the network; `mvn -f app/engine/pom.xml verify` is green including the Jacoco 70% rule in `engine-session`.
- Existing golden files other than `session-generated-debug` are unchanged.
- `FileRunRepository` and its test are gone; their two cases are ported to `LocalSessionStoreTest` with the new lock-aware third case (§5.5a). No reference to `FileRunRepository` remains in `app/engine/` or in Spec 27 text (F18).
- `ConsoleApp.java` is under 250 lines; `SessionConsole`, `SessionWiring`, `ConsoleErrors`, `ConsoleTuning` and `Sleeper` exist; the split commit changed no test (§5.5b).
- Session timing is injected; the slow-command tests (27.2 C1) run without real sleeping (F17).

**Residual risks (accepted, documented):**
- A duplicate counted call in the millisecond window between a leader's provider return and the row insert (§5.2).
- The in-flight registry is per process: two machines can both generate the same scene (Spec 27 §10.1).
- `wastedCalls` is an upper bound (D7); pre-v2 stores undercount prefetch calls.
- Peak provider concurrency is now `maxConcurrentGeneration + prefetchMaxConcurrent` (D2).
