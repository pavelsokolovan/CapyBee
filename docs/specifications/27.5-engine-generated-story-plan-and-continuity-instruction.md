# Spec 27.5 — Generated Story Plan and Scene Continuity

**Type:** Implementation specification  
**Parent:** Spec 27.4 — Full Generated Game Contract  
**Depends on:** Specs 26, 26.1, and 27.4  
**Baseline:** repository commit `b00c545`, plus the approved design in Spec 27.4. The current `SCENARIO` payload, generation pipeline, output parser, fallback, artifact restore, and scene composition code were inspected while writing this specification. The build was not run.  
**Status:** Ready for implementation after Spec 27.4  
**Primary outcome:** Every declared full generated game starts with one validated narrative plan covering its five trusted phases. Every generated scene receives the relevant phase plan, trusted slot information, and bounded continuity facts from already visited scenes. The model may shape the story’s theme, dramatic purpose, and presentation, but it cannot create or alter routes, choices, mechanics, IDs, objectives, outcomes, or completion rules.

Spec 27.4 owns the trusted scene graph. This specification intentionally does **not** introduce an AI-generated graph. It introduces an AI-generated narrative plan for the already validated graph.

---

## 1. Problem

The current `SCENARIO` result contains:

- title;
- premise;
- setting;
- a short string list named `beats`.

The current pipeline passes prior startup artifacts to later stages, but lazy scene generation does not have a structured contract for:

- the purpose of the current story phase;
- what should change during that phase;
- which trusted actors or objectives matter there;
- promises that must be resolved near the ending;
- important facts established in scenes already shown to the player;
- the difference between a scene’s mechanical role and its narrative presentation.

As a result, scenes can be individually valid but feel unrelated. A cast member may change personality, a quest may disappear, a problem may be introduced and never resolved, or a later scene may repeat the opening.

The solution is a bounded, typed story plan created during the existing `SCENARIO` stage, plus small continuity facts produced with each scene. The plan guides narrative generation only. The authored pack remains the source of truth for gameplay.

## 2. Current implementation findings

| ID | Finding | Consequence |
|---|---|---|
| F1 | `ScenarioPayload(title, premise, setting, beats)` accepts 1–8 free-form beat strings. | It cannot prove coverage of the five full-game phases. |
| F2 | The SCENARIO request currently receives `sceneSlots`, but the values are slot IDs only. | The model does not receive trusted phase, role, actor-slot, objective, or ending information in a typed form. |
| F3 | `GenerationPipeline.contextJson` sends `stageArtifacts` to later calls. | CAST, QUEST, and SCENE can see the scenario artifact, but the context is not minimized per stage. |
| F4 | Previously generated scene artifacts live in `resolvedScenes`, not `stageArtifacts`. | A later lazy scene does not receive structured facts from earlier generated scenes. |
| F5 | `ScenePayload` contains display text and trusted choice labels only. | There is no bounded narrative-memory output for later scenes. |
| F6 | The trusted scene supplies routes, conditions, effects, input mode, end marker, and outcome. | Narrative planning can be added without giving control to the model. |
| F7 | Generated artifacts are stored in snapshots and restored without provider calls. | Story plan and continuity data should use the same artifact mechanism. |
| F8 | One repair attempt and validated fallback already exist. | Story-plan failures should use the same behavior, not a parallel retry system. |
| F9 | Input context is capped by `maxInputCharacters`. | Context selection must be deterministic and bounded before encoding. |
| F10 | Engine-assigned actor IDs are created after CAST output is accepted. | The plan must reference trusted actor **slot IDs**, not generated runtime actor IDs. |

## 3. Goals and non-goals

### 3.1 Goals

1. Replace the loose full-game `beats` list with one typed phase plan for each trusted phase.
2. Keep schema-v1 generated-content packs and their `ScenarioPayload` unchanged.
3. Bind plan references only to pack-declared phase IDs, scene roles, actor slots, objective IDs, tone tags, and outcome IDs.
4. Give every scene-generation request the minimum relevant plan and continuity context.
5. Persist the plan and continuity facts in versioned generation artifacts.
6. Make restore and resume reproduce the same context without new provider calls.
7. Use the existing repair, fallback, budget, safety, and diagnostic behavior.
8. Make all context-selection behavior deterministic and testable.
9. Prevent generated planning data from affecting legal commands or runtime state.

### 3.2 Non-goals

- Generating scene routes or selecting the player’s future path.
- Skipping, adding, deleting, or reordering trusted phases.
- Adding new actors, objectives, choices, effects, flags, counters, places, outcomes, or scene IDs.
- Applying quest or cast data to runtime views and state; Spec 27.6 owns that work.
- Choosing success, partial-success, or failure endings; Spec 27.7 owns result resolution.
- Adding player setup questions; Spec 27.8 owns them.
- Solving final prose-quality evaluation; Spec 27.11 owns broader quality rules.
- Sending a full transcript to the provider.
- Persisting raw player free text as continuity memory.

## 4. Decisions

| ID | Decision |
|---|---|
| D1 | The existing `SCENARIO` stage produces the story plan. No new provider stage or call is added. |
| D2 | Schema-v1/content-only packs continue to use `ScenarioPayload`. A Spec 27.4 `FULL_GAME` pack uses `StoryPlanPayload`. |
| D3 | Full-game artifacts use generation artifact schema version 2. Schema version 1 remains readable for existing packs and snapshots. |
| D4 | The story plan contains exactly one `PhasePlan` for each trusted phase ID from Spec 27.4, in trusted phase order. |
| D5 | The model describes narrative purpose and continuity, but cannot choose graph edges or declare a canonical player route. All reachable branches remain valid. |
| D6 | Each story scene slot gains trusted planning metadata: `phaseId`, `storyRole`, allowed actor slots, allowed objective IDs, and allowed tone tags. |
| D7 | A phase plan may reference only values allowed by the union of its scene slots. It cannot widen any slot’s permissions. |
| D8 | Every v2 scene payload includes 0–4 short `continuityFacts`. Facts are narrative memory only and cannot encode control instructions. |
| D9 | Scene generation receives the current phase plan, current trusted slot metadata, startup narrative artifacts, and continuity facts from visited predecessor scenes. It does not receive unvisited scene text. |
| D10 | Continuity facts are selected in stable visit order and capped by count and character budget. The newest facts win after required plan data is included. |
| D11 | Raw player free text, raw provider requests/responses, prompts, and rejected outputs never enter the plan or continuity context. |
| D12 | A scene reached by different routes has one cached artifact per trusted scene slot. Packs that need route-specific narration must use distinct trusted destination scene IDs. |
| D13 | Fallback plan and fallback scenes provide the same typed planning/continuity fields as generated output. |
| D14 | Planning artifacts never affect `RunState` counters, flags, sets, objectives, place, outcome, legal options, or routing. |
| D15 | Context construction is part of engine-core and provider-neutral. Provider adapters receive an ordinary `StructuredGenerationRequest`. |

## 5. Catalog additions

Spec 27.5 refines generation-catalog schema v2 introduced by Spec 27.4. These fields are required only when `runContract.kind = FULL_GAME`.

### 5.1 Template planning vocabulary

Extend `TemplateDefinition` with:

```java
public record TemplateDefinition(
    String id,
    Stage stage,
    List<String> actorSlots,
    List<String> objectiveIds,
    List<String> toneTags,
    List<String> storyRoles) {}
```

Compatibility constructor: the current five-argument constructor remains and uses `storyRoles = List.of()`.

Rules:

- `storyRoles` is used only by `SCENARIO` and `SCENE` templates.
- Values follow `[a-z][a-z0-9-]{0,63}`.
- Values are unique and ordered.
- 0–24 roles per template.
- A full-game `SCENE` template must declare at least one role.
- A full-game `SCENARIO` template must declare the union of roles usable by its phase plans.

Examples: `arrival`, `discovery`, `conversation`, `choice`, `setback`, `challenge`, `recovery`, `reveal`, `resolution`, `ending`.

Roles are neutral engine vocabulary supplied by the pack. They have no hard-coded mechanics.

### 5.2 Scene-slot planning metadata

Extend schema-v2 `SceneSlot` with:

```java
public record SceneSlot(
    String slotId,
    String sceneId,
    String templateId,
    String fallbackResource,
    List<String> choiceIds,
    String phaseId,
    String storyRole,
    List<String> actorSlots,
    List<String> objectiveIds,
    List<String> toneTags) {}
```

Keep the existing five-argument constructor for schema v1 and content-only tests. Its planning fields are `null` or empty and must not be used for `FULL_GAME`.

For a full game:

- `phaseId` equals the phase containing `sceneId` in `runContract`;
- `storyRole` is allowed by both the referenced SCENE template and the SCENARIO template;
- actor slots are a subset of the CAST template’s trusted `actorSlots`;
- objective IDs are a subset of the QUEST template’s trusted `objectiveIds` and pack rules;
- tone tags are a subset of the scene template’s and scenario template’s `toneTags`;
- lists contain no duplicates;
- 0–8 actor slots, 0–8 objective IDs, and 0–8 tone tags per slot;
- ending slots use a role allowed for endings and may reference only their trusted outcome indirectly through the phase plan; model output never supplies an outcome ID for the runtime.

### 5.3 Example

```json
{
  "slotId": "meet-guide-slot",
  "sceneId": "meet-guide",
  "templateId": "scene-basic",
  "fallbackResource": "generation/fallbacks/meet-guide.json",
  "choiceIds": ["ask-help", "continue-alone"],
  "phaseId": "journey",
  "storyRole": "conversation",
  "actorSlots": ["guide"],
  "objectiveIds": ["reach-lantern"],
  "toneTags": ["warm", "curious"]
}
```

## 6. Story-plan artifact

### 6.1 Artifact versioning

`GenerationArtifact.SUPPORTED_SCHEMA_VERSION` becomes `2`, but validation accepts versions 1 and 2.

- Existing schema-v1 pack runs continue to create and restore artifact version 1.
- A full-game catalog creates artifact version 2 for all stages in that run.
- A version-1 artifact is not accepted into a full-game schema-v2 run.
- A version-2 artifact is not accepted into a schema-v1/content-only run.
- Pack ID, pack version, locale, stage, and template checks remain mandatory.
- Snapshot format changes only as needed to encode the new artifact payloads; existing snapshot version compatibility must be preserved according to the current snapshot rules.

### 6.2 Payload type

Add `StoryPlanPayload` to the sealed `GenerationArtifact.Payload` hierarchy:

```java
public record StoryPlanPayload(
    String title,
    String premise,
    String setting,
    List<String> themes,
    List<String> storyPromises,
    List<PhasePlan> phases) implements Payload {}

public record PhasePlan(
    String phaseId,
    String goal,
    String development,
    String transition,
    List<String> actorSlots,
    List<String> objectiveIds,
    List<String> toneTags,
    List<String> storyRoles) {}
```

Meaning:

- `title`: display-ready run title.
- `premise`: one short statement of the main situation.
- `setting`: one bounded setting description.
- `themes`: pack-allowed tone/theme tags, not free-form tags.
- `storyPromises`: short narrative questions or facts that should be resolved by the ending.
- `goal`: narrative purpose of the phase.
- `development`: what should become different by the end of the phase.
- `transition`: narrative direction into the next phase; for `ENDING`, the final emotional note.
- actor/objective/tone/role lists: selections from trusted allow-lists for that phase.

`ScenarioPayload` remains unchanged for artifact version 1.

### 6.3 Closed output schema

The full-game SCENARIO JSON schema allows exactly:

```json
{
  "title": "The Lantern Road",
  "premise": "A courier must restore the valley lantern before the fog closes the road.",
  "setting": "A quiet valley of bridges and old observatories.",
  "themes": ["warm", "curious"],
  "storyPromises": [
    "The sealed letter reaches its trusted keeper.",
    "The broken lantern receives a clear resolution."
  ],
  "phases": [
    {
      "phaseId": "opening",
      "goal": "Introduce the courier, the letter, and the failing light.",
      "development": "The courier chooses to enter the fog.",
      "transition": "A guide becomes important on the road.",
      "actorSlots": ["hero"],
      "objectiveIds": ["reach-lantern"],
      "toneTags": ["curious"],
      "storyRoles": ["arrival", "choice"]
    }
  ]
}
```

No other fields are accepted. In particular, reject `sceneId`, `slotId`, `next`, `route`, `choiceId`, `condition`, `effect`, `counter`, `flag`, `placeId`, `outcomeId`, or arbitrary runtime state anywhere in the output.

### 6.4 Bounds

- title: 1–80 code points;
- premise: 1–500;
- setting: 1–300;
- themes: 0–8 unique trusted tags;
- story promises: 1–8 unique strings, each 1–180;
- phases: exactly five, matching trusted phase order and IDs;
- goal: 1–240;
- development: 1–240;
- transition: 1–200;
- phase actor slots: 0–12 unique trusted IDs;
- phase objective IDs: 0–12 unique trusted IDs;
- phase tone tags: 0–8 unique trusted tags;
- phase story roles: 1–12 unique trusted roles.

All human-readable fields pass the same normalization, markup rejection, PII scrubbing, forbidden-tag checks, and output-safety policy used by existing generated content.

### 6.5 Semantic validation

The parser validates:

1. exactly one phase plan for every contract phase;
2. exact trusted phase order;
3. all selected references belong to the union allowed by scene slots in that phase;
4. every slot’s `storyRole` is included in its phase plan;
5. every actor slot or objective required by a scene slot is included in its phase plan;
6. an ending phase includes at least one story promise and an ending-compatible role;
7. no duplicate or blank narrative values;
8. no control-like keys or unknown fields;
9. no identifiers disguised inside human-readable arrays where trusted IDs are required.

The plan does not need to name every scene. Scene-slot metadata supplies that trusted mapping.

## 7. Fallback story plan

### 7.1 Resource

The SCENARIO stage fallback for a full game uses the `StoryPlanPayload` schema. It must cover all five phases and pass the complete semantic validator during pack load.

No second fallback file is introduced. Existing `StageDefinition.fallbackResource` remains the source.

### 7.2 Requirements

The fallback plan must:

- be specific enough to guide every trusted scene role;
- use only trusted actor slots, objectives, tone tags, and roles;
- contain no player input or provider data;
- resolve all declared story promises in its ending direction;
- work with every structural route, not only one preferred branch;
- be safe for display-derived use in all supported locales.

Fallback is marked through the existing artifact outcome `FALLBACK`. Later scenes may still be generated using a fallback plan. A fallback plan does not force all scenes to fallback.

## 8. Scene continuity payload

### 8.1 Version-2 scene payload

Add a version-2 scene payload while retaining the current `ScenePayload` for artifact version 1:

```java
public record PlannedScenePayload(
    String sceneId,
    String title,
    String narration,
    List<Dialogue> dialogue,
    List<ChoiceLabel> choices,
    List<String> continuityFacts) implements Payload {}
```

The trusted composition behavior is unchanged: generated data replaces narrative text and choice labels only. `continuityFacts` are not displayed by `View`.

### 8.2 Fact rules

- 0–4 facts per scene;
- each fact 1–140 code points;
- total facts per scene at most 400 code points;
- no markup, PII, raw player text, control syntax, IDs presented as instructions, or secrets;
- facts describe only narrative information established in that scene;
- facts cannot assert that an objective completed, a flag changed, an item was gained, a place was reached, or an outcome occurred unless the trusted scene mechanics establish the same fact;
- duplicate facts after normalization are rejected;
- ending scenes may use zero facts because no later scene needs them.

Examples of valid facts:

- “The guide promised to wait beside the north lantern.”
- “The courier learned that the fog reacts to bell sounds.”

Examples of invalid facts:

- “Set courage to 5.”
- “The player selected ask-help.”
- “Objective reach-lantern is complete.” when the trusted rules did not complete it.

### 8.3 Mechanical consistency check

Add a small validator that receives trusted post-entry facts derived from the scene definition:

- objective IDs completed by unconditional trusted effects;
- trusted outcome for an ending;
- unconditional flag, set, counter, and place changes, represented as identifiers only.

The generated fact text is not parsed into mechanics. Instead, the request tells the model which mechanical facts may be mentioned, and output safety rejects reserved mechanical-control patterns. Spec 27.11 may add stronger semantic quality checks. Runtime correctness never depends on continuity fact text.

## 9. Request context contracts

### 9.1 Principle

Do not send `stageArtifacts.values()` blindly to every stage. Build a typed, stage-specific context document containing only required data.

The context document is trusted engine-produced JSON. Generated narrative inside it is data, never instructions. The existing system policy statement remains mandatory.

### 9.2 SCENARIO context

The full-game SCENARIO request receives:

- locale;
- scenario template ID;
- ordered phase IDs and kinds;
- for each phase: allowed roles, actor slots, objective IDs, tone tags, and declared ending outcome IDs where applicable;
- pack-provided sanitized start inputs allowed for scenario generation;
- optional THEME artifact payload;
- audience and forbidden content tags;
- the closed `StoryPlanPayload` output schema.

It does **not** receive scene routes, conditions, effects, internal rule expressions, provider credentials, or raw free-text start input that Spec 25 forbids from persistence/provider use.

The phase/slot capability summary is derived from trusted catalog metadata. The model does not need the full authored scene JSON.

### 9.3 CAST context

CAST receives:

- title, premise, setting, themes, story promises;
- phase actor-slot selections and short phase goals;
- trusted CAST actor-slot allow-list;
- existing audience and safety constraints.

It does not receive phase objective details unrelated to actor creation or any scene text.

### 9.4 QUEST context

QUEST receives:

- title, premise, story promises;
- phase objective selections and short phase goals;
- trusted objective allow-list and presentation labels where safe;
- existing audience and safety constraints.

It does not receive generated cast descriptions unless the quest template explicitly declares that actor presentation is needed. When needed, pass actor slot, engine-assigned actor ID, and display name only—not the full description.

### 9.5 SCENE context

Each scene request receives:

- scene ID and slot ID;
- phase ID and phase kind;
- trusted story role;
- trusted choice IDs;
- allowed actor slots mapped to accepted engine actor IDs and display names;
- allowed objective IDs mapped to generated quest titles;
- allowed tone tags;
- story title, premise, setting, themes, and promises;
- only the current `PhasePlan`;
- trusted mechanical facts that may be mentioned;
- selected continuity facts from already visited scenes;
- whether this is a declared ending and, if so, a narrative-only ending direction without granting control of the runtime outcome;
- the closed `PlannedScenePayload` schema.

Do not send:

- unvisited generated scene content;
- the complete transcript;
- rejected provider output;
- raw player free text;
- secrets or operational metadata;
- conditions/effects as executable JSON;
- scene destinations or route topology unless a later quality requirement proves it is necessary. The model needs narrative purpose, not control flow.

### 9.6 Context size allocation

Before encoding, reserve the configured `maxInputCharacters` in this order:

1. system policy and output schema;
2. current trusted slot metadata;
3. story title, premise, promises, and current phase plan;
4. relevant cast and quest display data;
5. trusted mechanical facts;
6. continuity facts, newest first;
7. optional nonessential setting/theme detail.

Required items 1–5 must always fit. If they do not, use failure code `GENERATION_CONTEXT_REQUIRED_TOO_LARGE` and fallback without calling the provider. Optional items are deterministically trimmed at item boundaries until the request fits.

Never truncate a JSON string by character position. Never cut a Unicode code point. Never produce invalid JSON to meet the limit.

## 10. Continuity selection

### 10.1 Source

Continuity facts come only from accepted version-2 `PlannedScenePayload` artifacts for scenes already entered by the run.

Prefetched but unvisited scenes do not contribute facts. A fallback scene contributes its validated fallback facts only after the player enters it.

### 10.2 Ordering and cap

Add a pure selector:

```java
List<ContinuityFact> selectContinuity(
    List<String> visitedSceneIds,
    Map<String, GenerationArtifact> acceptedScenes,
    String currentPhaseId,
    int maxFacts,
    int maxCodePoints)
```

Defaults for a full game:

- maximum 12 facts;
- maximum 1,200 code points total;
- preserve scene visit order in the final request;
- selection priority: current phase facts, immediately previous phase facts, then older facts;
- within equal priority, newest facts are selected first;
- after selection, restore chronological order for the provider context;
- normalized duplicates are included once, keeping the earliest established occurrence;
- facts from the current destination scene are never included in its own request.

These limits are engine defaults in v1 and are not new CLI flags. A later catalog version may make them configurable within hard bounds.

### 10.3 Branch and convergence behavior

The model does not plan a canonical route. It sees only facts from the route the player actually visited.

When two choices converge on the same destination scene:

- if both routes must produce materially different narration, the pack must use two trusted destination scene IDs;
- if one shared destination is used, its generation must be valid with the bounded context of whichever predecessor is visited first;
- once generated, the destination artifact is cached and reused on resume or revisit;
- prefetch may generate a converging scene before the final predecessor is known, so the pack must not require predecessor-specific text for a prefetched shared slot.

This rule keeps single-flight, prefetch, snapshot continuity, and deterministic reuse correct.

## 11. Pipeline behavior

### 11.1 Initial generation

For a full game:

1. Run optional THEME as today.
2. Generate or fall back to `StoryPlanPayload` during SCENARIO.
3. Generate CAST using the accepted story plan.
4. Generate QUEST using the accepted story plan and only the allowed cast subset when declared.
5. Generate the opening `PlannedScenePayload` using the opening phase plan.
6. Compose the trusted opening scene and start the run.

If story-plan validation fails:

- use the existing one repair attempt;
- send stable validation codes and trusted retry context only;
- if repair fails, use the validated fallback plan;
- continue to CAST, QUEST, and SCENE with that fallback plan.

### 11.2 Lazy scenes

Before resolving a lazy scene:

1. look up its trusted slot and phase;
2. obtain the accepted story plan, cast, and quest artifacts;
3. select continuity facts using §10;
4. build the stage-specific context from §9.5;
5. generate, repair, or fall back using existing limits;
6. validate the v2 scene payload and facts;
7. compose it with the trusted scene;
8. cache the complete artifact.

No run-state mutation happens until the existing atomic transition accepts the destination scene.

### 11.3 Prefetch

Prefetch uses the same plan and context builder.

Because a prefetched scene is unvisited and may be reached from several predecessors:

- it receives facts from the run state at prefetch time;
- it must not claim the player selected a choice that has not yet been selected;
- it must not receive a predicted option ID;
- its accepted artifact remains valid if entered later;
- fallback prefetch remains discarded under existing session rules;
- no extra plan-generation call is made.

### 11.4 Diagnostics

Keep existing stage outcome and provider metadata. Add content-free validation codes where needed, but do not log:

- plan text;
- phase goals;
- story promises;
- continuity facts;
- cast/quest descriptions;
- scene text;
- player input.

Debug mode may report only counts, for example:

```text
plan=GENERATED phases=5 promises=2 continuity=7/12 context=6840/12000
```

This diagnostic is optional in 27.5 and must not change existing golden output unless `--debug` is active.

## 12. Snapshot and restore

### 12.1 Encoding

Extend the generation artifact codec for:

- artifact schema version 2;
- `StoryPlanPayload`;
- `PlannedScenePayload` and continuity facts.

Use exact-field validation. Unknown fields, wrong payload for stage, duplicate phase IDs, invalid reference sets, and unsupported versions fail closed.

### 12.2 Restore validation

Restore validates story-plan references against the currently pinned pack contract:

- phase IDs and order;
- actor slots;
- objective IDs;
- tone tags;
- story roles;
- field bounds and safety.

Restore validates planned scenes against:

- matching scene slot and template;
- choice IDs;
- accepted cast actor IDs;
- fact bounds and safety;
- pack ID/version and locale.

A mismatch returns the existing safe snapshot/artifact error path. Do not regenerate a replacement for already displayed invalid snapshot content.

### 12.3 Context reconstruction

After resume, the next scene request must receive the same selected continuity facts as it would have received before process restart, given the same visited scene list and accepted artifacts.

No separate continuity store is introduced. Generation artifacts remain the source of narrative memory.

## 13. Error codes

Use existing provider, budget, repair, fallback, and snapshot codes. Add stable codes for new validation failures:

| Code | Meaning |
|---|---|
| `GENERATION_STORY_PLAN_INVALID` | General story-plan shape or semantic validation failed. |
| `GENERATION_STORY_PLAN_PHASE_MISMATCH` | Phase IDs, order, or coverage differ from the trusted contract. |
| `GENERATION_STORY_PLAN_REFERENCE_INVALID` | Actor, objective, tone, or role is not allowed. |
| `GENERATION_STORY_PLAN_PROMISE_INVALID` | Story promises are missing, duplicated, unsafe, or outside bounds. |
| `GENERATION_SCENE_FACT_INVALID` | A continuity fact is invalid, unsafe, duplicated, or outside bounds. |
| `GENERATION_CONTEXT_REQUIRED_TOO_LARGE` | Mandatory trusted and accepted context cannot fit before a provider call. |
| `GENERATION_ARTIFACT_VERSION_MISMATCH` | Artifact version is not valid for the selected catalog/run contract. |
| `GENERATION_ARTIFACT_PLAN_MISMATCH` | Restored plan no longer matches the pinned full-game contract. |

Parser errors used for repair must expose only these codes or existing stable codes. They must not echo rejected content.

Pack-load failures for invalid templates, slots, or fallback plans use `PackIssue` errors:

- `PACK_GENERATION_ROLE_INVALID`;
- `PACK_GENERATION_SLOT_PLAN_INVALID`;
- `PACK_GENERATION_PLAN_FALLBACK_INVALID`;
- existing dangling-reference and fallback codes when they are more specific.

## 14. Required tests

All normal tests use deterministic generators. No test in the normal Maven lifecycle contacts a provider.

### 14.1 Backward compatibility

- Schema-v1 fixture parses and creates artifact version 1.
- Its current SCENARIO and SCENE schemas remain byte-compatible.
- Existing snapshot fixtures still decode.
- Existing generated CLI golden tests remain unchanged.
- Authored packs never parse or create a story plan.

### 14.2 Catalog validation

- Valid full-game planning metadata loads.
- Missing phase, role, actor, objective, or tone metadata fails.
- Slot phase differing from run-contract membership fails.
- Unknown and duplicate references fail.
- Schema-v1 constructors continue to work for content-only packs.
- A utility scene cannot have planning metadata or a scene slot.

### 14.3 Story-plan parser

- Valid five-phase plan passes.
- Missing, extra, duplicate, or reordered phase fails.
- Unknown field fails.
- Every string and list boundary is tested.
- Unknown actor slot, objective, tone, or role fails.
- Phase selection wider than its scene-slot union fails.
- Missing slot-required reference fails.
- Markup, PII, forbidden content, and control-like fields fail.
- Engine—not model—assigns artifact ID and provenance.

### 14.4 Repair and fallback

- Valid first plan gives `GENERATED` with one provider call.
- Invalid first plan and valid repair gives `REPAIRED` with two calls.
- Two invalid results use the validated fallback plan.
- Provider failure goes directly to fallback without repair.
- Fallback plan itself is rejected at pack load when invalid.
- CAST, QUEST, and opening generation continue from a fallback plan.

### 14.5 Scene context

- Opening context contains only its phase plan and no continuity facts.
- Later scene context contains current phase data and visited facts.
- Unvisited and prefetched-only scene facts are absent.
- Actor and objective data is limited to the slot allow-list.
- Context contains no route destinations, effects, raw input, secrets, or complete transcript.
- Required data too large falls back without calling the provider.
- Optional context trimming is deterministic and produces valid JSON.

### 14.6 Continuity selector

- Empty history returns empty facts.
- Facts preserve final chronological order.
- Current-phase and recent facts win when capped.
- Duplicates are removed deterministically.
- Count and code-point limits are exact.
- Destination scene never sees its own prefetched facts.
- Same snapshot and artifacts select identical facts after restart.

### 14.7 Scene payload

- Valid facts are stored but not displayed.
- Too many, too long, duplicate, unsafe, or control-like facts fail.
- Existing choice and actor validation still runs.
- Generated facts cannot change state or events.
- Fallback planned scene composes correctly.

### 14.8 End-to-end full game

- Scripted provider generates plan, cast, quest, and at least five phase scenes.
- Each scene reflects its current phase plan.
- A fact established in DEVELOPMENT is present in CHALLENGE context.
- A fact from an unvisited branch is absent.
- The ending context contains story promises and visited facts.
- The run reaches its trusted outcome.
- Saving and resuming in every phase does not add provider calls for accepted artifacts.
- Provider failure at plan generation still permits a complete run using fallback plan and scenes.

### 14.9 Safety and observability

- Plan text and facts do not appear in normal logs, errors, diagnostics, or exception messages.
- Fake PII markers do not appear in snapshots when rejected.
- Accepted generated narrative remains only in the intended artifact snapshot fields.
- API keys and provider bodies never enter any artifact or context diagnostic.

## 18. Definition of done

Spec 27.5 is complete when:

- Schema-v1 generated-content packs behave exactly as before.
- Every full game produces or falls back to one typed five-phase story plan.
- The plan references only trusted phase, actor-slot, objective, tone, and role IDs.
- Model output cannot add or alter scenes, routes, choices, mechanics, or outcomes.
- CAST and QUEST receive only their relevant plan context.
- Every v2 scene request receives its trusted slot, current phase plan, allowed cast/quest data, and bounded visited continuity facts.
- Unvisited, rejected, and raw player content is absent from scene context.
- Every accepted v2 scene artifact contains validated bounded continuity facts.
- Continuity facts never change runtime state or legal actions.
- Prefetch and demand generation follow the same narrative-context contract.
- Story plan and facts survive snapshot round-trip and resume without regeneration.
- Invalid plan or facts receive at most one repair attempt and then validated fallback.
- A fallback story plan can guide otherwise generated scenes.
- A deterministic full run carries an established fact into a later phase and resolves its story promises at the ending.
- No generated content appears in operational logs or diagnostics.
- `mvn -f app/engine/pom.xml clean verify` passes without network or credentials.

## 19. Handoff to Spec 27.6

Spec 27.6 will make generated cast and quest artifacts visible and meaningful during play. It may:

- resolve engine actor IDs to generated display names in `View` and CLI output;
- expose the active generated quest title and description;
- connect trusted objective progress to generated quest presentation;
- include trusted character and quest summaries in status output.

It must not:

- let generated cast or quest data define runtime IDs or mechanics;
- parse continuity prose to change state;
- allow the model to complete objectives or choose outcomes;
- weaken the story-plan, context, safety, fallback, or snapshot rules established here.

The control boundary remains unchanged: the pack and engine run the game; generated artifacts provide bounded narrative content.
