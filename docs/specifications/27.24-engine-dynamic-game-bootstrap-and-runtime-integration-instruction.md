# Spec 27.24 — Dynamic Game Bootstrap and Runtime Integration

**Type:** Implementation instruction
**Parent:** Dynamic-game series, following Spec 27.23
**Depends on:** Specs 22–27.23, especially `BlueprintGenerationResult.CandidateReviewed`, `MaterializedGameCompiler`, `MaterializedGameDefinition`, `MaterializedGameDefinitionVerifier`, `DefaultEngine` and `RunImpl`
**Baseline:** Inspected local `main` at commit `63ef248` on 2026-10-26. Specs 27.18–27.23 are implemented. A reviewed blueprint can be compiled into a verified materialized definition, but `Engine.start(...)`, `DefaultEngine` and `RunImpl` still require a registered Pack. `RunSnapshot` also identifies only a Pack. Unrelated UI working-tree changes were present and must not be modified. No build or live-provider test was run while preparing this document; implementation must inspect current HEAD again.
**Status:** Ready for implementation; dynamic gameplay becomes mechanically executable in memory, while player-facing lazy presentation, durable resume and CLI exposure remain owned by Specs 27.25–27.27
**Primary outcome:** Bootstrap a complete reviewed dynamic definition before gameplay, reverify it at the execution boundary, and run its trusted scenes and rules through the existing deterministic `RunImpl` state machine without constructing a Pack or a second gameplay engine.
**Repository location:** `docs/specifications/27.24-engine-dynamic-game-bootstrap-and-runtime-integration-instruction.md`

---

## 1. Purpose

Spec 27.23 ends with a verified `MaterializedGameDefinition`, but the runtime can execute only content loaded from Pack files. `DefaultEngine` loads scenes, rules, strings, content policy, places and generation configuration from a `Pack`; `RunImpl` retains that Pack and reads it during views, input handling, events, snapshots and narrative generation.

This specification creates the single transition from dynamic preparation to the existing runtime:

```text
confirmed GamePreparation
  -> GAME_BLUEPRINT generation/review
  -> semantic validation and generated-rules binding
  -> MaterializedGameCompiler
  -> execution-boundary verification
  -> dynamic RuntimeGameDefinition
  -> existing RunImpl state machine
```

The complete mechanical definition must exist before the run ID is published or the first gameplay command is accepted. No route, rule, objective or ending may be invented after startup.

## 2. Scope and non-goals

### 2.1 In scope

- Add an explicit dynamic bootstrap result and start request that cannot be confused with `RunRequest`.
- Compose the existing blueprint-generation and compilation boundaries without duplicating either one.
- Reverify every materialized definition immediately before runtime publication.
- Refactor Pack-dependent runtime inputs behind one internal immutable runtime-definition abstraction.
- Adapt authored Packs and dynamic materialized definitions to that abstraction.
- Start a dynamic run with engine-owned run identity, seed, timestamps and initial rule state.
- Execute choices, requirements, effects, objectives, routes and endings using the existing `RunImpl` algorithms.
- Define honest temporary capability boundaries for unresolved presentation and dynamic snapshots.
- Preserve authored and fixed-Pack generated behavior byte-for-byte at public boundaries where currently covered.

### 2.2 Out of scope

- Lazy scene prose, final choice labels, generated ending narrative, prefetch and scene fallback; Spec 27.25 owns them.
- Durable materialized-definition codecs, definition fingerprints, dynamic snapshot serialization, migration and resume; Spec 27.26 owns them.
- CLI commands, interactive setup exposure, session-service persistence, web/API exposure and release certification; Spec 27.27 owns them.
- A synthetic Pack, transient Pack registration, fake `PackId`, manifest, virtual resource tree or JSON serialize/reparse bridge.
- New mechanics, conditions, effects, automatic routes, places, events, free-text commands or model calls during rule execution.
- Changing the one-repair blueprint budget or performing compiler/runtime repair.

## 3. Verified implementation state

| Component | Current state | Required action |
| --- | --- | --- |
| `BlueprintGenerationService` | Returns reviewed candidate, fallback offer or failure after the bounded generation flow. | Reuse as the proposal boundary; do not copy its retry logic. |
| `MaterializedGameCompiler` | Purely compiles a reviewed candidate and verifies the result. | Reuse, then independently verify again when crossing into execution. |
| `MaterializedGameDefinition` | Contains locale, canonical scenes, `SceneSet`, `Rules`, localized planning content and provenance. | Adapt directly; do not convert it to Pack files. |
| `Engine.start(RunRequest)` | Looks up a Pack and optionally initializes the fixed-Pack `GenerationPipeline`. | Keep unchanged and add an unambiguous dynamic entry point. |
| `DefaultEngine` | Allocates seed/run ID/time and builds `RunImpl` from parsed Pack sections. | Extract shared allocation/start logic only where semantics remain identical. |
| `RunImpl` | Holds a `Pack`; loads `RuleStrings`; reads manifest policy/events; builds Pack snapshots. | Depend on a runtime-definition source instead of Pack for common execution. |
| `GenerationPipeline` | Requires a Pack/catalog and resolves fixed Pack scene slots. | Leave on the authored/fixed-generated adapter; 27.25 adds a dynamic presentation resolver. |
| `RunSnapshot` / `SnapshotCodec` | Require `PackRef`; resume reloads a registered Pack. | Do not forge a Pack reference. Dynamic durability stays unavailable until 27.26. |
| CLI/session host | Starts only Pack-backed requests and assumes snapshots are available. | Do not expose dynamic runs through these hosts in 27.24. |

## 4. Public bootstrap contracts

### 4.1 Separate requests

Do not add nullable dynamic fields to `RunRequest` and do not overload `generated=true`. That flag continues to mean generated presentation inside an authored Pack.

Introduce explicit immutable contracts conceptually equivalent to:

```java
record DynamicGameBootstrapRequest(
    GamePreparation preparation,
    Long seed) {}

sealed interface DynamicGameBootstrapResult {
    record Started(Run run, MaterializedGameDefinition definition,
                   List<Issue> issues, List<Event> events) implements ... {}
    record FallbackOffered(ReviewedFallbackOffer offer, List<Issue> issues) implements ... {}
    record Failed(String code, List<Issue> issues) implements ... {}
}
```

The exact owning class/package may follow existing API conventions, but the variants and trust distinctions must remain explicit. A fallback offer is not a started game. The returned definition exists for in-process handoff and tests only; 27.26 decides its durable envelope.

The request carries the already validated `GamePreparation`, including its ephemeral approved-suggestion capability where applicable. It must not carry raw/scrubbed suggestion strings, arbitrary `PreparedStartInputs`, Pack identifiers, caller-provided IDs, timestamps or a `validated` boolean.

### 4.2 Optional lower-level start seam

The engine may expose a package-private or clearly advanced `startMaterialized(...)` seam for deterministic tests and later restore work. It accepts only a `MaterializedGameDefinition` plus optional seed, reverifies the definition and never bypasses bootstrap verification. Normal host code must use the end-to-end bootstrap operation.

Do not offer a public method that starts a raw blueprint, parser result, `SceneSet`, `Rules`, or caller-assembled runtime adapter.

## 5. Bootstrap coordinator and atomic publication

Add one coordinator, with dependencies supplied through the existing builder/wiring style, that performs:

1. Reject null, stale or mismatched preparation before provider work.
2. Call `BlueprintGenerationService` exactly once for this confirmed start operation.
3. Preserve `FallbackOffered` as a non-started result; do not auto-accept it.
4. Accept only `CandidateReviewed` from successful generation.
5. Compile it through `MaterializedGameCompiler` exactly once.
6. Require `Compiled`; map invalid-input/compiler failures to bounded content-free start codes.
7. Reverify the compiled definition through `MaterializedGameDefinitionVerifier` at the execution boundary.
8. Adapt it to the dynamic runtime-definition source.
9. Allocate the seed, run ID and timestamps only after every deterministic check passes.
10. Construct and fully initialize `RunImpl`; publish `Started` only after startup contains no error.
11. Release references to the ephemeral suggestion capability after success or terminal failure.

There is no partial success. A failed compile/start creates no visible run, snapshot, session, registration or cache entry. Provider/repair usage belongs exclusively to the generation result evidence; runtime validation never calls the provider.

The coordinator is per-operation or otherwise concurrency-safe. Two concurrent starts cannot share candidate, definition, run identity, mutable state or suggestion capability. A caller retry is a new start operation and may generate a new blueprint; internal retries after a terminal result are forbidden.

## 6. RuntimeGameDefinition boundary

### 6.1 One engine, two definition sources

Introduce a package-private immutable abstraction named for its purpose, for example `RuntimeGameDefinition`, with two trusted adapters:

- `PackRuntimeGameDefinition` for existing authored/fixed-generated runs;
- `DynamicRuntimeGameDefinition` for a verified `MaterializedGameDefinition`.

This is not a new domain schema and is not persisted. It supplies only what `RunImpl` needs:

```text
origin and locale
SceneSet and canonical Rules
localized string lookup
content/input capabilities
event metadata
optional PlaceMap
optional presentation resolver
snapshot capability/source metadata
```

`RunImpl` remains the only gameplay state machine. The adapters must not implement command routing, conditions, effects, objectives or endings.

### 6.2 Pack adapter

The Pack adapter delegates to the same current loaders and values:

- `SceneSets.load(pack)`;
- `RulesParser.parse(pack)`;
- `RuleStrings.load(pack, locale)`;
- manifest content policy/event declarations;
- `PlacesParser` and the existing place cache;
- existing `GenerationPipeline` for `RunRequest.generated()`.

Avoid eagerly changing parse/cache/error order when that would alter existing behavior. Existing `RunRequest`, issue codes, snapshots, generated artifacts and resume semantics remain compatible.

### 6.3 Dynamic adapter

The dynamic adapter is created only after verifier success and supplies:

- `definition.locale()` exactly; no locale negotiation or fallback;
- `definition.runtimeSceneSet()` and `definition.runtimeRules()`;
- deterministic lookup from `definition.localizedContent()`;
- no Pack, Pack features, manifest, resources, places or authored events;
- no free-text command capability and no start-input persistence;
- a presentation resolver marked unavailable until Spec 27.25;
- snapshot durability marked unavailable until Spec 27.26.

It retains the materialized definition for the run lifetime in memory. It never registers it globally and never makes it discoverable through `PackRegistry`.

## 7. Run identity and initialization

For a verified dynamic definition:

- use `request.seed()` when supplied, otherwise exactly one `random.nextLong()` call;
- call `ids.nextId()` exactly once for the run ID after validation;
- call `clock.instant()` once and use it for both `createdAt` and initial `updatedAt`;
- initialize `visited` with the trusted start scene ID;
- initialize counters, flags, sets and objectives through the same `RunImpl` path as Pack rules;
- execute start-scene entry/objective semantics through the same methods and ordering;
- use no place state, generation artifacts, Pack start inputs or suggestion data;
- return startup events/issues with the same defensive-copy behavior as `StartResult`.

Run IDs are runtime identities, not definition IDs or persistence fingerprints. Never derive them from content, profile, provider request, `hashCode` or seed.

Startup must reject, without allocating a run identity:

- null or unsupported definition/version/origin;
- verifier failure or locale mismatch;
- absent/mismatched start scene;
- unresolved trusted references;
- a dynamic definition carrying places, events, inputs or unsupported mechanics;
- any definition whose mechanical scene labels are mistaken for ready player presentation.

Use bounded issue codes such as `DYNAMIC_PREPARATION_INVALID`, `DYNAMIC_BLUEPRINT_FAILED`, `DYNAMIC_COMPILATION_FAILED`, `DYNAMIC_DEFINITION_INVALID`, `DYNAMIC_START_FAILED` and `DYNAMIC_PRESENTATION_PENDING`. Messages contain no story text, source symbols, rule trees, prompt/response data or suggestion-derived excerpts.

## 8. Shared RunImpl execution

Refactor only Pack reads that block the dynamic adapter. `RunImpl` must continue to own and share:

- state initialization and mutation;
- `ConditionEvaluator` and `StateEffectSemantics` usage;
- option availability and rejection without mutation;
- effect ordering;
- visited-scene tracking;
- objective completion evaluation;
- ending/outcome resolution;
- command step/time updates;
- deterministic `View` state assembly where presentation is available.

Dynamic mechanics use only the already compiled trusted IDs and existing generated-rules-v1 vocabulary. They must produce the same state transition as an equivalent trusted `SceneSet`/`Rules` fixture passed through the shared runtime.

Do not branch on dynamic origin inside condition/effect evaluation. Origin-specific behavior belongs in the definition adapter or presentation/snapshot capability boundary.

## 9. Presentation readiness boundary

The compiled scenes intentionally contain empty blocks and `MaterializedGameCompiler.UNRESOLVED_LABEL`; choice intents are planning data, not final labels. 27.24 must not expose that marker, substitute IDs as labels or promote intents to final player copy.

A dynamic run started in 27.24 is **mechanically executable but host-ineligible** until a presentation resolver is installed by 27.25:

- startup reports the non-error capability issue `DYNAMIC_PRESENTATION_PENDING`;
- normal CLI/session/web wiring must not publish or persist the run;
- internal integration tests may apply trusted choice IDs directly to prove runtime parity;
- `view()` must redact unresolved labels and never return the sentinel as player text;
- no model call occurs merely because `view()` is requested.

Choose one explicit internal representation for the pending view and freeze it in tests. It may contain story/objective metadata already approved in `localizedContent`, but it must contain no selectable option whose label is unresolved. Spec 27.25 replaces this pending boundary with lazy validated scene presentation and fallback.

## 10. Snapshot and resume boundary

`RunSnapshot` v1 requires a `PackRef`; a dynamic run has none. Never invent one.

Add an explicit capability query/result so callers can distinguish snapshot support before requesting it. Existing Pack runs remain snapshot-capable. For dynamic runs in 27.24:

- snapshot capability is `PENDING_DYNAMIC_DEFINITION_PERSISTENCE`;
- the legacy `snapshot()` method fails deterministically with a bounded engine exception/code rather than returning null or a malformed Pack snapshot;
- `SnapshotCodec` receives no dynamic branch;
- `Engine.resume(...)` remains Pack-only;
- session/CLI code must not receive these runs yet.

The compatibility shape may be a default method on `Run`, a small capability enum, or an equivalent nonbreaking API. Do not change existing Pack snapshot JSON or force authored callers to provide new arguments. Spec 27.26 replaces this temporary barrier with the versioned dynamic snapshot/definition envelope and exact resume.

## 11. Privacy, failure and observability

- No prompt, provider response, reviewed prose, source symbol, rule tree or suggestion text enters issue messages, logs, metrics, exceptions or `toString()`.
- Metrics may include operation status, bounded stage/code, definition/compiler versions, counts, duration and provider-budget evidence already approved by earlier specs.
- Do not hash the suggestion or use it in IDs, cache keys or correlation IDs.
- Runtime failure after provider acceptance does not trigger another provider call or blueprint repair.
- A rejected command leaves step, scene, state, timestamps and events unchanged, as on the Pack path.
- A dynamic adapter/start failure returns no `Run` and does not expose the compiled definition unless the result is the explicit successful in-process handoff.
- No static mutable map of definitions/runs is introduced.

## 12. Compatibility requirements

The following remain unchanged:

- authored Pack start and resume;
- `generated=true` fixed-Pack Willow Marsh/content-generation behavior;
- Pack registry/loader/validators and manifest feature semantics;
- places, events, input guard/interpreter and generated artifact behavior for Packs;
- `RunRequest`, Pack `StartResult` issue ordering, and Pack snapshot v1 JSON;
- existing test fixtures and generation provider budgets.

Do not add a `DYNAMIC` Pack feature, reserved Pack ID or hidden Willow Marsh fallback. Do not move provider, session, Spring or CLI dependencies into engine core.

## 13. Required test matrix

| Group | Evidence |
| --- | --- |
| Bootstrap success | Confirmed preparation yields one reviewed candidate, one compilation, one execution verification and one started in-memory run. |
| Bootstrap variants | Generation failure, fallback offer, invalid accepted input, compiler failure and final verifier failure return exact non-started variants. |
| Atomicity | Failed operations allocate no run ID/time/seed after the failing boundary and publish no run/definition/session. |
| Calls/budgets | No duplicate blueprint/provider/compiler calls; fallback is never auto-accepted; runtime performs no repair. |
| Adapter | Dynamic source exposes exact locale/scenes/rules/strings and no Pack/resources/places/events/free text. |
| Identity | Supplied/random seed behavior, one run ID, one initial clock instant and distinct concurrent run state. |
| Runtime parity | Requirements, all v1 effects, objectives, routes, ending/outcome and rejection atomicity match equivalent shared-runtime fixtures. |
| No second engine | Dynamic commands execute in `RunImpl`; no duplicated evaluator/state machine exists. |
| Presentation | Sentinel/IDs/intents never appear as final selectable labels; pending capability prevents host publication. |
| Snapshot | Pack snapshot JSON remains exact; dynamic capability is unavailable and snapshot fails explicitly without fake `PackRef`. |
| Privacy | Results/issues/exceptions/log-capture/toString contain no suggestion, prose, source symbols or rules. |
| Compatibility | Authored, places, input, fixed-generated, generation-artifact and resume suites remain green. |
| Full gate | `mvn -f app/engine/pom.xml clean verify` passes without lowering gates. |

At least one route test must use a structurally different non-Willow-Marsh EN fixture and one PL fixture. Tests must exercise branches gated by counters, flags, sets, visited scenes and objective state, plus every ending class supported by generated-rules-v1.

## 14. Implementation sequence

1. Reinspect HEAD/status, AGENTS/build guidance, Specs 27.17–27.23 and current runtime/snapshot APIs; preserve unrelated UI work.
2. Add explicit bootstrap request/result and bounded issue contracts.
3. Add the internal runtime-definition abstraction and Pack adapter without changing behavior.
4. Refactor `RunImpl` Pack reads through the adapter; run authored/fixed-generated regression tests.
5. Add the verified dynamic adapter with disabled places/events/free text/presentation/snapshot capabilities.
6. Implement atomic coordinator order from generation through compilation and execution verification.
7. Add dynamic `DefaultEngine` startup using the shared `RunImpl` initialization path.
8. Add the presentation-pending and snapshot-unavailable capability barriers.
9. Add adversarial, parity, identity, concurrency, privacy and compatibility tests.
10. Update the engine README/spec index to mark dynamic mechanics executable in memory but not yet player-facing or durable.
11. Run focused tests and `mvn -f app/engine/pom.xml clean verify`; fix implementation failures without lowering gates.
12. After complete implementation, commit only 27.24 changes to main as `spec 27.24 is implemented - <short description>`.

No live-provider test is required. Do not implement lazy scene generation, dynamic persistence or CLI exposure implicitly.

## 15. Acceptance criteria and handoff

27.24 is complete when a confirmed preparation can produce exactly one reviewed blueprint, compile and reverify its full mechanical definition before publication, and execute that definition through the same `RunImpl` transition logic used by Packs; dynamic IDs/state/routes/objectives/endings behave deterministically; no Pack is fabricated or registered; failed starts are atomic and content-free; unresolved presentation cannot leak to a player-facing host; unsupported dynamic snapshots fail honestly without changing Pack snapshot behavior; and authored plus fixed-Pack generated paths remain compatible.

**Next: 27.25 — Blueprint-Driven Lazy Scene Generation.** It adapts theme/cast/quest/scene presentation to the accepted definition, installs the dynamic presentation resolver, adds continuity/prefetch and validated scene-level fallback, and turns the mechanically executable run into a player-facing one without changing its compiled routes, effects or endings.
