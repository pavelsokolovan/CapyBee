# Spec 30.4 — Befriend and Recruit

**Type:** Implementation instruction
**Intent:** [Illustrated Honeycomb RPG](intent/03-illustrated-honeycomb-rpg.md)
**Depends on:** [30.1](30.1-visual-design-and-svg-catalog-instruction.md), [30.2](30.2-public-presentation-contracts-instruction.md)
**Related:** [30.3](30.3-playable-honeycomb-board-instruction.md) (board draft; not an implementation prerequisite)
**Baseline:** `055b4c6`, inspected 2026-11-16
**Status:** Implemented 2026-11-16; see [acceptance](../game-befriend-recruit-acceptance.md)

## Deliverable

Show discovered fictional characters as animal/abstract portraits with their
public trait and need, and display recruited companions in the active run.
Use existing SVGs and accepted public presentation metadata. Helping remains
an ordinary authored choice through `SceneActions`; this part adds no recruit
button, command, state flag, endpoint, queue or persistence.

This can ship independently of 30.3's board. Do not change movement/encounter
entry, Pack resources/versions, generation, production flags or rewards.
Illustrated backdrops and full scene/text-mode composition remain 30.5 work.

## Public data and identity

Join `view.presentation.characters` to discovered `view.characters` exclusively
by public `id`. Preserve accepted names, descriptions and current-scene presence.
Use metadata's asset ID, expression, trait and need; never identify a hero by
name, species, slot ID, place ID, prose or Pack/version. The player/guide is an
ordinary public character and must not be excluded through hardcoded identity.

Party members must occur in the explicit public `presentation.party` list,
have a discovered character record and metadata with `recruited === true`.
Respect public party order, deduplicate IDs and ignore unknown/inconsistent
references. Do not create membership from a clicked option or from `recruited`
alone when the party list omits that character. No hidden snapshots, flags,
blueprints or future cast may be inspected.

Missing/unsupported presentation keeps the existing text-first character panel.
Unknown/wrong-family art uses 30.1's neutral character while retaining the public
name. Unspecified traits/needs are omitted, never inferred or replaced with
affection/health scores. All content is React text, not parsed markup or links.

## Surfaces and interaction

1. **Current characters:** display current-scene enriched characters between
   the shared narrative and existing choices. Use 64px portraits, names, trait
   and need with readable labels. If neither trait nor need exists, show the
   public description. A joined character has a calm joined status; its original
   need is labeled as something helped with rather than an unresolved demand.
2. **Party:** show an always-visible compact named portrait list below the run's
   existing status area. Use 40px decorative portraits and the explicit public
   party list. An empty party has gentle EN/PL text explaining that exploring
   without companions is valid. No empty collectible slots, total-to-complete,
   score, progress meter or pressure to recruit every hero.
3. **Discovered history:** reuse the existing expandable Characters section,
   enriching discovered records with portraits/trait/need and joined state when
   metadata is available. Retain description/current-scene context. Do not add
   a second catalog of undiscovered characters or make cards into controls.

The party and current portraits remain the last accepted public state while
a choice is queued, pending, offline or uncertain. Declining, rejected actions,
replays and revisits cannot add or duplicate companions. A completed run may
retain its public party. Abandon, account changes and run replacement follow
the existing controller's cleared/replaced view; no client-owned membership
history survives it.

Optionally announce newly accepted joins with one short polite status in the
shell locale. Baseline the initial/resumed party silently. Announce only new
IDs on an eligible later accepted revision of the same run; do not announce
initial hydration, repeated polls, same-revision replay, stale views, unrelated
background changes or run replacement. Keep this transient accessibility state
in memory and never store or submit it. Do not introduce timers, celebration
animations, sound or focus changes; preserve the run's existing focus behavior.

## Accessibility, layout and tone

Portraits are decorative beside visible names: unfocusable SVGs with
`aria-hidden`, no duplicated alt labels or raw asset IDs. Use semantic sections,
headings, lists and definition labels. Controls stay in the existing actions
and native expandable history, with visible focus and at least 44px targets.

Use existing warm cream/ink/muted tokens and fixed catalog art. Names and need
text wrap without truncation or horizontal page overflow at 360px and 200%
zoom. Party members wrap; no forced carousel/panning. Forced colors and hidden
SVGs preserve every name, trait, need and joined state. Respect reduced motion;
the new surfaces are static. No hearts, padlocks, human figures or competition.

All shell headings, statuses, labels and empty-state copy use the existing
EN/PL copy-object pattern. Story names/traits/needs retain their public locale;
mark shell labels with their own language where they differ from story text.
Joining records fictional cooperation, not a replacement for a real friend.

## Acceptance and gates

- Test the pure public-data join/filter logic: ordinary and generated IDs,
  current versus discovered characters, explicit party order, duplicate/missing
  references, absent metadata and unknown art. Public data must not be mutated.
- Component tests cover all three companions and neutral fallback, optional
  fields, hostile plain text, EN/PL copy, decorative SVG semantics, joined need
  labeling, completed/abandoned and new-run views. Verify initial/resumed party
  silence and one later join announcement without poll/replay duplicates.
- Through `GameRun` with a controller double, prove that pending/rejected/offline
  choices retain accepted portraits/membership, and accepted recruitment updates
  the visible party without adding a second command or speculative state.
- Extend the existing Spring/PostgreSQL browser checks for the actual authored
  and generated-fallback Pack: encounter portraits/needs before help; party after
  accepted help; exact reload/replay; no duplicate membership after revisits;
  decline and rest remain valid. Exercise mobile/desktop, 200% zoom, keyboard,
  reduced motion, forced colors and hidden artwork. Legacy text-only games keep
  their existing panel and choices.
- Run frontend tests/coverage and the official UI build/static-sync workflow;
  verify both static directories and inspect the production Spring-served UI.
  Run the integrated backend/browser gate with deterministic providers. No live
  provider or new engine/backend production logic is required for this UI work.
- Record real-run screenshots, executed checks and limitations in
  `docs/game-befriend-recruit-acceptance.md`; update the spec index. Commit on
  `main` using the repository's spec implementation format after checks pass.
