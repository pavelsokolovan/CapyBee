# Spec 27.16 — Normal CLI Play Readiness

**Type:** Final player-facing readiness and manual acceptance specification  
**Parent:** Spec 27.15 — Reliable CLI Scripts and Real Process Resume Tests  
**Depends on:** Specs 27.8–27.15  
**Baseline:** repository commit `f1eebcb`, plus the prepared Specs 27.14 and 27.15. The current PowerShell launcher, CLI entry point, default save-path resolver, session startup and command loop, setup metadata, generation provider selection, Willow Marsh documentation, and CLI tests were inspected while writing this specification. The build and manual game were not run. Existing uncommitted specification work was preserved.  
**Status:** Ready for implementation after Spec 27.15  
**Primary outcome:** A normal player can run one documented command, complete safe setup, understand whether external generation or reviewed fallback is being used, play with readable UTF-8 output, save automatically, quit, resume, use the standard utility commands, and finish Lanterns of Willow Marsh through the CLI.

---

## 1. Purpose

Specs 27.14 and 27.15 make generated saves durable and make automated route evidence trustworthy. The remaining work is intentionally small and player-facing:

- Windows output must render UTF-8 punctuation and localized text correctly;
- the already specified interactive setup questions and provider disclosure must be wired into normal play;
- the standard utility commands must be comfortable and truthful;
- an unavailable default or explicit save directory must produce a clear actionable error;
- absent provider configuration must select complete authored fallback automatically;
- one human must play the normal command from setup through ending, including quit/resume;
- documentation must recommend the maintained Willow Marsh pack rather than a technical fixture.

This specification is a release-readiness pass, not another engine expansion. It verifies and finishes the normal path already designed in Specs 27.8–27.15.

## 3. Goals and non-goals

### 3.1 Goals

1. Produce valid readable UTF-8 on Windows terminals and redirected output.
2. Run the approved localized setup flow for normal full generated games.
3. Show the approved external-provider disclosure before any external-capable setup data collection or call.
4. Clearly announce provider-free authored fallback and omit ineffective free-text setup.
5. Verify every normal utility command against an active durable Willow Marsh game.
6. Provide a clear save-directory error with an actionable `--store-dir`/`--memory` alternative.
7. Keep normal play durable by default and temporary play explicit.
8. Automatically finish through authored fallback when provider credentials/configuration are absent.
9. Complete one final provider-free human play from setup through ending, with a process restart.
10. Optionally complete one provider-backed human play when reviewed credentials and budget are available.
11. Document the exact normal Willow Marsh launch command.

### 3.2 Non-goals

- Changing durable snapshot/store semantics from Spec 27.14.
- Changing strict script/process certification semantics from Spec 27.15.
- Adding new story routes, commands, mechanics, locales, providers, or a graphical client.
- Making live-provider play a release prerequisite when credentials are unavailable.
- Persisting setup consent or free-text input.
- Guaranteeing terminal font glyph coverage; the application guarantees correct UTF-8 bytes/stream configuration.
- Adding command aliases beyond those already supported.
- Parsing console prose as automated route evidence.
- Logging prompts, provider responses, setup free text, or secrets during manual acceptance.

## 5. Windows UTF-8 console contract

### 5.1 Required behavior

On supported Windows PowerShell/Windows Terminal execution, these must render without replacement characters or mojibake:

- `CapyBee is thinking…`;
- em dashes in character/objective descriptions;
- curly apostrophes or other punctuation present in reviewed content;
- non-ASCII localized text supplied by a test pack, including Polish diacritics;
- the same text when stdout/stderr are redirected to files and decoded as UTF-8.

No UTF-8 BOM is written to stdout/stderr or script/save JSON.

### 5.2 Launcher boundary

Before invoking Java, the `game`, `game-package`, and certification launcher paths establish UTF-8 for child-process I/O. An acceptable PowerShell implementation configures session-scoped input/output encoding and launches Java with explicit UTF-8 stdout/stderr/file properties supported by the selected JDK.

Requirements:

- preserve forwarded arguments exactly;
- preserve Java exit code;
- do not print `chcp` banners into the game transcript;
- do not permanently change the user's console/system locale;
- do not require a PowerShell profile;
- behave correctly in Windows PowerShell and PowerShell 7 where supported by the repository workflow.

### 5.3 Java entry point

`PlayMain` must write and read UTF-8 predictably even when launched directly, including the packaged command. Implementation may create UTF-8 wrappers around the real standard file descriptors or use the supported JDK console charset facilities.

It must:

- auto-flush interactive output appropriately;
- keep stdout and stderr separate;
- avoid double-wrapping injected test streams in `ConsoleApp`;
- not close global streams;
- retain UTF-8 script and snapshot file handling;
- produce byte-identical UTF-8 under redirected-output tests.

### 5.4 Tests

Add:

1. renderer/unit coverage for ellipsis, em dash, and Polish sentinel text;
2. a subprocess test that captures raw stdout/stderr bytes and decodes with a strict UTF-8 decoder;
3. a PowerShell launcher smoke on Windows CI, when Windows CI exists, using redirected files;
4. an assertion that no replacement character (`U+FFFD`) or common mojibake sequences appear;
5. an argument-forwarding/exit-code regression test for `dev.ps1 game`.

Do not make locale-dependent assertions about terminal fonts or glyph width.

## 6. Interactive setup readiness

### 6.1 Entry conditions

Run interactive setup when all are true:

- top-level `play` mode;
- `--generated` is selected;
- the pack declares the full-game setup resource;
- no gameplay script is active;
- a new run is being created.

Resuming an active or ended saved run never asks setup questions again. Explicit new-game flow asks again after the existing confirmation rules.

### 6.2 Provider-backed flow

When a usable external provider is configured, before collecting free text or making any provider call show the approved Spec 27.8 disclosure in simple language:

- a configured AI text service may shape story presentation;
- selected setup answers may be sent to that service;
- optional text is checked locally and detected personal details are removed, without claiming perfect detection;
- the player should not enter names, contact details, exact address, school/class details, passwords, or secrets;
- optional text is not saved in the game snapshot;
- cancel sends nothing and creates no run.

Prompt:

```text
Continue? [y/N]
```

Empty input, `n`, EOF, or `/cancel` cancels with exit 0, creates no run/store record, and performs zero provider calls. `y` continues. Invalid answers repeat without advancing.

### 6.3 Provider-free flow

When the provider is disabled, credentials/model are absent, `--offline` is set, or configuration cannot be constructed safely:

- do not present the external-provider disclosure as though data will leave the process;
- print a short notice such as `AI text service unavailable; using the complete reviewed story.`;
- do not ask the optional `story-wish` free-text question;
- ask supported preset questions/defaults as defined by the pack;
- make zero provider calls;
- start and complete the authored-fallback game.

Malformed/partial credentials are treated as unavailable for ordinary play and never printed. Provider-required diagnostic/certification modes remain strict.

### 6.4 Questions

Render questions from the typed pack setup resource in manifest/setup order:

1. Story tone — one option, default `Cozy`;
2. Story interests — zero to two options;
3. Companion focus — one option, default `Balanced`;
4. Story wish — optional free text, provider-backed interactive flow only.

Use localized labels and help from pack strings. Java code must not special-case those four IDs or English labels.

Required interaction:

- numbered choices and visible defaults;
- immediate local validation;
- enum-set max enforcement without losing prior answers;
- `b` to go back;
- `q` or `/cancel` to cancel setup;
- empty input accepts a declared default or skips an optional value;
- safe retry for invalid or blocked text;
- review screen before start;
- preset answers shown by localized label;
- free text displayed only as `[provided]` or `[provided, personal details removed]`;
- final confirmation creates the run only once.

### 6.5 Privacy and persistence

Retain all Spec 27.8 privacy invariants:

- raw/scrubbed free text is transient;
- it may reach only allowed initial THEME/SCENARIO generation;
- it never enters snapshot, local store, pending start, scripts, transcript echo, logs, events, diagnostics, lazy scenes, continuation facts, or manual evidence;
- preset enum values may persist as already designed;
- resume relies on accepted artifacts and never asks for free text again.

### 6.6 Non-interactive setup

Spec 27.15 scripts continue using `--input` preset values/defaults. They never consume gameplay lines as setup answers. A configured provider in script mode requires `--accept-generation-disclosure`; fallback-only script mode does not. Command-line free text remains `FREE_TEXT_COMMAND_LINE_FORBIDDEN`.

## 7. Normal command behavior

The supported repository-root command is:

```powershell
./dev.ps1 game `
  --pack-dir ./app/engine/reference-game-packs/lanterns-of-willow-marsh `
  --generated
```

It must:

1. build the required engine modules unless `-SkipBuild` is explicitly used;
2. launch the session-backed `play` command;
3. resolve the Willow Marsh pack;
4. use the default durable save directory;
5. detect provider availability without requiring it;
6. run disclosure/setup as appropriate;
7. save every accepted choice automatically;
8. find and offer the saved run on the next invocation;
9. allow the player to finish and reopen the result.

`--memory` is documented as intentionally temporary. It is never added implicitly by `dev.ps1 game`.

## 8. Save-directory usability

### 8.1 Default locations

Retain the platform conventions already implemented:

- Windows: `%LOCALAPPDATA%\CapyBee\cli`;
- macOS: `~/Library/Application Support/CapyBee/cli`;
- Linux/Unix: `$XDG_STATE_HOME/capybee/cli` or `~/.local/state/capybee/cli`.

Paths are normalized before use. The CLI does not print a private absolute path during normal startup.

### 8.2 Preflight

Before setup collects free text or a provider call is made, normal durable play must prove the selected store directory can be used sufficiently to open/create the local store and key.

Handle at least:

- path resolves to an existing regular file;
- parent/directory cannot be created;
- directory or required files cannot be read/written;
- lock file cannot be created;
- store is already locked;
- key is missing/invalid for an existing store;
- existing store is corrupt/unsupported.

Do not perform a destructive probe or overwrite an existing store merely to test writability. Use the real safe store open path and existing recovery rules.

### 8.3 Player-facing error

For an unusable new/default directory, print a stable top-level code and action:

```text
STORE_UNAVAILABLE
  This save directory cannot be used. Choose --store-dir <directory>, or use --memory for a temporary game.
```

Exit 3. For locked, corrupt, unsupported, missing-key, or recovery-specific existing stores, retain the more precise safe code/hint where it gives the player a safer action. Never print exception text, credentials, file contents, or an untrusted path.

The failure occurs before creating a run or calling a provider.

### 8.4 Tests

Cover default and explicit paths with injected path/store seams:

- resolvable writable directory;
- existing file instead of directory;
- create/open/write failure;
- locked store;
- custom `--store-dir` recovery suggestion;
- `--memory` bypasses durable store intentionally;
- no provider call/run record on preflight failure.

Tests must not depend only on POSIX permission bits, which may behave differently on Windows or under privileged CI users.

## 9. Utility-command readiness

Verify commands interactively against a durable active Willow Marsh run. Utility commands do not advance story step/revision, create command-log entries, call the provider, or change generated artifacts unless explicitly stated.

| Command | Required behavior |
|---|---|
| `/help` | Lists normal choice guidance and all supported player commands without developer-only commands unless debug was explicitly enabled. |
| `/look` | Re-renders current scene narration/dialogue/options; no mutation or provider call. |
| `/status` | Shows current trusted counters/visible status and save/run state clearly; no mutation. |
| `/objectives` | Shows every discovered objective with clear active/done state and description. `/quests` may remain an alias. |
| `/characters` | Shows discovered generated/fallback cast names and descriptions safely. |
| `/map` | Shows current place, visited/available places, and movement guidance without advancing the story. |
| `/save` | Durable run: confirms already-saved run ID/revision. Temporary run: clearly says it cannot survive process exit and suggests durable play. No extra story mutation. |
| `/quit` | Exits 0 after pending work is resolved, leaves active run resumable, and releases the store lock. |
| `/abandon` | Explains irreversibility, defaults to No, requires confirmation, applies one abandonment command, and makes the run non-resumable as active play. |

Additional readiness rules:

- `q` without slash does not silently quit normal play;
- unknown slash commands show help guidance and are never submitted as story text;
- command output is sanitized and UTF-8;
- commands work before and after a process restart;
- `/help` accurately distinguishes `/quit` from `/abandon`;
- `/save` never implies that setup free text or provider secrets were stored;
- on an ended reopened game, read-only inspection commands remain usable where the current CLI lifecycle allows them, while story mutation is refused clearly.

## 10. Provider absence and fallback

### 10.1 Detection

Ordinary generated play uses authored fallback when any of these applies:

- `--offline`;
- `GENERATION_PROVIDER_MODE` is disabled or invalid;
- `GENERATION_MODEL_ID` is missing/blank;
- `ANTHROPIC_API_KEY` is missing/blank;
- provider configuration validation fails before a call.

No credential value is displayed or persisted. An invalid provider-mode value continues to fail closed to disabled.

### 10.2 Runtime failures

When an optional provider is configured but a bounded generation attempt fails, the normal generation pipeline uses validated authored fallback according to existing rules. Billing, timeout, refusal, schema, safety, repair, and quality failure remain content-free diagnostics and do not prevent completion when a fallback exists.

Normal play must not tell the player to configure credentials merely because fallback was selected. Developer diagnostics may expose stable reason codes under explicit debug mode.

### 10.3 Provenance disclosure

The player-facing story card/setup explains:

- trusted choices, rules, objectives, effects, and outcomes are authored;
- presentation may be generated when a provider is available and accepted;
- a complete reviewed version is available without the provider.

It does not overstate generated quality, provider privacy/retention, or PII detection.

### 10.4 Tests

Test ordinary play with:

1. no provider-related environment variables;
2. model only;
3. key only;
4. disabled provider mode with credentials present;
5. `--offline` with credentials present;
6. local provider double failure leading to fallback;
7. explicit provider-required live-smoke still failing when unavailable.

The first six complete without network access; the first five instantiate no adapter.

## 12. Manual provider-free acceptance

### 12.1 Environment

Run from a clean built checkout on Windows, because Windows encoding is the known player-facing risk. A Linux/macOS repeat is useful but not required if automated gates cover them.

Before the run:

- unset `ANTHROPIC_API_KEY` and `GENERATION_MODEL_ID`;
- set provider mode disabled or leave ordinary missing-configuration behavior in effect;
- use a fresh isolated default-state root for the test account/session;
- do not delete or overwrite an existing user's save directory;
- use the exact documented command without `--offline`, `--memory`, or developer/debug flags.

Using an isolated temporary `%LOCALAPPDATA%` for the manual session is acceptable because it still exercises default-path resolution. Record only a path digest or `isolated-default-store=true`, never the raw private path.

### 12.2 Required flow

1. Launch the exact command in Section 7.
2. Confirm pack card, durable-saving status, and authored-fallback notice are clear.
3. Complete preset setup; verify no ineffective free-text question appears.
4. Start the game and inspect non-ASCII punctuation.
5. Use `/help`, `/look`, `/status`, `/objectives`, `/characters`, `/map`, and `/save`.
6. Make at least four accepted choices.
7. Use `/quit` and confirm the Java process exits normally.
8. Launch the exact same command in a new Java process.
9. Choose Continue and verify the same scene/revision/progress appears.
10. Use the remaining utility commands again as useful.
11. Finish one complete trusted route.
12. Confirm result class, objectives, facts, and ending are coherent.
13. Exit and launch once more to reopen the completed game.
14. Confirm no setup or generation repeats and the ending/result is readable.
15. In a separate disposable run, test `/abandon`, decline once, then confirm once.

### 12.3 Pass criteria

- no mojibake or replacement characters;
- no provider prompt, credential request, or network dependency;
- fallback notice is clear but not alarming;
- setup is understandable without internal IDs;
- commands are discoverable and truthful;
- every accepted choice is saved;
- restart resumes exact progress;
- ending and completed reopen work;
- `/quit` and `/abandon` behave differently and clearly;
- no raw setup/private/provider content appears in evidence.

Any functional failure blocks completion of Spec 27.16. Pure wording observations may become focused edits only when they are within this specification's existing command/setup scope.

## 13. Optional provider-backed acceptance

Run only when all of these are available:

- an explicitly approved credential;
- a pinned supported model ID;
- provider mode enabled;
- reviewed call/cost/time limits;
- authorization to incur the expected cost.

Use a fresh isolated store and the same normal command. Verify:

1. disclosure appears before setup/provider call;
2. default No cancels with no call;
3. a second invocation with explicit Yes proceeds;
4. optional safe story wish is processed without echo and is not persisted;
5. generated/repaired/fallback provenance is truthful in developer evidence;
6. save/quit/new-process resume makes no call for accepted content;
7. the game reaches an ending within the approved limit.

Do not paste credentials into command arguments, transcripts, reports, or source files. If credentials/budget are absent, record `SKIPPED_NOT_CONFIGURED`; this does not block provider-free readiness. A configured-provider failure is reported honestly and must not be relabeled as a passed provider-backed run merely because authored fallback completed.
