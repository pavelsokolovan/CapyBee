# Spec 28.4 — Game Client Recovery and Release Acceptance

**Type:** Implementation instruction
**Parent:** [Spec 28 — Web RPG Client](28-client-rendering-contract-instruction.md)
**Depends on:** Specs [28.1](28.1-game-client-contracts-and-transport-instruction.md), [28.2](28.2-game-preparation-and-start-instruction.md) and [28.3](28.3-gameplay-renderer-and-run-controls-instruction.md)
**Baseline:** `48bb38b`, inspected 2026-11-14; see the parent for evidence and verification limits.
**Status:** Implemented
**Primary outcome:** The integrated browser/PWA client survives interrupted connections, restart, auth restoration and competing tabs without duplicate paid starts, cross-account commands, private-text persistence or false progress claims.

## 1. Recovery ownership

Finish and verify the policies introduced in 28.1 across the real app lifecycle.
Use the existing auth and sync loop; do not register a second periodic flusher
or an effect that starts games whenever the app becomes active. Tests must
exercise React effect cleanup/remount as well as explicit user events.

Game queue keys/records and non-sensitive operation markers are scoped to the
authenticated stable owner ID, never an email or display name. The server still
derives ownership from the session; a local owner key is not authorization.
Compare the owner again before dispatch and before applying a response.

On logout/account change: abort/detach reads, stop game polling, clear in-memory
views/drafts, and remove outgoing game actions/markers belonging to that owner.
Do not clear unrelated unsynced check-ins/memories or reinterpret them as game
actions. On temporary auth expiry, retain only permitted markers/non-text queue
records and pause dispatch. Same-owner restoration reconciles; different-owner
restoration never replays the previous owner's work.

Migration of pre-28 ownerless game queue entries must fail closed: remove them
without dispatch and show a generic check-saved-game/reconfirm notice to the
current user. Never assign them to whoever signs in next. Do not render their
payloads or copy them into logs. Leave existing non-game queue migration rules
unchanged.

## 2. Offline behavior

Generation and mechanical execution remain on the server. While disconnected,
the currently mounted accepted scene may stay readable in memory. No persistent
story cache or offline engine is added; cold offline launch shows the existing
app shell and a localized reconnect message rather than a made-up saved view.

The player may queue one explicitly selected non-text command from the current
accepted scene. Keep that scene/revision frozen with Waiting for connection /
Czekamy na połączenie. Disable further game commands. There is no speculative
next scene or claim that the selection succeeded. A user may remove an action
only while it is demonstrably unsent; a sent/ambiguous action must first be
reconciled and cannot be replaced with another choice.

Starts and free-text submissions are disabled offline with an explanation.
They do not silently wait in IndexedDB for reconnect. The app's general pending
count must not label a transient paid start as a durable offline action.

On reconnect, recover pending identities before presenting new controls. Reuse
the exact durable command ID/revision/payload; use GET status first after an
ambiguous send. Handle a higher server revision or non-ACTIVE run as a stale
intent, remove it after reconciliation and show the actual saved state. Never
rebase the command onto a new scene or mint a new UUID to overcome a conflict.

Queue exhaustion is a recoverable attention state, not proof of failure. Offer
Check status and, only after a proved unsent/not-applied outcome, an explicit
retry of the original safe action. Do not retain or recreate text payloads.

## 3. Slow requests, restart and publication

Exercise wait-then-poll through the production HTTP/session/persistence paths.
Browser timeouts are shorter than or independent of total engine operation
time; they must not cancel/restart paid work. A delayed worker is handled by
status queries, not by repeated starts.

After browser/PWA reload:

1. Restore authentication through the existing mechanism and confirm the owner.
2. Read the minimal operation marker and query its status, if present.
3. Fetch a known run and current run as needed, without deriving private IDs.
4. Adopt only an identity-verified server summary and its revision.
5. Resume command polling, or show explicit unknown/reconfirmation recovery.

A server restart can erase an unpublished dynamic operation. A not-found
operation is not permission to repost its lost body or claim cancellation.
Apply 28.2's unknown-outcome flow. Successfully published dynamic games restore
their exact accepted definition/content from PostgreSQL, with no blueprint
regeneration. New-start/profile/provider disablement must not prevent normal
read/command/resume while the game API is enabled.

Cancellation tests must prove the ordered winner introduced in 28.1, including
cancel-before-start, during provider work, immediately before activation and
after publication. Do not promise that network cancellation reverses a charge.
The prior current run is unchanged if cancellation/failure wins before atomic
replacement; a publication winner remains available through Continue.

## 4. Competing tabs and devices

Coordinate same-browser game dispatch with a bounded owner/run lock using Web
Locks where supported and an IndexedDB transactional lease fallback elsewhere.
Do not build a lease with a read-then-write localStorage race. Expire leases
after crashed tabs and use content-free notifications (IDs/revisions only).
If safe coordination is unavailable, disable background game dispatch and
require foreground status reconciliation; never claim a guaranteed lock.

The server revision/idempotency contract remains authoritative for competing
devices. A second tab/device can make a selected scene stale. One command may
win; the other reconciles without automatic rebasing. Broadcast notifications
must not contain draft text, generated prose or snapshots. A stale tab cannot
overwrite a newer revision on visibility change.

## 5. Service worker and data boundary

Preserve `/api/` NetworkOnly and navigation fallback exclusions in
`app/ui/vite.config.ts`. No service worker, Cache Storage or persistent query
cache may store game API responses or private drafts. Add `Cache-Control:
no-store` consistently to authenticated game read/write/error responses where
missing, including Pack run/command responses; retain same-origin/auth checks.

Only static shell/assets are precached. A service-worker update/reload must
recover through operation markers and server state, not resubmit an effect.
Existing mini-game offline results and other offline writes continue to work.

Inspect actual browser storage using a unique private sentinel in both setup
and gameplay text tests. Inspect IndexedDB, local/session storage, Cache
Storage, history/URL, console and captured test logs. The sentinel must not
appear outside the transient request/textarea. Accepted story data may reflect
the fictional idea; do not confuse that with retaining the raw input body.

## 6. Integrated acceptance matrix

Use deterministic generation/reviewer/input-guard doubles through an explicitly
test-only host boundary. They must be unavailable in the production profile and
must not bypass ownership or production persistence. Use PostgreSQL 16 for
migration/restart tests. No paid provider call is required or permitted by this
specification's automated gates.

| Scenario | Required result |
|---|---|
| Authored Pack with choices, text, advance and places | Legal commands reach an ending through real HTTP |
| Generated Pack with reviewed fallback | Generated/fallback behavior is labeled honestly; no implicit dynamic start |
| Dynamic preparation/start, delayed `202`, lost response | One confirmed attempt, status polling, one accepted saved run |
| Browser reload during start/command | IDs recover; no hidden POST with a reconstructed body |
| Server restart after publication | Exact dynamic run/revision/game fingerprint resumes without blueprint calls |
| Server restart before publication | Unknown outcome requires explicit recovery/review; no automatic paid retry |
| New starts/profile/provider disabled after save | Existing run remains readable and commandable |
| Offline non-text choice, reconnect, acknowledgement lost | One intent/UUID, authoritative reconciliation, no speculative advance |
| Offline text/start attempt | No POST or durable private body |
| Two tabs/devices select different options | One wins or both reconcile; no rebase/duplicate application |
| Auth expiry then same/different account | Safe same-owner recovery; zero cross-owner dispatch/content |
| Dynamic replacement fails/cancels | Previous current run survives; successful replacement is atomic |
| Stale profile/view contract or malformed response | Safe localized state; no guessed setup or command |
| Reopen completed/abandoned game | Correct ending, no reward or command replay |
| Game API/new starts/client rollout disabled | Correct availability messaging; mini-games remain usable |
| EN/PL, 360px/desktop, zoom, keyboard/reduced motion | Readable, accessible, stable navigation/focus |

Add maintainable browser integration automation for the critical start/play/
reload/recovery paths. Prefer a small Playwright test suite if the existing
Vitest/happy-dom setup cannot exercise real browser persistence/service workers.
Keep test-only dependencies/configuration explicit; do not rewrite the whole
UI test stack. Assert state/network effects, not screenshots alone. Include
sanitized failure evidence without story/text/database dumps.

## 7. Required checks and release claim

Run focused tests first, then the repository gates:

```powershell
mvn -f app/engine/pom.xml clean verify
mvn -B -f app/pom.xml -pl server -am verify
```

In `app/ui`, run `npm run test:coverage`, then from the repository root run
`./scripts/dev-workflow.ps1 -Action sync`. Run the new browser integration suite
against the integrated Spring-served build, not Vite alone. Verify both static
destinations are current. Perform the manual accessibility/navigation/PWA cases
that automation does not prove.

Rerun the existing package/verifier/offline certification and PostgreSQL release
gate when engine/session/public DTO or packaged host behavior changed across
28.1–28.4. The inherited backend migration-test and workflow-definition failures
must be resolved and their gates pass before a release claim. Do not convert
them into skipped tests or claim they are resolved because unrelated UI tests
pass. Fixes should be focused and documented separately from client behavior.

Paid live certification remains separately opt-in under the existing operator
policy. Offline deterministic acceptance proves client integration and restart
behavior; it does not prove current live-provider story quality or cost.

## 8. Documentation and completion

Add `docs/game-web-client.md` describing configuration, published audience/profile
policy, disclosure revision, online/transient exceptions to offline writes,
unknown operation recovery, owner cleanup and how to stop new paid starts while
preserving saved-run access. Update the specification index, client contract
fixtures and relevant scoped instructions to match implemented behavior.

Record content-free acceptance evidence: tested revision, test commands and
outcomes, browser versions, viewports, restart/offline cases and known limits.
No credentials, provider response bodies, private prompts, transcripts or
snapshots belong in that note. Enabling production generation is a separate
operator action, not an automatic consequence of a successful test.

28.4 is complete when the matrix and required gates pass, queue/auth/PWA
regressions are covered, and the documentation reflects verified behavior.
Then mark 28.4 and the parent implemented and commit with the repository
implementation-message convention. Spec 29 remains explicitly unimplemented.


## 9. Implementation evidence — 2026-11-14

Typed non-text intents now use the existing owner-scoped queue/sync loop.
Foreground polling and the queue reconcile the same UUID/revision; ambiguous
sends never become removable unsent choices. Web Locks and transactional,
renewable IndexedDB leases coordinate dispatch. Owner cleanup, cross-tab token
changes, shared auth restoration, stale-account HTTP guards and no-store
responses are implemented without changing mini-game/general offline policies.
Starts/text remain transient; private sentinels and worker caches are checked.

The deterministic Spring/PostgreSQL browser suite is integrated into normal
GitHub Actions. It covers interrupted starts/commands, offline reload, competing
tabs, auth restoration/account changes and the PWA shell. A fresh HTTP host
restores the exact published dynamic game and applies a legal command with
new dynamic starts/generation disabled. Cancellation/restart operation tests
cover non-publication without hidden paid replay.

All local gates passed: 109 frontend tests/coverage, build/static sync, standalone
engine verification, 88 backend tests, integrated Chromium acceptance,
package/verifier/failure injection, authored/dynamic offline certification and
packaged PostgreSQL migration/restart compatibility. The release harness's
Linux process launch and empty-issuer configuration were fixed; production
OAuth configuration and default rollout flags remain unchanged.

See [operator documentation](../game-web-client.md) and
[content-free acceptance evidence](../game-web-client-acceptance.md) for commands,
environment, exact candidate identity and limits. Deterministic acceptance does
not certify real Google sign-in, live-provider quality/cost, audio screen-reader
output, physical mobile PWA behavior or Windows execution from this Linux host.
The parent is implemented; Spec 29 remains unimplemented. No production
activation or paid live certification is implied.
