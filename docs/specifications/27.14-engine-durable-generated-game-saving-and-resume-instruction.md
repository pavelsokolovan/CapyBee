# Spec 27.14 — Durable Generated Game Saving and Resume

**Type:** Corrective persistence and runtime implementation specification  
**Parent:** Spec 27.13 — Live Provider Certification and Full-Game Release Readiness  
**Depends on:** Specs 26.1 and 27.1–27.13  
**Baseline:** repository commit `f1eebcb`. The current snapshot codec, generated artifact model, session store v1–v3 migration, local and in-memory stores, accepted-command transaction, start recovery path, session-backed CLI, Willow Marsh pack, and relevant tests were inspected while writing this specification. The build was not run.  
**Status:** Ready for implementation  
**Primary outcome:** A player can start Lanterns of Willow Marsh without `--memory`, make accepted choices, stop the Java process, restart it, resume the same generated run without regenerating accepted content, and reopen the completed game.

---

## 1. Purpose

The generated runtime can already represent and resume a full generated game in memory. `SnapshotCodec` round-trips generated artifacts, including their concrete payload types and quality stamps. The session host also intends to persist the run after every accepted command.

The durable path does not currently preserve that contract. `LocalSessionStore` passes `StoredRun`, `RunSnapshot`, and nested `GenerationArtifact.Payload` values to the general session JSON mapper. `Payload` is a sealed interface with several concrete record types, but the session mapper has no safe polymorphic wire contract for it. A full generated snapshot can therefore fail while the same snapshot succeeds through `SnapshotCodec`. During start, that persistence failure is caught as a generic runtime failure, the lease is released, and later polls schedule the same start again. The player sees repeated `PREPARING` behavior instead of either a saved game or a durable failure.

This specification closes that narrow blocker. It makes the existing snapshot codec authoritative inside the local store, preserves authored saves, defines the accepted-choice save boundary, and proves active and completed generated runs survive reopen. Script correctness and real second-JVM route tests remain in Spec 27.15. Console encoding and normal-play polish remain in Spec 27.16.

## 2. Current implementation findings

| ID | Finding | Consequence |
|---|---|---|
| F1 | `SnapshotCodec` explicitly writes and reads every `RunSnapshot` field. | Reuse it; do not create a second generated-snapshot format in the session module. |
| F2 | The codec supports THEME, SCENARIO, STORY_PLAN, CAST, QUEST, SCENE, and planned SCENE payloads. | A durable run must retain all initial and lazy generated content. |
| F3 | Planned scene payloads may contain structured endings and objective notes. | Ending prose and objective-specific ending text must survive completion and reopen. |
| F4 | Artifact schema v3 requires a `QualityStamp`. | Evaluator version, profile IDs/fingerprints, decision, advisory codes, and report fingerprint must round-trip exactly. |
| F5 | `SessionJson` is a plain `ObjectMapper`; `LocalSessionStore.RunData` currently contains `StoredRun` directly. | General record binding is not a valid decoder for the polymorphic generated payload graph. |
| F6 | Local store v3 writes a checksummed envelope and supports v1/v2 migration. | Introduce the new snapshot wire form through an explicit store migration, not an unversioned shape change. |
| F7 | `processCommand` groups snapshot save, outbox append, prefetch cleanup, and command completion in one transaction. | Preserve this transaction as the automatic-save boundary. |
| F8 | Rejected commands complete their command record without advancing or replacing the snapshot. | Rejection remains durable evidence but is not an accepted-choice save. |
| F9 | `Engine.resume` restores its generation pipeline from snapshot artifacts. | Correct persistence is sufficient to prevent regeneration of already accepted content. |
| F10 | Prefetched artifacts are stored separately from the accepted snapshot. | They are cache data; they must either use the same artifact codec or be safely discarded, never block recovery of the accepted snapshot. |
| F11 | `processStart` releases the lease on an unexpected runtime failure and leaves the run `PREPARING`. | A deterministic start or save failure can be retried forever by polling. |
| F12 | `SessionConsole.awaitActive` eventually fabricates a local failed summary without durably changing the run. | Restart can re-enter the same preparation loop. |
| F13 | `findCurrent` intentionally selects only `PREPARING` or `ACTIVE` runs. | Completed games need an explicit reopen path; they must not be mistaken for a new current active game. |
| F14 | Existing local-store tests cover authored snapshots and store recovery but not full generated snapshots. | Add generated codec and local-store fixtures that exercise every payload family. |

## 3. Goals and non-goals

### 3.1 Goals

1. Persist and load complete generated `RunSnapshot` values through `SnapshotCodec`.
2. Preserve theme, scenario/story plan, cast, quests, generated scenes, planned endings, provenance outcomes, and quality stamps exactly.
3. Keep authored snapshots and existing v1, v2, and v3 authored stores readable.
4. Save every accepted command atomically before reporting it as applied.
5. Resume from the last committed accepted snapshot without regenerating any artifact already present there.
6. Keep an ended generated snapshot and its result available after the store is closed and reopened.
7. Turn start/generation/persistence failure into a stable terminal result instead of repeated `PREPARING` retries.
8. Preserve command idempotency, outbox ordering, revisions, leases, generation ledgers, and optional prefetch behavior.
9. Add focused generated snapshot, local-store, service, and CLI-level reopen tests.
10. Keep standard verification provider-free and deterministic.

### 3.2 Non-goals

- Changing generated game schemas, prose rules, trusted mechanics, or Willow Marsh content.
- Adding a new snapshot codec or enabling Jackson default typing.
- Persisting provider prompts, raw responses, credentials, or transient free-text setup input.
- Replaying an interrupted accepted command automatically.
- Requiring prefetched content to survive a crash; prefetch remains an optional cache.
- Proving restart in a second operating-system process; Spec 27.15 owns that gate.
- Changing script EOF/rejection/pending-command semantics; Spec 27.15 owns them.
- Adding UTF-8 console setup or command usability changes; Spec 27.16 owns them.
- Implementing the broader archive/export/retention work beyond what is already present from Spec 27.10.

## 4. Decisions

| ID | Decision |
|---|---|
| D1 | `SnapshotCodec` is the sole durable codec for `RunSnapshot`, including generated artifacts. |
| D2 | The store embeds the codec's JSON object as structured JSON, not as an escaped JSON string. |
| D3 | The local store format advances from v3 to v4 because the snapshot wire representation becomes explicit and older readers must reject it rather than misread it. |
| D4 | Store v4 keeps the existing envelope, checksum, revision, backup, temporary-file, quarantine, and locking model. Only the data DTO and migration boundary change. |
| D5 | v1–v3 authored snapshots remain readable. They are decoded by a narrowly scoped legacy reader and normalized to the v4 canonical snapshot form on the next committed write. |
| D6 | No general polymorphic type metadata, class names, or Jackson default typing may appear in a save file. |
| D7 | A snapshot codec parse containing any error makes that run/store candidate invalid under existing corruption and recovery rules. Warnings alone do not discard a valid snapshot. |
| D8 | Separately persisted prefetch artifacts use the artifact encoding owned by the snapshot codec. If a legacy prefetch row cannot be decoded, discard that cache row and retain the accepted run. |
| D9 | An accepted command is successful only after the transaction containing the snapshot, status, revision, events, command completion, and related prefetch invalidation commits. |
| D10 | Generated runs in `ENDED` status retain their full final snapshot. Reopen is read-only and makes no provider call. |
| D11 | A caught start failure is terminal for that start attempt. It is persisted as `FAILED` with a stable safe code; polling does not reschedule it. |
| D12 | An actual process death may leave `PREPARING`; after lease expiry a later process may perform one recovery attempt. A failure in that attempt is also terminal. |
| D13 | If the store itself cannot persist either the snapshot or a failed status, the CLI exits with the existing storage/service error. It must not claim the run was saved. |
| D14 | Standard tests use local provider doubles and authored fallback only. They make no network call and read no provider credential. |

## 5. Store v4 wire contract

### 5.1 Envelope

The v4 envelope retains the v3 fields:

```json
{
  "format": "capybee-session-store",
  "version": 4,
  "storeId": "uuid",
  "storeRevision": 12,
  "writtenAt": "2026-10-22T12:00:00Z",
  "checksumAlgorithm": "SHA-256",
  "checksum": "base64",
  "data": {
    "format": "capybee-session-store-data",
    "version": 4,
    "runs": []
  }
}
```

All v3 durability rules continue to apply. The checksum is calculated over the canonical encoded `data` object exactly as the implementation currently does. Candidate selection still chooses the highest valid store revision.

### 5.2 Run DTO

The wire DTO must separate session metadata from the snapshot codec boundary. Its conceptual form is:

```json
{
  "run": {
    "id": "uuid",
    "owner": { "value": "local-console" },
    "packId": { "value": "lanterns-of-willow-marsh" },
    "packVersion": "1.0.0",
    "locale": { "value": "en" },
    "status": "ACTIVE",
    "revision": 3,
    "snapshot": { "snapshotVersion": 1, "runId": "uuid", "state": {} },
    "pendingStart": null,
    "lease": null,
    "failureCode": null
  },
  "commands": {},
  "events": [],
  "prefetch": {}
}
```

The exact representation of unchanged metadata may follow the existing v3 form. The required boundary is:

- before writing, call `SnapshotCodec.toJson(snapshot)` and parse that result as a JSON object for the `snapshot` field;
- while reading, serialize only the `snapshot` JSON node and call `SnapshotCodec.fromJson`;
- construct `StoredRun` only after the codec returns a non-null snapshot with no error issues;
- never ask `SessionJson` to infer a `GenerationArtifact.Payload` implementation;
- never duplicate the private snapshot codec logic in `LocalSessionStore`.

Implementation may add a small session wire adapter/DTO. It must not make Jackson APIs part of session domain ports.

### 5.3 Canonical generated content

The v4 snapshot must round-trip all supported artifact payloads:

| Content | Required fields |
|---|---|
| Theme | title, premise, tone tags |
| Scenario | title, premise, setting, beats |
| Story plan | title, premise, setting, themes, story promises, phase plans and their actor/objective/tone/role links |
| Cast | slot ID, trusted actor ID, name, description |
| Quests | trusted objective ID, title, description |
| Scene | trusted scene ID, title, narration, dialogue, choice labels |
| Planned scene | scene content, actor slots, continuity facts, optional structured ending |
| Ending | headline, summary, objective notes, reflection |
| Provenance | artifact version, pack/version/locale, stage, template ID, artifact ID, `GENERATED`/`REPAIRED`/`FALLBACK` outcome |
| Quality | evaluator version, profile ID/fingerprint, decision, sorted advisory codes, report fingerprint |

Order remains meaningful for the artifact list, phase list, dialogue, choices, objective notes, and continuity facts. The codec's existing normalization rules remain authoritative for sorted sets/advisory codes.

### 5.4 Prefetch rows

A v4 prefetch row may be persisted only if its `GenerationArtifact` can be encoded and decoded by the same artifact logic used by `SnapshotCodec`.

One of these implementations is acceptable:

1. expose a bounded artifact node/string adapter from `SnapshotCodec`; or
2. introduce a core JSON helper used internally by `SnapshotCodec` and by the session wire adapter.

It is not acceptable to create a third payload switch in the session module. A malformed or unsupported prefetch artifact is removed during recovery and reported through existing safe recovery diagnostics; it does not invalidate a valid accepted snapshot. Once a prefetched artifact is merged into an accepted snapshot, the snapshot copy is authoritative.

## 6. Backward compatibility and migration

### 6.1 Supported inputs

The v4 reader must accept:

- empty/new stores;
- v1 and v2 documents supported by the existing migration path;
- checksummed v3 authored stores;
- v3 stores containing a `PREPARING` generated run with no snapshot;
- v4 authored and generated stores.

Future versions remain `STORE_VERSION_UNSUPPORTED` and are never downgraded.

### 6.2 Legacy authored snapshot reader

The v1–v3 compatibility reader is allowed to decode the previous record-shaped snapshot only when:

- the store version is 1, 2, or 3;
- the artifact list is absent or empty; and
- all existing authored snapshot validations pass.

This path must be isolated and test-named as legacy behavior. It must not become an alternative generated snapshot codec. If a legacy document contains a non-empty artifact list that cannot be proven valid, fail/recover with the existing store corruption rules instead of guessing payload classes.

### 6.3 Rewrite behavior

Opening a legacy store is read-only with respect to the bytes on disk. On the first real mutation:

1. convert all valid snapshots to the canonical `SnapshotCodec` representation;
2. write one v4 commit with the next store revision according to the existing migration policy;
3. retain the previous valid file as backup;
4. preserve command IDs/MACs, revisions, events, lifecycle state, counters, and generation ledger values.

Opening and closing without mutation must not silently rewrite the store.

### 6.4 Compatibility invariants

For every migrated authored run:

- `SnapshotCodec.toJson(before)` equals `SnapshotCodec.toJson(after)`;
- status, run revision, scene, trusted state, result, and end reason are unchanged;
- no generated artifacts are invented;
- completed authored games still reopen;
- command replay and outbox sequence remain unchanged.

## 7. Automatic save transaction

### 7.1 Accepted choice

For every accepted `Choose`, `SubmitText`, `Move`, or other accepted engine command, one outer session-store transaction commits:

1. the full post-command snapshot encoded through `SnapshotCodec`;
2. `ACTIVE` or `ENDED` status derived from that snapshot;
3. run revision incremented exactly once;
4. stable outbox events for the command;
5. command-log completion with `accepted=true` and the same revision/events;
6. removal of consumed or invalidated prefetch rows;
7. generation ledger changes already completed for that command.

The command outcome may be returned/displayed only after this transaction succeeds. There is no additional `/save` requirement for accepted progress.

### 7.2 Rejected choice

A rejected command:

- does not change or rewrite the accepted snapshot;
- does not increment run revision;
- persists its completed rejected command record for idempotent replay;
- returns a rejected outcome only after that command record commits.

### 7.3 Commit failure

If snapshot encoding, validation, or disk commit fails:

- roll back snapshot, status, revision, events, command completion, prefetch changes, and ledger changes to the last committed store state;
- do not return `APPLIED`;
- release/expire the lease safely;
- return the existing safe service/storage failure;
- allow a fresh process to reopen the last committed accepted snapshot.

No partial accepted choice may be visible after reopen.

### 7.4 Completion

The command that reaches an ending is saved by the same transaction. The committed run has:

- `status=ENDED`;
- final revision and step;
- final trusted counters, flags, sets, objectives, outcome/result, and end reason;
- every accepted generated artifact, including the structured ending and quality stamp;
- final command and outbox evidence.

## 8. Resume and regeneration rules

### 8.1 Active run

Reopening an active run must:

1. load the last committed snapshot through `SnapshotCodec`;
2. validate pack ID/version and locale through the normal engine resume path;
3. restore `GenerationPipeline` from `state.generationArtifacts`;
4. render the saved current scene and choices;
5. make zero provider calls for theme, scenario/story plan, cast, quests, and scenes already present in the snapshot.

Generation may occur only for a future lazy slot not already accepted or validly prefetched. Resuming is not itself permission to regenerate an accepted artifact.

### 8.2 Prefetch on resume

After the accepted snapshot is restored, normal prefetch may schedule future reachable scenes. Tests that assert zero calls during resume disable prefetch or distinguish prefetch calls from demand calls. A discarded legacy/corrupt prefetch row may be regenerated as cache data, but accepted snapshot artifacts remain unchanged.

### 8.3 Completed run

An ended run remains addressable by run ID and through the saved-game/reopen flow already defined by the session lifecycle:

- loading it returns `ENDED` and its final view/result;
- the CLI prints the saved ending/result and exits successfully;
- no start job, command job, prefetch, repair, or provider call is scheduled;
- reopening does not change store revision or run timestamps merely to render the result;
- a new game requires an explicit new-game action.

### 8.4 Idempotency

Reusing a completed command ID with the same payload returns the logged outcome and current saved view without applying effects or appending artifacts/events again. Reusing it with a different payload remains `COMMAND_ID_REUSED`.

## 9. Terminal preparation failure

### 9.1 Required failure codes

Add a stable public `START_FAILED` error for an unexpected engine/generation failure after authored provider fallback has been exhausted or for a generated snapshot that cannot be validated for saving. Continue using:

- `START_REJECTED` for normal pack/input validation rejection;
- `START_TIMEOUT` for the bounded start TTL or player-visible wait limit;
- existing `STORE_*`/`SERVICE_UNAVAILABLE` behavior when durable storage itself is unavailable.

Messages are safe and content-free. Do not expose exception text, prompts, provider output, or filesystem internals.

### 9.2 State transitions

For a live worker:

```text
PREPARING --successful start + committed snapshot--> ACTIVE or ENDED
PREPARING --validation rejection------------------> FAILED / START_REJECTED
PREPARING --unexpected start failure---------------> FAILED / START_FAILED
PREPARING --TTL exhausted--------------------------> FAILED / START_TIMEOUT
```

When `engine.start` or snapshot encoding fails, `processStart` must attempt to mark the run failed while it still owns the lease. It must not merely release the lease. `get` never schedules a start for a `FAILED` run.

### 9.3 Process interruption

If the process dies before it can persist a result, the durable row may remain `PREPARING` with an expired lease. A later process may claim and retry that interrupted start once under the existing recovery contract. Any ordinary exception in that recovery attempt persists `START_FAILED`. If bounded retry identity/count metadata is needed to distinguish a crash from repeated polling, add it to store v4; do not use an in-memory-only counter as the final guard.

### 9.4 CLI wait behavior

`SessionConsole.awaitActive` must not fabricate a failed `RunSummary` while leaving the store `PREPARING`. At the wait boundary it must request a durable timeout/failure transition through the session service, then render the stored code and a clear next action. If that write fails, exit with the storage error.

Expected player-facing shape:

```text
START_FAILED
  The game could not be prepared. Start a new game or check the saved-game status.
```

Exact warm wording may follow existing console style, but the stable code is required.

## 10. Validation and safety

On every decoded generated snapshot, require:

- supported snapshot and artifact schema versions;
- run ID agreement between session metadata and snapshot;
- pack ID/version and locale agreement;
- `ENDED` status iff the snapshot is ended;
- stage/payload compatibility;
- unique artifact identity according to the existing generation restore rules;
- required v3 quality stamps;
- valid trusted IDs and bounded lists/strings as enforced by existing codec/engine validators.

Do not log full snapshots or generated prose on failure. Tests may use synthetic non-sensitive fixtures but production diagnostics remain content-free.

Snapshot persistence must continue to exclude transient free-text setup values under Spec 27.8. This specification does not weaken that rule.

## 11. Required tests

### 11.1 Snapshot codec round-trip

Add a focused core test that builds one snapshot containing:

- THEME;
- SCENARIO and/or STORY_PLAN with all nested phase fields;
- CAST with multiple members;
- QUEST with multiple objectives;
- ordinary SCENE;
- planned SCENE with continuity facts and structured ending;
- `GENERATED`, `REPAIRED`, and `FALLBACK` provenance across the fixture set;
- quality stamps with pass/advisory decisions and advisory codes.

Assert:

```text
decoded issues are empty
decoded snapshot equals original snapshot
toJson(decoded snapshot) equals toJson(original snapshot)
GenerationPipeline.restore accepts decoded artifacts
```

Also retain malformed/unknown payload, unsupported version, missing quality stamp, and unknown-field rejection coverage.

### 11.2 Local store generated snapshot

Extend `LocalSessionStoreTest` to:

1. create a generated run;
2. save a complete generated snapshot;
3. close the store;
4. reopen the same directory;
5. compare canonical snapshot JSON, status, revision, command diagnostics, events, and generation usage;
6. resume it through the real engine with a provider double that fails the test if called for restored content.

The fixture must cover the content table in Section 5.3, not only one `ScenePayload`.

### 11.3 Authored compatibility

Keep existing authored persistence tests and add fixtures for:

- one v1 authored store;
- one v2 authored store;
- one checksummed v3 authored active store;
- one v3 authored ended store.

Each opens in v4, preserves canonical snapshot state, and rewrites only after a real mutation. A future v5 remains unsupported.

### 11.4 Accepted-choice autosave

At the session-service level, use a real `LocalSessionStore` directory and assert:

- every accepted choice increments the revision once and is visible after close/reopen;
- a rejected choice does not change snapshot JSON or revision;
- the accepted transaction contains matching command/outbox evidence;
- a forced commit failure returns failure and reopens at the prior snapshot;
- replaying the accepted command ID does not duplicate effects, events, artifacts, or provider calls.

### 11.5 Resume without regeneration

Use a counting local provider double:

- generate initial artifacts and an accepted lazy scene;
- close/reopen the store;
- resume and render with call count unchanged;
- choose into the already saved scene with call count unchanged;
- allow a call only when entering a genuinely missing future lazy slot.

Repeat with authored fallback artifacts to prove provider absence is equally durable.

### 11.6 Completed run reopen

Complete a generated fixture through an ending, close/reopen, and assert:

- status is `ENDED`;
- final result/outcome and objective states match;
- final ending payload and quality stamp match canonical JSON;
- reopening performs zero provider calls and zero store mutations;
- commands are rejected as not active, while read/view/result access succeeds.

### 11.7 Preparation failure

Use local doubles for:

- engine start throws unexpectedly;
- snapshot encoding/validation fails;
- start exceeds its bound;
- store write fails.

The first three end in durable `FAILED` with the appropriate stable code and are not scheduled again by repeated `get` calls. Store failure exits clearly and never loops or reports success.

### 11.8 Prefetch

Prove that:

- a valid generated prefetch artifact survives v4 reopen or is deliberately omitted according to the chosen cache policy;
- malformed legacy prefetch is discarded without losing the accepted run;
- merging a prefetched artifact into an accepted snapshot persists it exactly once;
- resume never duplicates that artifact.

## 16. Definition of done

Spec 27.14 is complete when:

- local store format v4 has an explicit `SnapshotCodec` boundary;
- theme, scenario/story plan, cast, quests, scenes, structured endings, provenance, and quality stamps round-trip exactly;
- general session JSON binding never chooses a generated payload implementation;
- existing authored v1–v3 saves still open and preserve state;
- every accepted command is committed atomically before `APPLIED` is returned;
- rejected commands do not change the accepted snapshot or revision;
- closing and reopening an active generated game restores the same canonical snapshot;
- resume and idempotent replay do not duplicate effects, events, or generated artifacts;
- accepted content is not generated again;
- a final accepted command saves an `ENDED` snapshot and final result;
- an ended game can be reopened without generation or mutation;
- start failures and timeouts become durable terminal states rather than recurring `PREPARING` work;
- store failures are clear and preserve the last committed state;
- generated snapshot, local-store, compatibility, autosave, resume, completion, and failure tests pass;
- the full engine verification gate passes offline.

## 17. Handoff to 27.15

Spec 27.15 may assume that one JVM can close a real directory-backed v4 store and another JVM can open the same accepted or ended generated snapshot safely. It must then prove the stronger route-level contract: strict script completion/failure semantics, real saved result/objective inspection, success/partial/postponed routes, a second Java process, and no duplicate effects or artifacts across that process boundary.
