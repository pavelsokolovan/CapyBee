# Spec 27.21 — Blueprint Semantic Validation and Bounded Playability Proof

**Type:** Implementation instruction
**Parent:** Dynamic-game series, following Spec 27.20
**Depends on:** Specs 22–27.20, especially the validated profile contract from 27.18, parsed blueprint contract from 27.19 and generation/repair coordinator from 27.20
**Baseline:** Inspected clean local checkout at commit `4e3fddb` on 2026-10-25. The current code contains the 27.18–27.20 profile, parser and generation contracts, a placeholder `BlueprintSemanticValidator` port and the authored-pack `FullGeneratedGameValidator`. No build or live-provider test was run while preparing this specification; implementers must inspect their current checkout again.
**Status:** Ready for implementation; dynamic blueprints remain non-executable after this specification
**Primary outcome:** A parsed generated-game blueprint can receive a deterministic, content-safe semantic verdict backed by complete bounded exploration. `PASS` proves that the accepted proposal is internally linked, forward-only, live, within route/state limits, and has executable witnesses for every declared ending and objective.
**Repository location:** `docs/specifications/27.21-engine-blueprint-semantic-validation-instruction.md`

---

## 1. Purpose

Specs 27.19 and 27.20 can parse and review a complete model proposal, but parser success proves only bounded shape. A proposal may still contain an unknown reference, a structurally reachable choice whose requirement can never be true, a counter update that escapes its declared interval, an unreachable ending, an impossible objective, or a reachable state with no enabled choice.

This specification adds the first production semantic validator for dynamic blueprints. It must answer a narrow question before compilation:

> Under the exact v1 closed mechanics semantics and trusted profile limits, is every reachable execution safe and live, and does every advertised ending and objective have at least one concrete witness?

The answer is established by deterministic local code. The model never declares itself valid, chooses the exploration budget, supplies a proof, or introduces an evaluator.

## 2. Scope and non-goals

### 2.1 In scope

- Bind every symbolic reference to a declaration in the same parsed blueprint.
- Recheck profile-bound counts, locale, schema version, allowed mechanics and expression/effect limits at the acceptance boundary.
- Validate phase coverage and ordering, start/ending roles, outcome mapping, forward-DAG topology, reachability, liveness and route lengths.
- Define v1 validation semantics for the already reserved condition/effect shapes sufficiently to explore proposals deterministically.
- Explore reachable configurations within the profile's `maxExploredStates` ceiling.
- Prove every ending reachable, every objective achievable, every reachable nonterminal state live, and every reachable state mutation within declared bounds.
- Produce a bounded, immutable semantic evidence object suitable for 27.23 compilation.
- Replace the 27.20 placeholder/fake-only handoff with the production validator while retaining explicit `INCONCLUSIVE` and `UNAVAILABLE` behavior.
- Extract only genuinely reusable graph algorithms from `FullGeneratedGameValidator`, preserving existing Pack behavior.

### 2.2 Out of scope

- Compiling symbols into runtime `Scene`, `Condition`, `Effect`, `Rules` or engine-assigned IDs; that is 27.23.
- Starting a `Run`, publishing a playable game, adding a CLI option, or persisting a definition; those are 27.24, 27.27 and 27.26.
- Adding rule types, scripts, arbitrary expressions, reflection, plugins or model-defined operators.
- Changing the authored-Pack DSL or broadening dynamic v1 mechanics.
- Narrative quality, language fidelity or output safety review; 27.20 owns accepted-output review and 27.25 owns generated prose quality.
- Proving that every objective completes on every route. V1 requires a witness for each objective, not universal completion.
- Proving subjective puzzle difficulty, fun, uniqueness or semantic truth of titles/descriptions.
- Silently repairing, pruning, clamping or completing an invalid proposal.

27.22 will consolidate the closed DSL mapping and runtime parity. It may extract shared evaluator primitives, but it must preserve the observable validation semantics and proof obligations defined here. Review 27.21 and 27.22 together before publishing dynamic execution.

## 4. Trust boundary and public contracts

### 4.1 Validation input

The production entry point receives all four values as one verified context or as explicit parameters:

1. `ParsedGameBlueprint` — untrusted, shape-checked proposal.
2. `ValidatedGeneratorProfile` — profile plus identity/fingerprint established by the loader.
3. `ResolvedGamePreferences` — selected locale and preset IDs bound to that identity.
4. `EffectiveGenerationConstraints` — host-narrowed limits produced for those preferences.

A recommended shape is:

```java
Validation validate(
    ParsedGameBlueprint blueprint,
    ValidatedGeneratorProfile profile,
    ResolvedGamePreferences preferences,
    EffectiveGenerationConstraints constraints);
```

An immutable `BlueprintValidationContext` is also acceptable if its only production factory re-establishes `GenerationProfileTrust.validContext(...)` and captures every required effective bound. A publicly constructible bag marked `trusted=true` is not acceptable.

Before proposal checks, verify profile identity/version/fingerprint equality, selected length/challenge existence, locale membership, all host-narrowed ranges and allowlist subset relationships. An invalid context is an engine/configuration failure, not model feedback. Add an explicit `INVALID_CONTEXT`/configuration result or a typed content-free exception which `BlueprintGenerationService` maps to `BLUEPRINT_CONFIGURATION_INVALID` without spending a repair attempt. Do not map it to `REVIEW_PENDING` or ask the model to fix host configuration.

### 4.2 Validation result

Keep explicit result variants:

| Status | Meaning | Coordinator behavior |
| --- | --- | --- |
| `PASS` | All required checks and complete reachable-state exploration finished within the trusted ceiling. | Return a semantically validated candidate; no compilation or gameplay yet. |
| `REJECT` | One or more deterministic proposal violations were found. | May consume the single remaining 27.20 repair attempt with sanitized codes/pointers. |
| `INCONCLUSIVE` | Validation was correct but the trusted exploration ceiling was reached before the complete proof finished. | Never treat as PASS. It may use the same one remaining repair attempt; limits are unchanged. |
| `UNAVAILABLE` | The required production validator capability is absent or deliberately disabled. | Return controlled non-executable pending/failure behavior as in 27.20; no model repair. |
| `INVALID_CONTEXT` | Profile/preferences/constraints cannot establish the trusted envelope. | Fail as configuration/internal integration error; no model repair. |

Unexpected bugs are not `INCONCLUSIVE`. Preserve fail-closed behavior, return a content-free internal failure, and do not expose exception messages or partially explored content.

### 4.3 Validated proposal and evidence

On PASS, create an immutable `SemanticallyValidatedBlueprint` (exact name may follow conventions) containing:

- the exact parsed blueprint instance/content,
- profile identity and fingerprint,
- selected locale, length preset and challenge preset,
- semantic contract version,
- validator implementation version,
- derived scene/edge/configuration counts,
- derived minimum and maximum executable transition counts,
- witnessed ending IDs and objective IDs in declaration order,
- a deterministic evidence digest over engine-owned structural facts if useful downstream.

Do not include paths containing narrative text, suggestion text, prompts, provider output, rejected values or a transcript. Evidence is proof metadata, not a durable definition fingerprint; 27.26 owns durable canonical encoding and integrity.

The validated wrapper must not have a public unchecked constructor. `ReviewPending` continues to carry only a parsed proposal. `CandidateReviewed` must carry the validated wrapper (plus 27.20 review/provenance evidence) or an equivalent capability that cannot be confused with parser success. Its `toString()` is redacted.

## 5. Deterministic validation pipeline

Run checks in the following order. Collect independent cheap issues where safe; skip dependent analysis after prerequisites fail so invalid references cannot crash exploration.

1. **Trusted context** — identity, selected presets, locale and every effective bound.
2. **Defensive envelope** — schema version, locale, counts, phase list, allowlists, expression/effect limits and declaration bounds.
3. **Symbol indexes** — actors, objectives, scenes, outcomes, counters, flags and sets.
4. **Cross-references** — phases/scenes, destinations, endings, state references and visited-scene references.
5. **Static graph** — start, phase direction, cycles, structural reachability, ending coverage and coarse path bounds.
6. **Expression relevance** — declaration-relative thresholds/values and statically impossible atoms that can be identified without exploration.
7. **Bounded configuration exploration** — exact enabled choices, ordered effects, visits, objective evaluation, liveness, route bounds and witnesses.
8. **Evidence construction** — only after complete exploration and zero rejection issues.

Use declaration/array order for iteration, stable maps/sets for indexes and deterministic issue ordering. Do not let hash iteration, thread scheduling or locale-sensitive collation change results.

The validator is pure with respect to the engine: no provider calls, filesystem access, wall clock, randomness, ID source, Pack loading, runtime start, logging of content or mutation of the parsed blueprint.

## 6. Defensive envelope and symbol binding

### 6.1 Rechecked bounds

Recheck at semantic acceptance even if the parser already checked them:

- blueprint schema version is 1 and locale equals the selected game locale exactly;
- scene count is within effective min/max;
- actor, objective and ending/outcome counts are within profile min/max;
- each decision choice count is 1–effective `maxChoicesPerScene`;
- counter/flag/set counts fit the selected challenge and effective capacities;
- set value count, counter declarations and deltas fit profile limits;
- every condition/effect type belongs to both the profile and selected challenge/effective allowlists;
- every condition tree fits effective depth and profile/effective node limit;
- every choice fits the effective effect count;
- all five `PhaseKind` values occur once in engine order.

Host ceilings currently do not cover every profile capability. Where there is no host override, the effective value is the trusted selected-profile value. Do not interpret a missing field as zero, unlimited or an engine constant chosen by the validator.

### 6.2 Namespaces and references

Build separate indexes and reject every unresolved or wrong-namespace reference:

- phase `actorIds` and scene `actorIds` → actor declarations;
- phase `objectiveIds` and scene `objectiveIds` → objective declarations;
- choice destination → scene declaration;
- ending `outcomeId` → outcome declaration;
- counter conditions/effects → counter declarations;
- flag conditions/effects → flag declarations;
- set conditions/effects → set declarations, with a declared set member where applicable;
- `VISITED_SCENE` → scene declaration.

Local parser uniqueness is defensively rechecked. References never create declarations. IDs from different namespaces may share spelling only if 27.19 allows it; the binder must still resolve by expected kind.

Every declared actor and objective must appear in at least one phase plan and at least one reachable scene plan. This is planning coverage only; it does not make prose truthful. An unused state declaration is not by itself a playability failure: it remains bounded and may be rejected by the existing output-quality review when it is decorative or narratively inconsistent. `VISITED_SCENE` may provide state-free objective mechanics.

### 6.3 Outcomes

- Every ending maps to exactly one declared outcome.
- Every outcome is used by exactly one ending.
- Outcome and ending counts therefore match and remain within the selected profile bounds.
- Require at least one `SUCCESS` and at least one non-`SUCCESS` outcome so advertised alternatives are materially distinguishable, preserving the current full-game product contract.
- Do not infer an outcome from text, an objective, an effect or array position.

## 7. Static graph and phase validation

Construct one edge per decision choice from its containing scene to `destinationSceneId`. Ending scenes have no outgoing edges.

### 7.1 Start and phases

- `startSceneId` resolves to a decision scene in `OPENING`.
- Decision scenes use OPENING, DEVELOPMENT, CHALLENGE or RESOLUTION; endings use ENDING.
- An edge may remain in the same phase or advance by exactly one phase.
- Reject backward edges and edges that skip a required phase.
- The graph is acyclic. Same-phase edges are allowed only when they do not form a cycle.
- At least one scene belongs to each phase, and every declared scene is structurally reachable from start.
- Every reachable scene can structurally reach an ending.
- A decision scene has at least one outgoing choice; an ending has none.

Because all nodes must be reachable and all edges are same/next-phase in a DAG, every start-to-ending route passes through the phase order. Do not satisfy phase coverage using an unreachable scene.

### 7.2 Structural route checks

Before state exploration:

- Compute the set of possible structural edge counts, or equivalent bounded evidence, from start to every ending.
- Reject an ending when none of its structural route lengths can fall inside the selected interval.
- Reject the whole graph when no structural start-to-ending route can fall inside the selected interval.
- Reject a reachable decision node which has no structural path to an ending.

Do not reject merely because the raw graph also contains a too-short or too-long route: requirements may make that route inexecutable. §10 must reject every actually executable route outside the interval. A simple global structural minimum/maximum check is therefore insufficient in both directions.

Static reachability is necessary but not sufficient. A required choice may be disabled in every reachable state; only §10 supplies executable witnesses and final route bounds.

### 7.3 Meaningful choice

Do not define meaningful choice as merely `choices.size() >= 2`. Complete exploration must find at least one reachable configuration in OPENING, DEVELOPMENT or CHALLENGE with at least two simultaneously enabled choices that have different semantic transition signatures.

A transition signature includes destination plus ordered effects. Two differently named choices that lead to the same destination with identical effects are not meaningful alternatives. Different requirements alone do not make two simultaneously enabled choices different. A validator may retain stricter distinctions only if documented and tested consistently with 27.22.

## 8. Closed v1 validation semantics

This section fixes the semantics used by the proof. It does not create a second public DSL. 27.22 must map these reserved blueprint nodes to the existing engine mechanics or extract one shared evaluator so validation and runtime cannot drift.

### 8.1 Configuration

A configuration contains:

- current scene ID,
- each counter value,
- each flag value,
- each finite-set membership set,
- visited scene IDs,
- completed objective IDs,
- transition count from start.

Start with declared initial state, the start scene marked visited, objectives whose predicates are already true marked complete, and transition count zero. Objective completion is monotonic; v1 objectives have no `onComplete` effects.

For state deduplication, the semantic key includes current scene, counters, flags, canonical set memberships, visited scenes, completed objectives and transition count. Retaining the count prevents converging routes of different lengths from being merged before exact route-bound evidence is recorded.

### 8.2 Conditions

Evaluate exactly:

| Node | Result |
| --- | --- |
| `COUNTER_AT_LEAST` | current counter `>= value` |
| `COUNTER_AT_MOST` | current counter `<= value` |
| `COUNTER_EQUALS` | current counter `== value` |
| `FLAG_IS` | current flag equals requested boolean |
| `SET_CONTAINS` | declared value is currently a member |
| `SET_SIZE_AT_LEAST` | current set size `>= size` |
| `VISITED_SCENE` | referenced scene is in visited scenes |
| `ALL` | all child conditions are true, evaluated in order without side effects |
| `ANY` | at least one child condition is true, evaluated in order without side effects |
| `NOT` | logical negation of its child |

Choice requirements are evaluated in the source configuration before effects. A null requirement is enabled. Objective predicates are evaluated initially and after every successful transition once the destination has been marked visited.

### 8.3 Effects

Apply a selected choice's effects in array order:

- `COUNTER_ADD`: add the signed delta using a wide intermediate.
- `COUNTER_SET`: replace with the declared integer.
- `FLAG_SET`: replace with the declared boolean.
- `SET_ADD`: add the declared member; adding an existing member is an idempotent no-op.
- `SET_REMOVE`: remove the declared member; removing an absent member is an idempotent no-op.

After all effects, move to the declared destination, mark it visited, evaluate objectives, then test ending status. There are no scene-entry effects in blueprint v1.

Every intermediate counter value after each ordered counter effect must stay within that counter's generated `min..max`. A reachable overflow/underflow is a rejection. Do not model `RunImpl` clamping as success, silently widen the declaration or reorder effects. `COUNTER_SET` values and set members are declaration-relative even on paths where an effect is unreachable.

### 8.4 Static condition relevance

Reject atoms that cannot express a meaningful result relative to declarations:

- counter threshold/equality outside the counter's declared interval;
- set-size threshold greater than the set's declared value count;
- unknown set member;
- a `VISITED_SCENE` reference to an ending from a pre-ending condition when the DAG makes it necessarily future;
- an objective condition that is statically constant only because its threshold is outside declarations.

Do not reject an intentional condition that is true in the initial state or a `NOT`/composite solely for being simple. Exploration, not heuristic algebra, decides reachability. Avoid an exponential SAT simplifier in this specification.

## 9. Objective semantics and witnesses

Evaluate all objective predicates against each reachable configuration using §8. Once true, an objective remains complete for that route. Since blueprint v1 has no objective completion effects and choices cannot reference objective state, this bookkeeping records evidence without changing choice availability.

Acceptance requires:

- every declared objective becomes true in at least one reachable configuration;
- every objective witness lies on a path that can continue to a reachable ending;
- every objective is included in relevant phase/scene planning references as required by §6.2;
- witness evidence records only the objective symbol/index and bounded structural metrics, never narrative text.

An objective need not complete on every route. A FAILURE or PARTIAL_SUCCESS route may leave objectives incomplete. This spec does not automatically require every SUCCESS ending route to complete all objectives because the contract supports optional objectives; any stronger success policy must be introduced explicitly with versioning and tests rather than inferred from the word “success.”

## 10. Bounded reachable-configuration exploration

### 10.1 Algorithm

Use deterministic breadth-first worklist exploration or an equivalent exhaustive finite-state algorithm:

1. Create the initial configuration from declarations and start scene.
2. At a decision configuration, evaluate choices in blueprint order.
3. If zero choices are enabled, record a reachable dead end.
4. For every enabled choice, clone immutable/copy-on-write state, apply ordered effects, enter destination, update objectives and add the canonical configuration if new.
5. At an ending configuration, record its outcome witness and path length; do not expand it.
6. Continue until the worklist is empty or adding another unique configuration would exceed `maxExploredStates`.

Count the initial configuration and every distinct admitted configuration. Do not count condition nodes, attempted duplicate transitions or static graph nodes as explored states. Check the ceiling before allocating/enqueuing an over-limit configuration.

### 10.2 Complete-proof obligations

PASS requires all of the following after the worklist empties:

- no reachable decision configuration has zero enabled choices;
- every reachable transition preserves state declarations;
- every terminal reachable configuration is a declared ending;
- every declared ending has at least one reachable configuration witness;
- every declared objective has at least one witness on a completable route;
- every executable start-to-ending path length is within selected min/max;
- global executable minimum and maximum transition counts are derived and recorded;
- at least one meaningful pre-resolution choice exists under §7.3;
- exploration did not exceed the trusted ceiling.

When a destination structurally exists but every incoming choice is disabled for all reachable source configurations, reject the destination/ending as semantically unreachable. Structural reachability cannot substitute for a witness.

### 10.3 Ceiling exhaustion

If the next distinct configuration would exceed `maxExploredStates` before the worklist is empty, stop and return `INCONCLUSIVE` with `BLUEPRINT_STATE_LIMIT_EXCEEDED`. Do not return partial PASS, infer safety from sampled routes, raise the ceiling, prune a valid branch, or fall back to structural reachability.

The repair coordinator may ask for one simpler complete replacement under the same profile limit. It must not grant another repair counter or increase limits. If the second attempt is also inconclusive, generation ends according to 27.20.

The validated v1 graph is a DAG with at most 24 scenes, so traversal depth is independently bounded. Implement graph algorithms iteratively or with explicit safe depth bounds; no model-controlled recursion may overflow the stack.

## 11. Diagnostics and privacy

Semantic issues use `BlueprintIssue` or a compatible immutable type. They are engine-authored and bounded to at most 100 entries; reserve the final slot for `BLUEPRINT_ISSUES_TRUNCATED`.

Required code families include:

| Family | Example codes |
| --- | --- |
| Context/envelope | `BLUEPRINT_VALIDATION_CONTEXT_INVALID`, `BLUEPRINT_CAPABILITY_VIOLATION` |
| References | `BLUEPRINT_ACTOR_UNKNOWN`, `BLUEPRINT_OBJECTIVE_UNKNOWN`, `BLUEPRINT_SCENE_UNKNOWN`, `BLUEPRINT_OUTCOME_UNKNOWN`, `BLUEPRINT_STATE_UNKNOWN`, `BLUEPRINT_SET_VALUE_UNKNOWN` |
| Coverage | `BLUEPRINT_ACTOR_UNUSED`, `BLUEPRINT_OBJECTIVE_UNPLANNED`, `BLUEPRINT_PHASE_COVERAGE_INVALID` |
| Graph | `BLUEPRINT_START_INVALID`, `BLUEPRINT_ROUTE_BACKWARDS`, `BLUEPRINT_ROUTE_SKIPS_PHASE`, `BLUEPRINT_ROUTE_CYCLIC`, `BLUEPRINT_SCENE_UNREACHABLE`, `BLUEPRINT_ROUTE_DEAD_END`, `BLUEPRINT_LENGTH_INVALID` |
| Ending/outcome | `BLUEPRINT_ENDING_UNREACHABLE`, `BLUEPRINT_OUTCOME_MAPPING_INVALID`, `BLUEPRINT_OUTCOME_VARIETY_REQUIRED` |
| Mechanics | `BLUEPRINT_CONDITION_INVALID`, `BLUEPRINT_EFFECT_INVALID`, `BLUEPRINT_STATE_BOUNDS_VIOLATED` |
| Playability | `BLUEPRINT_CHOICE_REQUIRED`, `BLUEPRINT_OBJECTIVE_UNACHIEVABLE`, `BLUEPRINT_STATE_LIMIT_EXCEEDED` |

Finalize one stable code per condition during implementation; do not emit several aliases for the same failure. Codes are repair API and test contract once released.

Pointers use only known field names and numeric indexes, such as `/scenes/3/choices/1/destinationSceneId`. Never place an untrusted symbol in a pointer. `resource` is a fixed engine-owned value such as `blueprint`. Messages are generic and contain no model text, IDs, titles, descriptions, condition values, provider response or suggestion. The generation service already sanitizes feedback, but the validator must be safe before that layer.

No logs, exceptions, metrics or `toString()` output may contain blueprint prose or rejected symbols. Content-free metrics may contain validator version/status, counts, elapsed duration supplied by an outer observer, limit exhaustion and issue codes.

## 12. Reuse of authored-game graph validation

Extract a small package-private or internal graph-analysis component when implementing cycle detection, reachable sets, can-reach-terminal and DAG path bounds. It should consume engine-owned node ordinals/keys and return facts, not emit Pack- or blueprint-specific issues.

Keep these responsibilities separate:

- `FullGeneratedGameValidator` retains utility-scene collapsing, Pack locale parity, generation slots, authored rule/outcome checks and all historical `PACK_*` diagnostics.
- The blueprint validator retains symbolic binding, state-aware enabled edges, objective witnesses and dynamic profile limits.
- Shared graph code knows neither Pack files nor model text.

Add regression tests proving the refactor produces the same accepted/rejected authored fixtures and issue codes. Do not change Willow Marsh topology, generation catalog, Pack contract, fallback behavior or snapshot formats to make sharing easier.

If safe extraction would create a larger compatibility risk than the duplication removed, leave the authored validator intact and introduce a focused tested graph utility for both in a later mechanical refactor. Reuse is a goal, not permission to destabilize the existing path.

## 13. Integration with 27.20

Wire the production validator into `BlueprintGenerationService` without changing confirmation, safety review, budget or attempt ownership:

- First complete PASS still uses one provider call.
- Semantic REJECT or INCONCLUSIVE may request only the one complete replacement already allowed by 27.20.
- Parser, reviewer and semantic failures share that same attempt counter.
- `UNAVAILABLE`, `INVALID_CONTEXT`, cancellation and internal failures do not consume a model repair.
- Repair feedback contains at most 20 engine codes and numeric/known-field pointers, never evidence paths or rejected values.
- A second semantic failure returns `BLUEPRINT_REPAIR_EXHAUSTED`; no third call or fragment merge.
- `CandidateReviewed` is returned only when output review passed and semantic exploration passed.
- A production dynamic route must not inject `Validation.pass("semantic-v1")` without running the validator. Test fakes remain allowed for focused 27.20 orchestration tests and must be named as fakes.

The in-memory candidate remains non-playable and non-durable. 27.23 is the sole next consumer allowed to convert it into trusted engine structures.

## 14. Required test matrix

All tests are local deterministic JUnit tests. No provider credentials, network, wall clock or random search is required.

| Group | Required evidence |
| --- | --- |
| Context | Profile identity/version/fingerprint mismatch, wrong preset/locale, widened limits and forged effective allowlists fail without repair; all omitted semantic bounds are available from trusted context. |
| Positive fixtures | The independent EN and PL complete proposals pass; at least two passing fixtures differ in topology, state kind and objective predicate. No production scenario constants. |
| References | Unknown actor/objective/scene/outcome/counter/flag/set/member/visited-scene; wrong namespace; all valid forward references resolve. |
| Coverage | Actor/objective absent from phases or reachable scenes; bounded unused state is not falsely treated as a graph/playability error. |
| Phases | Invalid start phase, missing phase scene, backward edge, skipped phase, valid same-phase edge and same-phase cycle. |
| Static graph | Unreachable scene, unreachable ending, non-ending terminal, cannot-reach-ending node, duplicate-equivalent routes, structural min/max exact boundaries. |
| Outcome mapping | Missing/unused/duplicate mapping, no success, no non-success, valid one-to-one 2–4 mappings. |
| Conditions | Every v1 atom/composite, declaration-relative thresholds, depth/node recheck, initial true/false, future VISITED_SCENE, null requirement. |
| Effects | Ordered combinations, add/set interaction, exact counter boundaries, reachable intermediate overflow, unreachable overflow, idempotent set add/remove, set member binding. |
| Liveness | Structurally connected scene with all choices disabled; one enabled branch; requirements becoming enabled after earlier effects; every reachable state has an action. |
| Objectives | Initially complete, completes after effect, completes through VISITED_SCENE, achievable on only one route, impossible objective, witness that cannot reach an ending. |
| Endings | Every ending has an executable witness; structurally reachable but gated-off ending rejected; multiple configurations reaching one ending handled. |
| Length | Executable shortest/longest exact boundaries, too short, too long, gated branch changing effective bounds, converging paths of different lengths retained. |
| Meaningful choice | Two simultaneously enabled distinct transitions pass; two labels with identical destination/effects fail; alternatives never enabled together fail; meaningful choice only in RESOLUTION fails. |
| Exploration | Exact `maxExploredStates` passes; one additional distinct configuration returns INCONCLUSIVE; duplicates do not consume ceiling; traversal order and evidence stable across runs. |
| Status | REJECT, INCONCLUSIVE, UNAVAILABLE and INVALID_CONTEXT have distinct coordinator behavior; only complete PASS creates validated wrapper. |
| Repair | First semantic failure then valid replacement makes exactly two calls; second failure stops; state-limit repair keeps same limit; context failure makes no repair call. |
| Privacy | Synthetic private prose/symbols absent from issues, exceptions, logs, feedback and toString on every status; issue/pointer/count bounds enforced. |
| Immutability | Source collection mutation cannot alter validation input/evidence; exposed collections immutable; validated wrapper has no unchecked public construction path. |
| Authored compatibility | All existing `FullGeneratedGameValidator`, Pack loading, Willow Marsh, fallback binding and generated-run tests retain behavior and `PACK_*` issue codes. |
| Full gate | `mvn -f app/engine/pom.xml clean verify` passes with package coverage at or above existing thresholds; no gate is lowered. |

Add a small test-builder DSL for blueprint records if it makes adversarial mutations readable. Keep it under tests and ensure defaults form a genuinely valid neutral proposal; do not turn one story fixture into hidden production defaults.
