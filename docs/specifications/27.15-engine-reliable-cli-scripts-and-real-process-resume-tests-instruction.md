# Spec 27.15 — Reliable CLI Scripts and Real Process Resume Tests

**Type:** Corrective CLI automation and end-to-end verification specification  
**Parent:** Spec 27.14 — Durable Generated Game Saving and Resume  
**Depends on:** Specs 27.9–27.14  
**Baseline:** repository commit `f1eebcb`, plus the prepared Spec 27.14 durable generated-game save contract. The current session console, certification command, Willow Marsh certification suite and routes, local/in-memory store wiring, result/objective APIs, provider test seams, and CLI tests were inspected while writing this specification. The build was not run. Existing uncommitted specification work was preserved.  
**Status:** Ready for implementation after Spec 27.14  
**Primary outcome:** Automated CLI route tests prove that the success, partial-success, and responsible-postponement routes really finish with the expected trusted result and objective state, use automatic directory-backed saving, and survive a restart in a second Java process without duplicated effects or generated artifacts.

---

## 1. Purpose

The current CLI and certification harness can report a passing route without proving that the game ended correctly:

- script EOF returns exit code 0 even when the run is still active;
- a rejected choice prints issues and continues;
- EOF may arrive while a command is still pending;
- route completion is inferred from process/invocation exit codes;
- evidence sets `actualResult` to the suite's `expectedResult` whenever those exit codes are zero;
- certification creates a real directory path but injects one `InMemorySessionStore` into both invocations;
- the resume checkpoint calls `ConsoleApp` again in the same JVM with the same object;
- accepted-choice counts are obtained by counting script lines, not committed commands;
- saved result, objective state, trusted effects, events, and artifact identity are not inspected.

Those tests can therefore pass when a script stops early, a route reaches the wrong ending, persistence is bypassed, or a nominal resume reuses process memory.

Spec 27.15 turns strict scripts into an assertion-oriented interface and makes route evidence come from the reopened durable store. One route is split across two independently launched JVMs. All provider behavior used by automated tests comes from deterministic local doubles or authored fallback; standard tests remain offline and credential-free.

## 2. Current implementation findings

| ID | Finding | Consequence |
|---|---|---|
| F1 | `SessionConsole.run` returns 0 when `readLine` returns null, regardless of `view.ended()`. | An incomplete script is currently indistinguishable from a completed route. |
| F2 | Rejected command outcomes print issue codes and remain in the loop. | A bad scripted choice can be followed by EOF and still pass. |
| F3 | A command that exceeds the wait bound is retained only as `pendingCommandId`; the next read may be EOF. | Script completion can be reported while mutation is unresolved. |
| F4 | `/quit` returns 0 immediately. | Preserve explicit checkpoint semantics, but distinguish it from accidental EOF. |
| F5 | Certification's `executeRoute` constructs `InMemorySessionStore` and supplies it to both play invocations. | The `store` directory is not the authoritative state and no restart is proven. |
| F6 | `invokePlay` always adds `--memory`. | The route explicitly bypasses local persistence. |
| F7 | Both halves call `new ConsoleApp(...).run(...)` in one JVM. | Static state, objects, executors, or test injection may survive the alleged restart. |
| F8 | `RouteResult` stores the suite's expected result and writes it back as actual on exit-code success. | Evidence is circular and cannot detect a wrong ending. |
| F9 | `acceptedStoryChoices` is `countChoices(lines)`. | It proves fixture syntax, not accepted and committed commands. |
| F10 | Willow Marsh already has three eight-choice routes and trusted outcome IDs/classes. | Reuse these routes and assert their saved runtime truth. |
| F11 | The partial route has `/save` and `/quit` after choice four. | It is the canonical real-process resume route. |
| F12 | `RunResult` exposes outcome ID, result class, objective results, and facts; snapshots expose trusted objective/effect state. | Evidence can be derived without parsing console prose. |
| F13 | Session commands, outbox events, revisions, and artifacts are durable under Spec 27.14. | Use them to prove exactly-once behavior across restart. |
| F14 | Existing tests can inject local `TextGenerator` doubles only within one JVM. | Add a test-only subprocess seam; do not add a production option that loads arbitrary provider code or response files. |

## 3. Goals and non-goals

### 3.1 Goals

1. Make strict script exit status represent actual completion.
2. Return `SCRIPT_INCOMPLETE` when EOF occurs before an ending.
3. Fail immediately when a scripted command or choice is rejected.
4. Fail when a script ends or explicitly quits with an unresolved command, except where a test explicitly expects a pending-failure case.
5. Preserve explicit `/quit` as the successful way to create an intentional resume checkpoint after all prior commands have committed.
6. Run all three Willow Marsh routes and inspect their real saved terminal state.
7. Replace in-memory certification storage with a unique real `LocalSessionStore` directory per route.
8. Launch a second Java process for the partial route and prove it resumes the first process's committed run.
9. Derive actual result, objective state, facts, revisions, command counts, events, and artifact identities from the reopened save.
10. Remove copied `expectedResult` values and line-count-derived completion claims from evidence.
11. Prove restart introduces no duplicate trusted effects, commands, events, provider calls, or generated artifacts.
12. Cover clean provider success, successful repair, and authored fallback using deterministic local doubles only.
13. Keep automated tests offline, bounded, privacy-safe, and cross-platform.

### 3.2 Non-goals

- Reimplementing durable snapshot serialization; Spec 27.14 owns it.
- Testing a live network provider or reading real credentials.
- Treating console transcript text as authoritative game state.
- Adding a general-purpose subprocess/provider plugin mechanism to production CLI.
- Changing Willow Marsh story routes or trusted outcomes.
- Final Windows UTF-8 and normal interactive usability review; Spec 27.16 owns them.
- Requiring every unit test to fork a JVM. Process tests are focused integration tests.
- Making `/quit` mean completed game. It remains an explicit successful checkpoint/exit operation.
- Testing abrupt OS kill at every write instruction; local-store atomicity remains owned by Specs 27.10 and 27.14.

## 4. Decisions

| ID | Decision |
|---|---|
| D1 | Interactive EOF keeps its normal quit behavior. Strict script EOF is an assertion and succeeds only if the view is ended. |
| D2 | Strict script contract failures use exit code 4 and a stable code on stderr. Configuration remains exit 2; session/store failure remains exit 3. |
| D3 | `SCRIPT_INCOMPLETE` means EOF was reached with a non-ended run and no unresolved command. |
| D4 | `SCRIPT_COMMAND_REJECTED` means the engine/session returned a terminal rejected outcome for a scripted mutation. |
| D5 | `SCRIPT_COMMAND_PENDING` means a script cannot finish or checkpoint because its last mutation is still processing. |
| D6 | `/quit` may exit 0 from an active run only after all submitted commands are durably complete. This is the intentional checkpoint contract. |
| D7 | Certification and route integration tests never pass a shared store object and never add `--memory`; each invocation opens the same explicit directory independently. |
| D8 | The partial route uses two child JVMs with different process IDs. The first exits after choice four and `/quit`; the second uses `--continue`. |
| D9 | The parent/reviewer opens the store only after the child has exited and released the lock. |
| D10 | Expected route state remains suite input for gate comparison, but route evidence contains observed values only. |
| D11 | `actualResult` is never assigned from `expectedResult`. The old copied fields are removed rather than renamed. |
| D12 | Accepted-choice count comes from committed accepted command records and/or revision delta, not script lines. |
| D13 | Provider doubles used in forked tests are exposed only through a test-source child main or equivalent package-private test harness. Production users cannot select arbitrary response fixtures. |
| D14 | A content-free append-only call log may cross the process boundary in tests to prove stage/artifact attempts. It contains no prompts, responses, prose, secrets, or player input. |
| D15 | Prefetch is off for deterministic route certification. Any separate prefetch test must label its calls and must not alter route completion assertions. |

## 5. Strict script execution contract

### 5.1 Scope

Strict behavior applies when `--script <file>` is used with the session-backed `play` command and in certification. It does not make interactive stdin EOF an error. If legacy classic-console scripts remain supported, they must either implement the same completion rules or be explicitly excluded from certification and documented as non-strict fixtures.

### 5.2 Terminal conditions

A strict script invocation ends in exactly one of these states:

| Condition | Exit | Code/result |
|---|---:|---|
| Run reaches a trusted ending | 0 | completed |
| Explicit `/quit` with no pending command | 0 | intentional checkpoint/exit |
| EOF while run is not ended | 4 | `SCRIPT_INCOMPLETE` |
| Submitted command is rejected | 4 | `SCRIPT_COMMAND_REJECTED` |
| EOF or `/quit` while command remains processing | 4 | `SCRIPT_COMMAND_PENDING` |
| Invalid script path/encoding/shape | 2 | `SCRIPT_INVALID` |
| Store/session failure | 3 | existing safe store/session code |

Stable codes are printed to stderr once. Human hints may follow, but tests assert the stable code and exit status rather than prose.

### 5.3 EOF algorithm

When `readLine` returns EOF:

1. if `pendingCommandId` is present, query its durable status once;
2. if it is complete, refresh the saved run/view and evaluate that terminal outcome;
3. if it remains processing, return `SCRIPT_COMMAND_PENDING`;
4. if it completed rejected, return `SCRIPT_COMMAND_REJECTED`;
5. if the refreshed view is ended, return 0;
6. otherwise return `SCRIPT_INCOMPLETE`.

The console must not interpret read errors as ordinary EOF. A script read error is `SCRIPT_INVALID` or another stable I/O code with exit 2.

### 5.4 Rejected commands

In a strict script, any terminal `Outcome.REJECTED` fails the invocation immediately after persisting/retrieving its command record. The error output includes:

```text
SCRIPT_COMMAND_REJECTED
```

Issue codes may be emitted on following content-safe lines. The script never proceeds to later choices after rejection. Utility-command errors such as forbidden `/abandon` confirmation also remain non-zero.

### 5.5 Pending commands

Strict scripts do not report success while work is unresolved. If a submitted command exceeds the configured synchronous/polling bound:

- it may remain durably processing according to the session contract;
- the invocation returns exit 4 with `SCRIPT_COMMAND_PENDING` when no more script input can safely be consumed or when `/quit` is requested;
- later process recovery follows the existing interrupted-command rules;
- the harness never assumes the command was accepted.

Non-mutating commands may still be allowed while a command is pending during interactive use. A strict route script should not use them to hide an unresolved mutation at EOF.

### 5.6 Explicit checkpoint

`/quit` is not EOF. It is a deliberate checkpoint instruction and exits 0 only when:

- no command is pending;
- the latest submitted mutation has a terminal command record;
- the store commit containing it is complete;
- the local store closes and releases its lock normally.

The run may remain `ACTIVE`. This is how the first partial-route process ends after accepted choice four.

## 6. Route suite contract

### 6.1 Suite expectations

Advance the Willow Marsh suite schema if necessary so each route contains a trusted expectation block rather than one bare `expectedResult` string:

```json
{
  "id": "partial",
  "script": "routes/partial.script",
  "expected": {
    "status": "ENDED",
    "acceptedChoices": 8,
    "outcomeId": "gentle-lighting",
    "resultClass": "PARTIAL_SUCCESS",
    "objectives": {
      "find-lens": "DONE",
      "prepare-beacon": "DONE",
      "bring-neighbors-home": "ACTIVE"
    }
  }
}
```

Expectations are validation input only. They may appear in the signed/frozen suite but are not copied into observed route evidence.

### 6.2 Required route truth

| Route | Outcome ID | Result class | Objective state |
|---|---|---|---|
| `success` | `radiant-festival` | `SUCCESS` | all three `DONE` |
| `partial` | `gentle-lighting` | `PARTIAL_SUCCESS` | `find-lens=DONE`, `prepare-beacon=DONE`, `bring-neighbors-home=ACTIVE` |
| `postponed` | `festival-postponed` | `FAILURE` | all three `DONE`; postponement is a deliberate safe ending, not objective loss |

The gate also asserts the ending scene ID, end reason, and required fact IDs appropriate to each route. Result class alone is insufficient.

### 6.3 Committed progress

Every complete route must have:

- snapshot step 8;
- run revision 8;
- exactly eight accepted story-choice command records;
- no rejected or in-progress story command;
- one terminal `ENDED` run;
- command revisions increasing exactly once per accepted choice;
- outbox events whose command IDs/revisions correspond to committed commands;
- no command created for `/save`, `/quit`, `/status`, `/objectives`, or `/characters`.

If startup events exist, they are counted separately and do not inflate accepted choices.

### 6.4 Exact trusted-state assertions

The suite or route verifier records and compares trusted state sufficient to catch duplicated effects. At minimum:

- counters;
- relevant flags;
- clue-set membership;
- objective states;
- visited story scenes in order;
- outcome ID and ending scene;
- result fact IDs.

For the current frozen routes, expected counter examples are:

| Route | `teamwork` | `care` |
|---|---:|---:|
| success | 5 | 1 |
| partial | 0 | 5 |
| postponed | 5 | 1 |

The verifier derives these values from the saved snapshot. Console output is not parsed to reconstruct state.

## 7. Real directory-backed execution

### 7.1 Per-route isolation

For each route, create a unique temporary directory with:

```text
route-root/
  store/
  scripts/
  process/
  provider-observations.ndjson   # tests only, content-free
```

Pass `--store-dir <route-root>/store` to every child. Do not pass `--memory` and do not inject `SessionPorts.SessionStore` into `ConsoleApp`.

Cleanup occurs only after:

- all child processes exit;
- the parent reopens and validates the store;
- evidence is written or assertions complete.

On failure, test frameworks may retain paths only in local failure diagnostics; standard certification evidence never exposes raw machine paths.

### 7.2 Process launch

Use `ProcessBuilder` or an equivalent Java argument-array API. Never construct a shell command string. The launcher must:

- use the current test/runtime Java executable;
- identify the intended CLI/test-child main explicitly;
- pass absolute normalized pack, script, and store paths;
- set UTF-8 JVM/file encoding where needed for deterministic tests;
- capture stdout and stderr separately with bounded size;
- enforce a per-process timeout;
- terminate a timed-out child and fail with a stable harness code;
- record PID, start/end time, and exit code as content-free diagnostics;
- forward only allow-listed environment values;
- remove provider credentials for all automated child processes.

Windows and Linux path quoting is handled by the argument list, not manual quotes.

### 7.3 First process: checkpoint

For the partial route, process A receives the first four choices followed by `/save` and `/quit`.

After process A exits 0, the parent opens the store and asserts:

- one `ACTIVE` run;
- revision/step 4;
- exactly four accepted story commands;
- no pending command or live lease;
- current scene is the expected checkpoint scene;
- snapshot and artifact digests are captured;
- the store lock can be acquired, proving process A released it.

The parent closes the store before process B begins.

### 7.4 Second process: resume and finish

Process B has a different PID and runs with:

```text
play --pack-dir <pack> --store-dir <same-store> --continue --script <remaining-script> --prefetch off --no-color
```

It must not receive `--new`, `--generated`, start inputs, a seed, an in-memory store, or any Java object from process A. It discovers and resumes the durable run.

After process B exits 0, the parent reopens the store and asserts the final partial-success state from Section 6.

### 7.5 Success and postponed routes

The success and postponed routes each run in their own store and child process through a terminal ending. They are subject to the same reopened-store inspection. Running them in child JVMs is preferred so all three routes exercise the distributed CLI artifact path; at minimum the partial route must use two real processes.

## 8. Saved-state inspection

### 8.1 Authoritative source

After a child exits, open `LocalSessionStore` from the parent and locate the route's run by owner/run ID. The saved store—not stdout, exit code, suite expectation, or an in-memory reference—is the authoritative source.

Inspect:

- run status and revision;
- canonical snapshot and step;
- command records;
- outbox events;
- generation ledger/call totals;
- artifact identities/outcomes/quality decisions;
- absence of live lease or in-progress command.

Resume the saved snapshot with the real pack and a generator that throws if restored content attempts a provider call. Use the resulting `View.result` to observe:

- outcome ID;
- result class;
- objective result states;
- fact IDs.

An ended-state inspection that causes generation is a test failure.

### 8.2 Observed route evidence

Each route produces an observed structure similar to:

```json
{
  "routeId": "partial",
  "completed": true,
  "restartProcesses": 2,
  "checkpointRevision": 4,
  "finalRevision": 8,
  "acceptedStoryChoices": 8,
  "status": "ENDED",
  "endingSceneId": "ending-gentle",
  "outcomeId": "gentle-lighting",
  "resultClass": "PARTIAL_SUCCESS",
  "objectives": {
    "bring-neighbors-home": "ACTIVE",
    "find-lens": "DONE",
    "prepare-beacon": "DONE"
  },
  "factIds": ["..."],
  "artifactDigest": "sha256:...",
  "duplicateEffects": 0,
  "duplicateArtifacts": 0,
  "duplicateProviderAttempts": 0
}
```

This object contains observed values only. Remove these current shortcuts:

- `expectedResult` from route evidence;
- `actualResult = passed ? expected : "UNKNOWN"`;
- `acceptedStoryChoices = countChoices(script)`;
- `terminalReloaded = passed` without a real reload;
- `restartCheckpointResumed = secondInvocationExitedZero` without PID/store proof.

The comparison result may be emitted separately as gate IDs such as `RESULT_MATCH`, `OBJECTIVES_MATCH`, and `RESTART_MATCH`.

### 8.3 Evidence privacy

Evidence may include stable IDs, enum values, counts, digests, timings, PIDs, and exit codes. It must not include:

- narration/dialogue/provider prose;
- prompts or raw provider responses;
- free-text player input;
- credentials or environment dumps;
- command MAC keys;
- full local paths;
- full snapshot JSON.

## 9. Exactly-once restart assertions

### 9.1 Trusted effects

Capture checkpoint state after process A and final state after process B. Prove:

- the first four visited scenes remain one ordered prefix;
- their counters, flags, sets, and objective transitions are not reapplied;
- final counters match the exact route values;
- revision advances from 4 to 8, never to 12;
- each accepted command occupies one revision;
- no duplicate command/event pair exists.

### 9.2 Generated artifacts

Define stable artifact identity as the existing pack/version/locale/stage/template/artifact tuple. Across checkpoint and final saves:

- every checkpoint artifact is byte-for-byte canonical-equal in the final snapshot;
- an identity occurs at most once in the accepted artifact list;
- final artifacts added after the checkpoint correspond only to newly reached lazy slots;
- outcome and quality stamp for an existing artifact do not change on resume;
- ended reopen adds no artifact.

### 9.3 Provider attempts

The local double's content-free observation log records, per attempt:

- process role (`first`, `resume`, or single-process route);
- stage;
- template/slot ID or its stable digest;
- attempt number;
- returned test mode (`VALID`, `REPAIR_INPUT`, `REPAIRED`, `FAILURE`).

It records no body content. The verifier proves that process B makes no call for an artifact already accepted by process A. Calls for genuinely new post-checkpoint lazy scenes are allowed exactly according to the fixture plan.

## 10. Local provider-double matrix

### 10.1 Isolation

Automated tests must not instantiate the production Anthropic adapter, access the network, or read provider environment variables. Before launching children, remove all known provider keys/mode/debug variables from the child environment except an explicitly safe offline mode where required.

For subprocess tests, use a test-only child entry point that wires a deterministic `TextGenerator` from reviewed test fixtures. The entry point is compiled only in test scope and cannot be selected from the production CLI.

### 10.2 Required modes

| Mode | Double behavior | Required assertion |
|---|---|---|
| Provider success | Returns one schema-valid response per requested stage/slot. | Accepted artifacts are `GENERATED`; route completes; no repair/fallback. |
| Repair | Returns one repairable invalid response, then a valid repaired response for selected stages. | Artifact is `REPAIRED`, quality/provenance are saved, route completes, attempts are bounded. |
| Fallback | Returns provider error or invalid output through the allowed repair bound. | Authored artifact is `FALLBACK`; route still completes with the same trusted mechanics/result. |

Do not use a local HTTP server when a direct `TextGenerator` double is sufficient. No test sleeps to simulate provider behavior except the focused pending-command test, which uses latches/controlled timing and a strict bound.

### 10.3 Coverage allocation

Minimum route/provider coverage:

1. run all three routes provider-free/authored-fallback and validate their saved results;
2. run at least one complete route with all valid local provider responses;
3. run at least one complete route with selected repairable responses;
4. perform the two-process partial-route resume in at least fallback mode and, when fixture cost is acceptable, valid-provider mode;
5. assert trusted route outcomes are identical across generated/repaired/fallback presentation modes for the same choice route.

This matrix need not be a nine-case Cartesian product if the listed claims are independently proven.

## 11. Certification harness changes

### 11.1 Route execution

Replace the current `executeRoute` flow:

- remove `new InMemorySessionStore(clock)`;
- remove `--memory`;
- do not supply a store to `ConsoleApp`;
- run the route through the process runner and explicit `--store-dir`;
- split the declared resume route at its checkpoint;
- inspect the saved store after checkpoint and terminal exit;
- delete the route directory only after evidence is finalized.

If live certification later uses the same process runner, provider configuration is passed through the already approved production environment allow-list. Standard 27.15 tests remain local/offline.

### 11.2 Suite validation

Validate before launching any child:

- exactly three routes: success, partial, postponed;
- exactly eight story choices per complete route as fixture structure only;
- one resume route and checkpoint after accepted choice four;
- `/quit` occurs exactly at that checkpoint;
- no free-text input;
- only allow-listed utility commands;
- expected outcome/objective IDs exist in the pack;
- expected objective map lists every declared objective exactly once.

Line counting may validate suite shape but never populate observed evidence.

### 11.3 Pass/fail

A route passes only when all of these are true:

- every required child exits with the expected strict-script status;
- checkpoint assertions pass where applicable;
- terminal store reload succeeds;
- saved status is `ENDED`;
- saved accepted command count/revisions are exact;
- actual outcome, result class, objectives, facts, and trusted state match suite expectations;
- duplicate effects/artifacts/provider attempts are zero;
- ended reopen makes zero provider calls;
- no command remains pending and no lease remains live.

Exit code 0 alone is never completion evidence.

## 12. Required tests

### 12.1 Strict script tests

Add focused CLI tests for:

1. empty script on an active run → exit 4, `SCRIPT_INCOMPLETE`;
2. valid prefix then EOF → exit 4, `SCRIPT_INCOMPLETE`;
3. unknown/unavailable choice → exit 4, `SCRIPT_COMMAND_REJECTED` or the strict invalid-choice code chosen by the implementation;
4. engine-rejected scripted choice → exit 4, `SCRIPT_COMMAND_REJECTED`;
5. slow unresolved command then EOF → exit 4, `SCRIPT_COMMAND_PENDING`;
6. slow unresolved command then `/quit` → exit 4, `SCRIPT_COMMAND_PENDING`;
7. four committed choices then `/quit` → exit 0 and active revision 4;
8. complete route ending before EOF → exit 0;
9. script read failure → exit 2, not `SCRIPT_INCOMPLETE`;
10. interactive EOF retains normal behavior.

Tests inspect the store to ensure failure codes correspond to real durable state.

### 12.2 Three route tests

Run the frozen success, partial, and postponed scripts against separate real store directories. For each, assert Section 6 from reopened state. The partial route must use the real two-process flow.

### 12.3 Process identity test

Record both child PIDs and assert:

- PID A differs from PID B;
- process A is no longer alive before B starts;
- the store lock is acquirable between them;
- no shared Java store/provider/run object is supplied;
- B receives `--continue` and the same normalized store path.

### 12.4 Saved evidence test

Deliberately alter a test suite expectation to the wrong result/objective and prove certification fails even though the route process exits 0. Assert the evidence still reports the observed saved result and never changes it to the expected value.

### 12.5 Duplicate detection tests

Add negative fixtures/verifier tests containing:

- duplicated accepted command revision;
- duplicated event identity;
- doubled counter/effect state;
- repeated artifact identity;
- repeated pre-checkpoint provider attempt during resume.

Each must fail its named gate.

### 12.6 Provider matrix tests

Use deterministic test-child doubles to prove valid, repaired, and fallback artifacts. Assert exact attempt bounds, artifact outcome, quality stamp, terminal result, and zero network access.

### 12.7 Cross-platform test hygiene

Process tests must:

- use the current Java executable rather than assuming `java` is on `PATH`;
- use argument lists and normalized paths;
- avoid shell scripts for the child launch;
- bound captured output and runtime;
- close streams and process handles;
- clean temporary directories after successful assertions;
- preserve enough diagnostic metadata on failure without leaking content.

## 13. Acceptance scenarios

| Scenario | Required result |
|---|---|
| Script ends after three valid choices | Exit 4 and `SCRIPT_INCOMPLETE`; saved run remains active at revision 3. |
| Script submits a rejected choice | Exit 4 immediately; no later script line is executed. |
| Script exhausts while command is pending | Exit 4 and `SCRIPT_COMMAND_PENDING`; never reports route completion. |
| Success route | Reopened save is `ENDED`, `radiant-festival`, `SUCCESS`, all objectives done. |
| Partial route checkpoint | First JVM exits 0 after `/quit`; reopened save is active at revision 4. |
| Partial route resume | Different JVM continues same store to `gentle-lighting`/`PARTIAL_SUCCESS`; one objective remains active. |
| Postponed route | Reopened save is `festival-postponed`/`FAILURE` with all objectives done. |
| Wrong suite expectation | Route gate fails despite child exit 0; observed evidence stays truthful. |
| Valid local provider | Generated artifacts and quality data persist; no fallback. |
| Repair local provider | Bounded repair persists `REPAIRED`; route completes. |
| Failed local provider | Authored `FALLBACK` persists; route completes without network. |
| Resume checkpoint | No pre-checkpoint effect, artifact, event, or provider attempt is duplicated. |

## 14. Implementation sequence

### Step 1 — Make scripts strict

1. Introduce stable script result codes and exit mapping.
2. Separate interactive EOF, strict EOF, and explicit `/quit`.
3. Fail on rejected outcomes.
4. resolve/check pending state before EOF or checkpoint success.
5. Add the focused script tests first.

### Step 2 — Build saved-state verifier

1. Define observed route evidence independent of expectations.
2. Open `LocalSessionStore` after child exit.
3. Derive command/revision/event/artifact counts.
4. Resume terminal snapshot without generation and read `RunResult`/objectives/facts.
5. Add named gate comparisons and negative verifier tests.

### Step 3 — Replace certification storage

1. Remove `InMemorySessionStore` and `--memory` from certification routes.
2. Allocate one real store directory per route.
3. inspect and retain state until evidence finalization.
4. Remove copied/line-count-derived route evidence fields.

### Step 4 — Add process runner

1. Launch child JVMs with bounded streams/timeouts and environment allow-list.
2. Run success and postponed terminal scripts.
3. split partial at choice four.
4. prove distinct processes, released lock, same store, and `--continue`.

### Step 5 — Add local provider modes

1. Add test-only child wiring for valid, repair, and failure doubles.
2. Add content-free cross-process attempt observations.
3. prove outcomes/quality and no duplicate pre-checkpoint attempts.

### Step 6 — Final route gate

1. Run all three provider-free routes.
2. run the valid and repair cases.
3. validate evidence schemas/privacy.
4. run the full engine verification gate.

## 16. Traceability

| Requirement | Minimum evidence |
|---|---|
| EOF is not false success | Prefix/empty script tests returning `SCRIPT_INCOMPLETE` |
| Rejected choice fails | Strict rejection test and non-zero exit |

## 17. Definition of done

Spec 27.15 is complete when:

- strict script EOF before an ending returns exit 4 and `SCRIPT_INCOMPLETE`;
- a rejected scripted choice returns non-zero immediately;
- a script cannot finish or quit successfully while a command is pending;
- explicit `/quit` after committed work remains a valid active-run checkpoint;
- success, partial-success, and postponed routes run against separate real directory stores;
- route completion is verified from reopened saved state, not exit code or transcript;
- actual outcome ID, result class, objective states, facts, revision, and accepted commands are observed from the save;
- evidence contains no copied `expectedResult` and no script-line-derived accepted count;
- certification no longer injects `InMemorySessionStore` or passes `--memory`;
- the partial route stops after four accepted choices, closes process A, and resumes in a distinct process B;
- process B opens the same store using `--continue` and no shared Java object;
- the final partial route advances revision 4→8 with no duplicate trusted effects;
- checkpoint artifacts remain canonical-identical and occur once in the final snapshot;
- no provider attempt for accepted pre-checkpoint content is repeated;
- completed saved runs reload without provider calls;
- valid, repair, and fallback modes are proven with deterministic local doubles only;
- all automated tests run without network access or provider credentials;
- focused CLI/process tests and the full engine verification gate pass.
