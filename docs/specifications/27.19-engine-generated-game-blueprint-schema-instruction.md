# Spec 27.19 — Generated Game Blueprint Schema

**Type:** Implementation specification  
**Parent:** 27.17 — Dynamic Game Generation Architecture and Preparation Wizard  
**Depends on:** 27.18 — Generator Profile and Capability Contract  
**Baseline:** Local CapyBee checkout `bbc66e8fd55e9c3ca1390705614bf0bba4d4b07c`; current saved 27.17 and 27.18 read on 2026-10-24. Existing unrelated `SceneOption.java` modification is outside scope. Reinspect current code and repository guidance before implementation.  
**Status:** Ready for implementation review; coordinate mechanics contracts with 27.21/27.22 before enabling provider integration.  
**Primary outcome:** Strictly parse a complete, versioned, untrusted game proposal into immutable blueprint contracts. The proposal describes a new scenario rather than presentation slots copied from an existing playable pack. Parsing does not make the proposal safe, playable, persistent or executable.  
**Repository destination:** `docs/specifications/27.19-engine-generated-game-blueprint-schema-instruction.md`

## 1. Intent and player-facing result

The preparation wizard defined by 27.17 collects genre, setting, tone, interests, length, challenge, language and an optional game idea. Its output must be capable of shaping an entirely new premise, cast, objectives, graph, decisions and endings.

This specification defines the output contract for that planning operation. A future GAME_BLUEPRINT request receives resolved preferences and effective constraints from 27.18, together with a separately approved transient suggestion. It returns one complete blueprint document. The blueprint does not contain the original suggestion, input history or provider prompts.

The blueprint is a plan for an entire game. Detailed narration and dialogue remain lazy presentation generated later under 27.25. This contract contains enough narrative intent for that presentation to remain coherent and enough mechanical structure for deterministic validation before play.

No requirement promises that every live response is unique or perfectly follows a natural-language request. Distinct controlled blueprint examples must demonstrate structural variation; creative fidelity requires later quality evaluation.

## 2. Scope and ownership

### In scope

- Blueprint schema version 1 and exact JSON shapes.
- Immutable domain records with symbolic references, separate from runtime IDs.
- Strict bounded parsing and profile-bound shape/capability checks.
- Reserved closed condition/effect shapes matching the existing engine vocabulary.
- Deterministic serialization and machine-readable JSON Schema resources.
- Safe diagnostics, compatibility rules, test resources and implementation tests.

### Out of scope

- Wizard rendering, suggestion collection or external-processing confirmation.
- Provider requests, retry/repair orchestration and fallback selection: 27.20.
- Reference binding, graph proofs, path bounds and state-space playability: 27.21.
- Detailed mechanical semantics, bounds enforcement and achievability: 27.22.
- Trusted ID allocation, compilation and materialized definitions: 27.23.
- Runtime startup, lazy prose, durable codecs or CLI commands: 27.24–27.27.
- New effects, new condition operators, places, scripts or open-world graphs.

27.19 must not introduce a second interpreter or treat a parsed blueprint as an ordinary Pack. No production GAME_BLUEPRINT catalog-stage integration is needed merely to test these contracts. Preserve the sequence and integration restrictions in 27.17 §9.

## 3. Existing implementation and reuse

| Existing component | Required relationship |
| --- | --- |
| `GenerationOutputParser` | Existing narrative-stage parser stays compatible. Its control-word filters are not suitable for a mechanical blueprint document. Use a dedicated parser rather than weakening historical output checks. |
| `GenerationArtifact` | Do not add an unchecked mechanical payload to an existing accepted narrative artifact. Blueprint provenance/acceptance lifecycle belongs to later integration. |
| `Condition` / `Effect` | Reuse discriminator spelling and field meanings. Blueprint nodes hold symbolic references and are not executable runtime nodes. |
| `RulesParser` | Reuse suitable strict JSON utilities through a safe extraction; its Pack-bound reference checking cannot establish blueprint trust. |
| `ObjectiveDef` | Has `completeWhen` and `onComplete`; v1 blueprints expose only `completeWhen`. The compiler later supplies empty objective-completion effects. |
| `Scene` / `SceneOption` | Support richer authored features. Dynamic v1 is a deliberate subset: explicit choices and terminal mappings, no automatic transitions/branches/on-enter mechanics. |
| `PhaseKind` | Reuse OPENING, DEVELOPMENT, CHALLENGE, RESOLUTION, ENDING in that order. |
| `ResultClass` | Reuse SUCCESS, PARTIAL_SUCCESS, FAILURE; never infer classification from generated wording. |
| 27.18 profile contracts | Consume a validated profile plus its matching resolved preferences/effective constraints; never reparse raw profile JSON or trust model-supplied limits. |

Use existing `tools.jackson` dependencies and Java/package conventions. Do not add a second JSON stack solely for this feature.

## 4. Parse boundary and trust lifecycle

Suggested API responsibilities, with final names following repository conventions:

```text
BlueprintOutputParser.parse(response, validatedProfile, resolvedPreferences, effectiveConstraints)
    -> ParseResult<ParsedGameBlueprint>

ParsedGameBlueprint
    -> semantic/policy validation (27.21/27.22 and output safety)
    -> restricted validated result
    -> compiler and final verification (27.23)
    -> MaterializedGameDefinition
```

The parser returns a successful result only for a completely valid shape within the supplied envelope. It never returns a partial blueprint on failure. `ParsedGameBlueprint` means untrusted structured data, not proof of playability or safety.

The parser checks that supplied profile identity, version, fingerprint and resolved constraints match. A missing/mismatched context fails before consuming model data. Later validation results must remain bound to this context; callers cannot validate under one challenge preset and compile under another.

The model supplies no profile ID, run ID, fingerprint, validation stamp, engine ID, seed, model name or acceptance flag. The host owns all such metadata in a separate envelope defined downstream. Parsing invokes no provider, input guard, filesystem, clock, random source or runtime.

## 5. Normative root contract

All fields below are required, including empty arrays where allowed. No root field is nullable. Unknown fields are rejected at every depth.

| Field | Type and meaning |
| --- | --- |
| `schemaVersion` | Integer constant 1. |
| `locale` | Exact canonical locale selected by the preparation resolver. One game language, not a localization bundle. |
| `title` | Short game title. |
| `premise` | Self-contained fictional setup. |
| `setting` | Concise world description. |
| `toneTags` | 1–4 descriptive tags; advisory content, never authority to override policy. |
| `storyPromises` | 1–4 concrete narrative intentions for later presentation. |
| `actors` | Complete generated actor declarations. |
| `state` | Counter, flag and finite-set declarations. |
| `objectives` | Declared goals with completion predicates. |
| `phases` | Five ordered phase plans. |
| `startSceneId` | One symbolic start reference; scenes do not repeat a `start` boolean. |
| `scenes` | Complete mechanical graph and scene intent, including terminal scenes. |
| `outcomes` | Declared terminal result meanings and trusted-enum classification proposals. |

No `originalSuggestion`, `storyWish`, `userInput`, `setup`, `prompt`, `debug`, `metadata`, URL/resource manifest or arbitrary extension map. IDs and references are proposed symbols only. The model cannot supply a precompiled definition.

## 6. Identifiers, ordering and references

### 6.1 Symbol syntax

Symbolic IDs match `[a-z][a-z0-9-]{0,47}`. They are opaque ASCII tokens, not names, paths, class names, localization keys or executable expressions. Never normalize invalid IDs into valid ones. Reject leading/trailing whitespace and case mismatches.

Namespaces: actors, counters, flags, sets, objectives, scenes and outcomes are separate. Choices are unique within their owning scene. Set values are unique within their owning set and use the same symbol syntax. Phase identity is its PhaseKind enum value, not a generated arbitrary ID.

27.19 verifies lexical syntax, local declaration uniqueness and duplicate entries in reference lists. 27.21 resolves references to declarations and rejects dangling or wrong-namespace references. A syntactically valid unresolved reference may therefore parse successfully but cannot compile.

### 6.2 Stable arrays

Keep declaration order; it controls stable presentation and later deterministic compilation. Do not sort scenes topologically in the parser, reorder effects, or discard duplicates. Reject duplicate declarations instead of keeping the first/last value.

Object member order has no semantic meaning. Array order does, except that 27.21 may treat particular reference lists as sets while retaining their original deterministic representation. Scene-array order never proves graph direction or path length.

All cross-references remain symbolic. No direct construction of runtime Scene/Condition/Effect objects is permitted in this parser. A typed wrapper around String is recommended where it prevents passing a symbolic scene ID into a trusted engine ID API; avoid seven redundant hierarchies if existing value-object patterns suffice.

## 7. Narrative planning records

### 7.1 Actors

Each actor is exactly:

```json
{"id":"robot","name":"Pip","role":"A repair robot who joins the explorers","description":"Patient and inventive; explains tools without taking decisions for the player."}
```

The actor list has effective minActors–maxActors entries. Actor IDs are referenced by scenes and phases; no pre-existing actor slots are required. The model defines fictional roles rather than choosing Willow Marsh roles. No age, real-world identity, contact, portrait URL or hidden biography fields.

### 7.2 Phase plans

Each phase is exactly:

```json
{"kind":"OPENING","goal":"Discover the damaged beacon","development":"The team learns why a signal matters.","transition":"Choose the first investigation route.","actorIds":["robot"],"objectiveIds":["restore-signal"]}
```

All five PhaseKind values appear exactly once and in engine order. Lists may be empty, but are bounded by declared actor/objective capacity and contain no duplicate symbols. These lists describe narrative involvement, not actor availability or automatic goal completion. Exact reference validity, actual phase coverage and allowed phase transitions belong to 27.21.

### 7.3 Plain text

Text is inert content for later safety/quality checks, never an instruction channel. No template interpolation or expression evaluation. Reject active markup, control characters except normalized LF in long text, malformed Unicode and unresolved template markers such as `${...}` or `{{...}}`. Do not reject ordinary story prose solely for containing words such as “counter”, “objective” or “route”.

Parser text checks are not a claim of output moderation, PII removal, locale correctness or narrative truth. 27.20 must arrange output safety/quality checks before acceptance or persistence. Prose may reflect a fictional suggestion, but the response must not carry its verbatim input as a dedicated field.

## 8. State declarations

`state` has exactly three required arrays: `counters`, `flags`, `sets`. Empty arrays are valid when effective capabilities permit them.

```json
{
  "counters":[{"id":"charge","min":0,"max":3,"initial":0}],
  "flags":[{"id":"signal-ready","initial":false}],
  "sets":[{"id":"tools","values":["wire","lens"],"initial":[]}]
}
```

- Counters: exactly `id`, `min`, `max`, `initial`; integers only; `min < max`, initial inside declared interval, interval inside effective profile bounds.
- Flags: exactly `id`, `initial`; actual JSON boolean.
- Sets: exactly `id`, `values`, `initial`; finite nonempty allowed-value list, initial duplicate-free subset. Bounds derive from effective maxSets/maxSetValues.
- Counts cannot exceed the selected challenge/profile capacities. No undeclared dynamic keys, string-valued arbitrary variables, inventory object metadata or player-defined functions.

Counter `min/max` are generated-definition invariants, not a claim that the existing CounterDef already stores bounds. 27.22/27.23 must prove that reachable transitions preserve them or provide explicit compatible enforcement. Do not silently clamp, widen or discard declared bounds in this spec.

Unused capacity is allowed; unused declarations can be reviewed under semantic quality later. State data is scenario-specific; the profile remains scenario-neutral.

## 9. Objectives and outcomes

### 9.1 Objectives

Each objective has exactly:

```json
{"id":"restore-signal","title":"Restore the signal","description":"Help the explorers make the beacon work.","completeWhen":{"type":"FLAG_IS","flag":"signal-ready","value":true}}
```

Count respects effective minObjectives/maxObjectives. Every objective has one predicate. No model-supplied completion booleans, rewards, onComplete effects, dependencies or arbitrary score formulas. Completion is determined by the existing deterministic runtime semantics, with detailed evaluation order reconciled in 27.22.

Objectives need achievable witnesses under 27.21; this does not imply every objective must be completed on every route. Narrative labels must not fabricate success in an incomplete objective.

### 9.2 Outcomes

Each outcome has exactly:

```json
{"id":"signal-restored","resultClass":"SUCCESS","title":"The beacon shines","description":"The explorers establish a reliable signal."}
```

`resultClass` is one existing ResultClass enum value. Its presence remains an untrusted proposal until semantic validation and compilation; future prose cannot change it.

V1 has one outcome per terminal scene, with a one-to-one mapping checked by 27.21. Outcome count uses effective ending bounds, 2–4 globally. Endings may include partial/failure results but must remain within audience policy. No requirement forces all three result classes to exist.

## 10. Scenes and choices

Use a discriminated union with `kind` exactly `DECISION` or `ENDING`. This is a blueprint-only structural discriminator; it is not a second runtime scene kind hierarchy.

### 10.1 Decision scene

Exact shape:

```json
{
  "id":"inspect-beacon",
  "kind":"DECISION",
  "phase":"OPENING",
  "title":"A silent beacon",
  "intent":"Introduce the team and let the player choose how to investigate.",
  "actorIds":["robot"],
  "objectiveIds":["restore-signal"],
  "choices":[
    {"id":"ask-robot","intent":"Ask Pip to inspect the beacon before moving onward.","destinationSceneId":"workshop","requires":null,"effects":[]}
  ]
}
```

- `phase`: OPENING, DEVELOPMENT, CHALLENGE or RESOLUTION.
- `choices`: 1–effective maxChoicesPerScene, global maximum 4.
- Choice fields exactly `id`, `intent`, `destinationSceneId`, `requires`, `effects`.
- `requires` is the sole nullable contract field: null means unconditional. It must be explicitly present; an empty object or missing field is invalid. Do not invent TRUE/FALSE condition operators.
- Effects are an ordered array, including empty when no mutation is needed.
- Each choice has exactly one destination. No destination can be supplied by an effect or by prose.
- `intent` is a semantic planning statement for truthful later labels; it is not the final player-visible choice label.

### 10.2 Ending scene

Exact shape:

```json
{
  "id":"beacon-shines",
  "kind":"ENDING",
  "phase":"ENDING",
  "title":"A signal across the clouds",
  "intent":"Describe the actual successful repair and thank the team.",
  "actorIds":["robot"],
  "objectiveIds":["restore-signal"],
  "outcomeId":"signal-restored"
}
```

No choices, requirements, effects or outgoing destinations on terminal scenes. `outcomeId` exists only on endings. Conversely, decision scenes cannot declare an outcome. The parser checks these variant-local invariants.

### 10.3 Deliberate v1 restrictions

No scene-level next, branches, onEnter, automatic utility nodes, generated scene input modes or choice-specific outcome overrides. Every nonterminal transition is an explicit player choice. Terminal entry maps to a declared outcome.

This reduces ambiguity for path/state proofs and leaves places disabled consistently with 27.18. Authored packs retain their richer Scene features. At least one meaningful alternative, nonterminal liveness, forward DAG structure, path bounds and outcome consistency are semantic checks owned by 27.21/27.22, never inferred from scene titles.

## 11. Closed condition/effect shapes

These shapes reserve the v1 wire contract. They are not permission to enable every operator in every profile. The supplied effective allowlist must permit every used type. 27.22 refines evaluation/achievability using the existing interpreter without changing these shapes casually.

### 11.1 Conditions

| `type` | Exact additional required fields |
| --- | --- |
| COUNTER_AT_LEAST / COUNTER_AT_MOST / COUNTER_EQUALS | `counter`: symbol, `value`: integer |
| FLAG_IS | `flag`: symbol, `value`: boolean |
| SET_CONTAINS | `set`: symbol, `value`: set-value symbol |
| SET_SIZE_AT_LEAST | `set`: symbol, `size`: nonnegative integer |
| VISITED_SCENE | `scene`: symbol |
| ALL / ANY | `conditions`: array of 1–16 condition nodes |
| NOT | `condition`: one condition node |

Root condition depth is 1. Every node including composites counts toward the per-expression node limit. Both limits use the narrower effective profile values, with absolute maxima depth 4 and 32 nodes. Parse with a resource-bounded traversal; do not construct an unbounded tree before counting.

Each choice requirement and objective predicate is counted separately; the document-wide byte/node budgets still apply. No empty ALL/ANY and no special implicit boolean identities. Reference binding, threshold relevance and whether a condition can become true are later checks.

### 11.2 Effects

| `type` | Exact additional required fields |
| --- | --- |
| COUNTER_ADD | `counter`: symbol, `delta`: nonzero integer whose absolute value does not exceed effective maxCounterDelta |
| COUNTER_SET | `counter`: symbol, `value`: integer |
| FLAG_SET | `flag`: symbol, `value`: boolean |
| SET_ADD / SET_REMOVE | `set`: symbol, `value`: set-value symbol |

At most effective maxEffectsPerChoice (absolute maximum 6). Apply-order semantics are owned by 27.22 and must match runtime; array order is preserved. Declaration-relative bound checks and reachable-state overflow proof belong to 27.21/27.22.

Reject GO_TO, END_RUN, EMIT_EVENT, AT_PLACE, VISITED_PLACE, STEP_AT_LEAST and all unknown types. Reject class names, scripts, expressions, dynamic field paths, event payloads and extra fields even when the surrounding object contains an allowed `type`. No runtime reflection or default-to-no-op behavior.

## 12. Bounds and strict JSON handling

Use the narrower of trusted context and these absolute ceilings. All checks apply offline before compilation.

| Item | Ceiling / rule |
| --- | --- |
| Raw document | 256 KiB UTF-8 and 131072 Java UTF-16 code units; both enforced before tree materialization |
| JSON nesting | 32; independent of condition depth |
| JSON value nodes | 12000, including containers and scalar values; count during bounded parse |
| Object members | 20 per object; exact shape is normally smaller |
| Scenes | Effective minScenes–maxScenes; absolute maximum 24 including endings |
| Actors/objectives/outcomes | Effective bounds; absolute maxima 12/8/4 |
| State capacities | Effective limits; absolute maxima 4 counters/12 flags/2 sets, 8 values per set |
| Short title/name | 1–120 Unicode code points |
| Actor role / tone tag | Role 1–240; tag 1–48 code points |
| Premise / setting | 1–1200 / 1–800 code points |
| Actor/objective/outcome description | 1–600 code points |
| Scene/choice intent; phase goal/development/transition | 1–600 code points each |
| Story promise | 1–240 code points each |
| All narrative text together | 24000 Unicode code points, excluding IDs, enums and JSON syntax |
| Issues | At most 100 total entries; reserve final entry for ISSUES_TRUNCATED when needed |

Provider token budgets in 27.18 remain separate. A generous parser ceiling does not authorize larger provider calls or guarantee that a maximal graph fits a selected response-token budget. 27.20 must handle truncated responses and budget feasibility honestly.

Strict rules:

1. Exactly one JSON object; no Markdown fences, prefixes, suffix prose, trailing object or comments. Whitespace around the object is permitted.
2. Reject duplicate JSON keys at every depth, unknown fields, trailing commas and nonstandard numeric literals. Use parser-level duplicate detection; a tree that has already overwritten keys is insufficient.
3. No type coercion: `"1"`, `1.0`, `1e0`, booleans and integer overflow are not accepted as integer fields. Integer tokens must fit Java int; specialized bounds narrow further.
4. Decode byte inputs with strict UTF-8. For String inputs, reject unpaired surrogates. Reject a BOM consistently in both routes. Do not replace malformed text.
5. Enforce required fields, exact union shapes and nullability recursively. No omitted-to-empty normalization.
6. Reject blank narrative strings. Normalize CRLF/CR to LF before length checking; otherwise preserve accepted text rather than silently rewriting meaning. No case folding, silent truncation or ID repair.
7. Text is plain data. Parsing does not execute links or fetch referenced resources.
8. A parser exception is converted to a safe issue; do not return library exception messages, source excerpts or raw response text.

## 13. Diagnostics and safe domain behavior

Proposed codes:

- BLUEPRINT_CONTEXT_MISMATCH
- BLUEPRINT_SIZE_LIMIT / BLUEPRINT_COMPLEXITY_LIMIT
- BLUEPRINT_JSON_INVALID / BLUEPRINT_DUPLICATE_KEY
- BLUEPRINT_SCHEMA_UNSUPPORTED / BLUEPRINT_UNKNOWN_FIELD
- BLUEPRINT_FIELD_REQUIRED / BLUEPRINT_TYPE_INVALID
- BLUEPRINT_SYMBOL_INVALID / BLUEPRINT_DECLARATION_DUPLICATE
- BLUEPRINT_TEXT_INVALID / BLUEPRINT_LOCALE_MISMATCH
- BLUEPRINT_CAPABILITY_EXCEEDED / BLUEPRINT_MECHANIC_UNSUPPORTED
- BLUEPRINT_PHASE_INVALID / BLUEPRINT_VARIANT_INVALID
- BLUEPRINT_ISSUES_TRUNCATED

Return immutable issues with code, logical resource `blueprint`, safe JSON pointer and generic engine-owned description. Use numeric indexes and known contract field names only. For unknown keys, report their parent pointer rather than echoing the model-controlled key. Never print a rejected value, ID, text excerpt, response, suggestion or exception message. Deterministic traversal determines stable issue order; syntax errors may stop at one safe issue.

Domain `toString()` and result logging must redact narrative/symbol content; Java record defaults would expose it. A dedicated explicit serializer is allowed for controlled fixture transport and later accepted-definition work. Do not automatically serialize parser results in logs or persist rejected responses. Defensive immutable copies must cover every nested list and expression subtree.

No boolean `isValid=true` from the model or public unchecked constructor may create a semantically validated/compiled object. Prefer constructors/factories whose type names state the actual trust level.

## 14. Schema publication and deterministic serialization

Add a provider-neutral JSON Schema resource, for example `generation/blueprint/v1.schema.json`, alongside engine-owned contracts. Its dialect is JSON Schema 2020-12; do not use this spec-preparation task to add a network schema dependency. All `$ref` references are internal. Use exact required properties, `additionalProperties:false`, enum discriminators, `oneOf` variants, integer and array/string bounds. The formal schema documents shape; runtime parsing remains authoritative for duplicate keys, Unicode, context, text/code-point limits and semantic validation.

Provide a context-specialized schema view that narrows locale, list capacities, operator allowlists and integer limits to effective constraints without embedding a concrete scenario. Keep base shape and specialized schema generated from or tested against the same definitions. Operator-specific branches must not be left in a specialized union when unsupported; an empty allowed-effect set means only an empty effects array. Unconditional requirements remain nullable even when no condition operator is enabled for choices; objective feasibility still follows profile capabilities.

Structured-output providers support varying JSON Schema subsets. 27.20 owns adapter capability negotiation and must not silently drop parser restrictions or claim that provider schema enforcement replaces local validation.

Add a deterministic explicit writer for parsed blueprint data: UTF-8, LF, fixed property order, original array order, integer tokens and explicit `requires:null`. Read-write-read preserves all accepted fields. Equivalent object-key order/whitespace gives equivalent parsed content and stable serialized bytes. This is a proposal-format writer, not the durable snapshot codec, acceptance hash, provenance stamp or definition fingerprint in 27.26. No writer method implicitly writes to disk.

## 15. Complete illustrative proposal

This example uses a short/gentle context permitting FLAG_IS/FLAG_SET, 6–12 scenes, two endings, and a 5–7-transition route. It has eight scenes; either route uses five transitions through all five phases. It demonstrates contract shape, not a production fallback or live-generation quality certificate. A complete fixture must pass the later semantic validator before it is described as playable.

```json
{
  "schemaVersion":1,
  "locale":"en",
  "title":"The Cloud Beacon",
  "premise":"Animal explorers find a silent beacon on a floating island and help a friendly robot repair it.",
  "setting":"A small floating island with a workshop and a sheltered ridge.",
  "toneTags":["curious","cooperative"],
  "storyPromises":["Investigate a signal failure","Choose how the team helps"],
  "actors":[{"id":"robot","name":"Pip","role":"The island repair guide","description":"A patient robot who shares tools and asks the explorers to decide."}],
  "state":{"counters":[],"flags":[{"id":"signal-ready","initial":false}],"sets":[]},
  "objectives":[{"id":"restore-signal","title":"Restore the signal","description":"Prepare the beacon to guide passing explorers.","completeWhen":{"type":"FLAG_IS","flag":"signal-ready","value":true}}],
  "phases":[
    {"kind":"OPENING","goal":"Meet Pip","development":"Discover the silent beacon.","transition":"Choose where to investigate.","actorIds":["robot"],"objectiveIds":["restore-signal"]},
    {"kind":"DEVELOPMENT","goal":"Gather a repair clue","development":"Compare the workshop and ridge routes.","transition":"Bring the clue to the beacon.","actorIds":["robot"],"objectiveIds":["restore-signal"]},

    {"id":"arrival","kind":"DECISION","phase":"OPENING","title":"A quiet island","intent":"Meet Pip and choose an investigation route.","actorIds":["robot"],"objectiveIds":["restore-signal"],"choices":[

    {"id":"assemble","kind":"DECISION","phase":"RESOLUTION","title":"Prepare the signal","intent":"Prepare the selected approach without changing its recorded repair result.","actorIds":["robot"],"objectiveIds":["restore-signal"],"choices":[

      {"id":"share-plan","intent":"Share the temporary guidance and a plan to return.","destinationSceneId":"temporary","requires":{"type":"FLAG_IS","flag":"signal-ready","value":false},"effects":[]}

    {"id":"restored","kind":"ENDING","phase":"ENDING","title":"A beacon shines","intent":"Recognize the completed repair and cooperation.","actorIds":["robot"],"objectiveIds":["restore-signal"],"outcomeId":"repaired"},
    {"id":"temporary","kind":"ENDING","phase":"ENDING","title":"Guidance for today","intent":"Recognize temporary help and state honestly that repair remains unfinished.","actorIds":["robot"],"objectiveIds":["restore-signal"],"outcomeId":"helped"}

    {"id":"repaired","resultClass":"SUCCESS","title":"Signal restored","description":"The beacon works and the team can leave it guiding explorers."},
```

This is one test scenario, never a default graph embedded into the parser, profile or compiler. Another test blueprint must differ in topology, objectives and state rather than only renaming this one.

## 17. Required tests

Use JUnit and existing engine conventions, deterministic in-memory data, no API keys or external calls.

| Group | Required coverage |
| --- | --- |
| Positive | Complete EN example and independently authored PL example; optional creative preferences absent; no transient suggestion needed by parser. |
| Variation | Two valid-shape proposals with different graph topology, goal predicates and state declarations; no scenario constants in production code. |
