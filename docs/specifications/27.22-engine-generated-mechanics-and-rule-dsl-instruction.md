## 1. Purpose

The dynamic blueprint format already reserves a small set of condition and effect shapes. Spec 27.21 can prove their bounded playability, but it currently interprets those shapes in `DefaultBlueprintSemanticValidator` while `RunImpl` independently interprets the authored `Condition` and `Effect` types. Two implementations of the same rules can drift: a blueprint could pass under one order, overflow rule or default and execute differently after compilation.

This specification closes that gap. It defines the generated-game mechanics contract as a strict subset of the existing engine DSL and introduces shared, deterministic semantic primitives or an equivalently strong parity boundary. The model continues to emit data only. Engine code owns the vocabulary, binding, evaluation, mutation, limits and future versioning.

The core invariant is:

> A mechanic accepted by blueprint semantic validation has exactly one engine-owned meaning, and the same accepted transition produces the same condition result and state mutation after compilation.

## 2. Scope and non-goals

### 2.1 In scope

- Define the exhaustive v1 generated condition/effect vocabulary and its mapping to existing engine rule types.
- Centralize operator metadata so profile loading, schema specialization, parsing, semantic validation and later compilation cannot maintain contradictory allowlists.
- Bind validated symbolic state references to typed, declaration-aware mechanic nodes without reflection or dynamic lookup by class name.
- Extract or introduce shared condition-evaluation and bounded state-mutation primitives used by the 27.21 proof and suitable for `RunImpl`/27.23 execution.
- Preserve effect ordering, objective timing, visited-scene semantics and finite-state behavior established in 27.21.
- Define strict numeric, depth, node, capacity and cross-reference limits at every trust boundary.
- Add differential/parity tests against the existing authored runtime semantics.
- Preserve the authored Pack rule vocabulary and all existing games.

### 2.2 Out of scope

- Compiling the complete blueprint into scenes, rules, localized strings, outcomes or engine-assigned IDs; that is 27.23.
- Starting a dynamic `Run`, changing `DefaultEngine`, publishing CLI commands or persisting definitions; those are 27.24, 27.27 and 27.26.
- Adding new gameplay operators, places, events, automatic scene effects, objective completion effects or text-input mechanics to generated v1.
- General-purpose arithmetic, variables, formulas, predicates encoded as strings, JSONPath, regular-expression conditions or user-defined functions.
- Java/JavaScript/Kotlin/Groovy code, bytecode, reflection, class names, service loading, shell commands, SQL, templates or expression engines.
- Allowing narrative text, choice intent, actor role or objective description to mutate state.
- Changing the semantic proof obligations from 27.21 or treating compiler success as a replacement for that proof.
- Making dynamic games playable in this change.

## 4. Generated mechanics contract v1

### 4.1 Contract identity

Define an engine-owned semantic contract identifier such as `generated-rules-v1`. It is distinct from:

- blueprint JSON schema version,
- profile schema version,
- semantic validator implementation version,
- materialized-definition format version,
- snapshot format version.

`SemanticallyValidatedBlueprint` evidence must retain the semantic contract identity. If 27.21 currently uses a generic semantic contract string, align it with this generated-mechanics version without making old parser success imply the new contract.

Changing implementation code without changing observable semantics may bump a validator implementation version. Adding/removing an operator or changing evaluation/mutation behavior requires an explicit compatibility decision and normally a new generated-rules contract version.

### 4.2 Exhaustive condition subset

Generated v1 permits exactly:

| Blueprint discriminator | Existing engine type | Required state |
| --- | --- | --- |
| `COUNTER_AT_LEAST` | `Condition.CounterAtLeast` | Counter declaration |
| `COUNTER_AT_MOST` | `Condition.CounterAtMost` | Counter declaration |
| `COUNTER_EQUALS` | `Condition.CounterEquals` | Counter declaration |
| `FLAG_IS` | `Condition.FlagIs` | Flag declaration |
| `SET_CONTAINS` | `Condition.SetContains` | Finite-set declaration and declared member |
| `SET_SIZE_AT_LEAST` | `Condition.SetSizeAtLeast` | Finite-set declaration |
| `VISITED_SCENE` | `Condition.VisitedScene` | Scene reference |
| `ALL` | `Condition.All` | One or more child conditions |
| `ANY` | `Condition.Any` | One or more child conditions |
| `NOT` | `Condition.Not` | Exactly one child condition |

Generated v1 forbids `STEP_AT_LEAST`, `AT_PLACE`, `VISITED_PLACE` and every future authored-only condition unless a later generated-rules version explicitly admits it. Profile configuration cannot enable a type absent from this table.

### 4.3 Exhaustive effect subset

Generated v1 permits exactly:

| Blueprint discriminator | Existing engine type | Required state |
| --- | --- | --- |
| `COUNTER_ADD` | `Effect.CounterAdd` | Counter declaration |
| `COUNTER_SET` | `Effect.CounterSet` | Counter declaration |
| `FLAG_SET` | `Effect.FlagSet` | Flag declaration |
| `SET_ADD` | `Effect.SetAdd` | Finite-set declaration and declared member |
| `SET_REMOVE` | `Effect.SetRemove` | Finite-set declaration and declared member |

Generated v1 forbids `EMIT_EVENT`, `END_RUN`, `GO_TO` and every future authored-only effect. A generated ending is represented only by entering a validated terminal scene whose `outcomeId` maps one-to-one to an outcome. No effect may redirect a route or terminate a run.

### 4.4 Allowed mechanic locations

- Objective `completeWhen`: one non-null generated condition.
- Choice `requires`: null or one generated condition.
- Choice `effects`: ordered list of zero to the effective maximum.
- No phase, actor, state declaration, scene, ending or outcome contains hidden mechanics.
- No scene-entry effects, automatic branches, objective `onComplete` effects, result facts, event payloads or place mutations in generated v1.

If a field is not listed above, prose in that field has no mechanical interpretation.

## 5. One engine-owned operator registry

Introduce a scenario-neutral registry/descriptor set in core, for example `GeneratedMechanicsV1`. Exact naming may follow package conventions, but the registry must:

- enumerate every generated discriminator once;
- distinguish CONDITION and EFFECT categories;
- declare required state kind: NONE, COUNTER, FLAG, SET, SET_MEMBER or SCENE;
- expose whether the node is composite and its child shape;
- identify its existing `Condition`/`Effect` mapping without accepting a class name from data;
- expose the stable generated-rules contract version;
- contain no prompt text, locale, story constants, provider details or JSON library dependency.

Consumers may keep local switch expressions for typed construction, but tests must prove their accepted discriminator set equals the registry exactly. Prefer exhaustive enum switches with no permissive default.

The registry is the upper bound. The effective vocabulary is:

```text
registry v1
  ∩ validated profile capabilities
  ∩ selected challenge preset
  ∩ trusted host-narrowed effective allowlist
```

Every intersection is narrowing only. An empty effect allowlist means only `effects:[]`; it does not enable no-op unknown effects. An empty condition allowlist cannot support objectives in blueprint v1 and must already be rejected as an unsatisfiable profile/preparation context.

Adding a registry entry alone must not enable it. A new generated operator requires parser/schema shape, binder, validation semantics, runtime semantics, compilation mapping, adversarial tests and a versioning decision.

## 6. Binding untrusted blueprint mechanics

### 6.1 Boundary

The parser output remains untrusted. After 27.21 has established declarations and references, bind each mechanic to an immutable internal form associated with its exact declaration. A recommended internal result is `ValidatedMechanicsPlan`; it is not a Pack, runtime `Rules` object or `MaterializedGameDefinition`.

The bound plan may use:

- existing immutable `Condition` and `Effect` records with validated symbolic IDs, or
- internal bound nodes containing declaration indexes instead of repeated strings.

Either design is acceptable only if it has one exhaustive mapping to the existing DSL and cannot express an operator outside generated-rules-v1. Avoid maintaining a third public condition/effect hierarchy.

### 6.2 Ownership and construction

- Construction occurs only inside the semantic validator/binder after trusted context and cross-reference checks.
- No public constructor accepts an arbitrary blueprint plus `validated=true`.
- The plan is bound one-to-one to the `SemanticallyValidatedBlueprint`, profile identity/fingerprint and semantic contract version.
- Lists and nested values are immutable and preserve declaration/effect order.
- The plan contains no narrative text, prompts, suggestion, provider payload, Java class name or serialized expression.
- `toString()` is redacted and does not enumerate model-provided IDs.

27.23 may consume this plan through the validated wrapper or recreate engine values only via the same binder. It must not reparse JSON or reinterpret string discriminators independently.

### 6.3 Mapping rules

Mapping is total and deterministic:

- Every accepted blueprint condition maps to exactly one existing `Condition` variant.
- Every accepted blueprint effect maps to exactly one existing `Effect` variant.
- Child order for ALL/ANY and effect order are preserved.
- Null choice requirement remains null/always enabled; do not synthesize a `TRUE` operator.
- Blueprint IDs remain symbolic during 27.22. Trusted runtime ID assignment belongs to 27.23.
- No unknown operator maps to false, true, no-op, empty effects or a fallback type.

Binding failure after semantic PASS indicates an engine defect or stale contract, not a repairable model response. Fail content-free and do not spend another provider attempt.

## 7. Shared condition evaluation

Extract a pure condition evaluator from `RunImpl` or introduce an equivalent shared primitive. A suitable shape is:

```java
boolean evaluate(Condition condition, RuleStateView state)
```

`RuleStateView` exposes typed reads for counters, flags, finite sets, visited scenes, step and places as needed by the authored DSL. It contains no mutation, UI, Pack parsing or generation dependency.

Requirements:

- `RunImpl` uses the shared evaluator for existing authored conditions.
- `DefaultBlueprintSemanticValidator` evaluates its bound generated conditions through the same evaluator.
- Evaluation is deterministic and side-effect free.
- ALL/ANY preserve existing short-circuit behavior; child order remains stable for diagnostics even though conditions have no side effects.
- NOT negates exactly one child.
- Generated bound references are guaranteed present. Missing generated references are internal invariant failures, never false/default values.
- Existing authored runtime behavior for already validated Packs remains compatible. If `RunImpl` retains defensive missing-reference defaults at its adapter boundary, those defaults must not be exposed to generated mechanics.

The generated subset retains the exact truth table defined in 27.21. `VISITED_SCENE` observes the start scene initially and the destination after a transition, matching runtime visit ordering.

Do not add an expression parser to implement composites. They remain typed tree nodes with the established depth/node ceilings.

## 8. Shared state-effect semantics

### 8.1 Pure generated subset

Introduce a shared state mutation primitive for the five generated effects, or a lower-level mutation calculator used by both validator and runtime. It must:

- apply effects in array order;
- calculate counter addition with a `long` intermediate;
- distinguish in-range result from overflow/underflow before integer conversion;
- preserve flag replacement semantics;
- treat adding an existing set member as an idempotent no-op;
- treat removing an absent set member as an idempotent no-op;
- reject an undeclared target/member at the validated-generated boundary;
- report a bounded engine-owned failure code rather than an exception containing content.

An immutable transition result or transactional copy is preferred for validation. A failed generated transition must not leave partially mutated validator state.

### 8.2 Ordered effects and intermediate bounds

Bounds apply after every ordered counter effect, not only at the end of the list. For a counter declared 0–3 at value 3:

```text
[COUNTER_ADD +1, COUNTER_ADD -1]
```

is invalid on that reachable transition because the first intermediate value is 4. Reordering to `-1,+1` has a different valid meaning. The engine never sorts, combines or algebraically simplifies effects.

`COUNTER_SET` must target a value inside the generated counter's declared interval on every path, even though it does not depend on prior value. `COUNTER_ADD` absolute delta is nonzero and no greater than the profile's `maxCounterDelta`.

### 8.3 Authored clamp compatibility

`RunImpl` currently clamps authored counter mutations to `CounterDef.min/max`. Preserve this behavior for existing Packs and snapshots.

Generated semantics do not use clamping as a game rule. Spec 27.21 rejects a blueprint when any reachable intermediate counter mutation would leave its interval. Therefore, for every accepted generated transition:

```text
validated exact result == runtime clamped result
```

because the exact result is already in range. Add differential tests for this invariant. Do not weaken 27.21 to accept overflow because runtime can clamp, and do not change authored Pack behavior to throw on overflow.

The shared primitive may expose explicit `REJECT_OUT_OF_RANGE` and `CLAMP_TO_DECLARATION` policies internally if needed. Policy selection is engine-owned: generated proof uses reject; historical authored runtime keeps clamp. No profile, blueprint or player input selects it.

### 8.4 Authored-only effects

`EMIT_EVENT`, `END_RUN` and `GO_TO` remain handled by the authored runtime path. If `RunImpl.applyEffects()` is refactored, delegate only the common state-effect subset and retain event/end/place side effects in `RunImpl` or another trusted authored service. Do not create placeholder implementations for generated games.

## 9. State declarations and limits

The generated mechanics binder rechecks the narrower trusted values from profile, challenge preset and host constraints. Absolute v1 maxima remain those established in 27.18/27.19:

| State/structure | Limit |
| --- | --- |
| Counters | 0–4 |
| Flags | 0–12 |
| Sets | 0–2 |
| Values per set | 1–8 |
| Counter global interval | Profile bounded, within 0–20 |
| Counter add magnitude | 1–5 and no greater than profile maximum |
| Condition depth | 1–4 |
| Condition nodes per expression | 1–32 |
| Composite children | 1–16 |
| Effects per choice | 0–6 |
| Explored configurations | 1–100000 trusted profile ceiling |

State IDs and set members use the lexical symbolic contract from 27.19. No map key can be created dynamically at runtime.

Counter declarations preserve exact generated `min`, `max` and `initial`. Flag and set initial values are exact. Finite sets can contain only declared members and their runtime representation must not acquire another value. Objective completion is monotonic and is not a general writable flag.

An unused declaration remains legal as specified by 27.21; output-quality review may reject decorative content, but the mechanics binder does not invent a use or discard it.

## 10. Conditions, objectives and timing

The authoritative transition order remains:

1. At the current decision scene, evaluate each choice requirement against the current state.
2. Select one enabled choice.
3. Apply that choice's effects in declared order.
4. Move to the destination scene.
5. Mark the destination visited.
6. Evaluate all still-active objective predicates in declaration order.
7. Mark newly true objectives complete; apply no objective completion effects in generated v1.
8. If the destination is an ending, resolve its declared outcome.

The start scene is marked visited before initial objective evaluation. Objectives true in initial state begin complete. Completed objectives remain complete even if their predicate later becomes false.

Choice requirements cannot reference objective completion directly. Objectives cannot trigger effects, routes or other objective dependencies. Outcomes cannot alter state. These restrictions keep the proof finite and prevent implicit mechanics outside the closed DSL.

27.23/27.24 must preserve this order when wiring compiled definitions into `RunImpl`. If the current runtime constructor/start path evaluates objectives at a different instant for a compiled generated definition, adapt the integration rather than changing this contract silently.

## 11. Cross-reference and capability validation

Keep defense in depth across layers:

| Layer | Responsibility |
| --- | --- |
| Profile loader | Registry subset, capacity coherence and challenge narrowing. |
| Specialized schema | Remove disabled branches and narrow numeric/list limits for provider guidance. |
| Blueprint parser | Strict shape, discriminator, resource and immediate numeric limits. |
| Semantic validator/binder | Trusted-context recheck, declaration binding, cross-references, declaration-relative values and complete playability proof. |
| 27.23 compiler | Accept only semantically validated/bound mechanics; assert total mapping and trusted ID binding. |
| Runtime | Execute typed engine rules only; never inspect blueprint JSON or model strings. |

Required cross-reference rules remain:

- counter conditions/effects bind only to counters;
- flag conditions/effects bind only to flags;
- set conditions/effects bind only to sets, and values bind to members of that exact set;
- visited-scene conditions bind only to scenes in the same blueprint;
- no wrong-namespace fallback when symbols have equal spelling;
- no missing reference defaults at the generated boundary;
- no generated reference may resolve into an authored Pack object, fallback game or another run.

The binder uses indexes built from the exact accepted blueprint. It does not consult a global registry of game objects.

## 12. Security and trust rules

The following are binding prohibitions:

- Never load a Java class, method, bean or service based on model output.
- Never evaluate a condition/effect string with JavaScript, SpEL, MVEL, JEXL, OGNL, template engines or a shell.
- Never deserialize polymorphic class names or enable Jackson default typing for blueprint mechanics.
- Never accept a generic `operator`, `expression`, `script`, `code`, `formula`, `path`, `function`, `arguments`, `payload` or `metadata` escape hatch.
- Never fetch a URL, file or external resource named by a mechanic.
- Never promote narrative text to a label key, event name, variable name or executable identifier without 27.23's deterministic engine-owned mapping.
- Never let prompt instructions, provider schema extensions or unknown JSON fields expand the registry.
- Never log mechanic-bearing provider JSON or model-provided symbols on failure.

Unknown or disabled discriminators fail closed before binding. There is no compatibility mode that converts them to false/no-op.

## 13. Diagnostics and privacy

Reuse the bounded `BlueprintIssue` diagnostics and stable codes established by 27.19–27.21. Where more precision is required, use engine-owned codes such as:

- `BLUEPRINT_MECHANIC_UNSUPPORTED`
- `BLUEPRINT_MECHANIC_DISABLED`
- `BLUEPRINT_MECHANIC_BINDING_INVALID`
- `BLUEPRINT_CONDITION_INVALID`
- `BLUEPRINT_EFFECT_INVALID`
- `BLUEPRINT_STATE_UNKNOWN`
- `BLUEPRINT_SET_VALUE_UNKNOWN`
- `BLUEPRINT_STATE_BOUNDS_VIOLATED`
- `BLUEPRINT_MECHANICS_CONTRACT_MISMATCH`

Do not rename already released 27.21 codes merely for package aesthetics. Consolidate aliases only with explicit compatibility tests for repair feedback.

Pointers contain known field names and numeric indexes only. Messages never include model-provided IDs, values or prose. Shared evaluator/mutator exceptions are programming diagnostics and must remain content-free. Bound plan, state views and transition results use redacted `toString()` methods.

Metrics may report contract version, operator enum, status and numeric counts. They may not report state IDs, set members, story text, prompts or complete rule trees.

## 14. Authored-game compatibility

This specification narrows generated games only. It must not remove or change authored support for:

- `STEP_AT_LEAST`, `AT_PLACE`, `VISITED_PLACE`;
- `EMIT_EVENT`, `END_RUN`, `GO_TO`;
- scene `onEnter`, branches, objective `onComplete`, result facts and places;
- counter display metadata and existing `maxDelta` validation;
- counter clamping in `RunImpl`;
- missing-reference validation behavior and existing Pack diagnostics;
- existing snapshot state and restoration.

When extracting shared semantics, run the authored Pack/rules/runtime suites before and after the refactor. `RuleReferenceValidator`, `RulesParser`, `FullGeneratedGameValidator`, Willow Marsh and all fixtures must retain their observable behavior and issue codes.

Do not serialize a blueprint as `rules.json` and load it through a temporary in-memory Pack. Generated compilation has its own trusted boundary and 27.23 will materialize domain values directly.

## 17. Acceptance criteria and handoff

27.22 is complete when:

- The generated-rules-v1 vocabulary has one engine-owned exhaustive registry and remains exactly ten conditions/five effects.
- Every accepted blueprint mechanic binds deterministically to the existing closed engine DSL; no scripts, expressions, class names or unknown no-ops exist.
- The 27.21 validator and authored runtime use shared condition semantics and shared state-mutation primitives, or demonstrate equivalently strong exhaustive differential parity without duplicated semantic ambiguity.
- Effect order, visit/objective timing, finite-set behavior and counter intermediate bounds match the contract in this specification and 27.21.
- Generated counter overflow is rejected during proof while historical authored runtime clamping remains unchanged.
- Profile/challenge/host allowlists only narrow capabilities and every consumer is registry-parity tested.
- The semantically validated wrapper is bound to the generated mechanics contract and provides a compiler-ready internal mechanics plan without runtime IDs.
- Existing Packs, Willow Marsh, generated-content presentation, rules, snapshots and validation diagnostics remain compatible.
- No dynamic game is compiled, started, persisted or exposed through CLI by this change.

**Next: 27.23 — Blueprint Compilation and Materialized Game Definition.** It consumes only a reviewed `SemanticallyValidatedBlueprint` plus its bound generated-rules-v1 mechanics, assigns trusted deterministic IDs, creates immutable scenes/rules/objectives/outcomes/localization data, performs final definition validation and emits a `MaterializedGameDefinition`. It must not reparse provider JSON, reinterpret mechanic strings, execute gameplay or invent mechanics absent from this contract.
