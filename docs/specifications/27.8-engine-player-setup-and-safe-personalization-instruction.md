# Spec 27.8 — Player Setup and Safe Personalization

**Type:** Implementation specification  
**Parent:** Spec 27.7 — Challenges, Consequences, and Generated Endings  
**Depends on:** Specs 25, 26.1, 27.1–27.3, and 27.4–27.7  
**Baseline:** repository commit `b00c545`, plus the approved designs in Specs 27.4–27.7. The current start-input definitions, manifest parser, start validation, PII scrubber, input guard, snapshots, session start request, CLI arguments, and generated pipeline initialization were inspected while writing this specification. The build was not run.  
**Status:** Ready for implementation after Spec 27.7  
**Primary outcome:** A player can start a full generated game from the CLI through clear, localized setup questions instead of assembling command-line arguments. Trusted preset answers and optional safe free text can personalize initial generation. The player sees a provider disclosure before any external call. Raw and scrubbed free text remain transient and never enter snapshots, stores, scripts, logs, diagnostics, lazy-scene context, or generated continuity memory.

---

## 1. Problem

The engine already supports pack-declared start inputs:

- `ENUM`;
- `ENUM_SET`;
- `FREE_TEXT`.

The CLI already accepts repeated `--input key=value`, and the engine validates declared values. However, this is not yet a normal player setup flow:

- a player must know internal input IDs and allowed raw values;
- option values do not have a first-class localized display-label contract;
- there is no interactive question flow;
- there is no clear disclosure before setup data is sent to a text provider;
- command-line free text can leak into shell history and process listings;
- script echo can reveal free text;
- start free text is validated and then removed before `GenerationPipeline.initialize()`, so it currently cannot personalize generated content;
- the generation catalog does not declare which inputs each initial generation stage may receive;
- raw start inputs may be held in asynchronous session preparation data unless the host explicitly removes them;
- there is no clear retry/cancel flow for invalid, blocked, or unavailable free-text safety checks.

Spec 27.8 adds a provider-neutral setup contract, an interactive CLI flow, and a transient safe-input boundary. It preserves the rule that packs and engine mechanics—not setup prose—control the game.

## 2. Current implementation findings

| ID | Finding | Consequence |
|---|---|---|
| F1 | `StartInputDef` already supports enum, enum-set, and free-text values with required flags and localized question label keys. | Reuse the existing declarations instead of adding a parallel input type system. |
| F2 | Enum values are internal strings with no separate option label keys. | A setup presentation resource is needed for friendly localized choices. |
| F3 | `ConsoleArgs` accepts `--input key=value`. | Keep it for automation and advanced use, but do not use it for full-game free text. |
| F4 | `DefaultEngine.validateStartRequest` normalizes, bounds, scrubs, and guards free text. | Reuse and refactor this safety path; do not duplicate it in the CLI. |
| F5 | `DefaultEngine.start` removes free-text start inputs before constructing the run and before initializing generation. | Free text is private, but it currently cannot influence the generated story. |
| F6 | `GenerationPipeline.initialize()` receives no start-input context. | Add an explicit transient prepared-input parameter. |
| F7 | `RunSnapshot` intentionally omits free-text start inputs while preserving non-text inputs. | Keep this invariant. Resume relies on accepted artifacts, not original free text. |
| F8 | Session start requests may outlive the immediate caller while a run is `PREPARING`. | Raw or scrubbed free text cannot be placed in persistent pending-start storage. |
| F9 | Spec 25 requires local PII scrubbing before any external guard/provider and fail-closed behavior when required safety is unavailable. | Setup must use exactly that boundary. |
| F10 | Full generated games already have authored fallbacks. | Missing provider or dropped transient personalization cannot make a run unplayable. |

## 3. Goals and non-goals

### 3.1 Goals

1. Add a versioned setup-presentation contract for full generated games.
2. Present localized enum, enum-set, and optional free-text questions interactively in the CLI.
3. Show a clear disclosure before any setup data is sent to an external-capable generator.
4. Let players review preset selections and confirm start without echoing free text.
5. Pass only declared, validated, stage-allowed setup data into initial generation.
6. Keep free text transient and restricted to THEME/SCENARIO initialization.
7. Keep preset input persistence and deterministic resume behavior.
8. Support non-interactive scripts using trusted preset values.
9. Allow retry, skip, back, cancel, and safe fallback behavior.
10. Preserve authored packs, schema-v1 generated packs, and existing `RunRequest` compatibility.

### 3.2 Non-goals

- Adding user/profile preference storage.
- Reading CapyBee mood, child profile, check-ins, missions, or account data.
- Remembering setup free text between runs.
- Sending raw free text to any provider.
- Letting setup values define rules, routes, objectives, effects, outcomes, result classes, budgets, or safety policy.
- Adding arbitrary numeric/date/file inputs.
- Adding in-game text commands or CLI status/navigation commands; Spec 27.9 owns those.
- Solving provider legal terms or naming a specific vendor in engine core.
- Adding web setup screens; Spec 28 owns client rendering.
- Adding production cross-machine transport for ephemeral free text.

## 4. Decisions

| ID | Decision |
|---|---|
| D1 | Existing `StartInputDef` remains the validation source of truth. A new generation setup resource supplies presentation and stage-routing metadata only. |
| D2 | Full-game free-text start inputs are optional. Required free text is rejected at pack load because safe recovery cannot depend on retaining it. |
| D3 | Preset input values (`ENUM`, `ENUM_SET`) may be persisted in snapshots and session pending-start data exactly as today. |
| D4 | Raw, normalized, scrubbed, redacted, and approved free-text values are never persisted. Typed redaction placeholders are still text and are not persisted. |
| D5 | Full-game free text cannot be supplied through `--input`, command-line arguments, environment variables, URLs, or setup script files. Interactive stdin is the only production CLI source. |
| D6 | Automated free-text tests inject an in-memory input stream directly and assert the text is not echoed. Normal CLI script files support preset inputs only. |
| D7 | Free text follows Spec 25 in this order: normalize, bound, locally scrub PII, inspect scrubbed text, then make it available transiently to allowed initial generation stages. |
| D8 | Free text may be routed only to `THEME` and/or `SCENARIO`. CAST, QUEST, SCENE, repair summaries, continuity facts, endings, and diagnostics never receive it directly. |
| D9 | Accepted story/theme artifacts may naturally reflect safe personalization. Resume uses those artifacts and never needs the original text. |
| D10 | The CLI shows provider disclosure before collection of free text and before the first provider call. Refusal or cancellation creates no run and makes no call. |
| D11 | Interactive setup is the default when stdin is a terminal and any declared question lacks a supplied preset answer. Script mode is non-interactive. |
| D12 | In non-interactive mode, missing required preset input is an error; missing optional input uses a declared default or is omitted. |
| D13 | A configured default is allowed only for enum/enum-set input, must be valid, and is visible to the player. Free text has no default. |
| D14 | Setup values influence narrative context only. Mechanics cannot reference free-text content, and generated output cannot expand the trusted game contract. |
| D15 | Provider absence still allows setup and starts the fallback game. The CLI clearly says that no external generation is available and does not request free text that would have no effect. |

## 5. Setup resource

### 5.1 Location and indexing

Add one optional file for generation-catalog schema v2:

```text
generation/setup.json
```

Add nullable `setupResource` to the Spec 27.4 `RunContract`. `FULL_GAME` requires it. Content-only generated packs may omit it.

The path follows existing safe pack-relative resource rules, is listed in `pack.json.files`, and is parsed during pack loading.

### 5.2 JSON shape

```json
{
  "schemaVersion": 1,
  "questions": [
    {
      "inputId": "tone",
      "helpKey": "setup.tone.help",
      "stages": ["THEME", "SCENARIO"],
      "defaultValues": ["calm"],
      "options": [
        {"value": "calm", "labelKey": "setup.tone.calm"},
        {"value": "curious", "labelKey": "setup.tone.curious"}
      ]
    },
    {
      "inputId": "interests",
      "helpKey": "setup.interests.help",
      "stages": ["SCENARIO"],
      "defaultValues": [],
      "options": [
        {"value": "animals", "labelKey": "setup.interests.animals"},
        {"value": "mystery", "labelKey": "setup.interests.mystery"}
      ]
    },
    {
      "inputId": "story-wish",
      "helpKey": "setup.storyWish.help",
      "stages": ["THEME"],
      "freeTextNoticeKey": "setup.storyWish.notice"
    }
  ]
}
```

Question title continues to come from `StartInputDef.labelKey`. The setup resource does not redefine type, required flag, enum allow-list, enum-set maximum, or free-text maximum.

### 5.3 Java types

```java
public record GenerationSetup(
    int schemaVersion,
    List<SetupQuestion> questions) {}

public record SetupQuestion(
    String inputId,
    String helpKey,
    List<GenerationCatalog.Stage> stages,
    List<String> defaultValues,
    List<SetupOption> options,
    String freeTextNoticeKey) {}

public record SetupOption(
    String value,
    String labelKey) {}
```

All lists are immutable. `SUPPORTED_SCHEMA_VERSION = 1`.

### 5.4 Cross-validation

For a full game:

- exactly one setup question for every manifest start input;
- no question for an unknown input;
- question order is the manifest `startInputs` order;
- `inputId` is unique;
- stages contain only configured `THEME` and/or `SCENARIO`;
- every question routes to at least one configured stage;
- enum question options exactly cover the declared values, in declared order;
- enum-set question options exactly cover the declared values, in declared order;
- option values are unique and equal trusted raw values;
- option label keys and help keys resolve in every supported locale;
- free-text notice key is required for free text and forbidden otherwise;
- free-text input is optional and has no defaults/options;
- enum default is empty only when optional, otherwise exactly one valid value;
- enum-set defaults contain unique valid values and do not exceed `maxItems`;
- required preset inputs have a valid default only if non-interactive fallback is intended; otherwise scripts must supply them;
- setup schema is closed; unknown fields fail.

### 5.5 Limits

- 0–12 questions;
- 1–32 options per enum/enum-set question;
- 0–8 selected enum-set values, further limited by manifest `maxItems`;
- 1–120 code points for resolved question label;
- 0–240 for resolved help text;
- 1–120 for resolved option label;
- at most one free-text start question for a full game;
- full-game free-text maximum is `1..300` code points, below the global Spec 25 limit of 500.

## 6. Prepared start inputs

### 6.1 Purpose

The current start flow validates free text and then discards it before generation. Introduce a short-lived, provider-neutral boundary object:

```java
public final class PreparedStartInputs {
  public Map<String, String> persistentValues();
  public Map<String, SafeTextInput> transientTextValues();
  public List<Issue> issues();
  public boolean ok();
}
```

The exact API may be a record if its `toString()` is explicitly redacted. Requirements:

- maps preserve manifest order;
- persistent values contain only enum and canonical enum-set values;
- transient values contain only locally scrubbed, guard-approved `SafeTextInput`;
- no method returns raw input;
- `toString()` reports IDs/counts only;
- no equality/hash implementation should accidentally expose text in test failure output;
- lifecycle is limited to one start operation.

### 6.2 Preparation service

Extract start-input work from `DefaultEngine.validateStartRequest` into a reusable engine-core component, for example:

```java
public final class StartInputProcessor {
  public PreparedStartInputs prepare(
      Pack pack,
      LocaleTag locale,
      Map<String, String> submitted,
      InputGuard guard);
}
```

`DefaultEngine.start` and session/CLI orchestration use the same processor. Do not let the CLI become a second validator.

### 6.3 Preset normalization

- trim keys and values using current rules;
- enum values must exactly match trusted values;
- enum-set input accepts comma-separated transport form at API/CLI boundary;
- canonical persistent form is comma-separated trusted values in manifest value order, not user entry order;
- duplicates fail rather than silently collapse;
- unknown inputs fail;
- missing required inputs fail;
- defaults are applied by the setup orchestrator before engine preparation and then validated normally.

### 6.4 Free-text processing

For each submitted free-text value:

1. confirm manifest and content policy allow it;
2. normalize Unicode/controls/line endings and trim;
3. enforce the pack limit in Unicode code points;
4. scrub PII locally;
5. call `InputGuard` with scrubbed text and minimal policy context;
6. accept only `ALLOW` or `ALLOW_REDACTED`;
7. create transient `SafeTextInput` with no raw-text field;
8. add content-free `INPUT_REDACTED` warning when applicable;
9. drop all raw local references after preparation returns.

`BLOCK`, `NEEDS_CLARIFICATION`, unavailable guard, invalid response, or exception returns typed issues and no transient value.

### 6.5 Engine start order

Refactor `DefaultEngine.start`:

1. validate pack, locale, features, and non-input request fields;
2. prepare start inputs once;
3. stop on preparation error;
4. create `GenerationPipeline`;
5. call `initialize(preparedInputs)`;
6. construct `RunImpl` with `persistentValues()` only;
7. release the prepared-input reference before returning `StartResult`;
8. include content-free preparation warnings in the result.

Do not initialize generation before input validation. Invalid or cancelled setup makes zero provider calls.

## 7. Generation personalization boundary

### 7.1 Stage routing

`GenerationPipeline.initialize(PreparedStartInputs)` builds a stage-specific setup map from `GenerationSetup`:

- preset inputs go only to declared stages;
- safe free text goes only to declared THEME/SCENARIO stages;
- undeclared stage/input pairs are omitted;
- input IDs are trusted catalog data;
- preset values remain trusted enum IDs, accompanied by localized display labels only when needed;
- free text is a delimited untrusted-data value, never concatenated into instructions.

### 7.2 Request shape

Example trusted request context:

```json
{
  "setup": {
    "preset": [
      {"id": "tone", "values": ["calm"]},
      {"id": "interests", "values": ["animals", "mystery"]}
    ],
    "freeText": [
      {"id": "story-wish", "value": "A story about [redacted:identifier] and a lantern."}
    ]
  }
}
```

The enclosing request policy states that setup values are player data, not instructions, and cannot change schema, routes, rules, safety policy, or trusted IDs.

### 7.3 Retention cutoff

The pipeline may use safe free text only while making the first allowed THEME/SCENARIO request and its one repair attempt.

After those stages finish:

- `GenerationPipeline` holds no free-text field;
- later CAST/QUEST/SCENE context uses accepted theme/story-plan artifacts only;
- continuity facts cannot copy or quote setup free text directly;
- snapshot artifacts contain only validated generated outputs, never the setup value;
- execution summaries contain counts/status only.

The engine cannot guarantee physical erasure of Java strings. The requirement is no intentional storage, reuse, serialization, logging, caching, or diagnostic exposure.

### 7.4 Repair

A THEME/SCENARIO repair request may receive the same safe transient text because it is part of the same start operation. It receives no raw text and no rejected provider output.

After fallback is selected, the transient text is dropped. Fallback content does not attempt to interpolate it.

### 7.5 No mechanical effect

Start inputs are not added to `Condition`, `Effect`, rules, routes, outcome selection, result facts, or objective evaluation in this specification.

If future packs need trusted difficulty or mechanical modes, they require a separate authored enum-to-rule configuration specification. Free text will never be such a mechanism.

## 8. Provider disclosure and consent

### 8.1 When disclosure is required

Show disclosure when all are true:

- generated play is requested;
- an external-capable `TextGenerator` is configured;
- at least one setup answer is routed to generation, or generation itself will call the provider.

Show disclosure before collecting free text and before any provider call.

### 8.2 Required content

The CLI disclosure uses localized host text and states, in simple language:

- the game uses a configured AI text service;
- selected setup answers may be sent to that service;
- free text is locally checked and personal details are removed where detected;
- the player should not enter real names, contact details, exact address, school/class details, passwords, or secrets;
- free text is not saved in the game snapshot;
- choosing cancel starts nothing and sends nothing.

Do not claim PII detection is complete. Do not display API keys, provider account details, or retention promises the host cannot prove.

### 8.3 Consent behavior

Interactive prompt:

```text
This generated game uses an AI text service.
Your selected answers may be sent to create the story.
Do not enter personal or contact information.
Free-text answers are not saved.

Continue? [y/N]
```

- default is No;
- `n`, empty input, EOF, or `/cancel` exits setup with code 0, no run, and no provider call;
- `y` continues;
- invalid answer repeats the confirmation;
- do not persist consent in engine snapshots or infer long-term account consent.

### 8.4 Non-interactive acknowledgement

Add CLI flag:

```text
--accept-generation-disclosure
```

Rules:

- valid only with `--generated` and non-interactive/scripted play;
- contains no personal data and may appear in shell history;
- required when a configured provider may be called from script mode;
- not required when no provider is configured and the run will use fallbacks;
- live smoke requires it because a real provider call is mandatory;
- help text explains that it acknowledges one invocation only.

This is a CLI automation acknowledgement, not a legal-account-consent storage mechanism.

### 8.5 Provider unavailable

When no generator is configured:

- print a short notice that authored fallbacks will be used;
- do not show external-provider disclosure as if data will leave the process;
- do not ask the free-text question because its value cannot affect fallback content;
- use preset answers for local run metadata only where already supported;
- continue to a complete fallback game.

## 9. Interactive CLI setup

### 9.1 Entry conditions

Run interactive setup when:

- pack has a full-game setup resource;
- `--generated` is selected;
- no gameplay `--script` is active;
- stdin is interactive or the caller supplies an interactive stream in tests;
- at least one question is not fully answered by allowed preset arguments/defaults.

The CLI must not rely only on `System.console()` because tests and IDE terminals may provide streams without a Java console. Add injectable interaction-mode detection in `ConsoleTuning` or a small `ConsoleEnvironment` port.

### 9.2 Flow

1. Load and validate the pack before asking questions.
2. Resolve locale before rendering setup labels.
3. Determine whether a provider is configured.
4. Show disclosure/confirmation when required.
5. Ask questions in manifest/setup order.
6. Validate each answer immediately through trusted local rules.
7. For free text, call the shared processor/guard and retry on a recoverable issue.
8. Show a review screen with preset labels and free text as `[provided]` or `[provided, personal details removed]`.
9. Allow confirm, back, or cancel.
10. Start the engine only after confirmation.

### 9.3 Enum question

Example:

```text
Choose a story mood:
  1) Calm
  2) Curious
  3) Funny
Enter 1-3 [default: Calm], b to go back, or q to cancel:
```

- accept displayed number;
- advanced exact value IDs are accepted only through validated `--input`, not interactive text;
- empty input selects visible default when present;
- no default plus optional input means empty skips;
- invalid input repeats without changing prior answers.

### 9.4 Enum-set question

Example:

```text
Choose up to 2 interests:
  1) Animals
  2) Mystery
  3) Exploration
Enter numbers separated by commas, empty to skip, b to go back, or q to cancel:
```

- accept unique displayed numbers;
- normalize to trusted manifest value order;
- enforce `maxItems`;
- duplicates and invalid numbers produce a safe retry message;
- empty follows required/default rules.

### 9.5 Free-text question

Before the prompt, display its localized notice and current maximum. Do not echo the entered value again in review or debug output.

Commands:

- empty skips optional text;
- `b` alone goes back;
- `q` or `/cancel` alone cancels;
- other input is treated as data, not a command;
- a literal one-character story wish `b` or `q` is not supported in v1; localized help states these reserved setup commands.

On `INPUT_BLOCKED`, `INPUT_NEEDS_CLARIFICATION`, `INPUT_TOO_LONG`, or invalid characters, show only the safe issue message and ask again. On `INPUT_GUARD_UNAVAILABLE`, offer:

```text
Free-text safety checking is unavailable.
Press Enter to skip this optional question, or q to cancel.
```

Do not allow unchecked text through.

### 9.6 Review

Example:

```text
Game setup
  Mood: Calm
  Interests: Animals, Mystery
  Story wish: [provided, personal details removed]

Start this game? [Y/n], b to change answers, or q to cancel:
```

Review uses localized labels, never internal IDs. Free-text content is never displayed, even when unchanged.

### 9.7 Cancellation and EOF

Cancellation or EOF during setup:

- exits 0;
- prints a short “Setup cancelled.” message;
- creates no run/store record;
- performs no provider call;
- writes no setup values to a snapshot or store.

## 10. CLI arguments and scripts

### 10.1 `--input`

Keep existing syntax for enum and enum-set inputs:

```text
--input tone=calm
--input interests=animals,mystery
```

For a full game, `--input` targeting `FREE_TEXT` fails before start:

```text
FREE_TEXT_COMMAND_LINE_FORBIDDEN: enter optional story text only in interactive setup.
```

Legacy schema-v1 behavior may continue accepting free text temporarily only if required for compatibility, but help must discourage it and tests must prove it does not enter logs/snapshots. Prefer applying the prohibition globally when compatibility review shows no supported caller depends on it.

### 10.2 Script mode

Gameplay `--script` remains non-interactive:

- it never consumes setup answers from gameplay lines;
- free text setup is omitted;
- preset inputs come from `--input` or defaults;
- missing required preset without default exits 2 before creating a run;
- provider call requires `--accept-generation-disclosure`;
- the script transcript never echoes setup free text because none is accepted;
- existing schema-v1 scripts remain compatible.

### 10.3 Session mode

Interactive setup occurs before `RunSessionService.start`. The session receives:

- persistent preset values in `StartRequest.startInputs`;
- transient safe free text through a new in-memory start attachment described in §11;
- no raw text.

Resuming an existing run never asks setup questions again. `--new` asks setup again for the new run.

### 10.4 Help

CLI help documents:

- interactive setup is automatic for full games;
- preset `--input` syntax;
- enum-set comma syntax;
- free text cannot be supplied on the command line or in scripts;
- disclosure acknowledgement for scripted generation;
- cancellation creates no run;
- provider-unavailable fallback behavior.

## 11. Session preparation and persistence

### 11.1 Persistent pending start

Before any session-store write, remove all free-text start-input keys. `PendingStart.startInputs` contains preset values only.

Add tests for in-memory and local stores proving synthetic raw, normalized, scrubbed, and placeholder markers are absent from serialized store JSON.

### 11.2 Ephemeral attachment

Add an in-process, bounded attachment registry owned by `RunSessionService`:

```java
interface StartInputAttachments {
  void put(UUID runId, Map<String, SafeTextInput> values, Instant expiresAt);
  Map<String, SafeTextInput> take(UUID runId);
  void remove(UUID runId);
}
```

Production local implementation requirements:

- memory only;
- values never serialized;
- `take` is one-shot;
- maximum entries follows pending-start limits;
- expiry no later than existing start TTL;
- remove on success, failure, cancellation, delete, timeout, and service close;
- redacted `toString()`;
- no content in metrics or diagnostics.

### 11.3 Start sequence

1. CLI prepares inputs.
2. Session service creates the persistent PREPARING record with presets only.
3. Service registers transient values by run ID in memory.
4. Worker claims the run and atomically `take`s the attachment.
5. Engine starts with presets plus transient prepared values.
6. Attachment is removed in `finally`.

The attachment never crosses process or machine boundaries in this specification.

### 11.4 Recovery after process loss

If a PREPARING run is recovered without its ephemeral attachment:

- continue with preset inputs only;
- do not mark the run corrupt;
- use ordinary provider generation or fallback without free-text personalization;
- record content-free warning code `START_TEXT_NOT_AVAILABLE` in startup issues/diagnostics;
- never ask the player to re-enter text during automatic recovery;
- required free text is forbidden, so completion remains possible.

Spec 27.10 will expand general recovery behavior but must preserve this privacy rule.

### 11.5 Classic mode

Classic console passes `PreparedStartInputs` directly to `Engine.start` through an overload or internal start request wrapper and immediately drops it after initialization. No registry is needed.

Keep public `RunRequest` source-compatible. Preferred addition:

```java
StartResult start(RunRequest request, PreparedStartInputs preparedInputs)
```

The existing `start(RunRequest)` prepares from its ordinary map for non-interactive/API callers, subject to the same prohibition and safety behavior. Do not put `SafeTextInput` inside `RunRequest`, records used in logs, or wire DTOs.

## 12. View and wire exposure

### 12.1 Pack information

Extend pack-info metadata for hosts with a setup-safe description:

```java
public record StartInputInfo(
    String id,
    String kind,
    boolean required,
    String label,
    String help,
    List<StartInputOptionInfo> options,
    int maxItems,
    int maxChars,
    boolean acceptsCommandLineValue) {}
```

This contains definitions only, never answers.

The existing web `GamePackInfoDto.startInputs` should become typed when the server adopts this metadata. It must not expose prompt files or provider instructions.

### 12.2 Active run view

Do not add setup answers to `View` or `GameViewV2`.

Generated `StoryInfo` naturally reflects accepted personalization. The player-facing view does not need to repeat input values.

### 12.3 Session/wire requests

No wire field for transient free text is added in this CLI-focused specification. Existing `startInputs` maps are safe only for preset values at persistent service boundaries.

Future web setup must define a request-scoped, non-queued free-text path or omit free text. It cannot reuse persistent pending-start JSON.

## 13. Safety and privacy

### 13.1 Prohibited locations

Raw, normalized, scrubbed, or approved free text must not appear in:

- `RunRequest.toString()` output;
- `RunState` or `RunSnapshot`;
- local/session store JSON;
- pending start records;
- commands or command logs;
- events or outbox records;
- generated execution summaries;
- diagnostics, debug lines, metrics, traces, exceptions, or issue messages;
- CLI review or script echo;
- setup script files written by the application;
- lazy-scene, continuity, or ending request context;
- cached/prefetched scene artifacts as copied input.

Accepted generated THEME/SCENARIO output may contain a transformed story idea, subject to output safety. It must not quote or preserve detected personal details.

### 13.2 Logging tests

Use distinct synthetic sentinels for:

- raw input;
- normalized input;
- scrubbed input;
- each redaction placeholder;
- blocked input;
- guard exception text.

Capture stdout, stderr, structured logs, snapshots, local-store files, JSON DTOs, events, metrics fakes, and exception messages. Assert prohibited sentinels are absent. The provider fake may record its request only inside the test and must prove the raw sentinel is absent.

### 13.3 Prompt injection

Setup free text remains data. Test strings attempting to:

- override instructions;
- request a different schema;
- add routes/effects;
- reveal prompts;
- request tool calls;
- choose an outcome;

must not change the trusted request schema or accepted artifact contract. Invalid output repairs/falls back normally.

### 13.4 Provider retention

Engine core remains provider-neutral and cannot promise provider retention terms. CLI documentation states that the configured provider may process approved setup data and points operators to deployment/provider policy documentation.

No pack may supply its own weaker disclosure or retention promise.

## 14. Error and issue codes

### 14.1 Pack errors

| Code | Meaning |
|---|---|
| `PACK_SETUP_REQUIRED` | A full-game contract has no setup resource. |
| `PACK_SETUP_VERSION_UNSUPPORTED` | Setup schema version is unsupported. |
| `PACK_SETUP_QUESTION_MISMATCH` | Questions do not exactly cover manifest start inputs in order. |
| `PACK_SETUP_STAGE_INVALID` | Input routes to an absent or forbidden generation stage. |
| `PACK_SETUP_OPTION_INVALID` | Option values/labels do not match the manifest declaration. |
| `PACK_SETUP_DEFAULT_INVALID` | Default is missing when required or violates the input declaration. |
| `PACK_SETUP_FREE_TEXT_INVALID` | Free text is required, repeated, too large, or missing its notice. |

### 14.2 Runtime/CLI issues

| Code | Meaning |
|---|---|

- Every full game has a validated localized setup resource.

- Scripted runs use preset inputs and one-invocation disclosure acknowledgement.
- Resume never asks setup questions again and never needs original free text.
- Setup cannot alter trusted mechanics, routes, objectives, outcomes, result facts, or safety policy.
- Authored and schema-v1 generated behavior remains compatible.
- Engine and application verification pass without network or credentials.
