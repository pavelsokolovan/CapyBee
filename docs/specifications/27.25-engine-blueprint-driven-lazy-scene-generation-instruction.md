# Spec 27.25 — Blueprint-Driven Lazy Scene Generation

**Type:** Implementation instruction
**Parent:** Dynamic-game series, following Spec 27.24
**Depends on:** Specs 22–27.24, especially `MaterializedGameDefinition`, `DynamicRuntimeGameDefinition`, `RuntimeGameDefinition`, `GenerationPipeline`, `GenerationOutputParser`, `GenerationQualityEvaluator`, `StoryContinuity` and `RunImpl`
**Baseline:** Inspected local `main` at commit `65ead15` on 2026-10-26. Specs 27.18–27.24 are implemented. Dynamic games bootstrap into the shared `RunImpl`, but remain presentation-pending: compiled scenes have empty blocks and unresolved labels, the dynamic runtime has no presentation resolver, and Pack-bound `GenerationArtifact`/`GenerationPipeline` cannot represent a materialized definition without fabricating a Pack. Unrelated UI working-tree changes were present and must not be modified. No build or live-provider test was run while preparing this document; implementation must inspect current HEAD again.
**Status:** Ready for implementation; dynamic games become player-facing in memory, while durable artifacts/resume and public CLI release remain owned by Specs 27.26–27.27
**Primary outcome:** Materialize story, cast and objectives from the accepted blueprint, lazily generate validated scene prose and choice labels against the compiled definition, preserve trusted mechanics exactly, and guarantee a definition-specific playable fallback for every scene and ending.
**Repository location:** `docs/specifications/27.25-engine-blueprint-driven-lazy-scene-generation-instruction.md`

---

## 1. Purpose

Spec 27.24 proves that a dynamic definition can execute through the existing runtime, but intentionally hides unresolved choices from player-facing views. Spec 27.25 installs the missing presentation layer:

```text
MaterializedGameDefinition
  -> deterministic story/cast/objective presentation
  -> validated fallback set for every compiled scene
  -> resolve start scene before publishing Started
  -> lazily resolve reachable scenes on entry/prefetch
  -> compose prose onto trusted Scene mechanics
  -> existing RunImpl view and command flow
```

Presentation may describe the game. It may never change what the game does. Routes, option IDs, requirements, effects, objective conditions, state declarations, outcome IDs and result classes always come from the verified materialized definition.

## 2. Scope and non-goals

### 2.1 In scope

- Add a dynamic presentation pipeline built from the accepted definition and validated generator-profile resources.
- Reuse/extract Pack-neutral structured-output parsing, quality evaluation, continuity selection and composition logic.
- Treat accepted blueprint story, actors, objectives, phases and scene plans as authoritative presentation context.
- Resolve the start scene synchronously before a dynamic run is published as presentation-ready.
- Lazily resolve later scenes on entry and optionally through bounded prefetch.
- Validate exact scene/choice/actor/objective coverage and ending narrative shape.
- Permit at most one bounded repair attempt per scene according to profile/host budgets.
- Prevalidate deterministic definition-specific fallback presentation for every scene.
- Expose story, characters, objectives and completed-run results through existing `View` fields.
- Preserve fixed-Pack Willow Marsh generation behavior and its existing artifacts.

### 2.2 Out of scope

- Changing the accepted graph, mechanics, phase assignment, cast, objectives, outcomes or trusted IDs.
- Re-running GAME_BLUEPRINT or making independent THEME, SCENARIO, CAST or QUEST provider calls.
- Durable artifact/definition codecs, fingerprints, snapshot support, migration and resume; Spec 27.26 owns them.
- CLI/session/web release, wizard UX, commands and production prefetch scheduling; Spec 27.27 owns them.
- Free-text commands, new provider purposes, images/assets, URLs, tools, scripts or arbitrary model memory.
- Sharing generated presentation across players or definitions.

## 4. No duplicate planning stages

The complete blueprint has already supplied reviewed:

- story title, premise, setting, tone tags and promises;
- actors with names, roles and descriptions;
- objectives with titles, descriptions and completion conditions;
- ordered phase goals/development/transitions;
- scene title/intent, actor/objective participation and choice intents;
- ending titles, result classes and mappings.

Build deterministic initial presentation views directly from this data. Do not ask the model to generate another theme, scenario, cast or quest and do not let later output rename/redefine them.

The dynamic equivalents of `storyPlan()`, `cast()` and `quests()` are immutable projections:

- `StoryInfo` from `definition.storyPlan()`;
- `CharacterItem` identity/name/description from `definition.actors()`;
- objective label/description from `definition.localizedContent()` and trusted objective IDs;
- discovery/current-character status from each trusted `ScenePlan.actorIds()` and visited/current scenes.

These projections consume zero provider calls and are available even when every scene uses fallback.

## 5. Dynamic presentation pipeline

### 5.1 Construction input

Create a dedicated `DynamicPresentationPipeline` (name may follow repository conventions) from:

```text
verified MaterializedGameDefinition
validated GeneratorProfile and ProfileIdentity
ResolvedGamePreferences and EffectiveGenerationConstraints
blueprint provider attempts already consumed
TextGenerator, IdSource and Clock
```

The bootstrap request already contains the validated profile/preferences/constraints. Construct the pipeline during the successful 27.24 operation before releasing preparation references. Never pass the original, normalized, scrubbed or approved suggestion into the presentation pipeline. Any accepted influence is already represented in reviewed definition content.

Before provider work, require exact agreement among request, definition and profile identity, locale, length preset, challenge preset, quality resource and relevant budgets. A mismatch is `DYNAMIC_PRESENTATION_CONFIGURATION_INVALID` and publishes no run.

### 5.2 Shared resolver boundary

Refactor `RunImpl` to depend on one narrow internal resolver, conceptually:

```java
interface RuntimePresentationResolver {
    Scene resolveScene(String trustedSceneId, List<String> visitedSceneIds);
    boolean hasScene(String trustedSceneId);
    boolean isResolved(String trustedSceneId);
    Optional<PresentationArtifact> prefetch(String trustedSceneId, List<String> visitedSceneIds);
    StoryInfo story();
    List<CharacterItem> characters(List<String> visited, String currentSceneId);
    List<ObjectivePresentation> objectives();
    Optional<EndingPresentation> ending(String trustedSceneId);
    GenerationExecutionSummary summary();
}
```

Exact API types may differ, but mechanics stay in `RunImpl`; a resolver returns a trusted scene with presentation composed onto it. Provide:

- a Pack adapter around the existing `GenerationPipeline` with unchanged behavior;
- a dynamic resolver backed by `DynamicPresentationPipeline`;
- no-op/authored behavior where no generation is enabled.

Do not make `RuntimeGameDefinition` execute generation and do not create a dynamic `Run` implementation.

## 6. Dynamic scene contract

### 6.1 Output payload

Use one strict versioned planned-scene payload equivalent to the existing safe fields:

```text
sceneId
title
narration
dialogue[] = { actorId, text }
choices[] = { id, label }
continuityFacts[]
ending? = { headline, summary, objectiveNotes[], reflection }
```

For dynamic content, `actorId`, `choice.id`, `sceneId` and `objectiveId` are engine-assigned trusted IDs, not source blueprint symbols. Do not expose source symbols to the provider.

Requirements:

- decision scenes include each compiled choice exactly once and no extras;
- ending scenes include zero choices and exactly one ending object;
- dialogue actors are a subset of the trusted scene-plan actors;
- ending objective notes cover exactly the scene-plan objective IDs, in trusted order;
- title/narration are nonblank; dialogue, facts and reflection may be empty within bounds;
- exact fields only, bounded item counts and code-point limits;
- active markup, unsafe controls, unresolved placeholders, detected PII and identifier-like player copy are rejected;
- payload contains no route, condition, effect, state value, phase change or outcome-class field.

Add a definition-driven schema/parser context. Do not create a synthetic `GenerationCatalog`, `SceneSlot`, template, Pack or manifest merely to call the old parser.

### 6.2 Composition

Compose only presentation:

- replace empty blocks with one narration block and ordered dialogue blocks;
- replace each unresolved option label with the matching validated label;
- retain option ID, destination, effects, requirement, unmet hint and visibility exactly;
- retain scene ID, start/end, next, branches, onEnter, input and outcome exactly;
- do not add refs, events, inputs, places or automatic transitions;
- keep the compiled `SceneSet` immutable; cache separately composed immutable `Scene` values.

Before caching, compare every non-presentation field to the canonical compiled scene. Any mismatch is an internal `DYNAMIC_PRESENTATION_TRUST_VIOLATION` and falls back; it never reaches runtime.

## 7. Provider request and context

Each scene request uses `StructuredGenerationRequest.Purpose.PRESENTATION`, the profile's `sceneMaxOutputTokens`, the provider adapter input ceiling and a deterministic task/slot key. Instructions must state that supplied data is untrusted story data and that the response may only fill the schema.

The bounded context contains only:

- selected locale and audience/tone policy;
- story title/premise/setting/promises and current phase plan;
- trusted current scene ID, title, intent and story role derived from whether it is an ending;
- allowed actor IDs with reviewed names/roles/descriptions for this scene;
- objective IDs with reviewed title/description and current state where relevant;
- ordered choice IDs plus reviewed intents, destinations described only as opaque IDs if needed;
- bounded current runtime facts needed to avoid contradiction;
- deterministic continuity facts selected from accepted visited scenes.

Do not include condition/effect trees, hidden unavailable routes, raw setup values, suggestion, prompt history, rejected outputs, provider metadata, full snapshot, unrelated actors/scenes, or source blueprint symbols. If mechanics must influence wording, provide bounded declarative facts such as `choiceAvailable=true`, never executable expressions.

Request size is measured before the provider call. Deterministically omit lowest-priority optional context (older continuity, descriptions, then non-current objective descriptions) while retaining schema, policy, current scene, all choice IDs/intents and required ending coverage. If required context still exceeds the limit, use fallback without a provider call.

## 8. Budget and repair accounting

The single profile `totalCallsPerRun` covers GAME_BLUEPRINT plus all scene presentation attempts. Initialize used calls from `CandidateReviewed.evidence().attempts()`; do not reset the budget after compilation.

For each uncached scene:

- at most `profile.generationBudget().sceneMaxAttempts()` and never more than two attempts;
- the first provider attempt consumes one total call;
- one repair may consume one additional call only when configured and budget remains;
- parse, safety, quality, provider invalid-response and output-limit failures may be repairable;
- cancellation, deadline, unavailable/rate-limited provider, exhausted total budget and configuration errors go directly to fallback;
- fallback consumes zero provider calls;
- concurrent resolution of the same scene is single-flight and charged once;
- prefetch and on-entry resolution share the same cache and budget.

Repair input contains only bounded content-free finding codes/scopes/requirements plus the same trusted context. Do not echo the rejected output. A repair cannot change the definition or request more fields.

The execution summary distinguishes blueprint calls already consumed, scene generated/repaired/fallback outcomes, provider calls, bounded failure code, token usage and quality decision. Do not misreport a fallback as provider-generated.

## 9. Quality, safety and continuity

Load the selected profile quality resource through the Pack-neutral parse boundary anticipated by 27.18. Bind its tone rules to the definition's reviewed tone tags. Bind truth checks only to engine-produced stable fact IDs; profile resources may not name source blueprint symbols.

Run strict parser/safety checks before `GenerationQualityEvaluator`. Blocking findings trigger the one allowed repair or fallback. Advisory findings may be accepted and recorded in the quality stamp.

Continuity selection is deterministic and bounded:

- accepted visited scenes only; never rejected output;
- exclude the current scene and unvisited prefetched alternatives;
- prefer recent same-phase facts, then recent prior-phase facts;
- deduplicate normalized facts;
- include fact source scene/phase internally but send only the bounded text/fact IDs required;
- use fixed max-fact and max-code-point ceilings no larger than existing full-game limits;
- prefetch context is computed from the committed visited path at prefetch start and stored with the artifact;
- entering a prefetched scene reuses it only if its continuity basis is still compatible; otherwise discard it and resolve on entry subject to remaining budget.

Generated continuity facts are narrative memory, not engine state. They cannot unlock choices, complete objectives or alter outcome selection.

## 10. Definition-specific fallback

### 10.1 Prevalidation

Before any scene provider call or dynamic `Started` result, build and validate a fallback payload for every scene from reviewed definition content:

- title from the scene plan/localized scene-title key;
- narration from the reviewed scene intent;
- dialogue empty;
- choice labels from reviewed choice intents in trusted order;
- continuity facts empty;
- for endings, headline from the reviewed outcome title, summary from the ending scene intent, objective notes from reviewed objective descriptions, and empty reflection.

Spec 27.23 deliberately did not treat intents as final labels. Spec 27.25 may promote them only through a dedicated deterministic fallback validator that applies the same player-facing text, coverage, safety, PII, identifier-leak, locale-resource and quality checks. No hardcoded English/Polish copy or generic “Continue” label is permitted.

If any fallback fails, dynamic startup fails locally with `DYNAMIC_PRESENTATION_FALLBACK_INVALID` before a provider request and before run publication. Do not mix fallback fields with a partially accepted provider payload: a scene uses the complete accepted generated/repaired payload or the complete validated fallback payload.

### 10.2 Runtime fallback

Use the scene fallback on provider absence/failure, exhausted budget, request-too-large, rejected/failed repair, cancellation after blueprint acceptance, or incompatible prefetched continuity basis. Cache it exactly like accepted generated presentation and report `FALLBACK` with a bounded failure reason.

Fallback must always preserve full mechanical playability. A fallback ending produces a non-null `RunResult` with the compiled outcome/result class and reviewed objective presentation.

## 11. Startup, lazy resolution and prefetch

### 11.1 Startup

After compilation/runtime verification and fallback prevalidation:

1. Construct the dynamic presentation pipeline with blueprint calls already spent.
2. Resolve the trusted start scene synchronously through generation/repair/fallback.
3. Compose and verify the start scene.
4. Construct `DynamicRuntimeGameDefinition` with `presentationReady=true` and the resolver.
5. Construct `RunImpl`, allowing normal start-entry/objective behavior.
6. Publish `Started` only when `run.view()` has nonblank safe narration and every visible choice has a resolved label.

Remove `DYNAMIC_PRESENTATION_PENDING` from successful dynamic startup. A fallback start is successful and includes a warning/status that presentation source was fallback; unresolved presentation is never successful.

### 11.2 On entry

Resolve the target scene before applying choice effects or committing a transition. If generated presentation fails, substitute the prevalidated fallback and continue. Only an impossible internal fallback/composition defect rejects the command as `SCENE_RESOLUTION_FAILED`, preserving the pre-command run state exactly.

### 11.3 Prefetch

Candidates are unresolved, reachable one-step destinations from the currently resolved scene, deduplicated in option order. Do not prefetch the current scene, visited scenes, ending-incompatible hidden branches or already cached scenes. Respect existing configured fanout later in the session layer; core only returns candidates.

Because existing `Run.prefetch(String)` is Pack-artifact-specific, preserve it unchanged for compatibility. Add a source-neutral presentation prefetch result/API for dynamic use, or introduce a common nonbreaking abstraction that existing Pack callers can adopt without changing Pack snapshot JSON. It exposes only scene ID, outcome, call count/status and redacted artifact metadata; it does not expose definition internals. Spec 27.27 wires host scheduling and diagnostics to this common seam.

## 12. Views and endings

For presentation-ready dynamic runs:

- `View.blocks` comes from the resolved scene;
- visible options have trusted IDs, validated labels and existing enabled state;
- `StoryInfo` comes from the definition, not a second generated plan;
- objectives use reviewed titles/descriptions plus runtime objective state;
- discovered characters follow visited/current scene plans and use reviewed actor data;
- counter display remains absent unless a future trusted schema adds labels;
- places and free-text input remain unavailable;
- no internal sentinel, source symbol or trusted ID is used as player-facing fallback text.

On completed endings, build `RunResult` from compiled outcome ID/result class, validated ending narrative and exact objective states. Objective notes are presentation only. Result facts remain empty for generated-rules-v1. Abandonment has no generated ending and makes no provider call.

## 13. Artifact contract and persistence handoff

Do not put dynamic content in `GenerationArtifact` with fake Pack identity. Introduce an immutable redacted dynamic artifact, or a common source-neutral interface with a dynamic implementation, containing at least:

```text
artifactFormatVersion
trusted scene ID and locale
presentation schema/policy version
outcome = GENERATED | REPAIRED | FALLBACK
complete validated planned-scene payload
quality stamp and bounded continuity-basis metadata
content-free execution evidence
```

Artifact ID may use `IdSource`, but is not the durable definition fingerprint. Preserve deterministic collection order and defensive copies. No prompt, rejected response, suggestion, source symbol, provider request body or full context is retained.

27.25 caches artifacts only for the in-memory run and exposes them through the resolver. Spec 27.26 defines codecs, embeds them with the exact definition, verifies fingerprints and restores them without provider calls.

## 14. Failure, privacy and concurrency

- Generation never mutates runtime mechanics or state.
- Provider exceptions and malformed output are converted to bounded codes and fallback.
- Logs/metrics/issues/`toString()` contain no story text, suggestion, prompt, response, continuity text, actor name or source symbol.
- Two different runs never share mutable pipeline state, artifacts, budget or continuity history.
- Same-scene concurrent calls are single-flight; different-scene calls respect a thread-safe total budget and deterministic cache publication.
- A cancelled run/start makes no further calls; completed/abandoned runs return no prefetch candidates.
- Prefetch completion after cancellation may be discarded but never attached to another run.
- No global content cache is introduced.

## 15. Compatibility requirements

The following remain unchanged:

- authored Pack rendering and snapshots;
- fixed-Pack `generated=true` stage order, prompts, fallbacks, artifacts, summary and Willow Marsh behavior;
- Pack `GenerationArtifact` schema and `SnapshotCodec` JSON;
- Pack restore and prefetch APIs used by the session layer;
- rules/state/route execution introduced through Specs 22–27.24;
- profile/blueprint attempt limits and provider capability negotiation.

Refactoring reusable parser/evaluator/continuity/composition helpers must retain existing Pack tests. Do not route fixed Pack generation through dynamic fallback content or vice versa.

## 18. Acceptance criteria and handoff

27.25 is complete when a verified dynamic definition starts with a fully presented start scene; blueprint story/cast/objectives are reused without extra planning calls; every later scene resolves lazily through strict structured parsing, quality checks, bounded repair and a complete prevalidated fallback; composition cannot alter any trusted mechanics; continuity and prefetch are path-aware and budget-safe; views and endings contain no unresolved/internal labels; generated/fallback artifacts are immutable, redacted and definition-bound; Pack generation and persistence remain compatible; and the full game is playable in memory without a provider.
