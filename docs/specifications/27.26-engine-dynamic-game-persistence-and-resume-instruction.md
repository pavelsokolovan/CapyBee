# Spec 27.26 — Dynamic Game Persistence and Resume

**Type:** Implementation instruction
**Parent:** Dynamic-game series, following Spec 27.25
**Depends on:** Specs 22–27.25, especially `RunSnapshot`, `SnapshotCodec`, `MaterializedGameDefinition`, `DynamicPresentationArtifact`, `DynamicPresentationPipeline`, `DynamicRuntimeGameDefinition`, `DefaultEngine.resume(...)`, `RunSessionService` and `LocalSessionStore`

Dynamic games are fully playable in memory with lazy generated/fallback presentation, but `Run.snapshotCapability()` remains `PENDING_DYNAMIC_DEFINITION_PERSISTENCE`, `RunSnapshot` v1 requires a `PackRef`, `SnapshotCodec` knows only Pack-backed generation artifacts, and local session-store v4 validates every saved run against Pack identity. The working tree was clean. No build or live-provider test was run while preparing this document; implementation must inspect current HEAD again.
**Status:** Implemented; dynamic games are durable and exactly resumable, while normal CLI creation/resume UX and release certification remain owned by Spec 27.27
**Primary outcome:** Persist the accepted blueprint, exact materialized definition, engine-assigned IDs, canonical game fingerprint, runtime state, presentation continuation policy and all accepted dynamic scene artifacts; then restore the same game after store reopen without blueprint regeneration, Pack substitution, repeated accepted provider calls or duplicated effects.

## 1. Purpose

Specs 27.23–27.25 create a complete dynamic game and make it playable, but only while the original Java objects remain alive. A dynamic run cannot currently call `snapshot()`, survive `SnapshotCodec`, enter `LocalSessionStore`, or pass through `DefaultEngine.resume(...)` because all durable identity is Pack-based.

This specification establishes one durable chain:

```text
accepted reviewed blueprint
  + verified MaterializedGameDefinition
  + definition-bound presentation policy/artifacts
  + RunState
  -> canonical dynamic snapshot v2
  -> atomic session-store commit
  -> close/reopen store and create a fresh Engine
  -> verify fingerprint and every cross-reference
  -> restore DynamicPresentationPipeline cache/budget
  -> existing RunImpl state machine
```

The restored run is the same accepted game. Resume never asks AI to recreate its blueprint, recompiles a different graph, substitutes a reviewed Pack fallback, or generates presentation already saved in the snapshot.

## 2. Scope and non-goals

### 2.1 In scope

- Define a versioned accepted-blueprint archive and strict codec.
- Define a canonical `MaterializedGameDefinition` codec covering every trusted field and ID binding.
- Define a stable SHA-256 dynamic-game fingerprint over immutable game inputs.
- Persist the minimal safe presentation continuation policy needed for future lazy scenes.
- Persist all resolved/prefetched `DynamicPresentationArtifact` values and provider-call accounting.
- Add a discriminated dynamic source to `RunSnapshot` without changing Pack snapshot v1 JSON.
- Make dynamic `Run.snapshot()` supported and immutable.
- Restore dynamic runtime state and presentation cache through `DefaultEngine.resume(...)`.
- Extend local/in-memory session-store records and wire format for Pack or dynamic identity.
- Preserve atomic accepted-command saving, revisions, leases, outbox and recovery behavior.
- Add migration, corruption, privacy, reopen and exact-resume tests.

### 2.2 Out of scope

- Public CLI commands/wizard/retry UX for creating or selecting dynamic games; Spec 27.27 owns them.
- Persisting a raw/normalized/scrubbed/approved suggestion, setup transcript, prompt, rejected model output or provider request body.
- Retrying an interrupted pre-blueprint preparation after process death.
- Revalidating a saved game against a newer generator profile or regenerating it when the original profile is unavailable.
- Migrating mechanics/content of a dynamic definition to a newer semantic meaning.
- Cloud sync, shared games, export/import, encryption redesign or retention-policy changes.
- Changing fixed-Pack generated snapshot artifacts or authored Pack migration rules.

## 4. Durable dynamic game bundle

### 4.1 Bundle v1

Introduce an immutable redacted aggregate conceptually equivalent to:

```text
DynamicGameBundle v1
  acceptedBlueprint
  materializedDefinition
  continuationPolicy
  gameFingerprint
```

It is created once after 27.23 compilation and before 27.25 runtime publication. Presentation artifacts and mutable run state are stored beside it in the dynamic snapshot, not inside the immutable fingerprinted bundle.

The bundle has no Pack ID/version and is not registered in `PackRegistry`. It contains no `GeneratorProfile` resource tree, blueprint prompt, setup labels, fallback Pack reference, original suggestion, provider/model identifier or request metadata.

### 4.2 AcceptedBlueprintArchive v1

Persist the accepted blueprint as a bounded typed archive:

```text
archiveFormatVersion = 1
canonical ParsedGameBlueprint v1
profile identity, locale, length/challenge preset IDs
semantic evidence and generated-rules contract version
reviewer/validator versions
blueprint provider attempt count
blueprint fingerprint
```

Use the accepted parsed object, not the raw provider response. Conditions/effects remain the closed blueprint-v1 vocabulary. Preserve declaration order and source symbols because they are required to audit the trusted ID bindings, but keep all diagnostics and `toString()` redacted.

Add a strict archive reader with exact fields, existing hard host ceilings, bounded depth/items/text and no executable interpretation. Do not require the original provider, profile registry or suggestion. Do not call `BlueprintGenerationService`, output reviewer or semantic validator on resume.

The archive is supporting provenance, not the runtime authority. The materialized definition remains executable only after bundle verification.

## 5. Canonical codecs

### 5.1 Encoding rules

Use explicit Jackson tree construction/parsing like `SnapshotCodec`; do not enable default typing, class-name metadata or general record polymorphism.

Canonical JSON rules:

- UTF-8 without BOM;
- fixed object-field order owned by codec version;
- arrays preserve trusted declaration order;
- maps encode as arrays of `{source,target}` or fixed-order entries where source order matters;
- maps that are semantically unordered are sorted by Unicode code-point key order;
- integers/booleans use JSON primitives; no floating point;
- absent optional values are represented consistently as omitted or explicit null, frozen by golden tests;
- no insignificant whitespace;
- line endings inside text normalize to `\n` only if that normalization already occurred before acceptance; never mutate accepted content during save;
- decode followed by encode returns identical bytes.

### 5.2 Blueprint codec

Encode every `ParsedGameBlueprint` field, every condition/effect variant and semantic evidence explicitly. On decode reject:

- unknown/missing/duplicate fields or unsupported versions;
- unknown type discriminator/operator;
- values outside absolute blueprint-v1 host ceilings;
- malformed locale/IDs, unsafe text or unexpected nulls;
- archive evidence inconsistent with counts/contracts.

Calculate `blueprintFingerprint = sha256:<64 lowercase hexadecimal>` over the canonical UTF-8 accepted-blueprint archive bytes excluding the fingerprint field itself.

### 5.3 Materialized definition codec

Encode every field of `MaterializedGameDefinition` v1:

- all version/provenance/profile/preset values;
- story, actor, phase, scene and choice plans;
- canonical compiled scenes including blocks/options/routes/requirements/effects/outcomes;
- rules including counters/flags/sets/objectives/outcomes/result facts;
- selected-locale content entries;
- every namespace-separated ID binding and set-member binding;
- compilation evidence.

The codec must support only engine-owned current runtime condition/effect variants that the definition verifier accepts. Reject authored-only mechanics, inputs, places, events, unknown rule types and unresolved presentation markers where the saved artifact/view contract requires resolution.

After decode always run `MaterializedGameDefinitionVerifier`. Codec shape success alone is insufficient.

Calculate `definitionFingerprint` using the same SHA-256 format over canonical definition bytes excluding external fingerprint fields.

### 5.4 Dynamic artifact codec

Encode every `DynamicPresentationArtifact` v1 field explicitly, including complete planned-scene payload, ending/objective notes, continuity-basis scene IDs, outcome, policy version, provider call count, bounded failure/finding codes and token usage.

Reject content that does not pass the definition-driven scene parser, safety checks, exact trusted reference coverage and mechanical composition equality. Artifact IDs and scene IDs are unique. Artifact order is canonical scene declaration order, independent of asynchronous completion order.

## 6. Game fingerprint and bundle verification

Define:

```text
gameFingerprint = sha256(
  "capybee-dynamic-game-v1\n"
  + blueprintFingerprint + "\n"
  + definitionFingerprint + "\n"
  + canonicalContinuationPolicyFingerprint
)
```

Use UTF-8 and lowercase hexadecimal with the `sha256:` prefix. Do not include run ID, seed, timestamps, mutable state, generated scene artifacts, provider IDs or filesystem/session identity. The same immutable accepted game bundle has the same fingerprint across runs; different accepted content/IDs/policy must change it.

Add an independent `DynamicGameBundleVerifier` that checks:

- supported archive/definition/policy versions;
- stored and recomputed fingerprints using constant-time byte comparison where practical;
- profile identity/locale/presets/schema/rules contract/reviewer/validator agreement;
- blueprint declaration counts and semantic evidence against definition compilation evidence;
- every source actor/objective/scene/choice/outcome/state/member maps one-to-one through `IdBindings`;
- compiled plans, graph, conditions/effects, result classes and localized reviewed content correspond to the archived blueprint;
- trusted definition passes `MaterializedGameDefinitionVerifier`;
- continuation policy is compatible with the accepted profile identity and definition.

Return bounded codes only, such as `DYNAMIC_BUNDLE_VERSION_UNSUPPORTED`, `DYNAMIC_BUNDLE_FINGERPRINT_MISMATCH`, `DYNAMIC_BLUEPRINT_ARCHIVE_INVALID`, `DYNAMIC_DEFINITION_INVALID`, `DYNAMIC_BINDING_MISMATCH` and `DYNAMIC_CONTINUATION_INVALID`. Never report content/source symbols.

## 7. Presentation continuation snapshot

Persist only the immutable policy needed to resolve **future** scenes after restart:

```text
continuationFormatVersion
profile identity and selected locale
scene presentation policy/schema versions
effective total-call, scene-attempt, output-token and input-character ceilings
audience age bounds and forbidden tone/tag identifiers needed by validation
canonical parsed quality profile or its exact safe resource plus fingerprint
blueprintProviderCalls
totalProviderCallsSoFar
```

Do not persist setup questions/answers, blueprint prompts, fallback Pack refs, suggestion, deadline, cancellation token, provider capabilities, model name or credentials. On resume, `TextGenerator`, `IdSource` and `Clock` come from the fresh engine. An absent provider continues via the already validated definition-specific fallbacks.

Budget rules:

- `blueprintProviderCalls` equals accepted evidence attempts;
- `totalProviderCallsSoFar` equals blueprint calls plus the sum of restored scene artifact provider calls;
- both are nonnegative and do not exceed the effective total ceiling;
- restored cached scenes consume no new call;
- future scene calls start from the persisted total and preserve per-scene attempt bounds;
- resume itself performs zero provider calls.

The original start deadline/cancellation state does not survive a completed accepted snapshot. A resumed run receives a new host lifecycle cancellation scope without changing the immutable game fingerprint.

## 8. Dynamic snapshot v2

### 8.1 Source discrimination

Keep Pack snapshot v1 serialization byte-for-byte compatible. Add snapshot v2 only for dynamic games, with a conceptual root:

```json
{
  "snapshotVersion": 2,
  "runId": "...",
  "source": {
    "kind": "DYNAMIC",
    "gameFingerprint": "sha256:...",
    "bundle": {},
    "presentation": {
      "artifacts": [],
      "blueprintProviderCalls": 1,
      "totalProviderCalls": 4
    }
  },
  "locale": "en",
  "seed": 42,
  "createdAt": "...",
  "updatedAt": "...",
  "step": 3,
  "state": {}
}
```

Exact field names/order are frozen by codec tests. Dynamic snapshots contain no `pack` or `startInputs`. Pack v1 continues to contain both as today. Do not emit a v2 Pack snapshot merely because the codec changed.

### 8.2 Domain shape

Evolve `RunSnapshot` through a source-neutral sealed value or an equivalent explicit optional dynamic block. Preserve source compatibility for existing Pack constructors/accessors where practical. Invalid combinations are impossible or rejected:

- Pack v1: non-null Pack source, no dynamic bundle/artifacts;
- Dynamic v2: non-null verified dynamic source, no Pack/start inputs/Pack artifacts;
- never both, never neither.

Keep `RunState` mechanics source-neutral. Do not place dynamic presentation artifacts into its `List<GenerationArtifact>` using fake Pack identity. They belong to the dynamic source/presentation block. Existing Pack `generationArtifacts` remains unchanged.

### 8.3 Snapshot creation

For a dynamic run, `snapshot()` atomically captures under the run/pipeline synchronization boundary:

- immutable bundle and fingerprint;
- current runtime state, visited order, outcome and step/timestamps;
- every accepted cached dynamic artifact, including prefetch/fallback artifacts;
- continuation policy and exact provider-call counters;
- no in-flight/rejected partial artifact.

The snapshot must be self-contained: restore requires no generator profile registry, Pack registry, old `BlueprintGenerationRequest` or original process objects. After successful implementation, dynamic `snapshotCapability()` is `SUPPORTED`.

## 9. Dynamic resume

`DefaultEngine.resume(...)` branches only after strict snapshot-source parsing.

For dynamic v2:

1. Validate basic run/state timestamps, step and source combination.
2. Decode/recompute fingerprints and verify the complete dynamic bundle.
3. Validate locale equals definition/policy/artifact locale.
4. Validate runtime state against embedded scenes/rules using the existing exact-state checks with no Pack migration/pruning.
5. Validate every visited/current scene has a cached artifact; unvisited prefetched artifacts are allowed when their continuity basis is valid.
6. Validate artifact uniqueness, coverage, outcome/evidence, continuity-basis references and payload against the definition.
7. Restore `DynamicPresentationPipeline` with fallbacks, cache, continuation policy and persisted call counters without invoking provider APIs.
8. Rebuild `DynamicRuntimeGameDefinition` and the existing `RunImpl` using saved identity/seed/timestamps/step/state.
9. Build the current `View` solely from restored data and return success only if it matches the saved current artifact.

Do not call `BlueprintGenerationService`, reviewer, semantic validator, compiler, `PackRegistry`, profile registry or `TextGenerator` during resume. The compiler may be used only in a deterministic test oracle, not production restore.

Unlike Pack major-version migration, dynamic v1 definition semantics are immutable. Unsupported definition/artifact/policy versions fail with an explicit version code. Never clamp, prune, remap or silently regenerate a dynamic game to make it load.

## 10. Exact-resume and no-duplication guarantees

After snapshot round-trip and fresh-engine resume:

- run ID, game fingerprint, seed, created/updated times, step, current scene and visited order are exact;
- counters, flags, sets, objective states, outcome and ended status are exact;
- every saved artifact is canonical-equal and appears once;
- current/visited scenes cause zero provider calls;
- prefetched saved scenes are reused only with the saved compatible continuity basis;
- choosing a new route may generate only a previously unresolved scene and charges from the persisted total;
- no onEnter effect, choice effect, objective completion or ending effect is replayed during resume;
- an ended run reopens read-only with identical `View`/`RunResult` and zero provider calls;
- snapshotting immediately after resume yields canonical-equivalent dynamic content and state.

Tests must use a fresh engine with provider doubles that throw on any unexpected call. A second resume of the same snapshot produces an independent run object with identical initial state, not shared mutable cache/state.

## 11. Session domain and store v5

### 11.1 Source-neutral stored identity

Introduce a sealed/session-safe identity such as:

```text
StoredGameRef
  PackGameRef(packId, packVersion)
  DynamicGameRef(profileId, profileVersion, gameFingerprint)
```

`StoredRun` and `RunDescriptor` use this identity internally. Preserve Pack-facing convenience constructors/accessors/DTO fields so existing callers and wire contracts remain compatible. Dynamic descriptors may expose a bounded origin/title later through 27.27; they must not masquerade as a Pack.

`StartRequest` may remain Pack-only in 27.26. If an internal dynamic-activation seam is required, it accepts an already started/snapshotted dynamic run and atomically creates the stored ACTIVE row. It never persists `BlueprintGenerationRequest` or a pending suggestion.

An interrupted dynamic operation before a complete accepted bundle/snapshot is not recoverable and must become a stable failed/cancelled preparation in later host UX; it is never retried from partial provider data.

### 11.2 Store v5 wire contract

Advance `LocalSessionStore` envelope/data format from v4 to v5 because run identity becomes discriminated. Retain:

- checksum algorithm and canonical data checksum;
- store revision, primary/temp/backup selection and split-brain rules;
- key/MAC handling, locking, quarantine and recovery reports;
- command/outbox/usage/prefetch ledgers and lifecycle fields;
- embedded structured `SnapshotCodec` JSON as the sole snapshot boundary.

Migrate valid v1–v4 Pack stores to `PackGameRef` in memory and write canonical v5 on the next commit. Older readers must reject v5 as unsupported rather than misread dynamic rows.

On read, verify stored game identity agrees with snapshot source, run ID, locale, status/ended state and fingerprint/Pack version. A corrupt dynamic run follows existing candidate recovery/quarantine rules; no provider repair is attempted.

Separately stored Pack prefetch remains unchanged. Dynamic artifacts are authoritative inside the accepted snapshot in 27.26; do not put them in Pack `PrefetchedArtifact` rows. Spec 27.27 may optimize host prefetch transactions only if snapshot atomicity remains intact.

### 11.3 Atomic save boundary

For a dynamic accepted command, one transaction commits:

- new snapshot v2;
- run revision/status/updated/last-played fields;
- command completion/idempotency result;
- emitted events/outbox changes;
- generation-call/token ledgers derived from the snapshot/presentation result;
- cleanup of stale in-flight host prefetch metadata.

Report the command as applied only after commit. A persistence failure must not claim save success. Rejected commands remain non-mutating and do not replace the accepted snapshot.

## 12. Migration and compatibility

### 12.1 Supported inputs

| Input | Behavior |
| --- | --- |
| Pack snapshot v1 | Decode/resume exactly as before. |
| Store v1–v3 | Existing migrations continue, then normalize to Pack source. |
| Store v4 | Read existing explicit snapshot JSON, wrap Pack identity, rewrite as v5 on commit. |
| Dynamic snapshot v2 | Strict decode/bundle verification and exact restore. |
| Future snapshot/bundle/definition/artifact version | Fail with version-specific code; no downgrade. |
| Corrupt fingerprint/cross-reference/artifact/state | Fail/quarantine through existing recovery policy; no regeneration. |

Do not change Pack snapshot v1 JSON, Pack `GenerationArtifact` schemas, Willow Marsh restore, authored state migration or existing session command semantics.

### 12.2 No semantic dynamic migration

Codec migrations may normalize an older supported wire spelling only when semantics/bytes are unambiguous and covered by golden fixtures. They may not:

- assign new trusted IDs;
- recompile routes/rules;
- alter prose/labels/endings;
- drop unknown state/artifacts;
- substitute current profile limits;
- call a provider.

If exact meaning cannot be preserved, return `DYNAMIC_SNAPSHOT_VERSION_UNSUPPORTED` or `DYNAMIC_SNAPSHOT_INVALID`.

## 13. Privacy, size and security

- Original/raw/scrubbed/approved suggestion is absent from blueprint archive, definition, continuation, artifacts, state, store rows, logs and fingerprints.
- Prompts, provider responses, rejected outputs, credentials, model/provider IDs and request bodies are absent.
- Accepted game/story content necessarily persists and is treated as private per-run data.
- `toString()`, issues, store recovery notices and logs redact content/source symbols/artifacts.
- Fingerprints are integrity identifiers, not secrecy; never hash the suggestion separately.
- Enforce absolute byte/item/depth limits before allocating large collections. Keep snapshot/store maximums within existing local-store limits or raise them explicitly with adversarial tests.
- Reject duplicate JSON keys where the parser supports detection; otherwise tree construction plus exact-field checks must prevent ambiguous canonicalization.
- Use no Java serialization, reflection-based polymorphic type names or executable deserialization hooks.

## 14. Failure codes and observability

Use bounded content-free codes, including:

```text
DYNAMIC_SNAPSHOT_VERSION_UNSUPPORTED
DYNAMIC_SNAPSHOT_INVALID
DYNAMIC_BUNDLE_VERSION_UNSUPPORTED
DYNAMIC_BUNDLE_FINGERPRINT_MISMATCH
DYNAMIC_BLUEPRINT_ARCHIVE_INVALID
DYNAMIC_DEFINITION_INVALID
DYNAMIC_ARTIFACT_INVALID
DYNAMIC_CONTINUATION_INVALID
DYNAMIC_RESUME_FAILED
```

Metrics may contain origin, versions, status/code, counts, byte sizes, provider calls already consumed, duration and fingerprint prefix only if existing privacy policy permits it. Never emit canonical JSON or content excerpts.

Fingerprint mismatch, unknown mechanics or artifact/definition disagreement are corruption/trust failures, not repairable generation failures. They trigger zero provider calls.

## 17. Acceptance criteria and handoff

27.26 is complete when a dynamic run produces a self-contained canonical v2 snapshot containing its accepted blueprint, exact verified materialized definition/trusted IDs, safe continuation policy, stable game fingerprint, runtime state and all accepted presentation artifacts; the snapshot survives a real local-store close/reopen and resumes in a fresh engine with identical state/view/result; resume makes zero blueprint calls and zero calls for saved scenes, never reapplies effects, and charges future lazy scenes from the persisted budget; ended games reopen without calls; tampering fails closed; store v5 migrates all prior Pack fixtures; Pack snapshot v1 and Willow Marsh behavior remain compatible; and no ephemeral suggestion/provider secret is persisted.

**Next: 27.27 — Dynamic Game CLI, Testing and Release Readiness.** It exposes profile-driven preparation and dynamic start/resume through the normal CLI/session lifecycle, adds retry/fallback UX, real second-process route tests, optional live-provider certification and final backward-compatibility/release evidence.
