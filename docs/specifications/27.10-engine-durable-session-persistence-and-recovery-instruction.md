# Spec 27.10 — Durable Session Persistence and Recovery

**Type:** Implementation specification  
**Parent:** Spec 27.9 — Complete CLI Play Experience  
**Depends on:** Specs 25, 26.1, and 27.1–27.9  
**Baseline:** repository commit `b00c545`, plus the approved designs in Specs 27.4–27.9. The current session service, repository/command/outbox/prefetch/ledger ports, local and in-memory stores, store v1–v2 migration, lease handling, asynchronous start/command jobs, CLI session wiring, and persistence tests were inspected while writing this specification. The build was not run. Existing uncommitted CLI work was not modified.  
**Status:** Ready for implementation after Spec 27.9  
**Primary outcome:** A player can keep several local games, close the process at any safe or unsafe moment, reopen it, and receive a deterministic recovery result without duplicated game effects, lost accepted progress, repeated accepted generation, leaked private setup text, or silent deletion. Corrupt data is isolated and preserved for recovery. Store evolution is explicit, testable, and backward compatible.

---

## 1. Problem

The current session layer has useful foundations:

- snapshots are persisted after accepted commands;
- command IDs and payload MACs support idempotency;
- run leases prevent concurrent mutation;
- a local store uses a process lock and atomic file replacement where supported;
- starts and commands can run asynchronously;
- generated artifacts live inside snapshots and survive resume;
- store v1 can be opened and later rewritten as v2.

However, durable play is not complete:

- all local state is one JSON document with a fixed 16 MiB limit and no retention policy;
- a leftover temporary file is deleted on open without checking whether it is the newest valid commit;
- there is no durable commit sequence or checksum for choosing between primary, temporary, and backup files;
- there is no backup rotation or whole-store recovery flow;
- one malformed run can make the whole store unreadable;
- semantic relationships between runs, snapshots, commands, events, prefetch rows, and budget data are only partly validated;
- v1–v2 migration fills missing fields but does not define a complete migration contract or rollback evidence;
- expired leases can be reclaimed, but no recovery coordinator explains or resolves orphaned work;
- a persisted `IN_PROGRESS` command with no in-memory future remains processing forever after restart;
- a preparing run can restart, but recovery, cancellation, timeout, and missing transient setup text are not fully modeled;
- the command payload itself is intentionally not persisted, so an interrupted command cannot safely be reconstructed;
- durable budget reservations do not distinguish consumed calls from uncertain calls after a crash;
- only one active/preparing run can exist and there is no suspended-run library;
- delete removes the run, command log, events, prefetch, and counters immediately;
- there is no archive, trash, restore, export/import, or bounded cleanup contract;
- the CLI cannot clearly report what was recovered and what still needs player action.

Spec 27.10 defines a local durability model, store schema v3, deterministic crash recovery, safe run lifecycle operations, and a player-visible saved-game library. It preserves engine determinism and the CLI semantics from Spec 27.9.

## 2. Current implementation findings

| ID | Finding | Consequence |
|---|---|---|
| F1 | `LocalSessionStore` owns all session ports and commits one encoded document. | A command transaction can be atomic inside one process, but every write rewrites all retained state. |
| F2 | The local store holds an exclusive `session-store.lock`. | Keep single-writer local semantics; cross-process concurrent play is not required. |
| F3 | Commit writes `session-store.json.tmp`, forces that file, then moves it over `session-store.json`. | Add commit identity, backup selection, and directory durability around this useful base. |
| F4 | Open currently deletes `.tmp`. | A crash after forcing temp but before rename may leave the newest complete state there; it must be validated first. |
| F5 | Store schema v2 has no top-level commit revision/checksum. | Candidate ordering and corruption detection are ambiguous. |
| F6 | `StoreMigrations.toCurrent` only supplies absent maps and changes version in memory. | Define version-by-version semantic migrations and fixtures. |
| F7 | `SessionStore.execute` rolls back local state by re-decoding prior bytes, but the in-memory implementation executes without rollback. | Transactional behavior must be identical across adapters. |
| F8 | `saveActive`, outbox append, prefetch cleanup, and command completion are grouped in a store transaction. | Preserve this as the atomic accepted-command boundary. |
| F9 | `commands.begin` is committed before command execution. | After a crash, `IN_PROGRESS` proves intent existed but not whether a provider call occurred. |
| F10 | Only a payload MAC is stored, not the command body. | Recovery must not auto-replay interrupted commands. This also protects submitted text. |
| F11 | Completed command replay reads the current snapshot and logged result metadata. | A completed log and run revision must be cross-validated. |
| F12 | A stale preparing run is rescheduled when accessed; after TTL it is marked failed. | Make this policy explicit, bounded, and available during startup recovery. |
| F13 | Leases contain a token and expiry but no worker/attempt identity. | Add recovery metadata without treating leases as proof that work completed. |
| F14 | Prefetch artifacts are optional performance data and are already discarded when invalid. | Recovery may remove stale/corrupt prefetch without making a run unrecoverable. |
| F15 | Generation call counts are persisted as aggregate maps. | Uncertain calls must be charged conservatively and active reservations need durable identities. |
| F16 | `findCurrent` returns only the newest active/preparing run. | Add listing and suspension while retaining one mutable current run per owner. |
| F17 | `delete` immediately removes all related data. | Replace normal player deletion with trash and delayed purge. |
| F18 | The command MAC key is created when missing. | If a store already exists and its key is missing, creating a new key would invalidate old idempotency proofs; fail safely instead. |

## 3. Goals and non-goals

### 3.1 Goals

1. Define a precise durable commit and recovery model for the local session store.
2. Recover the newest valid committed state after interruption at any write step.
3. Preserve corrupt inputs before repair or replacement.
4. Isolate a corrupt run when other runs remain valid.
5. Make store migrations explicit, monotonic, idempotent, and fixture-tested.
6. Resolve stale leases and orphaned starts/commands deterministically.
7. Never auto-reapply a command whose durable completion is unknown.
8. Preserve every accepted snapshot, event, result, and generated artifact exactly once.
9. Support multiple saved games through active, suspended, ended, failed, archived, and trashed lifecycle metadata.
10. Keep at most one mutable active/preparing run per owner.
11. Provide safe list, activate, suspend, archive, trash, restore, export, import, and purge operations.
12. Bound local storage growth without silently deleting resumable games.
13. Surface recovery outcomes through safe session APIs and the Spec 27.9 CLI.
14. Preserve Spec 27.8 transient free-text privacy across every new file and recovery path.

### 3.2 Non-goals

- Cloud synchronization or distributed multi-writer storage.
- Network replication, consensus, or high-availability database behavior.
- Sharing one run between multiple owners.
- Encrypting the whole local store at rest. Hosts may provide filesystem encryption.
- Reconstructing or repeating a lost free-text setup attachment.
- Replaying a provider call to reproduce its exact previous output after a crash.
- Guaranteeing recovery from physical disk loss when primary, temporary, backup, and exports are all unavailable.
- Changing engine rules, snapshots, generated payload semantics, endings, or CLI command meanings.
- Keeping unlimited command/event/debug history.
- Treating checksums as protection against a malicious local administrator.
- Adding semantic generated-prose quality checks; Spec 27.11 owns those.

## 4. Decisions

| ID | Decision |
|---|---|
| D1 | Local storage remains a process-locked JSON document in schema v3. A database migration is not required for this scope. |
| D2 | Every committed document has a monotonic `storeRevision`, `writtenAt`, and SHA-256 checksum over canonical store data. |
| D3 | Primary, temporary, and backup candidates are validated on open. The highest valid store revision wins; path name alone does not decide. |
| D4 | Before automatic replacement of corrupt data, the original bytes are copied into a quarantine directory. |
| D5 | A valid backup/temp may recover the store automatically. The recovery report tells the player what happened. |
| D6 | Invalid individual run records are quarantined independently when the top-level document remains readable. Valid runs stay usable. |
| D7 | Store migrations never run provider code, engine commands, or pack generation. They transform persisted data only. |
| D8 | `IN_PROGRESS` commands left without a live job after lease expiry become `FAILED/COMMAND_INTERRUPTED`. They are not auto-replayed. |
| D9 | A player may retry an interrupted action with a new command ID after refreshing the current view. |
| D10 | `PREPARING` starts may be retried from persisted preset inputs before `startTtl`; absent Spec 27.8 transient text is never reconstructed. |
| D11 | Provider calls with uncertain crash outcome count against limits. Safety and cost bounds take priority over reclaiming an uncertain reservation. |
| D12 | Exactly one run per owner may be `PREPARING` or `ACTIVE`. Other resumable snapshots use `SUSPENDED`. |
| D13 | Suspension changes session lifecycle metadata only. It does not apply an engine command, increment game revision, or alter the snapshot. |
| D14 | Normal deletion is soft delete (`trashedAt`). Physical purge is separate, confirmed, and bounded. |
| D15 | Active/preparing/suspended runs are never removed by automatic retention. |
| D16 | Exports contain a safe snapshot bundle, not command MAC keys, provider diagnostics, transient input, leases, or active jobs. |
| D17 | Future unsupported store versions are opened read-only only when metadata can be safely identified; they are never downgraded. |
| D18 | Repair operations are idempotent and append a content-free audit entry. |

## 5. Durability model and invariants

### 5.1 Commit point

A mutation is committed only when a complete v3 document with the next `storeRevision` has been forced to disk and installed as the valid primary candidate.

For an accepted game command, one store transaction includes:

1. next run snapshot and status;
2. next session revision;
3. outbox events with stable sequence numbers;
4. command log completion and accepted flag;
5. consumed/invalidated prefetch changes;
6. generation ledger changes already known at commit time;
7. updated timestamps and lifecycle metadata.

The CLI must not show the new view as saved before this transaction commits.

### 5.2 Required invariants

For every non-quarantined store state:

- store revision is non-negative and increases by exactly one per changed commit;
- run IDs are unique;
- every run-owned command, event, prefetch row, and call record references an existing run;
- one owner has at most one `PREPARING` or `ACTIVE` run;
- `PREPARING` has a pending start and no snapshot;
- `ACTIVE`, `SUSPENDED`, and `ENDED` have a valid snapshot and no pending start;
- `ENDED` snapshot is ended;
- `ACTIVE`/`SUSPENDED` snapshot is not ended;
- `FAILED` has a stable failure code and may have a last valid snapshot only when recovery explicitly preserves it;
- `CANCELLED` has no live lease/job and is terminal;
- archived/trashed timestamps do not change engine status;
- only `PREPARING` or `ACTIVE` may hold a lease;
- an unexpired lease has attempt ID, token, acquired time, and expiry in correct order;
- run revision equals the revision represented by its accepted command history;
- a `DONE` accepted command has `revisionAfter = revisionBefore + 1`;
- a `DONE` rejected command has `revisionAfter = revisionBefore`;
- accepted command revisions are unique and contiguous for retained history, or a compaction checkpoint explains the removed prefix;
- outbox sequence is contiguous from its retained checkpoint and event revisions never exceed run revision;
- completed command events equal the corresponding retained outbox events by ID/order/content;
- prefetch rows reference the same pack/run contract and are based on an allowed revision;
- counters and call totals are non-negative and within numeric bounds;
- no pending start, snapshot, command log, audit entry, export, or quarantine metadata contains Spec 27.8 free text.

Violation handling is defined in Section 9.

### 5.3 Transaction parity

`InMemorySessionStore` and `LocalSessionStore` must provide the same all-or-nothing behavior for `Transaction.execute`.

- any thrown exception restores every participating port to its state before the outermost transaction;
- nested transactions commit only with the outermost transaction;
- no event, command completion, prefetch deletion, or budget mutation leaks from a rolled-back transaction;
- tests run the same contract suite against both adapters.

## 6. Store schema v3

### 6.1 Files

```text
<store>/
  session-store.lock
  session-store.key
  session-store.json
  session-store.json.tmp
  session-store.json.bak
  quarantine/
  exports/
```

`exports/` is optional and created only by an explicit export to the default location. Quarantine filenames are generated by trusted code and contain UTC timestamp, candidate kind, and short content hash, never pack/generated/player text.

### 6.2 Envelope

```json
{
  "format": "capybee-session-store",
  "version": 3,
  "storeId": "c7e5dba7-...",
  "storeRevision": 42,
  "writtenAt": "2026-10-22T12:00:00Z",
  "checksumAlgorithm": "SHA-256",
  "checksum": "base64...",
  "data": {
    "runs": [],
    "generationLedger": {},
    "retention": {},
    "audit": []
  }
}
```

Checksum input is UTF-8 canonical JSON of `data` using:

- lexicographically sorted object keys;
- array order preserved;
- no insignificant whitespace;
- normalized number representation;
- exact Unicode strings after JSON decoding, without locale transforms.

The checksum detects accidental damage only. It is not a signature.

### 6.3 Run record

```json
{
  "run": {
    "id": "...",
    "owner": "local-console",
    "packId": "generated-adventure",
    "packVersion": "1.2.0",
    "locale": "en",
    "status": "SUSPENDED",
    "revision": 12,
    "snapshot": {},
    "pendingStart": null,
    "lease": null,
    "failureCode": null,
    "createdAt": "...",
    "updatedAt": "...",
    "lastPlayedAt": "...",
    "archivedAt": null,
    "trashedAt": null
  },
  "commands": {},
  "events": [],
  "prefetch": {},
  "checkpoint": null,
  "checksum": "base64..."
}
```

Each run checksum covers the canonical run record excluding its `checksum`. This enables isolation of one damaged run after the top-level data remains parseable.

### 6.4 New/extended types

Extend `RunStatus` with:

```text
SUSPENDED
CANCELLING
CANCELLED
```

Do not add `ARCHIVED` or `TRASHED` as engine/session execution statuses. They are orthogonal timestamps.

Extend durable types with:

- `packVersion` directly on `StoredRun` if not already reliably retained by its snapshot;
- `lastPlayedAt`;
- `archivedAt`;
- `trashedAt`;
- lease `attemptId`, `acquiredAt`, and `kind` (`START`, `COMMAND`, `RECOVERY`);
- command `startedAt`, `completedAt`, and content-free recovery code;
- store/run compaction checkpoint metadata;
- durable generation-call records described in Section 13.

All new record collections are immutable at port boundaries.

### 6.5 Bounds

- maximum document: 64 MiB hard limit;
- maximum 200 non-trashed runs per local owner;
- maximum 500 total run records including trash before explicit cleanup is required;
- maximum 10,000 retained command summaries per run before compaction;
- maximum 50,000 retained outbox events per run before compaction;
- maximum 1,000 prefetch artifacts across the store;
- maximum 2,000 content-free audit entries;
- maximum quarantine copy size: the 64 MiB input bound;
- all strings retain their existing domain limits; error/audit codes are allow-listed ASCII identifiers.

Crossing a hard bound fails the mutation with `STORE_LIMIT_REACHED`; it does not silently discard active data.

## 7. Write protocol

For every changed outer transaction under the process lock:

1. validate the proposed in-memory state;
2. increment `storeRevision` once;
3. encode canonical data and checksums;
4. ensure encoded bytes fit the hard limit;
5. write a new temp file with create/truncate;
6. force temp-file contents and metadata where supported;
7. validate the bytes by reading and decoding temp through the production decoder;
8. copy or atomically replace the previous valid primary as `.bak` without destroying the only valid candidate;
9. atomically move temp to primary with replace when supported;
10. force the store directory where the platform permits it;
11. update in-memory committed bytes only after install succeeds;
12. retain one valid backup.

If atomic move is unsupported:

- use the safest replace operation available;
- keep the prior backup until the new primary revalidates;
- record `atomicMove=false` in content-free diagnostics;
- startup candidate selection must still recover from every injected interruption point.

On any error, restore in-memory state to the last committed state and return `STORE_WRITE_FAILED`. Never delete a valid primary or backup merely because temp cleanup failed.

No-op transactions do not increment the store revision or rewrite files.

## 8. Open and candidate selection

### 8.1 Opening order

1. Normalize the directory and acquire the exclusive lock.
2. Read primary, temp, and backup independently within size bounds.
3. Classify each as absent, valid v1/v2 legacy, valid v3, unsupported future, or corrupt.
4. Validate format, checksum, schema, and semantic invariants.
5. Select the valid candidate with the highest store revision.
6. For legacy candidates without revisions, primary outranks backup unless byte-identical migration metadata proves otherwise.
7. If the selected candidate is not primary, quarantine any invalid primary and install the selected candidate as primary.
8. Preserve a recovery report in memory and append it to the next successful v3 commit.
9. Clean only stale files whose contents are already preserved or proven older and valid.

### 8.2 Equal revisions

- Equal revision and identical bytes/checksum are duplicates; prefer primary.
- Equal revision with different valid content is `STORE_SPLIT_BRAIN` and requires explicit recovery selection.
- Never choose by modification time alone.

### 8.3 Unsupported future version

- Do not rewrite, migrate, repair, or quarantine merely because a version is newer.
- Return `STORE_VERSION_UNSUPPORTED` with found/supported versions.
- A metadata-only read may list file path, format, version, and size if safely parseable.
- CLI offers use of another store directory or upgrade of the application, not “start fresh” over the same files.

### 8.4 Key handling

- New empty store: create a 32-byte command MAC key with create-new semantics and restrictive permissions where supported.
- Existing non-empty store plus missing/invalid key: `STORE_KEY_MISSING` or `STORE_KEY_INVALID`; do not generate a replacement automatically.
- Key replacement requires explicit rekey recovery, which marks all non-completed ambiguous command proofs unusable and writes a quarantine backup first.
- Exports never contain this key.

## 9. Corruption and quarantine

### 9.1 Whole-document corruption

If primary is corrupt and another candidate is valid:

1. copy corrupt primary to quarantine;
2. verify the quarantine copy hash and size;
3. install the newest valid candidate;
4. report `RECOVERED_FROM_TEMP` or `RECOVERED_FROM_BACKUP`;
5. do not make provider calls during open.

If no valid candidate exists:

- do not create an empty store in the same directory;
- leave every source byte untouched;
- return `STORE_RECOVERY_REQUIRED` with safe candidate metadata;
- offer explicit export/copy of damaged files, choose another directory, or confirmed reset after quarantine;
- reset creates a new `storeId` and never reuses the damaged command key silently.

### 9.2 Run-level corruption

When top-level v3 data and checksum are valid but a run checksum or run invariant fails:

- preserve the raw run node in a quarantine artifact;
- exclude that run from mutable state;
- add a `QuarantinedRunSummary` containing run ID when safely parsed, pack ID when safely parsed, reason code, hash, size, and quarantine timestamp;
- valid runs remain listable/playable;
- never copy raw snapshot/generated/player content into the recovery report;
- an owner must explicitly remove, export, or attempt a future repair of the quarantined run.

If ownership cannot be safely parsed, only an administrative/local-store recovery view may see the quarantine entry.

### 9.3 Optional-data corruption

Prefetch rows, diagnostics, and expired audit entries are not authoritative game state.

- Invalid prefetch is dropped after its raw record is preserved in the recovery evidence or its hash/reason is recorded.
- Invalid diagnostics are dropped without failing the run.
- Snapshot, accepted artifacts, run status/revision, completed command proof, or trusted outbox corruption is authoritative and quarantines the run.

### 9.4 Recovery report

```java
public record StoreRecoveryReport(
    UUID storeId,
    long selectedRevision,
    RecoverySource source,
    List<RecoveryNotice> notices,
    List<QuarantinedRunSummary> quarantinedRuns,
    boolean degraded) {}
```

Messages contain codes and counts only. `toString()` must not include raw persisted content.

## 10. Migration contract

### 10.1 Supported path

```text
v1 -> v2 -> v3
v2 -> v3
v3 -> v3 (no-op)
```

Each step is a separate pure migration function with source and target validation.

### 10.2 Rules

- open legacy data read-only in memory first;
- never rewrite solely because the store was opened/listed;
- on first requested mutation, copy exact legacy primary bytes to `.bak` and quarantine/migration evidence before v3 commit;
- migration is deterministic and idempotent;
- preserve run IDs, owners, pack references, snapshots, revisions, events, command MACs, timestamps, usage, and prefetch where valid;
- derive new lifecycle fields conservatively;
- legacy `ACTIVE` remains `ACTIVE` only for the newest current run per owner; any additional legacy active run becomes `SUSPENDED` with a migration notice;
- legacy expired leases are cleared and recovered according to Sections 11–12;
- legacy `IN_PROGRESS` commands become recoverable interrupted commands, not `DONE`;
- unsupported/invalid fields never receive invented game values;
- migration does not call `Engine.resume`; post-migration recovery validation does.

### 10.3 Fixtures

Keep immutable golden fixtures for:

- empty v1;
- populated v1;
- empty v2;
- active v2 with completed commands/events;
- preparing v2;
- expired lease and in-progress command v2;
- generated full-game v2 with accepted artifacts;
- maximum supported v2 bounds;
- corrupt and unsupported versions.

Every fixture must prove stable v3 output after one mutation and byte-stable no-op after reopening.

## 11. Recovery coordinator

### 11.1 Invocation

Add a provider-neutral `SessionRecoveryService` in the session module. Run it:

- after store open and pack catalog initialization;
- before the CLI saved-game menu;
- on explicit `recover(runId)`;
- lazily before mutation when the startup scan was intentionally disabled by another host.

The coordinator is single-flight per store and uses store transactions. It never holds the store lock during provider calls or engine execution.

### 11.2 Scan result

For each run return one state:

```text
READY
RECOVERED
WAITING_FOR_LEASE
RETRYING_START
INTERRUPTED_COMMAND
PACK_UNAVAILABLE
PACK_VERSION_MISMATCH
QUARANTINED
FAILED
NO_ACTION
```

The report contains run IDs, safe codes, revisions, and next actions—not narrative or input content.

### 11.3 Recovery phases

1. Validate store and run invariants.
2. Resolve expired leases.
3. Reconcile preparing starts.
4. Reconcile in-progress commands.
5. Revalidate snapshots against exact installed pack versions.
6. Remove stale optional prefetch.
7. Reconcile uncertain generation calls conservatively.
8. Commit metadata-only recovery changes atomically.
9. Schedule allowed start retries after commit.

Recovery is safe to run repeatedly; a second run with no new failure is a no-op.

## 12. Run and command crash recovery

### 12.1 Lease rules

- An unexpired lease is not stolen.
- An expired lease may be cleared by a recovery transaction.
- Clearing records `LEASE_EXPIRED` with kind/attempt ID and no content.
- System clock moving backward cannot extend a lease beyond its stored duration plus a bounded skew allowance.
- Lease duration is not proof of provider timeout; it is only mutation ownership.
- Long operations must renew leases through compare-and-set on token/attempt ID.
- Renewal never changes game revision.

### 12.2 Preparing start

For `PREPARING`:

- valid unexpired live lease/job: report waiting;
- expired/no lease and age below `startTtl`: clear stale lease and schedule one start attempt;
- age at/after TTL: mark `FAILED/START_TIMEOUT` unless the player explicitly requests one recovery attempt under a host-configured extension;
- missing pack: keep recoverable metadata and report `PACK_UNAVAILABLE`;
- different installed pack version: do not start; report `PACK_VERSION_MISMATCH`;
- missing Spec 27.8 transient attachment: retry with persisted presets only and emit content-free `START_PERSONALIZATION_DROPPED`;
- cancellation request prevents new scheduling;
- if generation finishes after cancellation was requested, check status/attempt ID before commit and discard its uncommitted result.

Initial generation may be called again after a crash because no accepted snapshot existed. The uncertain prior call remains charged. Once an active snapshot exists, initial stages are never regenerated.

### 12.3 Cancelling a preparing run

Add `CANCELLING` and `CANCELLED` transitions:

1. player requests cancel;
2. transaction changes `PREPARING -> CANCELLING` and records request time;
3. no new start attempt may claim it;
4. live worker observes cancellation before snapshot commit;
5. after worker release or lease expiry, recovery changes it to `CANCELLED`;
6. cancellation never creates an engine run or ending and never calls `Command.Abandon`;
7. cancelled runs may be archived/trashed.

### 12.4 In-progress command

For a command log in `IN_PROGRESS`:

- if its in-memory future exists and lease is valid, report processing;
- if the run revision is greater than `revisionBefore`, require a matching `DONE` record in the same committed transaction; absence is authoritative corruption and quarantines the run;
- if the run revision equals `revisionBefore` and no live job remains after lease expiry, mark the command `FAILED` with `COMMAND_INTERRUPTED`;
- keep payload MAC, revision before, start time, and failure code;
- do not add events, advance revision, alter snapshot, or call the engine/provider;
- the player refreshes and chooses again with a new command ID;
- resubmitting the old command ID returns the same interrupted failure.

This rule avoids duplicate game effects and avoids persisting submitted text merely to enable replay.

### 12.5 Completed command

For `DONE`:

- replay returns the stored accepted/rejected result semantics and current view;
- accepted revision/outbox/snapshot relationships must validate;
- do not call engine `apply` or provider;
- a completed command whose current run has advanced remains replayable from its logged metadata but returns the latest current view, matching existing service behavior;
- compaction may replace old detailed command rows with a signed/checksummed checkpoint that still rejects reused IDs within the retained idempotency window.

### 12.6 Failed command

- stable deterministic failures remain failed across restart;
- retryable infrastructure failures require a new command ID after current-view refresh;
- `RUN_UNRECOVERABLE` transitions the run to `FAILED` only after the last known snapshot is preserved for export/quarantine;
- failure never deletes the run automatically.

## 13. Generation ledger recovery

### 13.1 Durable call record

Replace ambiguous aggregate active reservations with bounded records:

```java
public record GenerationCallRecord(
    UUID callId,
    UUID runId,
    String profileScope,
    LocalDate budgetDay,
    Priority priority,
    GenerationStage stage,
    CallState state,
    Instant reservedAt,
    Instant completedAt,
    TokenUsage usage) {}
```

States:

```text
RESERVED
SUCCEEDED
FAILED_BEFORE_SEND
FAILED_AFTER_SEND
UNCERTAIN
```

### 13.2 Accounting

- Reservation creates `RESERVED` before provider invocation.
- Failure proven before network/provider send releases capacity and becomes `FAILED_BEFORE_SEND`.
- Success records safe token counts and becomes `SUCCEEDED`.
- Known provider failure after send becomes `FAILED_AFTER_SEND` and consumes a call.
- Crash/restart leaving stale `RESERVED` becomes `UNCERTAIN` and consumes a call.
- Token counts for uncertain calls remain unknown/zero; never invent usage.
- Daily/run call limits count `SUCCEEDED`, `FAILED_AFTER_SEND`, and `UNCERTAIN`.
- Prefetch uncertain calls count as prefetch attempts.
- Recovery never contacts a provider to resolve an uncertain call.

Aggregate day/run diagnostics are derived from records or durable checkpoints. Migration converts existing counts into anonymous legacy aggregate checkpoints without pretending individual call identities.

## 14. Saved-run lifecycle and library

### 14.1 Listing

Add owner-scoped pagination:

```java
RunPage list(OwnerRef owner, RunQuery query, PageToken token, int limit);
```

`RunDescriptor` contains only:

- run ID;
- pack ID/version;
- locale;
- session status;
- revision;
- safe story title if available from accepted snapshot view;
- created, last played, ended, archived, and trashed times;
- resumable flag;
- failure/recovery code;
- storage estimate.

Default order: non-trashed current first, then `lastPlayedAt` descending, then run ID. Page tokens are opaque, bounded, owner-scoped, and invalidated safely when query shape changes.

### 14.2 Suspend and activate

- `ACTIVE -> SUSPENDED` is allowed when no unexpired command lease/job exists.
- The exact snapshot and revision are preserved.
- No engine event, game effect, or provider call occurs.
- Activating a suspended run atomically suspends the current active run and activates the selected run for the same owner.
- A preparing run cannot be suspended; cancel or wait.
- An ended/failed/cancelled run cannot become active.
- Pack ID/version and snapshot resume validation must succeed before activation commits.
- Failed activation leaves both runs in their previous lifecycle states.

### 14.3 Archive

- Archive hides a non-current run from the default list but preserves all data.
- Active must be suspended first in the same explicit operation.
- Preparing cannot be archived.
- Unarchive restores visibility, not active status.
- Archive is reversible and makes no engine change.

### 14.4 Trash and restore

- Trash sets `trashedAt`; it does not physically remove data.
- Active is suspended before trash only after explicit confirmation and no live job.
- Preparing must be cancelled first.
- Trashed runs cannot be activated or mutated.
- Restore clears `trashedAt` and returns the run to suspended/terminal status.
- Name/ID conflicts are handled without overwrite.
- The command MAC/idempotency history remains with the trashed run.

### 14.5 Purge

- Purge physically removes a trashed run and all run-owned commands, events, prefetch, call-detail records, and indexes in one transaction.
- Require explicit run ID plus confirmation token in interactive CLI, or `--yes` in non-interactive administrative mode.
- Refuse purge of non-trashed or recently trashed runs unless a separate force policy is explicitly enabled.
- Default trash grace period: 30 days.
- Purge is irreversible except from external filesystem backup/export.
- Report freed approximate bytes and whether recovery is possible from backup.

### 14.6 CLI library

Extend the Spec 27.9 startup menu with:

```text
Saved games
1) Lanterns of Willow Marsh — In progress — Oct 22, 18:42
2) The Glass Orchard — Suspended — Oct 20, 11:03
3) River Signals — Complete — Oct 18, 16:20

N) New game
A) Archived games
T) Trash
/quit) Leave
```

Player actions are explicit: Continue, Switch to, Archive, Move to trash, Restore, Export, Show recovery details. Normal player UI does not expose raw store files, checksums, leases, or commands.

## 15. Retention and compaction

### 15.1 Default policy

- Never automatically remove `PREPARING`, `ACTIVE`, or `SUSPENDED` runs.
- Keep ended/failed/cancelled runs until the player archives/trashes them.
- Purge trashed runs only through an explicit cleanup command or an opted-in policy after 30 days.
- Keep one backup document.
- Keep quarantine files until explicit cleanup, subject to a warning at 256 MiB total.
- Keep detailed generation call records for 30 days, then compact to daily/run aggregates.
- Keep content-free audit entries for 90 days or 2,000 entries, whichever is smaller.

### 15.2 Command/event compaction

Compaction is allowed only for terminal or long-suspended runs and must preserve:

- current snapshot and generated artifacts;
- current revision;
- final result and ending;
- an event checkpoint if event consumers need sequence continuity;
- a bounded idempotency window of at least the newest 1,000 command IDs or 30 days;
- aggregate diagnostics required by support/tests;
- a checksum of removed history and compaction metadata.

Do not compact an active/preparing run, an in-progress command, or data needed by an unacknowledged outbox consumer.

### 15.3 Capacity behavior

At soft thresholds, show cleanup guidance. At the hard limit:

- reject new runs and non-essential prefetch;
- still allow commands necessary to finish/abandon an active run if their bounded commit fits;
- allow archive/trash/purge/export/compaction;
- never truncate the current snapshot or accepted artifact;
- never overwrite the last valid committed file with an oversized document.

## 16. Export and import

### 16.1 Export bundle

Use a closed JSON format:

```json
{
  "format": "capybee-run-export",
  "version": 1,
  "exportedAt": "...",
  "sourceRunId": "...",
  "pack": {"id": "...", "version": "..."},
  "snapshot": {},
  "checksum": "..."
}
```

Export requirements:

- snapshot must pass production encoding/validation;
- only persistent preset start inputs may appear, as already allowed by snapshot rules;
- no transient/raw/scrubbed setup free text;
- no owner ID, command key/MAC, leases, command bodies, pending start, provider prompt/output diagnostics, budget scope, or filesystem path;
- generated artifacts already accepted into the snapshot are included;
- write with create-new by default; overwrite requires explicit confirmation;
- use safe temp/force/move behavior.

### 16.2 Import

- enforce size, format, checksum, and exact-field validation before mutation;
- require the exact pack ID/version to be installed and `Engine.resume` validation to pass;
- assign a new local run ID by default and rewrite only the top-level snapshot run ID through a trusted helper;
- never overwrite an existing run ID;
- imported resumable snapshots enter `SUSPENDED` unless no current run exists and the player explicitly requests activation;
- imported ended snapshots remain `ENDED`;
- imported data receives empty local command/event/prefetch history plus an import checkpoint;
- import makes zero provider calls;
- failed import leaves the store byte-identical.

Exports are portability/recovery aids, not authenticity proofs.

## 18. Privacy and security invariants

1. Preserve all Spec 27.8 start-input rules in primary, temp, backup, quarantine, migration, export, audit, and recovery reports.
2. Quarantine may preserve already-persisted bytes for recovery but must never add a new copy of transient free text. Sentinel tests must prove none existed.
3. Do not persist command bodies solely for crash replay; payload MAC remains sufficient for ID-reuse checks.
4. Do not log story text, generated prose, snapshots, provider prompts/output, API keys, command MAC key, or raw corrupt nodes.
5. File names use trusted fixed prefixes, UUIDs, timestamps, and hashes only.
6. All paths resolve under the selected store/quarantine/export directory unless the user explicitly selects an export destination.
7. Reject traversal, symlink escape where detectable, device files, and non-regular import candidates.
8. Owner filtering applies to list, lifecycle, export, recovery, and purge operations.
9. Checksums detect damage but do not grant trust; imported snapshots still pass full engine validation.
10. Restrict key/store file permissions on supported systems and document best-effort behavior elsewhere.
11. A recovery report is safe for normal CLI display and structured logs.
12. Debug mode does not expose quarantined content or weaken confirmation/ownership rules.

## 19. Failure-injection test plan

### 19.1 Write interruption matrix

Inject failure after each write-protocol step:

- before temp create;
- during temp write;
- after temp write, before force;
- after force, before validation;
- after validation, before backup;
- during backup replacement;
- after backup, before primary replace;
- after primary replace, before directory force;
- after directory force, before in-memory acknowledgement.

For each point, close abruptly, reopen, and assert selection of exactly the old or new complete revision—never mixed state.

### 19.2 Candidate matrix

Test absent/valid/corrupt/future/equal/divergent combinations for primary, temp, and backup. Prove:

- highest valid revision wins;
- equal divergent revision stops;
- corrupt primary is quarantined before fallback install;
- future version is untouched;
- invalid candidate never deletes the only valid candidate;
- recovery is idempotent on second open.

### 19.3 Transaction contract

Run the same tests against local and in-memory adapters:

- exception after snapshot save;
- exception after outbox append;
- exception after prefetch delete;
- exception after command completion;
- nested transaction failure;
- oversized commit;
- no-op transaction;
- concurrent compare-and-set failure.

Every failure restores all port state.

### 19.4 Start recovery

- crash before provider call;
- crash during provider call;
- crash after generation but before snapshot commit;
- retry under TTL;
- TTL expiry;
- missing transient setup attachment;
- cancellation before worker claim;
- cancellation during worker execution;
- result arriving after cancellation;
- missing/mismatched pack;
- repeated recovery scan.

### 19.5 Command recovery

- crash before `begin`;
- crash after `begin`, before lease;
- crash after lease, before engine resume;
- crash during provider call;
- crash after `run.apply`, before transaction;
- crash during transaction at every sub-step;
- crash after commit, before response;
- replay completed ID;
- retry interrupted action with new ID;
- old interrupted ID remains failed;
- no duplicated events/effects/revisions/provider call after committed completion.

### 19.6 Library lifecycle

- list pagination/order/owner isolation;
- active to suspended;
- atomic switch between suspended runs;
- failed switch rollback;
- preparing cannot suspend/archive;
- archive/unarchive;
- trash/restore;
- purge confirmation and grace period;
- current run never silently replaced;
- lifecycle operations make zero engine/provider calls.

### 19.7 Migration and corruption

- every v1/v2 fixture migrates;
- open-only is byte-preserving;
- first mutation creates recoverable legacy backup;
- migration failure leaves source untouched;
- one corrupt run does not hide valid runs;
- authoritative corruption quarantines run;
- optional prefetch corruption does not quarantine run;
- missing command key fails closed;
- future version remains untouched.

### 19.8 Export/import/privacy

- active/suspended/ended export;
- exact pack import success;
- pack mismatch/invalid checksum/oversize/traversal failure;
- new run ID and empty local command history;
- imported accepted artifacts require zero provider calls;
- failed import is byte-identical rollback;
- privacy sentinels absent from every new artifact and message.

### 19.9 Process-level proof

Use child JVMs and hard termination, not only mocked exceptions:

1. launch deterministic full generated game;
2. terminate at controlled start/command barriers;
3. reopen the same directory;
4. inspect recovery report;
5. continue to trusted ending;
6. assert accepted effects/events exactly once;
7. assert accepted generated artifacts are not regenerated;
8. assert uncertain provider calls are conservatively counted;
9. repeat after archive, suspend, trash/restore, and v2 migration.

No test may call a live provider.

## 22. Definition of done

Spec 27.10 is complete when:

- v3 commits have monotonic revisions, store/run checksums, validated temp files, and one valid backup;
- reopening after every injected write interruption selects a complete old or new commit;
- corrupt bytes are preserved before automatic recovery or reset;
- one corrupt run can be quarantined without hiding unrelated valid runs;
- v1 and v2 stores migrate deterministically on first mutation and remain untouched on read-only open;
- future store versions are never downgraded or overwritten;
- missing/invalid command key fails safely;
- local and in-memory store transactions have identical rollback semantics;
- accepted snapshot, command completion, events, and prefetch cleanup commit atomically;
- stale leases are reclaimed through compare-and-set recovery;
- preparing starts retry/cancel/timeout deterministically and never reconstruct transient free text;
- orphaned in-progress commands become interrupted and are never auto-reapplied;
- completed commands and accepted generated artifacts resume without repeated effects or provider calls;
- uncertain provider calls consume budget conservatively;
- multiple games can be listed, suspended, switched, archived, trashed, restored, and explicitly purged;
- only one run per owner is mutable/current;
- no active, preparing, or suspended run is automatically deleted;
- storage growth has documented soft/hard behavior and safe compaction;
- export/import is bounded, validated, pack-exact, private, and provider-free;
- the Spec 27.9 CLI preserves quit/abandon, commands, exit codes, and explicit destructive confirmations;
- privacy sentinels are absent from all new store, backup, quarantine, export, audit, recovery, log, and CLI surfaces;
- process-kill/restart tests continue a full generated game to a trusted ending with exactly-once accepted state;
- all standard verification passes without a live provider.
