# Spec 27.11 — Generated Content Quality and Semantic Consistency

**Type:** Implementation specification  
**Parent:** Spec 27.10 — Durable Session Persistence and Recovery  
**Depends on:** Specs 25, 26.1, and 27.1–27.10  
**Baseline:** repository commit `b00c545`, plus the approved designs in Specs 27.4–27.10. The current generation catalog, structured output parser, generation pipeline, artifact model, story-plan/continuity contracts, result model, safety checks, repair/fallback flow, snapshot restore, session generation accounting, and generated-game tests were inspected while writing this specification. The build was not run. Existing uncommitted work was not modified.  
**Status:** Ready for implementation after Spec 27.10  
**Primary outcome:** Generated theme, story plan, cast, quests, scenes, continuity facts, choice labels, and endings are evaluated by deterministic, provider-neutral quality rules before acceptance. Detectable contradictions, unsafe age/tone violations, unusable prose, and severe repetition receive the existing single repair attempt and then a validated authored fallback. Trusted engine state remains the only source of gameplay truth, and accepted artifacts resume without re-evaluation or new provider calls.

---

## 1. Problem

The generation pipeline already validates important structural and safety properties:

- exact JSON fields and payload types;
- bounded strings and collections;
- trusted IDs and complete coverage;
- actor, objective, phase, role, tone, and choice references;
- PII-like output rejection and markup/control-pattern rejection;
- complete cast and quest coverage;
- ending objective-note coverage;
- one repair attempt followed by an authored fallback;
- artifact persistence and deterministic resume.

This proves that generated output is well-shaped and cannot control mechanics. It does not prove that the output is good enough to play:

- prose can contradict trusted objective or outcome state while using valid IDs;
- a scene can repeat an earlier scene almost word for word;
- choice labels can be technically distinct IDs but have the same visible meaning;
- cast and quest descriptions can be generic, duplicated, or inconsistent;
- story phases can satisfy schema coverage while failing to develop the promised story;
- dialogue can sound like the wrong character or repeat narration;
- continuity facts can conflict with earlier accepted facts;
- non-ending scenes can announce that the game is already complete;
- ending prose can say success when the trusted result is partial success or failure;
- generated text can be too dense, fragmented, imperative, frightening, or otherwise unsuitable for the declared audience;
- tone tags are passed to generation but not checked against the returned prose;
- current repair receives a failure code but quality failures are not classified consistently;
- diagnostics do not distinguish shape, safety, semantic, repetition, readability, and tone failures;
- quality changes after an engine upgrade could make old accepted snapshots impossible to resume unless acceptance is stamped durably.

Spec 27.11 adds a conservative quality gate. It detects only claims and patterns that can be checked deterministically from trusted context and authored locale resources. It does not pretend to understand all prose, and it never derives game state from generated text.

## 2. Current implementation findings

| ID | Finding | Consequence |
|---|---|---|
| F1 | `GenerationOutputParser` combines schema, reference, basic presentation, PII, and markup checks. | Keep parsing strict, but move broader cross-field/cross-artifact quality into a separate evaluator. |
| F2 | `GenerationPipeline.execute` accepts any parsed payload immediately. | Insert quality evaluation after parse and before artifact creation/composition/cache. |
| F3 | The pipeline already permits at most one repair call. | Quality does not add a second retry loop or judge call. |
| F4 | Repair context uses stable failure information rather than rejected prose. | Continue sending finding codes/rules only; do not echo rejected output into repair. |
| F5 | Fallback payloads are parsed at pack load. | Require quality validation of fallback resources at pack load too. |
| F6 | Full-game output is artifact schema v2. | Add a v3 quality stamp while keeping v1/v2 restore compatibility. |
| F7 | Restored payloads are revalidated structurally. | Historical quality acceptance must not be rerun under a changed style profile during ordinary resume. |
| F8 | Story plan contains themes, story promises, phase goals/development/transitions, actor slots, objectives, tones, and roles. | It supplies enough trusted narrative structure for conservative coherence checks. |
| F9 | Scene context contains slot phase/role/allowed references and selected continuity facts. | Scene quality can be evaluated without route topology or hidden mechanics. |
| F10 | Ending generation receives trusted outcome, objective states, and result facts. | Ending contradictions can be checked using authored localized truth phrases. |
| F11 | Content policy declares audience age range and forbidden tags. | Quality profiles can apply age/tone defenses without changing the manifest policy source of truth. |
| F12 | Existing text limits are code-point bounds, not readability rules. | Add deterministic length, sentence, paragraph, and fragmentation checks. |
| F13 | Provider output is not sent to an external output judge. | Preserve offline, provider-neutral evaluation and bounded cost. |
| F14 | Prefetched scenes may be generated before entry. | They must pass the same quality gate before insertion into prefetch storage. |

## 3. Goals and non-goals

### 3.1 Goals

1. Add a pure deterministic quality evaluator after structured parsing.
2. Define mandatory rules that packs cannot disable.
3. Add bounded locale-specific resources for phrase, readability, tone, and truth checks.
4. Detect high-confidence contradictions with trusted state and accepted narrative facts.
5. Detect severe repetition, visible-choice ambiguity, fragmentation, and unusable prose.
6. Apply audience and tone defenses consistently across stages.
7. Use the existing repair budget and authored fallback path.
8. Validate all fallbacks with the same mandatory baseline before runtime.
9. Stamp accepted artifacts with evaluator/profile identity and content-free findings.
10. Preserve old artifacts and exact resume behavior.
11. Produce safe metrics for offline improvement without storing rejected prose.
12. Build a provider-neutral golden corpus with pass/fail explanations.

### 3.2 Non-goals

- Proving that prose is objectively creative, fun, or emotionally perfect.
- Using another model/provider as a quality judge.
- Adding provider calls, embeddings, vector databases, or network classifiers.
- Parsing prose to set counters, flags, objectives, routes, outcomes, or effects.
- Replacing Spec 25 input safety or provider safety policy.
- Claiming deterministic phrase lists catch every unsafe or contradictory statement.
- Rewriting generated text locally.
- Accepting partially valid payload fields and combining them with fallback fields.
- Changing choice IDs, actor slots, objective IDs, phases, or endings based on prose.
- Re-evaluating historical accepted prose on every resume.
- Defining the rich reference adventure and its full corpus; Spec 27.12 owns that game.
- Adding online experimentation or telemetry export.

## 4. Decisions

| ID | Decision |
|---|---|
| D1 | Quality evaluation is a pure engine-core operation with no I/O, clock, randomness, provider, session, or CLI dependency. |
| D2 | Structural parsing and quality evaluation remain separate phases with separate error codes. |
| D3 | Mandatory safety/truth/reference rules cannot be disabled or weakened by a pack profile. |
| D4 | Locale profiles may tune bounded readability/repetition values and provide authored phrase lexicons. |
| D5 | Findings are `BLOCKING` or `ADVISORY`; there is no opaque aggregate “AI score.” |
| D6 | Any blocking finding rejects the attempt. The first rejected attempt may use the existing one repair; the next failure uses fallback. |
| D7 | Advisory findings do not reject output. They are stamped and counted for offline evaluation. |
| D8 | Quality evaluation never mutates a payload. Accepted provider output is stored exactly as parsed. |
| D9 | Repair receives codes, scopes, and concise trusted requirements only—never the rejected prose or untrusted explanation. |
| D10 | Fallbacks must pass structural, mandatory, and configured quality checks at pack load. Runtime fallback does not consume a provider call. |
| D11 | A generated artifact accepted under v3 stores a content-free `QualityStamp`. Normal resume trusts that historical decision. |
| D12 | Legacy v1/v2 artifacts use legacy structural validation and are not retrospectively rejected by new style rules. |
| D13 | Similarity uses deterministic normalization and token/shingle rules, not embeddings. |
| D14 | Contradiction detection uses authored phrase families tied to trusted facts. Unknown language is not guessed. |
| D15 | Failure to load a required full-game quality profile is a pack-load error, not a runtime provider fallback. |
| D16 | Quality diagnostics contain rule IDs, counts, numeric measures, and hashes only; no generated or player text. |
| D17 | Quality checks run before engine IDs are assigned and before scene composition/cache/prefetch persistence. |
| D18 | Trusted state always wins. A missed contradiction may affect displayed prose, but never game mechanics or final result data. |

## 5. Quality resource

### 5.1 Location and indexing

Add a required locale map for `FULL_GAME` to the Spec 27.4 `RunContract`:

```json
{
  "qualityResources": {
    "en": "generation/quality/en.json",
    "pl": "generation/quality/pl.json"
  }
}
```

Rules:

- every generated-game supported locale has exactly one quality resource;
- paths use existing safe pack-relative validation and appear in `pack.json.files`;
- content-only schema-v1 generation may omit quality resources and keeps legacy behavior;
- quality resources are parsed and cross-validated during pack loading;
- the resource is trusted authored configuration, never provider output.

### 5.2 Shape

```json
{
  "schemaVersion": 1,
  "profileId": "family-adventure-en-v1",
  "locale": "en",
  "readability": {
    "maxSentenceCodePoints": 220,
    "maxParagraphCodePoints": 500,
    "maxConsecutiveShortSentences": 4,
    "maxUppercaseRatioBasisPoints": 2500
  },
  "repetition": {
    "fieldDuplicateThresholdBasisPoints": 9000,
    "recentSceneThresholdBasisPoints": 8200,
    "choiceThresholdBasisPoints": 7800,
    "recentSceneWindow": 4
  },
  "phraseSets": {
    "completionClaims": ["everything is finished", "the adventure is over"],
    "commandingLanguage": ["you must obey", "do exactly as I say"],
    "forbiddenAudienceTerms": ["..."]
  },
  "toneProfiles": {
    "warm": {
      "incompatiblePhraseSets": ["hostileTone"],
      "advisoryPhraseSets": ["coldTone"]
    }
  },
  "truthPhrases": [
    {
      "factId": "outcome:success",
      "affirming": ["the village was saved"],
      "contradicting": ["the village was lost"]
    },
    {
      "factId": "objective:repair-lantern:DONE",
      "affirming": ["the lantern was repaired"],
      "contradicting": ["the lantern was never repaired"]
    }
  ]
}
```

The example phrases are illustrative. Production phrase resources must be authored and reviewed for the declared locale and game.

### 5.3 Java types

```java
public record GenerationQualityProfile(
    int schemaVersion,
    String profileId,
    LocaleTag locale,
    ReadabilityRules readability,
    RepetitionRules repetition,
    Map<String, List<String>> phraseSets,
    Map<String, ToneProfile> toneProfiles,
    List<TruthPhraseFamily> truthPhrases,
    String fingerprint) {}
```

The loader computes `fingerprint` as SHA-256 over canonical parsed profile data excluding the fingerprint itself. It is not supplied by the pack.

### 5.4 Validation

- schema version exactly 1;
- profile ID matches `[a-z0-9][a-z0-9._-]{0,79}`;
- locale equals the map key and a supported locale;
- exact fields only;
- all maps/lists immutable and deterministically ordered;
- 0–64 phrase sets;
- 0–64 phrases per set;
- 1–120 code points per phrase;
- 0–64 tone profiles;
- every catalog tone tag used by the locale has a profile or explicitly uses `neutral` defaults;
- referenced phrase-set IDs exist;
- truth fact IDs are unique and reference declared outcomes/objectives/result facts through allowed namespaces;
- affirming/contradicting phrases are non-empty, normalized-unique, and do not overlap;
- phrase lists contain no PII, markup, control characters, command-looking identifiers, or empty normalized values;
- numeric bounds stay within engine hard limits in Section 5.5;
- a profile cannot raise a mandatory hard maximum or lower a mandatory detection threshold below safe engine bounds.

### 5.5 Hard bounds

| Setting | Allowed range | Default |
|---|---:|---:|
| Maximum sentence code points | 80–300 | 220 |
| Maximum paragraph code points | 200–700 | 500 |
| Consecutive short sentences | 2–8 | 4 |
| Uppercase ratio | 1,000–4,000 bp | 2,500 bp |
| Field duplicate threshold | 8,500–10,000 bp | 9,000 bp |
| Recent-scene threshold | 7,500–9,500 bp | 8,200 bp |
| Choice threshold | 7,000–9,500 bp | 7,800 bp |
| Recent scene window | 1–8 | 4 |

Lower similarity basis points mean stricter rejection. Pack values outside bounds fail load; they are not clamped silently.

## 6. Evaluation model

### 6.1 Types

```java
public interface GenerationQualityEvaluator {
  QualityReport evaluate(
      GenerationCatalog.Stage stage,
      GenerationArtifact.Payload payload,
      QualityContext context,
      GenerationQualityProfile profile);
}

public record QualityReport(
    QualityDecision decision,
    List<QualityFinding> findings,
    QualityMetrics metrics) {}

public record QualityFinding(
    String ruleId,
    FindingSeverity severity,
    String scope,
    Map<String, Integer> measures) {}

public enum QualityDecision { ACCEPT, ACCEPT_WITH_ADVISORIES, REJECT }
public enum FindingSeverity { BLOCKING, ADVISORY }
```

`scope` is a trusted path such as `scene.narration`, `choices`, `ending.objectiveNotes`, or `phase:middle`. It never includes prose.

### 6.2 Determinism

Given the same:

- evaluator version;
- quality profile fingerprint;
- locale;
- payload;
- trusted quality context;

the report is byte-for-byte equivalent after canonical encoding.

No rule depends on system time, hash-map iteration order, random values, machine locale, provider ID, or prior diagnostics.

### 6.3 Processing order

1. Traverse payload fields in a fixed stage-specific order.
2. Normalize text only for comparison; retain original payload unchanged.
3. Apply mandatory universal rules.
4. Apply stage semantic rules.
5. Apply trusted-fact contradiction rules.
6. Apply audience/tone rules.
7. Apply readability and repetition rules.
8. Sort findings by severity, rule ID, and scope.
9. Decide reject if any blocking finding exists.

### 6.4 Text normalization

For comparisons only:

1. Unicode NFKC;
2. locale-neutral lowercase unless the locale profile supplies an engine-supported case strategy;
3. replace punctuation/separators with one space;
4. collapse whitespace;
5. retain letters and numbers;
6. tokenize with Java Unicode word boundaries for supported whitespace-delimited locales;
7. for non-whitespace locales, use code-point trigrams through a tested locale strategy;
8. do not stemming/translate/phonetic-match in v1.

The profile declares one of the engine-supported tokenization strategies. Unknown strategies fail pack load.

### 6.5 Similarity

Use integer basis-point Jaccard similarity over unique token bigrams, falling back to normalized tokens for text shorter than two tokens:

```text
similarity = floor(intersectionCount * 10000 / unionCount)
```

No floating-point comparison is used. Exact normalized equality always yields 10,000.

## 7. Quality context

### 7.1 Purpose

`QualityContext` contains only trusted data already allowed for the stage plus accepted artifacts needed for comparison:

```java
public record QualityContext(
    LocaleTag locale,
    ContentPolicy contentPolicy,
    GenerationCatalog.Stage stage,
    String phaseId,
    String storyRole,
    List<String> toneTags,
    Set<String> allowedActorSlots,
    Set<String> allowedObjectiveIds,
    Set<String> choiceIds,
    StoryPlanPayload storyPlan,
    CastPayload cast,
    QuestPayload quest,
    List<AcceptedSceneText> recentScenes,
    List<ContinuityFact> selectedContinuity,
    TrustedResultContext resultContext) {}
```

Fields irrelevant to a stage are empty/null. Lists are bounded before evaluation.

### 7.2 Trusted result context

Ending context includes:

- exact outcome ID/class;
- exact objective IDs and states;
- selected authored result facts;
- ending scene ID/phase/role;
- truth fact IDs active for this result.

It contains localized authored labels only when needed for phrase matching. Generated quest descriptions are not trusted truth.

### 7.3 Context bounds

- at most 4 recent accepted scenes;
- title, narration, dialogue, choices, and facts only, using existing field limits;
- at most 8 selected continuity facts;
- no raw provider response;
- no rejected payload from another attempt;
- no start free text;
- no hidden route topology, effects, conditions, counters, flags, or sets;
- ending context uses only the already-authorized structured result facts.

## 8. Mandatory universal rules

These rules apply to generated, repaired, and fallback payloads. Packs cannot disable them.

### 8.1 Output safety defense

In addition to current parser checks, reject:

- terminal/ANSI controls and bidi override controls outside explicitly safe text characters;
- prompt/meta language that claims to be system/developer instructions;
- requests for credentials, contact details, exact address, school/class identity, or secrets;
- command-like lines that imitate CLI commands or engine control fields;
- attempts to expose internal IDs, JSON/schema, provider prompts, hidden rules, or policy;
- URLs or contact handles when the pack policy does not explicitly permit reviewed authored links;
- phrase-set matches for mandatory audience-prohibited categories.

Use bounded, reviewed phrase/pattern matching. Do not put matched text in findings.

### 8.2 Presentation integrity

Reject when:

- a title is normalized-identical to its premise/narration/description;
- two required visible labels in the same list are normalized-identical;
- two choice labels exceed the configured choice similarity threshold;
- a choice label is only punctuation, an internal ID, a bare number, or a slash command;
- prose contains unresolved template markers such as `{{...}}`, `${...}`, `<slot>`, or allow-listed placeholder patterns;
- text addresses the player as a model/operator or discusses generation mechanics;
- non-ending scene prose matches a completion claim;
- an ending contains a “continue choosing” or unfinished-output marker.

### 8.3 Mechanical truth boundary

Reject prose that contains recognized instructions to:

- set/increment/decrement counters;
- add/remove flags or set members;
- complete/fail objectives as an instruction;
- jump to a scene, phase, route, or ending;
- choose an option automatically;
- alter outcome/result class;
- save/delete/abandon a run;
- ignore policy, schema, or trusted context.

This extends existing reserved-control patterns. Detection rejects presentation; it never executes the text.

## 9. Stage-specific quality rules

### 9.1 THEME

Blocking:

- title and premise are near-duplicates;
- premise is too short to establish a subject under locale minimums;
- output tone tags are not allowed or contradict mandatory audience phrase sets;
- title is a generic placeholder from the configured generic-title phrase set.

Advisory:

- title repeats a major phrase from the premise;
- premise reaches maximum length with one sentence;
- no tone-associated phrase signal is found when the profile defines advisory signals.

Tone signals are never required to contain literal keywords unless the profile explicitly marks them advisory. Avoid keyword-stuffed output incentives.

### 9.2 SCENARIO / story plan

Blocking:

- phase goal/development/transition fields are duplicates within or across adjacent phases;
- all phase goals are near-identical;
- a phase refers through truth phrases to an objective/outcome not allowed in that phase;
- a non-ending phase announces final completion;
- ending-phase text contradicts allowed ending outcome families;
- a story promise has no deterministic token overlap or authored anchor coverage in any phase development;
- phase progression reverses a recognized trusted fact without a declared transition allowance;
- premise/setting/title conflict with profile truth phrases for authored immutable setting facts.

Advisory:

- one story promise is covered only weakly;
- adjacent transition/development similarity is high but below rejection threshold;
- every phase uses the same sentence opening pattern.

The evaluator does not decide whether a story idea is imaginative. It checks distinct progression and detectable contract use.

### 9.3 CAST

Current exact slot/name rules remain. Add blocking checks for:

- descriptions near-duplicate another character;
- character name appears to be another slot/internal identifier;
- description contradicts an authored immutable slot truth phrase;
- description claims a role/objective not allowed for the slot/template;
- name or description matches audience-prohibited phrase sets.

Advisory:

- every description has the same normalized opening;
- description is below the locale’s useful-detail threshold;
- character name is very similar to another name without being identical.

Do not infer gender, identity, or personality attributes that are not explicitly authored.

### 9.4 QUEST

Current exact objective coverage remains. Add blocking checks for:

- title/description duplicates another objective;
- description says the objective is already complete at game start;
- description contradicts authored objective truth/goal phrases;
- title/description refers to another objective’s exclusive truth phrase;
- text gives engine/control instructions rather than a player-facing goal.

Advisory:

- title restates the description exactly;
- description has no verb/action signal when the locale profile provides one;
- all objectives share a formulaic opening.

Quest prose never changes objective conditions or completion.

### 9.5 SCENE

Blocking:

- narration is near-duplicate to any recent accepted scene above threshold;
- title is near-duplicate to a recent title where the profile marks this blocking;
- dialogue duplicates narration or another line above field threshold;
- a dialogue actor’s text contradicts immutable authored actor facts;
- a continuity fact contradicts active trusted truth phrases or a selected prior continuity fact;
- two continuity facts in the payload express opposite authored truth values;
- scene text contradicts its phase, story role, allowed objective state, or allowed outcome family;
- a non-ending scene claims final completion;
- an ending scene omits or contradicts required truth coverage;
- choice labels are semantically indistinguishable under the deterministic similarity rule;
- a choice label promises a mechanical effect that its trusted option does not have, when an authored option-effect phrase mapping exists.

Advisory:

- narration is similar to a recent scene but below blocking threshold;
- repeated opening/closing phrase across the recent window;
- dialogue speaker alternation is highly repetitive;
- continuity fact repeats an earlier fact exactly and adds no new accepted fact;
- narration has no overlap with the phase goal/story promise where configured anchors exist.

### 9.6 ENDING

In addition to all scene rules, blocking checks require:

- headline/summary result language agrees with exact outcome class;
- every objective note contains an affirming phrase for its exact trusted state or a state-neutral authored phrase explicitly valid for that state;
- no objective note contains a contradicting phrase for its exact state;
- selected result facts are not contradicted;
- success, partial success, and failure terms do not cross their authored phrase families;
- reflection is optional, non-commanding, and does not shame, diagnose, threaten, or pressure the player;
- ending does not claim rewards, penalties, saved data, real-world contact, or future actions not present in trusted result data.

If a locale/profile cannot provide complete truth phrase coverage for every declared ending/objective state, the pack fails validation. Ending truth does not rely on general sentiment scoring.

## 10. Contradiction evaluation

### 10.1 Truth set

Build an immutable `NarrativeTruthSet` from trusted context:

```java
public record NarrativeTruth(
    String factId,
    TruthValue value,
    Set<String> allowedScopes,
    boolean requiredCoverage) {}
```

Examples:

- `outcome:success = TRUE`;
- `outcome:failure = FALSE`;
- `objective:repair-lantern:DONE = TRUE`;
- `objective:repair-lantern:FAILED = FALSE`;
- `phase:ending = TRUE`;
- `actor:guide:present = TRUE` only when authored context declares it.

### 10.2 Phrase matching

- Normalize profile phrases and candidate fields using the same strategy.
- Match whole normalized token sequences, not arbitrary substrings, for whitespace locales.
- Longest phrase wins when phrases overlap.
- Negation is encoded in authored phrase families; the engine does not attempt open-ended grammar parsing.
- A phrase assigned to multiple incompatible fact values fails pack load.
- A contradicting match creates a blocking finding with fact ID hashed or safely allow-listed, never the matched excerpt.
- Missing coverage is blocking only where `requiredCoverage=true`, primarily endings.

### 10.3 Continuity facts

Continuity fact text remains narrative memory, not state. Quality evaluation may reject a new fact when it matches an authored contradiction pair against:

- trusted state;
- selected prior facts;
- immutable story/actor/setting facts.

Unknown or unrecognized claims are allowed unless another rule blocks them. The engine never converts continuity prose into a new truth value.

### 10.4 Limitations

Documentation must state:

- phrase matching is conservative and incomplete;
- no claim of full semantic understanding is made;
- false negatives affect prose only because mechanics remain trusted;
- false positives are bounded by repair then fallback;
- profile authors must test inflections, negations, and locale-specific boundaries.

## 11. Readability, repetition, and tone

### 11.1 Readability

Deterministically measure:

- code points per sentence and paragraph;
- token count per field;
- consecutive very short sentences;
- uppercase letter ratio;
- repeated punctuation runs;
- unmatched paired punctuation/quotes for locale-supported pairs;
- excessive list-like or fragment-like lines;
- repeated sentence openings.

Do not use English-only syllable formulas as a universal age score. Locale profiles may add an engine-supported, tested readability strategy later; unsupported formulas fail load.

Blocking applies only to extreme configured violations. Borderline measures are advisory.

### 11.2 Repetition

Compare only bounded fields relevant to the stage:

- within payload;
- against dependencies such as theme/plan/cast/quest;
- against recent accepted scenes selected deterministically;
- never against unvisited prefetch output;
- never against rejected provider output.

Generic stop phrases supplied by the locale profile can be removed before shingling, but the stop list is bounded and fingerprinted.

### 11.3 Tone

Tone evaluation is phrase-set compatibility, not sentiment analysis:

- mandatory content-policy categories always block;
- active scene/phase tone tags select compatible/incompatible phrase sets;
- incompatible matches block or advise as declared within engine-safe bounds;
- absence of “positive” keywords does not block;
- irony, sarcasm, and subtle emotional meaning are not guessed;
- ending reflection has stricter non-shaming/non-commanding mandatory rules.

### 11.4 Audience

Use `ContentPolicy.Audience` to select mandatory engine rule bands. At minimum define reviewed bands:

```text
EARLY_CHILDHOOD
CHILD
TEEN
GENERAL
```

Mapping from min/max age is deterministic and documented. A pack spanning bands uses the strictest included band unless explicitly split into separate packs/profiles. Pack `forbiddenTags` can add restrictions but cannot remove band rules.

## 12. Pipeline integration

### 12.1 Attempt flow

For every provider attempt:

1. call provider;
2. verify finish reason;
3. parse and structurally validate;
4. construct trusted `QualityContext`;
5. evaluate quality;
6. accept only `ACCEPT` or `ACCEPT_WITH_ADVISORIES`;
7. otherwise set the primary stable quality failure code;
8. if this was the first attempt and one repair is configured/budgeted, issue repair;
9. otherwise load validated fallback;
10. assign engine IDs and create/stamp artifact;
11. compose/cache/persist only the accepted artifact.

Quality rejection never partially updates stage artifacts, resolved scenes, continuity, prefetch, or snapshots.

### 12.2 Primary failure code

When several blocking findings exist, choose the repair code by fixed priority:

1. safety/audience;
2. trusted-state contradiction;
3. mechanical-control/meta content;
4. required coverage;
5. choice ambiguity;
6. severe repetition;
7. readability/tone;
8. general quality invalid.

All finding codes remain in the internal content-free report, subject to count bounds.

### 12.3 Repair request

Repair context includes:

```json
{
  "repair": {
    "failureCode": "GENERATION_QUALITY_STATE_CONTRADICTION",
    "findingCodes": ["Q_ENDING_OUTCOME_CONTRADICTION"],
    "scopes": ["ending.summary"],
    "requirements": ["Present the supplied trusted outcome without changing it."]
  }
}
```

Requirements are fixed localized-independent engine instructions selected by rule ID. Do not include:

- rejected text;
- matched phrase;
- player free text;
- provider commentary;
- arbitrary profile-authored instructions.

The original trusted stage context may be resent under existing rules.

### 12.4 Calls and budgets

- Quality evaluation itself costs zero provider calls.
- Total attempts remain initial plus at most one repair.
- A quality repair counts exactly like existing schema/safety repairs.
- If no repair budget remains, select fallback immediately.
- Diagnostics and Spec 27.10 generation ledger classify the call by stage and quality outcome without prose.

### 12.5 Prefetch

- Evaluate before `PrefetchStore.insertIfAbsent`.
- A rejected prefetch may use the same one repair allowance for that scene if budget permits.
- Fallback prefetch remains non-persisted under existing rules.
- Only accepted visited scenes enter continuity selection.
- Prefetch quality results never include future narrative in player diagnostics.

## 13. Fallback quality

### 13.1 Pack-load validation

Every fallback passes:

- current exact parser/reference/safety checks;
- mandatory universal quality rules;
- stage-specific intra-payload rules;
- locale audience/tone checks;
- declared trusted-fact checks for every applicable allowed state;
- route-level repetition/coherence validation through pack test scenarios.

If one fallback text cannot be truthful for multiple materially different objective/outcome states, the pack must provide distinct ending slots/resources as recommended by Spec 27.7.

### 13.2 Runtime guarantee

Once the pack loads:

- fallback is always available for its declared context;
- fallback quality requires no provider or external service;
- runtime does not reject a valid fallback because provider output failed;
- unexpected fallback/context mismatch is `GENERATION_FALLBACK_CONTEXT_INVALID` and prevents state transition as specified in Spec 27.7;
- such mismatch is an implementation/pack corruption error, not a reason to accept rejected provider prose.

### 13.3 Fallback diversity

For full-game packs, the loader/test harness evaluates reachable fallback sequences:

- adjacent scene narration under recent-scene thresholds;
- distinct choice labels;
- phase progression/promise anchors;
- continuity fact compatibility;
- each ending against its outcome/objective-state matrix.

Conservative graph paths from Spec 27.4 are sufficient; do not attempt unrestricted symbolic execution.

## 14. Artifact schema v3 and resume

### 14.1 Quality stamp

Extend `GenerationArtifact` for schema v3:

```java
public record QualityStamp(
    int evaluatorVersion,
    String profileId,
    String profileFingerprint,
    QualityDecision decision,
    List<String> advisoryCodes,
    String reportFingerprint) {}
```

Rules:

- generated and repaired accepted artifacts require a stamp;
- fallback artifacts require a stamp created from pack-load/runtime evaluation;
- advisory codes are unique, sorted, allow-listed, maximum 16;
- no text snippets, truth values, player data, or provider response;
- report fingerprint hashes the canonical content-free report, not the payload;
- `toString()` remains payload/report redacted.

### 14.2 Versioning

- New full-game artifacts produced after implementation use artifact schema 3.
- Schema 1 and 2 remain decodable/restorable according to their historical contracts.
- Snapshot codec reads/writes v3 stamps with exact fields.
- Unknown artifact/stamp versions fail with existing unsupported-version behavior.
- Content-only packs may remain schema 1 until explicitly upgraded.

### 14.3 Resume behavior

For a valid schema-v3 artifact:

- revalidate pack ID/version, locale, stage/template/slot, structural references, and stamp shape;
- verify the stored profile ID/fingerprint belongs to the exact pack version recorded by the snapshot;
- do not rerun style/repetition/semantic quality against a newer engine implementation;
- make zero provider calls;
- preserve the exact payload and artifact outcome;
- a missing/malformed stamp makes the artifact invalid and uses normal snapshot recovery/quarantine rules.

Security-critical retroactive invalidation requires an explicit future migration/security specification, not an incidental evaluator update.

## 17. Offline golden corpus

### 17.1 Location

Add test resources, not production telemetry:

```text
core/src/test/resources/generation-quality/<locale>/<stage>/
```

Each case contains:

- case ID;
- quality profile ID/fingerprint fixture;
- typed trusted context;
- candidate payload;
- expected decision;
- expected finding codes/scopes/measures;
- short author rationale stored only in test data.

### 17.2 Required corpus classes

For every required locale:

- clean provider-like output for every stage;
- structurally valid but repetitive output;
- near-threshold similarity pairs;
- ambiguous choice labels;
- plan promise covered/uncovered;
- distinct/non-distinct phases;
- duplicate cast/quest descriptions;
- pre-completed quest wording;
- continuity affirmation/contradiction/unknown;
- ending success/partial/failure truth matrix;
- every objective state phrase family;
- age/tone allowed, advisory, and blocked cases;
- meta/prompt/control language;
- Unicode normalization, punctuation, casing, and boundary cases;
- non-whitespace tokenization cases where supported;
- false-positive regression cases.

### 17.3 Corpus rules

- no real personal information;
- no provider credentials or production conversations;
- use authored synthetic examples;
- cases are small and bounded;
- expected results are reviewed, not generated at test time;
- corpus IDs may appear in metrics; payload text may not appear in logs on failure unless the local unit test explicitly opts into fixture diagnostics.

### 17.4 Threshold stability

Changing normalization, rule severity, or a threshold requires:

1. evaluator version increment when acceptance can change;
2. corpus diff report by rule/stage/locale;
3. review of new false positives and fallback rate;
4. unchanged legacy artifact resume tests;
5. regenerated profile fingerprint fixtures.

## 18. Testing requirements

### 18.1 Profile parser

- valid multi-locale resources;
- missing locale/profile/tone/truth mapping;
- unknown fields and schema;
- phrase normalization duplicates/overlap;
- invalid truth references;
- unsafe phrase content;
- every numeric boundary;
- deterministic fingerprint;
- exact pack file indexing.

### 18.2 Normalization and similarity

- NFKC equivalents;
- case and punctuation;
- repeated whitespace;
- token bigram behavior;
- short-text fallback;
- integer threshold equality (`>=` behavior specified by each rule);
- stop phrases;
- Unicode/non-whitespace strategy;
- iteration-order independence;
- no floating-point variation.

### 18.3 Universal rules

- control/meta/prompt language;
- private-data requests;
- unresolved placeholders;
- terminal/bidi control;
- URLs/contact handles policy;
- title/body duplication;
- completion claim in non-ending;
- command-looking choice labels;
- no matched text in findings.

### 18.4 Stage rules

- THEME title/premise/tone;
- SCENARIO phase distinction, promises, progression;
- CAST duplicate/inconsistent descriptions;
- QUEST pre-completion and objective truth;
- SCENE recent repetition, dialogue, choices, phase/role, continuity;
- ENDING outcome/objective/result fact matrix and reflection;
- multiple simultaneous findings and priority;
- advisory-only acceptance.

### 18.5 Pipeline

- parsed + quality pass accepts generated artifact;
- advisory accepts with stamp;
- first blocking failure + valid repair yields `REPAIRED`;
- first and second quality failure select fallback;
- no repair budget selects fallback directly;
- structural failure behavior unchanged;
- provider failure behavior unchanged;
- rejected payload never enters artifact/cache/prefetch/snapshot/context;
- repair context contains codes but not rejected text;
- no extra provider calls beyond configured maximum;
- execution summary reports safe fields.

### 18.6 Fallbacks

- every valid fallback passes at pack load;
- unsafe/repetitive/contradictory fallback fails load;
- route-level duplicate fallback fails fixture validation;
- ending fallback matrix covers all declared states;
- runtime fallback requires no quality service/provider;
- impossible context mismatch prevents transition without state mutation.

### 18.7 Persistence and restore

- artifact schema v3 snapshot round-trip;
- stamp exact-field validation;
- profile fingerprint binding;
- v1/v2 artifact compatibility;
- no retrospective style evaluation of legacy/v3 accepted artifact;
- restore performs zero provider calls;
- Spec 27.10 export/import preserves stamp and exact payload;
- corrupt stamp quarantines/rejects through normal recovery.

### 18.8 Privacy

Use sentinels in rejected output, setup text, prompts, and truth phrases. Assert absence from:

- repair request except fixed trusted requirements;
- `QualityFinding`, reports, stamps, `toString()`, exceptions;
- execution summaries and session diagnostics;
- store primary/temp/backup/quarantine metadata beyond already accepted artifact rules;
- CLI stdout/stderr;
- aggregate metric exports;
- test names/failure summaries in integration tests.

### 18.9 Full-game routes

Run deterministic provider-double matrices:

| Route | Injected issue | Expected |
|---|---|---|
| Opening | repeated prior narration | repair succeeds |
| Middle | ambiguous choices | fallback scene |
| Development | continuity contradiction | repair or fallback, state unchanged until accepted |
| Pre-ending | early completion claim | fallback |
| Success ending | says failure | repair succeeds and trusted success result remains |
| Partial ending | says total success | fallback partial ending |
| Failure ending | shaming reflection | fallback non-shaming ending |
| Entire run | advisory-only style | generated run completes with advisories |
| Entire run | provider unavailable | validated fallback run completes |

Every route must reach a trusted ending, preserve command/event idempotency, and resume without quality/provider work.

## 22. Definition of done

Spec 27.11 is complete when:

- every full-game locale has a validated, fingerprinted quality profile;
- parsed output passes a pure deterministic quality evaluator before acceptance;
- mandatory rules cannot be disabled by pack configuration;
- blocking versus advisory behavior is explicit and stable;
- high-confidence trusted-state and continuity contradictions trigger repair/fallback;
- severe repetition, ambiguous choices, unusable readability, and audience/tone violations are handled as specified;
- generated prose never changes mechanics or truth;
- quality consumes no judge/provider call and does not expand the existing retry budget;
- repair requests contain safe codes/requirements and no rejected prose;
- rejected output never enters artifacts, snapshots, prefetch, continuity, logs, or later context;
- all authored fallbacks pass static and route-level quality validation before play;
- success, partial-success, and failure endings agree with exact trusted result/objective facts;
- artifact schema v3 stores a content-free quality stamp;
- legacy artifacts resume unchanged and accepted v3 artifacts are not re-judged on normal resume;
- quality diagnostics/metrics contain no prose or player data;
- the offline corpus covers every stage, locale strategy, threshold boundary, and ending truth matrix;
- provider-double and all-fallback full games complete from setup through trusted ending;
- Spec 27.10 crash/recovery/export/import guarantees remain intact;
- authored/schema-v1 generation and Spec 27.9 CLI behavior remain compatible;
- all standard verification passes without a live provider.
