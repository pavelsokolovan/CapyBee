# Spec 27.4 — Full Generated Game Contract

**Type:** Implementation specification  
**Parent:** Spec 27 — Engine API Contract; extends the generated-play work from Specs 26, 26.1, and 27–27.3  
**Depends on:** Specs 22–27.3  
**Baseline:** repository commit `b00c545`. The source and existing generated fixture were inspected while writing this specification; the build was not run. Step 0 requires a clean baseline build before implementation.  
**Status:** Ready for implementation  
**Primary outcome:** The engine can distinguish a small generated-content demo from a complete generated game. A pack that declares the new full-game contract is rejected before play unless it contains a bounded, finishable story structure, every required generation stage and scene slot, validated fallback content, and enough budget to complete the shortest supported run. Existing authored packs and generation-catalog schema v1 remain compatible.

This specification defines the foundation for Specs 27.5–27.13. It does not yet add dynamic story planning, new mechanics, generated endings, or the final friendly CLI flow. It defines the contract those later specifications must satisfy.

---

## 1. Why this specification exists

The current generated fixture proves that the technical generation loop works:

1. generate or fall back for `SCENARIO`, `CAST`, and `QUEST`;
2. generate the opening scene;
3. lazily generate one later scene;
4. enter an authored ending.

That is a valid integration fixture, but it is not yet a full game. The current contracts do not answer these questions:

- How long must a complete run be?
- Which story phases must exist?
- Must all routes reach an ending?
- Which scenes must be generated and which may be authored control scenes?
- How many ending routes must exist?
- Is there enough generation budget to finish when no prefetch is used?
- Can the pack finish entirely from fallbacks when the provider is unavailable?
- How does a host know whether a pack is a demo or a complete game?

Without an explicit contract, each later feature would invent a different meaning of “full generated game.” Spec 27.4 adds one versioned definition at the pack boundary.

## 2. Findings in the current implementation

| ID | Finding | Consequence |
|---|---|---|
| F1 | `GenerationCatalog` schema v1 contains stages, templates, scene slots, and generation limits, but no complete-run declaration. | The loader cannot identify or validate a full game. |
| F2 | `SceneSlot` binds one trusted scene ID to one template, fallback, and list of trusted choice IDs. | This remains the correct closed-world generation boundary. |
| F3 | `ScenarioPayload.beats` is narrative data only. It does not control routes. | Story planning may describe the route, but the pack must remain authoritative for the graph. |
| F4 | `CastPayload` and `QuestPayload` are persisted, but current runtime behavior does not depend on their narrative fields. | Runtime use belongs to Spec 27.6, not this contract spec. |
| F5 | Routes, conditions, effects, objective rules, and end behavior come from authored scenes and rules. | Full-game validation can analyze trusted content without trusting model output. |
| F6 | The current generated fixture has generated `opening` and `meeting` scenes followed by one authored ending. It has no rules, objectives, places, or start inputs. | Keep it as a small compatibility fixture; do not relabel it as a full game. |
| F7 | Generated artifacts and snapshots already preserve accepted content. | No new artifact-store design is needed in 27.4. |
| F8 | Session mode already provides persistence, metering, prefetch, and diagnostics. | 27.4 adds pack preflight facts; it does not redesign session lifecycle. |
| F9 | Pack validation already runs before `Engine.start`. | Full-game structural failures belong at pack-load time, before any provider call. |
| F10 | Generation limits cap calls, output tokens, input characters, and repairs. | A new budget feasibility check can use these trusted limits. |

The implementation baseline must be rechecked in step 0 because this specification was written after the original Spec 27.3 baseline and the repository has continued to change.

## 3. Goals and non-goals

### 3.1 Goals

1. Add a versioned, optional full-game contract to the generation catalog.
2. Preserve generation-catalog schema v1 and all authored-pack behavior.
3. Define a common five-phase story lifecycle.
4. Prove that the trusted scene graph is bounded and can reach a declared ending.
5. Prove that required generated scenes have valid templates, choices, and fallbacks.
6. Prove that the configured call budget can complete at least the shortest valid route without prefetch.
7. Make full-game capability visible through a small public engine API.
8. Provide stable validation codes and deterministic tests.
9. Establish exact boundaries for Specs 27.5–27.13.

### 3.2 Non-goals

- Generating or changing runtime routes. Routes remain authored and trusted.
- Letting model output define rules, effects, conditions, IDs, objectives, or endings.
- Implementing the story-plan artifact. Spec 27.5 owns it.
- Making cast or quest artifacts change state. Spec 27.6 owns it.
- Adding result quality, outcome selection, or generated ending summaries. Spec 27.7 owns them.
- Adding interactive setup questions. Spec 27.8 owns them.
- Redesigning the console. Spec 27.9 owns it.
- Redesigning session persistence or recovery. Spec 27.10 owns it.
- Changing provider adapters, prefetch behavior, or web APIs.
- Replacing the existing generated fixture with the future full reference pack.

## 4. Decisions

| ID | Decision |
|---|---|
| D1 | Generation-catalog schema v1 remains supported. Schema v2 adds the optional `runContract`. |
| D2 | A catalog with no `runContract` is a generated-content pack, not a declared full game. It continues to work with `--generated`. |
| D3 | `runContract.kind` has one value in this version: `FULL_GAME`. Future kinds require a later schema version. |
| D4 | A full game has five ordered phase kinds: `OPENING`, `DEVELOPMENT`, `CHALLENGE`, `RESOLUTION`, `ENDING`. Pack phase IDs are stable trusted IDs and may use any valid identifier. |
| D5 | The pack owns the complete scene graph. Generation fills narrative slots only. A model cannot create a route, phase, scene ID, choice ID, condition, effect, or outcome ID. |
| D6 | A full-game graph is bounded by construction: after collapsing authored self-contained utility scenes, story-phase edges may stay in the same phase or move forward, but cannot move to an earlier phase. Cycles in the story scene graph are rejected in v1 of this contract. |
| D7 | Every reachable non-ending story scene must have at least one structural path to a declared ending. Every reachable terminal story scene must be a declared ending. |
| D8 | Every player-visible narrative scene in a full game must have a `SceneSlot`, including endings. Authored scene definitions own the trusted routes and mechanics; slot fallback resources supply the player-facing fallback narrative. A pack may have authored utility scenes only when the contract marks them `UTILITY`. |
| D9 | Provider-free completion is mandatory. Every required stage and every scene slot reachable on a shortest valid route has a validated fallback. In practice, pack validation continues to require a fallback for every declared stage and slot. |
| D10 | Budget feasibility is calculated for demand generation only. Prefetch can spend extra calls but must never be necessary to finish. |
| D11 | The minimum game length counts accepted story transitions, not console commands, rejected commands, map movement, help commands, or short replies. |
| D12 | A full game must offer at least one meaningful choice before `RESOLUTION`; the future reference pack will require more, but the engine contract stays general. |
| D13 | Completion means entering a declared ending scene and producing `EndReason.COMPLETED` with a trusted non-blank outcome ID. Abandonment is not game completion. |
| D14 | Contract validation happens while loading the pack. No provider is configured or called during validation. |
| D15 | Full-game capability is reported by the engine as typed metadata, not inferred by a host from filenames or pack IDs. |

## 5. Terminology

**Generated-content pack**  
A pack with feature `GENERATION`. It may be a test, demo, mixed authored/generated story, or full game.

**Full generated game**  
A generation-enabled pack with a valid schema-v2 `runContract` whose kind is `FULL_GAME`.

**Story scene**  
A scene that participates in the ordered story arc and is assigned to one contract phase.

**Utility scene**  
An authored support scene outside the story arc, for example instructions or a non-narrative status screen. It cannot end the game, apply story outcomes, or be the only path between phases.

**Phase**  
A pack-defined part of the story with one of the five trusted phase kinds.

**Declared ending**  
A trusted story scene in the `ENDING` phase, listed in `completion.endings`, with `end: true` or an unconditional trusted `END_RUN` effect on entry.

**Structural path**  
A path through authored `next`, option, and branch destinations. Static validation treats conditional edges as possible edges; it does not ask the model to reason about conditions.

**Shortest completion path**  
The reachable structural path from the start scene to a declared ending that needs the fewest not-yet-generated stage or scene artifacts.

## 6. Generation catalog schema v2

### 6.1 Compatibility

`GenerationCatalog.SUPPORTED_SCHEMA_VERSION` becomes `2`. The parser accepts versions 1 and 2.

- Version 1 is parsed into the existing fields with `runContract = null`.
- Version 2 may omit `runContract`; it is then still only a generated-content pack.
- `kind = FULL_GAME` requires every rule in this specification.
- Unknown v2 properties remain errors, following the existing closed-schema rule.
- Serialization of existing v1 fixtures and artifact schema version 1 does not change.
- This change does not require a generation-artifact schema bump because the contract is trusted pack metadata, not model output.

### 6.2 JSON shape

```json
{
  "schemaVersion": 2,
  "supportedLocales": ["en"],
  "defaultLocale": "en",
  "stages": [],
  "sceneSlots": [],
  "limits": {},
  "runContract": {
    "kind": "FULL_GAME",
    "contractVersion": 1,
    "phases": [
      {
        "id": "opening",
        "kind": "OPENING",
        "sceneIds": ["arrival"]
      },
      {
        "id": "journey",
        "kind": "DEVELOPMENT",
        "sceneIds": ["meet-guide", "find-path"]
      },
      {
        "id": "challenge",
        "kind": "CHALLENGE",
        "sceneIds": ["crossing"]
      },
      {
        "id": "resolution",
        "kind": "RESOLUTION",
        "sceneIds": ["return-letter"]
      },
      {
        "id": "ending",
        "kind": "ENDING",
        "sceneIds": ["ending-success", "ending-partial"]
      }
    ],
    "utilitySceneIds": [],
    "length": {
      "minimumStoryTransitions": 4,
      "maximumStoryTransitions": 16
    },
    "completion": {
      "endings": [
        {"sceneId": "ending-success", "outcomeId": "success"},
        {"sceneId": "ending-partial", "outcomeId": "partial"}
      ]
    }
  }
}
```

### 6.3 Java contract

Add the following immutable catalog types, using the project’s existing records and defensive-copy conventions:

```java
public record RunContract(
    RunContractKind kind,
    int contractVersion,
    List<RunPhase> phases,
    List<String> utilitySceneIds,
    RunLength length,
    CompletionContract completion) {}

public enum RunContractKind { FULL_GAME }

public record RunPhase(String id, PhaseKind kind, List<String> sceneIds) {}

public enum PhaseKind { OPENING, DEVELOPMENT, CHALLENGE, RESOLUTION, ENDING }

public record RunLength(int minimumStoryTransitions, int maximumStoryTransitions) {}

public record CompletionContract(List<EndingContract> endings) {}

public record EndingContract(String sceneId, String outcomeId) {}
```

`GenerationCatalog` gains nullable `RunContract runContract`. Provide a source-compatible secondary constructor with the current v1 parameters and `runContract = null` so tests and internal callers do not require a mechanical rewrite.

`contractVersion` supports only `1`. It is separate from catalog schema version so later full-game rules can evolve without changing unrelated catalog fields.

### 6.4 Identifier and size limits

Use the existing pack identifier grammar where one already exists. Otherwise use:

- phase ID and outcome ID: `[a-z][a-z0-9-]{0,63}`;
- exactly five phases for `FULL_GAME` contract version 1;
- exactly one of each phase kind;
- 1–64 scene IDs per phase;
- 0–16 utility scene IDs;
- 1–16 endings;
- `minimumStoryTransitions`: 4–31;
- `maximumStoryTransitions`: minimum value through 32.

The phase array order must be exactly the enum order. Duplicate phase IDs, scene IDs, utility IDs, ending scene IDs, and outcome IDs are errors.

## 7. Full-game structural rules

### 7.1 Required generation stages

A `FULL_GAME` contract requires exactly one definition for each of:

- `SCENARIO`;
- `CAST`;
- `QUEST`;
- `SCENE`.

`THEME` remains optional. If present, it must precede `SCENARIO` through the existing dependency rules.

Every required stage must have:

- a template with the matching stage;
- a safe pack-relative fallback resource;
- a valid fallback payload;
- dependency ordering accepted by the existing generation catalog validator.

The `SCENE` stage definition supplies the common stage fallback contract; every actual story scene is additionally represented by a scene slot and its slot-specific fallback.

### 7.2 Phase membership

For a full game:

1. Every authored scene in the locale's scene set is listed in exactly one phase or in `utilitySceneIds`.
2. The start scene belongs to `OPENING`.
3. Every ending belongs to `ENDING`.
4. No non-ending story scene has `end: true`.
5. Utility scenes cannot be start or ending scenes.
6. Utility scenes cannot have `END_RUN` effects or an outcome.
7. A story scene and utility scene cannot share an ID.
8. Every locale supported by the generation catalog has the same trusted scene IDs and graph. Localized text may differ.

The existing per-locale scene parser remains responsible for scene validity. The new validator compares graph identity across supported locales.

### 7.3 Generated scene coverage

Every story scene must have exactly one `SceneSlot`.

For each slot:

- `sceneId` resolves to its authored scene;
- `templateId` resolves to a `SCENE` template;
- `fallbackResource` exists and validates as a scene payload;
- `choiceIds` equals the authored scene’s complete ordered option-ID list;
- fallback choice IDs equal that same trusted list;
- fallback dialogue actor IDs, if any, resolve through trusted cast actor slots;
- the scene ID may appear in only one slot.

The generated payload may replace only title, narration, dialogue text, and choice labels. The authored scene continues to supply its ID, routes, branches, conditions, effects, input mode, objective behavior, and end marker.

Utility scenes must not have generation slots in contract version 1.

### 7.4 Phase progression

Build the story graph from:

- `Scene.next`;
- every `SceneOption.next`;
- every `SceneBranch.next`.

Ignore map links because moving does not change story scenes. Ignore disabled-state analysis because conditions are runtime state, but retain all conditional branches as possible edges.

For each story-to-story edge:

- the destination phase may be the same phase;
- or the next or any later phase;
- it must never be an earlier phase.

For utility edges:

- a story scene may enter a utility scene;
- the utility subgraph must be acyclic;
- every utility path must return to the same story phase;
- utility traversal does not count as a story transition;
- utility scenes cannot bridge one story phase to another.

After removing utility detours, the complete story graph must be acyclic. This deliberately excludes repeatable story loops in contract version 1. A later contract version may add explicitly bounded loops.

### 7.5 Reachability and completion

The validator must prove:

1. Every phase contains at least one scene reachable from the start.
2. Every structural path from the start to an ending visits all five phase kinds in order; it is not enough that each phase is reachable on a different branch.
3. Every declared ending is reachable from the start.
4. Every reachable story scene can reach at least one declared ending.
5. Every reachable terminal story scene is a declared ending.
6. A declared ending has no `next`, no options, and no branches.
7. Entering a declared ending always ends the run as `COMPLETED`.
8. The trusted outcome ID produced by that ending equals its `EndingContract.outcomeId`.
9. At least one reachable scene before `RESOLUTION` has two or more enabled-by-structure choices. Static validation does not attempt to prove runtime conditions, so the pack’s deterministic tests must prove at least two choices are actually usable on one route.

Unreachable authored scenes are rejected for a full game rather than silently ignored. This keeps pack size, fallback coverage, and route testing honest.

### 7.6 Length bounds

Calculate the minimum and maximum number of story-to-story edges from the start scene to any declared ending in the acyclic graph.

- Calculated minimum must be at least `length.minimumStoryTransitions`.
- Calculated maximum must be at most `length.maximumStoryTransitions`.
- The declared maximum must be at least the declared minimum.
- The calculated maximum cannot exceed the hard engine limit of 32.

The contract describes the structural route length. Rejected commands, free-text clarification, utility scenes, and map movement do not change this count.

### 7.7 Locale parity

For every supported locale, compare these trusted fields by scene ID:

- start/end marker;
- option IDs and destinations;
- `next` destination;
- branch count, conditions, and destinations;
- effects and input mode;
- phase membership and ending outcome.

Only player-facing localized text may differ. If the existing pack format intentionally stores trusted scene structure once rather than per locale in the future, this check can become unnecessary, but schema v2 must validate the format that exists now.

## 8. Budget feasibility

### 8.1 Purpose

A structurally complete pack is still not playable as a generated game if its own generation limits guarantee fallback before the shortest route can be generated. Fallback keeps the run playable, but the `FULL_GAME` declaration must reserve a realistic opportunity for generation.

### 8.2 Required-call calculation

Calculate `minimumRequiredProviderCalls` as:

```text
number of configured non-SCENE startup stages
+ number of distinct SCENE slots on the shortest completion path
```

Rules:

- Include optional `THEME` when configured.
- Count `SCENARIO`, `CAST`, and `QUEST` once each.
- Count each distinct scene slot on the shortest route, including its ending.
- Count one first attempt per stage or scene.
- Do not count repair attempts.
- Do not count prefetch.
- Use the route with the smallest number of generated slots; in v1 every story scene has a slot, so this normally equals the shortest story route.

Validate:

```text
limits.totalCallsPerRun >= minimumRequiredProviderCalls
limits.callsPerStage >= 1
```

Also calculate and expose:

- `minimumRequiredProviderCalls`;
- `minimumStoryTransitions` derived from the graph;
- `maximumStoryTransitions` derived from the graph;
- number of reachable story scenes;
- number of declared endings.

The daily/profile/session limits from Spec 27 may be smaller at runtime. That is allowed: the engine uses fallbacks and remains playable. The catalog check only proves that its internal generation budget is not self-contradictory.

### 8.3 Fallback-only completion

Pack validation must build the complete fallback scene set and run a structural dry check with no provider:

- all stage fallbacks parse and validate;
- all scene fallbacks compose with their trusted authored scenes;
- all composed choices preserve the trusted choice IDs;
- every structural route still ends because generated content cannot change routes;
- no fallback contains unsafe markup or violates pack content policy.

This check does not create a `Run`, allocate IDs, mutate a store, or call a provider.

## 9. Public capability metadata

Add a small immutable API in `engine-core`:

```java
public record GeneratedGameProfile(
    Kind kind,
    int contractVersion,
    List<PhaseProfile> phases,
    int reachableStoryScenes,
    int endings,
    int minimumStoryTransitions,
    int maximumStoryTransitions,
    int minimumRequiredProviderCalls) {
  public enum Kind { CONTENT_ONLY, FULL_GAME }
}

public record PhaseProfile(String id, PhaseKind kind, int sceneCount) {}
```

Extend `Pack` with a third record component:

```java
public record Pack(PackManifest manifest, Map<String, String> files,
                   Optional<GeneratedGameProfile> generatedGameProfile) {
  public Pack(PackManifest manifest, Map<String, String> files) {
    this(manifest, files, Optional.empty());
  }
}
```

The existing two-argument constructor is mandatory for source compatibility. `PackLoader` attaches the validated profile only after every section validator succeeds. A manually constructed two-argument `Pack` has no trusted precomputed profile; tests that modify full-game pack files must pass the modified pack through `PackLoader` before asserting full-game capability.

Requirements:

- packs without `GENERATION`: empty;
- generation schema v1 or v2 without `runContract`: `CONTENT_ONLY`;
- valid `FULL_GAME`: `FULL_GAME` with precomputed facts;
- hosts do not re-run graph validation;
- the metadata contains no generated text, prompt content, or secrets.

The implementation computes this once during pack loading and keeps it with the validated pack. Do not parse the catalog on every view or command. `GeneratedGameProfile` remains in the provider-neutral core module and contains no provider details.

## 10. Runtime invariants

Spec 27.4 does not change the normal command loop. It adds these invariants for a declared full game:

1. `Engine.start(... generated=true)` requires a valid generation provider or uses fallbacks under the existing rules.
2. Starting with `generated=false` remains invalid for a pack whose required `GENERATION` feature is not enabled for the run, following the existing feature check.
3. The start scene resolves through its declared scene slot.
4. Every story scene, including endings, resolves through its declared scene slot and is cached as an artifact.
5. Provider failure cannot make a structurally valid full game unfinishable because its fallback is already validated.
6. A generated payload cannot alter the phase, route, game length, ending, or outcome.
7. A snapshot stores accepted generated artifacts exactly as it does today.
8. Resume revalidates artifacts against pack and template identity; it does not regenerate displayed content.
9. `EndReason.ABANDONED` never satisfies the completion contract.
10. A completed run’s `outcome` must be one of the trusted outcome IDs declared in the contract.

If current runtime composition does not generate an ending because the ending has no options, that is an implementation defect exposed by this spec: entering any scene slot, including a terminal slot, must resolve its generated narrative before `View` is returned.

## 11. Validation codes

Use `PackIssue` with `ERROR` severity for all failures. Messages must identify trusted IDs but must not include file bodies, prompts, generated text, or credentials.

| Code | Meaning |
|---|---|
| `PACK_RUN_CONTRACT_VERSION_UNSUPPORTED` | `contractVersion` is not supported. |
| `PACK_RUN_CONTRACT_INVALID` | General shape, bounds, order, or identifier rule failed. |
| `PACK_RUN_PHASE_MISSING` | One of the five required phase kinds is missing. |
| `PACK_RUN_PHASE_DUPLICATE` | A phase kind, phase ID, or scene membership is duplicated. |
| `PACK_RUN_SCENE_UNCLASSIFIED` | An authored scene is neither a story scene nor utility scene. |
| `PACK_RUN_SCENE_UNKNOWN` | The contract references an unknown scene. |
| `PACK_RUN_START_PHASE_INVALID` | Start scene is not in `OPENING`. |
| `PACK_RUN_ENDING_INVALID` | Ending shape, outcome, or end behavior is invalid. |
| `PACK_RUN_ROUTE_BACKWARDS` | An edge moves to an earlier phase. |
| `PACK_RUN_ROUTE_CYCLIC` | Story or utility graph contains a forbidden cycle. |
| `PACK_RUN_ROUTE_DEAD_END` | A reachable non-ending scene cannot reach a declared ending. |
| `PACK_RUN_SCENE_UNREACHABLE` | A declared scene or ending cannot be reached from start. |
| `PACK_RUN_LENGTH_INVALID` | Calculated path length violates declared or hard limits. |
| `PACK_RUN_CHOICE_REQUIRED` | No meaningful pre-resolution choice exists. |
| `PACK_RUN_SCENE_SLOT_MISSING` | A story scene has no generation slot. |
| `PACK_RUN_SCENE_SLOT_DUPLICATE` | More than one slot targets the same scene. |
| `PACK_RUN_CHOICE_SET_MISMATCH` | Slot or fallback choices do not exactly match trusted scene choices. |
| `PACK_RUN_LOCALE_GRAPH_MISMATCH` | Trusted scene structure differs between locales. |
| `PACK_RUN_BUDGET_INSUFFICIENT` | Catalog call limits cannot attempt the shortest complete route. |
| `PACK_RUN_FALLBACK_INCOMPLETE` | Full fallback composition cannot be validated. |

Reuse an existing more specific pack-validation code when it already describes the failure exactly, such as missing files, unsafe paths, dangling references, or malformed JSON. Do not emit two errors for the same root cause merely to include a `PACK_RUN_*` code.

## 12. Required tests

### 12.1 Catalog compatibility

- Existing schema-v1 generated fixture loads unchanged and reports `CONTENT_ONLY`.
- Existing authored fixtures load unchanged and expose no generated-game profile.
- A valid schema-v2 catalog without `runContract` loads as `CONTENT_ONLY`.
- Unsupported catalog and contract versions fail with stable codes.
- Unknown v2 fields fail closed.

### 12.2 Contract shape

- Valid five-phase contract loads and reports all derived facts.
- Missing, duplicated, or wrongly ordered phase kind fails.
- Duplicate phase ID, scene membership, utility membership, ending, or outcome fails.
- Invalid identifier and every numeric boundary are tested.
- Unknown and unclassified scenes fail.
- Start scene outside `OPENING` fails.

### 12.3 Graph validation

- A straight five-phase route passes.
- Same-phase forward edges in an acyclic phase subgraph pass.
- A route that skips an optional scene or phase scene but still visits every phase passes only when another scene in that phase is reached; a route that can skip an entire required phase fails.
- Backward phase edge fails.
- Same-phase cycle fails.
- Dead end fails.
- Undeclared terminal scene fails.
- Unreachable story scene and unreachable ending fail.
- Valid utility detour passes; utility cycle, phase bridge, ending, or outcome fails.
- At least one real usable choice is proven by an engine integration test.

The validator must check required-phase visitation on **every** start-to-ending path, not only that each phase has one globally reachable scene. Use DAG dynamic analysis; do not enumerate an exponential number of paths.

### 12.4 Scene-slot and fallback coverage

- Every story scene with exactly one valid slot passes.
- Missing and duplicate slot fail.
- Slot choice order or membership mismatch fails.
- Fallback choice mismatch fails.
- Utility scene with a slot fails.
- Invalid fallback actor reference fails.
- Generated ending slot composes and displays generated ending text.
- Provider unavailable from start through ending completes with only fallbacks.

### 12.5 Length and budget

- Derived shortest and longest transition counts are exact for a branching DAG.
- Below-minimum and above-maximum paths fail.
- Hard maximum above 32 fails.
- Budget equal to minimum required calls passes.
- Budget one call below minimum fails.
- Optional `THEME` adds one required startup call.
- Repair allowance and prefetch do not incorrectly increase the minimum calculation.

### 12.6 Runtime and snapshots

- A scripted provider plays a minimal conforming full game from opening to generated ending.
- Every displayed story scene has one cached `SCENE` artifact.
- Generated output cannot change route, effect, end marker, or outcome.
- Completed outcome belongs to the declared set.
- Abandonment is not reported as completion.
- Save/resume at each phase makes zero repeated calls for displayed artifacts.
- Provider failure at each phase separately still reaches an ending through fallback.

### 12.7 Boundary and regression tests

- No new dependency from `engine-core` to CLI, session, provider, Spring, or application packages.
- Pack validation performs no network call and requires no API key.
- Existing authored CLI golden files remain byte-for-byte unchanged.
- Existing generated fixture output remains compatible except for optional non-player-facing profile diagnostics added in explicit debug mode.
- Normal Maven verification needs no network or provider credentials.

- one locale;
- five phase kinds;
- at least one scene per phase;
- at least one pre-resolution branch;

## 14. Implementation sequence

### Step 0 — Reconfirm baseline

1. Run `git status` and record the current baseline commit in the implementation notes.
2. Run `mvn -f app/engine/pom.xml clean verify` before changes.
3. Re-read current catalog/parser, scene parser, pack validator order, generated runtime, snapshot codec, and generated CLI tests.
4. If the current source differs from a finding in §2, update this spec only when the difference changes a contract decision.

### Step 1 — Add schema-v2 data types

1. Add nullable `RunContract` to `GenerationCatalog`.
2. Add the records and enums from §6.3.
3. Preserve the old constructor.
4. Update the parser for schema versions 1 and 2.
5. Add closed-schema and bounds tests.

### Step 2 — Add structural validation

1. Build a locale-neutral trusted scene graph from parsed scene sets.
2. Validate classification, phase order, slots, endings, and utility restrictions.
3. Validate graph reachability, acyclicity, required-phase presence on every completion path, and length.
4. Compare trusted graph structure across locales.
5. Emit the stable codes from §11.

### Step 3 — Add fallback and budget validation

1. Compose every slot fallback into its trusted scene.
2. Validate choice equality and actor references.
3. Calculate shortest completion cost and budget feasibility.
4. Cache the derived profile facts.

### Step 4 — Expose capability metadata

1. Add `GeneratedGameProfile` and `PhaseProfile`.
2. Add the optional profile component and compatibility constructor to `Pack`.
3. Attach the validated profile in `PackLoader` only after successful validation.

## 16. Definition of done

Spec 27.4 is complete when all of the following are true:

- Catalog schema v1 remains supported without migration.
- Catalog schema v2 parses with strict closed-field behavior.
- A generated-content pack and full generated game are distinguishable through typed metadata.
- A valid full game has exactly the five required phase kinds.
- Every story scene, including every ending, has one trusted generation slot and validated fallback.
- Every possible structural completion path visits all five phase kinds in order.
- The trusted story graph is acyclic, bounded to at most 32 transitions, and has no reachable dead end.
- Every declared ending is reachable, terminal, generated, and produces its declared trusted outcome.
- The catalog generation budget can attempt the shortest completion route without repair or prefetch.
- Provider-free fallback composition validates before play.
- A deterministic test plays a conforming full game from generated opening to generated ending.
- The same run completes when every provider call fails.
- Save/resume does not regenerate displayed scenes.
- Existing authored and schema-v1 generated CLI behavior remains green.
- `mvn -f app/engine/pom.xml clean verify` passes without network or credentials.
- Documentation clearly assigns dynamic plan generation to 27.5, runtime cast/quest use to 27.6, and richer resolution behavior to 27.7.

## 17. Handoff to Spec 27.5

Spec 27.5 may add a generated story-plan artifact, but it must operate inside this trusted contract:

- it may select or describe pack-declared beats and optional scene slots;
- it may assign narrative meaning to trusted phases;
- it may not create scene IDs, choices, routes, phases, effects, objectives, outcomes, or length limits;
- the authored graph and `GeneratedGameProfile` remain the source of truth;
- an invalid plan is repaired once or replaced by a validated authored fallback plan;
- plan generation cannot make a previously valid full game structurally invalid.

This boundary preserves the original engine rule: AI supplies bounded content; the pack and engine own the game.
