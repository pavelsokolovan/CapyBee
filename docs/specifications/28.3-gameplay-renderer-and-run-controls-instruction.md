# Spec 28.3 — Gameplay Renderer and Run Controls

**Type:** Implementation instruction
**Parent:** [Spec 28 — Web RPG Client](28-client-rendering-contract-instruction.md)
**Depends on:** [28.1](28.1-game-client-contracts-and-transport-instruction.md); [28.2](28.2-game-preparation-and-start-instruction.md) for integrated entry
**Baseline:** `48bb38b`, inspected 2026-11-14; see the parent for evidence and verification limits.
**Status:** Draft
**Primary outcome:** One accessible, text-first renderer lets players read and act on authored or dynamic views, inspect their adventure and reach its ending without browser-owned rules or speculative progress.

## 1. Component boundary

Build focused function components under `app/ui/src/components/game/` for the
scene, choices/input, status, objectives, characters, places, result and run
controls. One run controller hook/module owns server state and pending command
identity; presentational components accept normalized data and callbacks.

Use the same renderer for Pack and dynamic sources. Source identity affects
labels/start policy, not a separate scene component tree or mechanics. Do not
parse blueprint, snapshot, rules, Pack files or generation resources in React.

## 2. Layout and scene content

Use a full-height mobile reading layout within the existing app shell:

1. Back/Leave, story title when provided, and a compact saved/pending status.
2. Ordered narration/dialogue/system blocks.
3. Legal choices, text input or explicit Continue affordance.
4. Secondary expandable objectives, characters, status and places.

Preserve server block order. `NARRATION` is body prose, `SPEECH` includes a
resolved speaker label, and `SYSTEM` is a neutral informational block, not a
browser alert. Unknown block kinds render safe plain text if the envelope is
otherwise supported. Resolve speaker IDs only through public character data;
an unresolved ID uses a generic localized speaker label rather than displaying
an internal identifier. Do not expose characters not yet present in the View.

Render all content as escaped React text. Preserve paragraph/newline readability;
no `dangerouslySetInnerHTML`, arbitrary Markdown/HTML, remote image loading,
autolinked URLs or script/style interpretation. `refs` and old `tags` are opaque
references, not asset URLs, CSS classes or commands. No generated prose becomes
an accessible label for an unrelated control or an application instruction.

Do not translate or regenerate accepted story text on the client. Shell copy
is bilingual; the run's text stays in its selected locale. Long titles, Polish
characters and long words must wrap without horizontal overflow.

## 3. Legal commands and input

| View data | Rendered interaction |
|---|---|
| Enabled option | Choice button submits exactly its `id` through `CHOOSE` |
| Disabled option | Non-actionable choice with readable `hint`, if supplied |
| Input `TEXT` or `CHOICE_OR_TEXT` | Optional text entry within the advertised bound and host limit |
| Input `CHOICE` | Choices only; no invented text field |
| Input `NONE`/absent | No text field |
| `canAdvance=true` | Continue / Dalej submits `ADVANCE` |
| Place in `availableMoves` | Move control submits exactly that place ID |
| Ended/non-ACTIVE/unsupported view | Reading and recovery controls only |

Use 28.1's authoritative `canAdvance`; never infer it from a missing choice
list, input mode, narration text or graph coordinates. Never auto-submit
`ADVANCE`. A malformed combination is a recoverable unsupported-view state,
not an opportunity to guess legal commands.

Free-text entry includes a short privacy reminder and explicit Send action.
Enter does not submit during IME composition; multiline input remains possible.
Validate Unicode code points against `min(input.maxChars, 1000)` and show a
localized length error without truncation. Do not persist drafts, submissions
or hashes. Do not clear the box merely on keypress; after dispatch remove it
from ordinary component state, keeping any necessary in-flight payload only in
the memory dispatcher until its terminal result, then release that reference.
An uncertain result recovers by command ID, not background replay of the text.

## 4. Pending command and authoritative reconciliation

Snapshot the current run/revision and allocate one UUID at explicit submission.
While unresolved, disable all state-changing controls for that run, including
map movement and abandon. Keep the last accepted scene readable and mark the
selection as pending. Do not animate a completed choice, mark an objective done
or append an invented next scene before acceptance.

`202` is processing; poll the same command. Apply `APPLIED` or `REPLAYED` once
and reconcile with a summary when needed. A replay may describe an older
`appliedRevision` than the current `revision`; never roll the UI backward or
repeat result effects. `REJECTED` retains the authoritative view and displays
a stable mapped issue; unchanged revision is not a transport failure.

For `REVISION_CONFLICT`/`RUN_NOT_ACTIVE`, discard the stale local intent after
status reconciliation and fetch the run/current state. Do not retarget the
choice to a new option or revision. `RUN_BUSY`, `429` and transient unavailable
states follow the transport backoff without unlocking a competing command.
Missing/archived/trashed/quarantined/unrecoverable states show safe recovery
copy and Back; do not fabricate a replacement or delete state automatically.

Use request identity/revision checks to ignore late responses after Leave,
another run opens, auth changes or a newer response has arrived. A refreshed
run is not permission to issue a command selected on an older scene.

## 5. Status, objectives, characters and places

Render public status items as label/value pairs with no guessed maximum,
health-meter or currency semantics. Objectives use their supplied label,
description and state. Character panels show only supplied discovered cast,
description and current-scene indication; no hidden cast or inferred traits.
Hide absent/empty sections rather than rendering technical placeholders.

The map in this series is an accessible place list with current/visited labels
and legal destination buttons. Render all public places but enable movement
only from `availableMoves`. Links are informational, not an authorization list.
Do not derive reachability from coordinates, visited history or bidirectionality.
Coordinates/layout kind may be ignored; a graphical honeycomb RPG map belongs
to Spec 29. Missing places is a normal text-only game, not an error.

Secondary panels do not change the run or make provider calls. Reopening them
does not fetch internal mechanics. Do not persist a story transcript merely to
support a panel or Back navigation.

## 6. Endings, leave and abandon

Use `view.ended` and authoritative run status/result. Render a supplied result
headline, summary, outcome label, objective results, facts and reflection in
server order. Treat `SUCCESS`, `PARTIAL_SUCCESS` and `FAILURE` as narrative
outcomes, never a score, punishment or diagnosis. If `result` is absent, show
the legacy ending text and a neutral completed/abandoned label.

Provide Back to Play / Wróć do gier and an explicit Start another adventure
that returns to selection/review. Do not start automatically from an ending,
replay a reward animation after reload, call `/api/games/results`, create a
Mission or add a honeycomb cell. Those product policies belong to Spec 29.

Leave / Wróć closes the panel and detaches local work; it preserves the saved
run and does not issue `ABANDON` or DELETE. Show Saved / Zapisano only after a
server-accepted persisted revision is known; while pending say Saving/checking,
not a promise that the command succeeded. No separate browser Save mechanism.

Abandon / Zakończ przygodę is a secondary control with an accessible confirmation
explaining that this run will end. Confirm sends one `ABANDON` command with the
current revision via the same mutation path. Cancel does nothing. Offline
abandon may be queued but must remain visibly pending; it is not an ended run
until acknowledged. No delete, archive or purge controls are added here.

## 7. Accessibility and calm behavior

Target 360px width without horizontal scrolling and usable layout at 200% zoom.
Use semantic headings, real buttons, labeled fieldsets/textarea and visible
focus. Touch targets are at least 44px. Disabled hints are readable without
hover. Collapse panels retain keyboard access and expansion state in memory.

On accepted scene change, focus its heading or a stable scene container and
announce a short status with `aria-live=polite`; do not announce the whole
story, optional text, every poll or every loading frame. Opening/closing a
dialog restores focus. No keyboard traps, timed choices, flashing content,
autoplay sound or forced animation. Respect reduced motion.

## 8. Tests and completion

Test v1/v2 authored and dynamic fixtures, narration/dialogue order, missing
optional fields, safe HTML/URL-like text, long EN/PL copy, legal/disabled
choices, text bounds/IME, explicit advance, places availableMoves, pending
locking, rejected/replayed/stale outcomes, ending compatibility and abandon.
Include assertions that a malicious block cannot execute HTML, fetch a URL or
produce an unintended command. Use real public view shapes rather than a
renderer-only mock schema.

Play one authored fixture with movement/advance and one dynamic fixture through
real HTTP to an ending. Leave/reopen preserves accepted state and locale. The
same run remains readable with new starts/provider disabled. Test keyboard,
focus, 360px, zoom, reduced motion and screen-reader status behavior manually
against Spring-served assets after build/static sync.

Run frontend tests/coverage and the documented sync workflow. Run the backend
gate for any server changes and standalone engine verification for any view
changes. Keep rollout disabled pending 28.4. Mark 28.3 implemented only after
these checks and commit with the repository implementation convention.
