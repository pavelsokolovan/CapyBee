# Spec 29.4 — Missions and Daily Game-cell Integration

**Type:** Implementation instruction
**Parent:** [Spec 29](29-capybee-polish-game-and-product-integration-instruction.md)
**Depends on:** 29.1; integrate with 29.3 UI when available
**Baseline:** `967e1d9`, inspected 2026-11-14
**Status:** Host bridge implemented; Polish Pack binding awaits 29.1

## Trust boundary and product policy

Add a host-owned completion bridge from a persisted owned run to optional
Missions and the existing daily game-cell policy. Do not place CapyBee Mission,
OAuth, calendar or reward logic in the universal engine. Only an authoritative
run ending with `COMPLETED` qualifies; source/Pack eligibility is explicitly
allowlisted. Abandon, failed/suspended/preparing runs, cancelled starts, partial
progress and browser-declared completion do not qualify. Narrative SUCCESS,
PARTIAL_SUCCESS and FAILURE do not alter worth, score or reward eligibility.

Existing `/api/games/results` accepts client-selected game keys/metrics and is
not proof of RPG completion. Reserve the new RPG result key against that generic
write route, preserving mini-game compatibility. Derive RPG eligibility,
completion timestamp and any result projection from the owned persisted run;
never trust a client duration, outcome, grade or metrics payload to award it.

## Idempotent host contract

Design the concrete DTO/migration in this part around existing server services.
Use an owner/run unique completion identity and transactional upsert/projection
that can safely recover after worker/process interruption. Completion transaction/outbox processing and server-owned reconciliation
must repair missing projections idempotently; GET reads remain side-effect-free.
Use existing host execution facilities, not a new always-on Fly worker. A React
effect must not issue an untrusted completion/reward POST. Scope every read/write to
the server-authenticated owner and apply 28.4 no-store/stale-owner guards.
Do not add fields to applied Flyway migrations or make browser clock authority.

Persist only minimal linkage: owner/run identity, eligible completion timestamp,
reviewed suggestion key/version and resulting catalog Mission identity if chosen.
No dialogue, raw wish, transcript, generated reflection or personal mood notes
belong in game-result metrics or Mission history. Define deletion/archive
behavior so later reads cannot resurrect a deliberately deleted game or Mission.
Replays/reloads/second devices cannot create another projection or repeat an
acknowledged reward effect.

## Optional Mission offer

Bind each eligible authored ending/outcome to a versioned, reviewed existing
Mission catalog code or a reviewed neutral no-Mission/rest alternative. Inspect
the current Mission service/catalog API first; do not assume that arbitrary
custom-Mission creation exists. Never use generated prose as a Mission title,
instruction, URL or catalog identifier. A new catalog entry must be explicitly
reviewed and localized, with a forward migration when required.

Display one suggested step and explicit accept/dismiss controls. Accept may
select/add the reviewed Mission using its established product semantics; it
never marks a real-world activity complete. Dismiss/Back does nothing. Do not
replace an existing selected Mission silently. Define an owner-scoped, idempotent
non-text offline action for acceptance if the current queue does not support
this contract; do not smuggle it through engine CHOOSE or `gameResult` metrics.

## Daily cell contract

Retain Spec 20's one game-earned hive cell per local calendar day shared across
Pollen Match, Hive Builder and eligible RPG endings; replay remains allowed.
Do not invent an extra RPG daily allowance, streak, leaderboard or punishment.
The existing cap is a UI offer policy, not a server-enforced grant system:
reconcile/deduplicate all game entries in `useHoneycombCells` and all offer
checks rather than claiming stronger enforcement from current storage.

Use the existing local-calendar convention consistently for offers and displayed
history. Test midnight, timezone/DST changes, multiple games, offline results
and reconciliation of duplicate rows. If implementation needs a different
account-timezone/server-ledger product policy, specify it explicitly rather
than silently changing Spec 20. One accepted game cell does not create or
complete a Mission; accepting a Mission does not grant another game cell.

## Acceptance

Prove fabricated generic results cannot qualify an RPG run; cross-owner access,
revision/status mismatch and abandon produce no projection. Test duplicate
completion/acceptance, concurrent devices, restart between run save/projection,
offline acceptance, replayed outcomes, deletion and midnight/cap interactions.
Verify existing mini-game saves and other offline mutations still work.
Run backend/DB gates, frontend coverage/static sync and real Spring/PostgreSQL
browser tests. Keep production rollout disabled and record exact DTO/schema
changes, eligibility policy and data-retention behavior for 29.5.
