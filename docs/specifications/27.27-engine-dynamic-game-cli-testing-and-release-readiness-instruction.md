**Type:** Implementation instruction
**Parent:** Dynamic-game series, following Spec 27.26
**Depends on:** Specs 22–27.26, especially `GeneratorProfile`, `PreparationPresetResolver`, `DynamicGameBootstrapRequest`, `DynamicGameBootstrapResult`, dynamic snapshot v2, source-neutral session identity, `RunSessionService`, `SessionConsole`, `InteractiveSetup`, `CertificationCommand` and the engine build workflow

Spec 27.26 is present in the working tree as a ready implementation instruction but is not implemented or committed. The current normal CLI requires `--pack-dir`; its setup presenter reads Pack resources, session start is Pack-only, summaries/rendering require Pack identity, and certification suites describe Pack routes. **Status:** Implemented; completes the dynamic-game series and is the release gate for public CLI use
**Primary outcome:** A player can prepare, start, save, resume and finish a genuinely new profile-driven dynamic game through the normal CLI and session lifecycle, with honest provider/fallback UX, deterministic adversarial and end-to-end coverage, real second-process resume evidence, optional cost-bounded live certification and preserved authored/Willow Marsh compatibility.

## 1. Purpose

Specs 27.17–27.26 establish the safe dynamic-game pipeline from a scenario-neutral profile to an exactly resumable compiled game. They deliberately do not make that pipeline a normal player entry point. This specification closes that gap:

```text
normal CLI dynamic entry
  -> validated generator-profile selection
  -> local setup, disclosure and confirmation
  -> one session-owned dynamic preparation
  -> complete blueprint generation/repair/validation/compilation
  -> atomic initial dynamic snapshot activation
  -> existing SessionConsole and RunImpl gameplay
  -> accepted-command saves and exact resume
  -> deterministic release suite + optional live certification
```

This is host integration, not another generation architecture. The CLI orchestrates existing trusted boundaries and reports their outcomes; it does not parse model output, validate mechanics, compile rules, reconstruct definitions or maintain a second gameplay loop.

## 2. Release boundary

The released capability is:

> A completely new scenario and game configuration for every confirmed attempt, using only the bounded engine-supported mechanics permitted by the selected generator profile.

“New” means a fresh blueprint attempt is requested and structural variation is supported. It is not a mathematical uniqueness guarantee, and resume is never a new attempt.

The capability is not:

> AI inventing Java rules, arbitrary expressions, executable scripts, commands, tools, URLs, assets or rule types.

The CLI must not expose an escape hatch around the closed blueprint/rule schemas, semantic validation, compiler, definition verifier, output review, budgets or snapshot verification. No prompt option, debug flag, profile file or certification route may weaken this boundary.

Dynamic play remains unreleased until every required gate in this specification passes. In-memory play from 27.24–27.25 and durable core/session tests from 27.26 are necessary but not sufficient release evidence.

## 3. Scope and non-goals

### 3.1 In scope

- Add an explicit normal CLI entry for a dynamic game without requiring a playable Pack.
- Load and validate scenario-neutral generator-profile bundles from a bounded local path or bundled release catalog.
- Adapt the existing setup presenter to `ProfileSetup`, profile strings and resolved capabilities.
- Provide quick-start, customization, back/edit/clear, review, disclosure, confirmation and cancel flows.
- Integrate dynamic preparation with `RunSessionService`, current-run replacement rules and atomic initial persistence.
- Present `Started`, `FallbackOffered`, correction/retry and terminal failure outcomes honestly.
- Continue gameplay through the existing `SessionConsole`, source-neutral summaries, prefetch and commands.
- Resume dynamic games from the normal saved-game selection without profile or provider availability.
- Extend offline certification for dynamic fixtures, adversarial blueprints, route completion and restart.
- Add an optional explicitly authorized and cost-bounded live-provider dynamic certification scope.
- Publish release documentation, packaged profile resources and exact verification evidence.

### 3.2 Out of scope

- React/web/API setup screens, server endpoints, cloud storage or multiplayer.
- A profile authoring UI, downloading profiles, arbitrary filesystem discovery or remote profile URLs.
- New mechanics, conditions, effects, blueprint fields, persistence formats or provider adapters unless a verified integration defect requires a narrowly compatible correction.
- Persisting wizard drafts, suggestions, prompts, rejected responses, provider credentials or setup transcripts.
- Guaranteeing every two live generations differ, judging creative quality from keyword matching, or treating one successful live response as complete certification.
- Replacing existing Pack play, fixed Willow Marsh generated content, classic snapshot files or Pack certification.

## 4. Required preconditions and implementation-state audit

Before changing CLI code, implement Spec 27.26 and verify its acceptance criteria. Then inspect current HEAD rather than assuming the baseline names survived implementation. Record the concrete types that provide:

- canonical dynamic snapshot v2 and bundle verification;

Do not persist a `PREPARING` row containing transient suggestion data and do not fabricate `PackId`, `PackVersion`, `Pack`, `GeneratedGameProfile` or Pack generation artifacts for a dynamic run.

The implementation must also inventory the current commands and scripts so new names do not collide. Preserve the normal `play --pack-dir <dir>` contract and the existing `certify` contract.

## 5. CLI command contract

### 5.1 Entry points

Add the explicit form:

```text
java -jar engine-cli.jar play --dynamic --profile-dir <dir> [options]
```

The exact packaged-launcher spelling may additionally provide a friendly shortcut, but the shaded JAR contract above is authoritative. `--dynamic` and `--pack-dir` are mutually exclusive. A dynamic new game requires one validated profile source; it does not infer a profile by scanning arbitrary directories.

Supported shared options remain source-neutral where meaningful:

```text
--locale <tag>
--seed <signed-64-bit-integer>
--store-dir <dir> | --memory
--run <uuid> | --continue | --new [--replace-current]
--prefetch on|off
--calls-per-day <n>
--run-calls <n>
--offline
--debug
--no-color
--script <file>     # deterministic test/certification use under existing rules
```

Do not accept `--input key=value` as the primary dynamic player interface. If retained for test automation, it must use public profile input IDs, pass the same resolver and privacy rules, be documented as non-interactive automation, and must never carry the free-text suggestion in argv. `--generated` remains the fixed-Pack presentation flag and is not an alias for `--dynamic`.

### 5.2 Argument validation

Reject ambiguous or unsafe combinations locally with exit code 2 and a stable bounded code/message:

- dynamic plus Pack directory, classic mode, snapshot `--load`/`--save`, or Pack-only live smoke;
- profile directory without dynamic mode;
- `--run` plus any new-game setup option;
- suggestion text in arguments or environment-backed generic input;
- offline mode plus an option that promises live generation;
- scripted new dynamic start without an explicit reviewed setup fixture and disclosure acceptance required by the test-only contract;
- unsupported locale, seed, budget or store combination.

`--help` documents Pack play, dynamic play and certification separately. Help, argument errors and profile-load errors make zero provider calls and create no run/store row.

### 5.3 Profile loading

Load a profile only through `GeneratorProfileLoader` and `GeneratorProfileRegistry`. Apply path containment, resource-size/count limits, exact schema validation, fingerprints and fallback binding from 27.18. The CLI may provide an engine-owned profile catalog adapter, but core profile validation remains the authority.

Before showing the wizard:

- validate the profile, all localized setup resources and quality resources;
- resolve requested UI/game locale against supported locales;
- determine provider mode and host ceilings;
- verify any reviewed fallback binding against the explicitly configured Pack catalog;
- remove unsupported controls rather than displaying choices that cannot affect generation.

Profile titles, descriptions, questions and option labels are untrusted display data: sanitize terminal control characters and enforce existing output bounds.

## 6. Dynamic preparation wizard

### 6.1 Startup and saved-game choice

When a compatible saved run exists, show **Continue**, **Prepare a new game**, **Show details** and **Cancel** before opening the wizard. Continue uses the stored source discriminator and bypasses profile loading when the selected dynamic snapshot is self-contained. It must work when `--profile-dir` is absent, moved or invalid and when no provider is configured.

Preparing a new game does not abandon the current run until the player confirms replacement under existing session lifecycle rules. Pre-confirmation cancel leaves the current marker, snapshot, revision and status unchanged.

Details for a dynamic game show sanitized story title when available, “Dynamic game”, locale, status, last saved time, revision and a shortened game-fingerprint suffix suitable for support. Do not print profile paths, blueprint content, prompts or a fake Pack line.

### 6.2 Guided flow

Present the validated `ProfileSetup` rather than reading `generation/setup.json` from a Pack. Preserve the Spec 27.17 flow:

- quick start with visible defaults;
- at most six customization questions plus review;
- only profile-supported genre/world/tone/interests controls;
- exact length and challenge preset labels;
- supported game locale;
- optional bounded suggestion only when provider mode and policy allow it;
- back, keep, clear/skip, edit, start and cancel.

Use `PreparationPresetResolver` as the sole preference/constraint resolver. The CLI must not reinterpret preset meanings or manufacture defaults. Enter keeps the displayed current/default value; explicit clear remains distinguishable from omission.

Review displays friendly labels and suggestion status only: `[provided]`, `[skipped]` or `[needs editing]`. Never echo the suggestion in review, diagnostics, exceptions, debug output, golden files or certification evidence.

### 6.3 Disclosure and external-call boundary

When provider-backed generation is available, show the approved disclosure before collecting optional text and again make clear at final review that **Start game** may send the selected setup and approved suggestion to the configured external service. Explain that cancellation prevents later calls but cannot retract an already submitted request or guaranteed charge.

All navigation, defaults, local validation and review before final confirmation make zero provider calls, including external-capable guard calls. Final confirmation freezes a preparation revision and invokes the shared safety/generation pipeline once for that attempt.

Keep raw, normalized, scrubbed and approved suggestion values only in an in-memory non-serializable preparation object. Release references after start, retry/edit transition or cancel. Never put them in a session pending-start row. A crash before an accepted initial snapshot restarts preparation and asks for re-entry; it must not silently regenerate.

### 6.4 Provider-free/offline UX

When `--offline`, the provider host switch is disabled or no usable provider exists:

- explain before setup that a new AI-generated game cannot be created;
- omit the suggestion control and any preference the bound fallback cannot honor;
- offer only an actual compatible reviewed fallback or cancel;
- label the fallback by its authored name and identify it as a reviewed offline game;
- require explicit confirmation before starting it as ordinary Pack play;
- never store or display it as a dynamic game and never claim it used the custom idea.

If no compatible fallback exists, fail locally with an actionable stable code and no new run. Do not synthesize a dynamic definition from fragments or clone Willow Marsh under a dynamic identity.

## 7. Session-owned dynamic start

### 7.1 Start request

Add a source-explicit session operation conceptually equivalent to:

```text
startDynamic(owner, requestId, confirmedPreparation, seed, wait)
```

The operation accepts a non-serializable in-process preparation capability, not raw maps or a generic JSON DTO. It calls `Engine.startDynamic(...)` exactly once per accepted request ID. Repeated polling or idempotent replay must return the recorded bounded outcome and must not issue another blueprint request.

The session service, not the CLI, owns run ID allocation, engine construction, metering, lifecycle checks and activation. Use the same owner scopes, global/profile/run call ceilings, single-flight control, cancellation/deadline rules and worker isolation used by session generation.

### 7.2 Publication and atomic initial save

Do not publish a current playable run until `DynamicGameBootstrapResult.Started` contains a verified definition, resolved start-scene presentation and a snapshot capability supported by 27.26.

In one durable activation transaction:

- save the self-contained dynamic snapshot;
- create/update the source-neutral run record and revision;
- set the current-run marker;
- record bounded start outcome/events and accounted usage;
- clear any safe non-sensitive transient operation metadata.

If that transaction fails, report no started/saved game, do not replace the previous current run, and never leave a resumable row without its snapshot. The in-memory uncommitted run may be discarded.

No store file may contain setup answers that 27.26 excludes, suggestion text or provider request/response payloads. Profile preset IDs required by the accepted bundle are stored only through its canonical provenance.

### 7.3 Start outcomes and recovery

Map engine results without hiding distinctions:

| Result | CLI behavior |
| --- | --- |
| `Started` | Atomically activate, print the source-neutral run header and enter normal play. |
| `FallbackOffered` | Explain that dynamic generation did not produce a game; offer explicit reviewed Pack fallback, edit/retry if allowed, or cancel. Never auto-start it. |
| Correctable preparation/input issue | Return to the relevant setup step with prior safe selections; suggestion is status-only and may be replaced/cleared. |
| Retryable generation failure | Show bounded reason and allow one newly confirmed attempt subject to remaining host budget; no implicit retry loop. |
| Cancelled/deadline/budget failure | Stop further calls, preserve old saved run and offer a fresh preparation later. |
| Invalid/tampered profile or internal definition failure | Fail closed with a bounded code; do not expose content or compiler details. |

A retry is a new blueprint attempt, requires a new confirmation and request ID, and is charged normally. The one repair attempt inside a single blueprint attempt remains owned by 27.20 and is not presented as a separate player retry.

## 8. Shared gameplay and resume

After activation, use the same `SessionConsole.run(...)`, command parser, optimistic revision checks, accepted-command transaction, events, rendering and `RunImpl` as Pack games. Do not create `DynamicSessionConsole` or a parallel command service.

Make existing host-facing models source-neutral:

- a summary contains a sealed/equivalent Pack or dynamic game reference;
- rendering uses story/title/source labels rather than `packId()` assumptions;
- `/status`, `/help`, `/events`, debug diagnostics and completion work for either source;
- dynamic prefetch uses the 27.25 source-neutral presentation seam and persists artifacts through 27.26;
- player-facing errors remain useful while diagnostics contain codes/counts only.

Resume behavior:

1. Open the existing store and select a run by current marker, `--run` or normal recent-run flow.
2. Parse and verify the stored source and snapshot before presenting it as resumable.
3. Build a fresh engine using current host ports/limits.
4. Call the normal resume boundary exactly once.
5. Make zero blueprint calls and zero calls for already accepted presentation artifacts.
6. Continue future unresolved scenes from persisted budgets, or use definition-specific fallbacks when no provider exists.

A dynamic resume never reopens the setup wizard, asks for the original profile/suggestion or silently converts to a Pack fallback. Corrupt/tampered dynamic snapshots fail closed and leave the store available for diagnosis/recovery under existing policies.

## 9. CLI rendering and localization

Provide tested English and Polish host copy for the dynamic entry, setup controls, disclosure, generation progress, fallback offer, retry/cancel and source labels. Game prose remains in the selected game locale; terminal chrome follows the CLI host locale policy already established by 27.16.

All output is UTF-8, terminal-control sanitized and bounded. While preparation runs, print one initial progress message and bounded polling progress rather than content or model details. Do not promise a duration.

The dynamic header should communicate:

- CapyBee and the accepted story title;
- “new dynamic game” only after successful activation;
- selected game language and saving status;
- generated/repaired/fallback presentation status only in bounded diagnostics, not alarming player prose;
- run ID where existing CLI contracts require it.

Script mode must have stable machine-checkable exit behavior and must not depend on ANSI color, prompt timing or localized prose for assertions. Prefer bounded status codes/evidence fields over scraping narrative text.

## 10. Deterministic fixture matrix

Add repository-owned scenario-neutral generator-profile fixtures with EN/PL strings, quality policy and bounded reviewed fallback bindings. Add complete structured provider responses that are clearly test data, including at least:

- quick-start exploration game;
- custom short Polish puzzle/helping game;
- structurally different space-rescue game with no Willow Marsh IDs, roles, objectives or routes;
- first-response-invalid then repaired valid game;
- valid blueprint whose one scene output fails and uses definition-specific fallback;
- explicit whole-game generation failure with compatible fallback offer;
- provider-free fallback path;
- mid-route dynamic snapshot used for restart;
- ending/result variants that prove objective/result rendering.

Fixtures must use deterministic IDs/clocks/random/provider doubles and exact call counters. Do not assert only titles. Assert graph topology, objectives, selected constraints, compiled effect/condition types, trusted ID separation, reachable endings, result class and exact persisted game fingerprint.

No standard fixture reads credentials, network state or developer home-directory files.

## 11. Adversarial integration coverage

Retain the focused parser/semantic/compiler tests from earlier specs and add host-level cases proving the CLI/session cannot bypass them:

| Area | Required case |
| --- | --- |
| Setup | Defaults, explicit locale, back/edit/clear, cancel, conflicting suggestion, excessive suggestion, PII/unsafe/unavailable guard and prompt injection. |
| Privacy | No suggestion in stdout/stderr, `toString`, store bytes, evidence, snapshot, pending metadata, exception or debug output. |
| Trust | Unknown field/type, script/expression text, unsupported mechanics, forged IDs, invalid routes, unreachable endings and excessive complexity never activate a run. |
| Bounds | Profile/host/provider call and token ceilings, deadline, cancellation, one repair, one player-confirmed retry and prefetch reserve. |
| Identity | Dynamic start has no Pack identity; reviewed whole-game fallback remains its true Pack identity. |
| Atomicity | Failure before/within initial commit preserves the previous current run and leaves no false-success row. |
| Idempotency | Same start request/poll does not repeat blueprint generation; a newly confirmed retry does. |
| Presentation | Trusted choices/routes/effects are unchanged by generated, repaired or fallback prose. |
| Resume | Saved blueprint/definition/artifacts are not regenerated; future unresolved scene accounting continues exactly. |
| Compatibility | Authored Pack, fixed generated Pack, Willow Marsh setup/prefetch/snapshot/resume and historical store fixtures remain unchanged. |

Use content-independent failure codes in assertions. Include a scan for banned dynamic source files/resources referencing Willow Marsh-specific actor IDs, scene IDs, objectives or plot phrases, while excluding the explicitly bound reviewed fallback and compatibility fixtures.

## 12. End-to-end route suite

Create deterministic CLI routes that enter through the real argument parser and session wiring, not a direct `DefaultEngine` shortcut. At minimum certify:

1. quick-start dynamic generation to a successful ending;
2. customized EN game whose selected length/challenge affect the compiled definition;
3. customized PL game including edit/back behavior;
4. repaired blueprint route;
5. scene fallback route that still completes with correct mechanics;
6. failed blueprint followed by explicit reviewed Pack fallback;
7. provider-free fallback/cancel behavior;
8. dynamic mid-route save, process restart and completion;
9. resumed run with provider disabled and no calls for accepted artifacts;
10. Pack-authored and Willow Marsh fixed-generation compatibility routes.

Each route records source kind, run ID, revision sequence, terminal result class, game/definition fingerprints where applicable, provider call counts by purpose, fallback/repair codes and restart process count. Evidence must contain no game prose, prompt, response or setup suggestion.

## 13. Real second-process resume proof

At least one required offline route must use two independently launched JVM processes and the same explicit temporary `--store-dir`:

```text
process A: start a dynamic game -> accept choices -> persist checkpoint -> exit
process B: open the same store -> select the same run -> resume -> finish
```

This is not satisfied by two `ConsoleApp` objects in one JVM, an in-memory store, copying an object, or decoding a snapshot inside the first process.

The harness must verify:

- distinct positive process IDs and successful expected exit codes;
- process A completed an atomic dynamic checkpoint;
- process B observed the same run ID, game fingerprint, definition fingerprint and next view/revision;
- blueprint call count remains unchanged across process B;
- accepted scene call counts are unchanged; only later unresolved scenes may consume calls;
- no entry/on-choice/objective/ending effect is duplicated;
- final result and final revision are durable after a third read-only store reopen;
- logs/evidence are redacted and temporary credentials are unnecessary.

Use bounded process timeouts, kill the child tree on timeout, preserve failure diagnostics under a size ceiling and clean temporary stores after successful tests.

## 14. Certification command

### 14.1 Offline certification

Extend the existing `certify` command rather than creating an unrelated framework. Add an explicit dynamic suite/source option whose manifest names a generator profile and deterministic provider fixture rather than a Pack. Preserve existing Pack suite compatibility.

Offline dynamic certification is deterministic, credential-free and part of the release gate. It executes the end-to-end routes, including the real second-process route, and writes evidence atomically using the existing incomplete/final directory policy.

Evidence schema must be versioned and source-discriminated. Include only bounded operational data:

- build/revision and suite IDs;
- profile ID/version/fingerprint;
- game/blueprint/definition fingerprints;
- route status, result class, revisions and restart process count;
- generation purpose counts, numeric usage and repair/fallback codes;
- compatibility route results and overall pass/fail.

### 14.2 Optional live-provider certification

Live dynamic certification is optional, diagnostic release evidence and never runs from normal `mvn verify`. It requires all of:

- provider mode explicitly set to certification;
- an explicit dynamic live scope;
- explicit cost confirmation;
- provider credentials supplied through the supported environment mechanism;
- positive maximum provider-call and USD ceilings;
- bounded timeout and dedicated evidence directory.

Use a real validated release profile, preset-only or a repository-owned non-private fictional suggestion, and the normal start/compile/play path. Stop before a request that could exceed either ceiling. Record estimates and observed numeric usage without provider response content.

Live certification must prove at least one complete accepted dynamic blueprint and playable route; full scope should additionally sample repair or scene continuation only within the approved budget. A provider refusal, safety failure, rate limit or structurally invalid output is reported honestly as a failed/inconclusive live route—it is never replaced silently and called a live pass.

The package verifier loads and fingerprints every bundled profile and fallback binding. It rejects missing resources, unexpected files, path escapes and manifest mismatches.

Update `app/engine/README.md`, CLI help and certification/operations documentation with:

Do not mark the feature released in documentation until required offline evidence passes.

## 16. Compatibility requirements

This specification must not regress:

- `play --pack-dir` normal and classic modes;
- authored Pack inputs, movement, commands, results and snapshots;
- fixed generated-content `--generated` semantics;
- Willow Marsh provider-backed presentation, repair/fallback, prefetch and resume;
- Pack snapshot v1 byte compatibility and historical session-store migration;
- existing Pack certification suite/evidence semantics;
- provider-neutral core boundaries and the absence of CLI/session dependencies from core.

Avoid broad renames of current public Pack accessors solely to make the CLI generic. Add a source-neutral abstraction with compatibility accessors/adapters where practical, then migrate only host code that truly handles both sources.

## 19. Acceptance criteria

27.27 is complete when all of the following are true:

1. `play --dynamic --profile-dir <dir>` is a documented normal entry point and never requires or fabricates a playable Pack.
2. The profile-driven wizard supports defaults, customization, locale, length, challenge, optional suggestion, back/edit/clear, review, confirmation and cancel within the Spec 27.17 bounds.
3. No external call happens before final confirmation; suggestion material is absent from output, diagnostics, persistent bytes and evidence.
4. A confirmed dynamic start traverses the existing generation, review, semantic validation, closed mechanics, compiler and definition-verifier boundaries without CLI shortcuts.
5. A run becomes current only after its initial self-contained dynamic snapshot is atomically saved; failure preserves the prior current run.
6. Dynamic gameplay uses the normal `RunImpl`, session command path, rendering, prefetch, accepted-command save and ending/result behavior.
7. Resume in a fresh process restores the exact game/fingerprints/state/artifacts with no blueprint regeneration, no duplicated effects and no repeated calls for accepted scenes.
8. Provider-free mode never claims a fresh dynamic game; compatible reviewed Pack fallback is labeled and explicitly accepted, or the flow cancels/fails safely.
9. Deterministic fixtures prove genuinely different scenario structures, custom constraints, repaired/fallback paths and adversarial rejection—not merely renamed Willow Marsh content.
10. The offline certification suite includes real second-JVM dynamic resume and produces redacted, source-discriminated evidence.
11. Optional live certification is explicit, credentialed, time/call/cost bounded and excluded from normal tests.
12. Authored Packs, fixed generated Packs, Willow Marsh, historical snapshots/stores and Pack certification remain green and behaviorally compatible.
13. `mvn -f app/engine/pom.xml clean verify`, packaging, offline certification and packaged manual acceptance pass.
14. Documentation accurately states the trust boundary: AI configures a bounded existing mechanics vocabulary and never contributes executable code or new rule implementations.
