# Spec 28.2 — Game Preparation and Start

**Type:** Implementation instruction
**Parent:** [Spec 28 — Web RPG Client](28-client-rendering-contract-instruction.md)
**Depends on:** [Spec 28.1](28.1-game-client-contracts-and-transport-instruction.md)
**Baseline:** `48bb38b`, inspected 2026-11-14; see the parent for evidence and verification limits.
**Status:** Draft
**Primary outcome:** The Play tab offers eligible adventures and an honest, localized preparation flow that starts a game only after explicit confirmation and recovers uncertain outcomes without a fresh paid request.

## 1. Entry and structure

Add one Adventures / Przygody entry to the existing Play list when the host's
web-client capability is enabled. Keep the two mini-games and their reward
behavior. Extract the RPG flow into focused components under
`app/ui/src/components/game/` with orchestration under `src/game/`; do not grow
`AuthenticatedHome.tsx` into another game implementation.

The entry opens a full-height mobile panel with normal Back/Close navigation,
an accessible title and focus restoration. Use the app's existing navigation
model; do not introduce a router dependency just for this feature. Browser Back
must step out of the wizard/panel without signing out or silently abandoning a
run. History state may contain screen IDs only, never setup or story content.

On entry, authenticate, fetch capabilities, read `/api/game/runs/current`, and
discover eligible Packs/profiles independently. A discovery failure must not
erase a successfully read saved run. Offer Continue / Kontynuuj first when a
current ACTIVE or PREPARING run exists; show source-appropriate title and locale
without raw technical IDs or fingerprints.

Distinguish these states: loading, available, no configured new games, game API
disabled, temporary network/server failure, and sign-in required. Empty catalogs
are not errors. If new starts are disabled, preserve Continue for saved runs
while `gameEnabled` remains true. If the entire game API is disabled, explain
unavailability without implying progress was deleted.

## 2. Selecting a game

Show only host-discovered, eligible entries. Do not hardcode a profile ID or
guess that an installed profile is suitable for a child. The initial child
deployment may enable `generic-adventure`; the detective profile remains an
older-teen/operator example unless the server audience checks allow it.

Clearly distinguish a reviewed/authored game, generated presentation within a
reviewed Pack, and a new AI-created adventure. For a generation-capable Pack,
reviewed play is the default; an explicit capability-gated choice enables
generated presentation. Do not label reviewed fallback as newly AI-generated.
Unsupported input metadata disables that entry with a retry/update message,
not an approximate form.

No start occurs when opening Play, selecting a card, applying defaults,
mounting a component, restoring auth, or returning online.

## 3. Metadata-driven preparation

Render the ordered public steps/inputs from 28.1. Use labels/help/options from
the response, and EN/PL shell copy through the existing copy-object approach.
An input's kind and bounds determine radio buttons, a bounded checkbox/chip
group, or the optional story-wish textarea. Every control has a visible label,
accessible help/error association and keyboard support. A Pack without inputs
can proceed directly to review.

Honor 28.1's Pack transient-text limitation: an optional unsupported Pack start
text field is not offered, and a required unsupported field makes that Pack
unavailable. Do not confuse start personalization with supported in-scene text.

Preserve three answer states in the form model: untouched (use the declared
default), explicitly cleared (empty), and selected IDs. Required fields cannot
be cleared. Enforce selection ceilings without hiding the reason. Never parse
translated labels into values. Defaults in review must be the effective values
that will be submitted, not a visual placeholder.

For dynamic requests, `length`, `challenge` and `game-locale` become the three
top-level preset/locale fields. Do not duplicate them in `selections`.
`story-wish` becomes optional `suggestion`, never a selection. Creative answers
use omitted keys for untouched, `[]` for cleared, and option ID arrays for
selected. Pack start inputs use the existing Pack-specific encoding and are
validated against real DTO fixtures rather than reusing the dynamic encoder.

The app locale controls the shell; the selected game locale controls generated
content. Default to the app locale only if supported, otherwise the advertised
default, and show that choice. Changing shell language must not secretly alter
the selected game locale or lose selected IDs. Clear private text before a
profile switch; never migrate it to another game/profile.

Validate text length in Unicode code points, including paste and IME input.
Do not truncate silently or rely only on HTML UTF-16 `maxLength`. Optional text
is local until final confirmation, cannot be required to play, and carries a
short warning against real names, contacts, school/location details or secrets.
Do not copy account/profile/mood/friendship/memory data into setup or a prompt.
Spec 29 owns any separately specified product personalization.

## 4. Disclosure, review and final confirmation

Before the optional text step, explain in the shell language what may leave
CapyBee. Repeat a short disclosure at final review when generation is selected:
presets, choices and an optional fictional idea may be sent to an external AI
service. Explain that the accepted adventure is saved, while the raw optional
idea is not stored for resubmission. Do not promise zero provider retention or
claim that a UI disclosure settles provider/legal terms. Production operators
must retain the existing provider and child-audience release requirements.

Review shows profile/game title, selected locale, length/challenge and selected
preset labels. It shows only Idea added / Dodano pomysł for optional text, with
Edit/Remove; it never echoes or summarizes that text. No raw draft appears in
logging, accessibility announcements, diagnostics or errors. The textarea is
the only place the draft itself is rendered.

The final action is Start adventure / Rozpocznij przygodę. It is enabled only
when online, metadata is compatible, local validation passes, and no start is
unresolved. Create a UUID for this explicit confirmed attempt, use the current
disclosure revision and send through 28.1's transient dispatcher. Disable the
button synchronously against double taps. React effects must not submit.

Editing any answer after review invalidates confirmation. A stale fingerprint
or changed disclosure requires refreshed metadata and another review; preserve
compatible public selections only and clear optional text. Never silently
reconfirm or submit with a new fingerprint.

## 5. Existing current run and replacement

Prefer Continue. Offer a deliberate New adventure action separately. For a
dynamic replacement, explain that the previous run will be paused only if the
new game starts successfully. Require a separate explicit replacement choice
and pass the exact observed `expectedCurrentRunId` with final confirmation.
Do not abandon/delete the current run before generation.

If the current run changes before activation, reconcile and show the new
current state; do not change the replacement target or retry automatically.
Failure/cancellation before publication leaves the previous run available.
State honestly that a library/switch-back UI for older paused runs is outside
this series; do not promise a navigation control that does not exist.

Pack start has no atomic replacement parameter in the baseline API. If a run
is active, keep Continue and explain that the player must explicitly end it
through the run controls before starting a different Pack. Do not simulate
atomic replacement with a hidden ABANDON-then-POST sequence.

## 6. Waiting and terminal outcomes

Use calm indeterminate progress, a short explanation and Leave/Cancel controls.
Do not show invented percentage progress, claim a retry is free, or suggest
rapid repeated attempts. The operation marker holds only the minimal 28.1 IDs.

| Response | UI behavior |
|---|---|
| Pack `200`/`202` start response | Read/poll its `runId`; open gameplay only when an authoritative playable view exists |
| Dynamic `PROCESSING` | Poll the same `requestId` at the server delay |
| Dynamic `STARTED` | Adopt the returned summary; hand off to the renderer, no second start |
| `NEEDS_INPUT` | Return to correction/review, clear private text; no automatic new UUID or submit |
| `FALLBACK_OFFERED` | Explain unavailability; offer navigation to independently discovered reviewed games, never auto-start |
| `CANCELLED` | Reconcile current run before declaring no new game was saved |
| `FAILED` | Show a localized stable category with Back/Edit/Check saved game as appropriate; no automatic paid retry |

The current coordinator/DTO does not provide a concrete fallback descriptor and
the shipped profiles declare no fallback bindings. Do not invent a fallback
Pack ID or describe all catalog games as profile-matched fallback. Starting any
reviewed game from that screen is a separate deliberate start.

Map safe input correction, temporary unavailability/rate limiting, configuration
unavailability and unknown failure into short EN/PL copy. Distress-related input
actions use the existing safe host path and no provider retry; never reproduce
the triggering text or invent a clinical assessment. Raw provider messages,
prompts and technical stack traces never reach the child.

## 7. Uncertain outcome, cancellation and refresh

If the submit response is lost, poll its ID before considering another attempt.
If a process-local dynamic operation returns not found, read current and any
already-known run ID. Without a verified matching published run, show Outcome
unknown / Nie znamy jeszcze wyniku and Check again/Back to review. Do not select
an unrelated current run as proof that this request succeeded. A new attempt
requires a fresh explicit review and UUID, with an explanation that the first
attempt may already have used the service. Never derive internal run UUIDs in
the browser.

Leave stops local polling and clears the draft; it does not cancel server work.
On return, check the operation marker and saved run. Cancel is an explicit
best-effort server request: explain that a request already sent may finish and
the service may already have been used. Reconcile the publication/cancellation
winner required by 28.1. If a run was saved first, show Continue rather than
claiming it disappeared or automatically abandoning it.

On reload/auth restoration, recover only IDs and server state. Never restore
the optional idea or repost a lost body. On a changed owner, stop recovery and
clear that owner's in-memory state and private marker according to 28.4.

## 8. Tests and completion

Automated component/hook tests cover metadata-driven EN/PL setup, single/multi
selection/default/clear encoding, code-point limits and IME, locale separation,
private-text review masking, double tap/remount, stale metadata, every operation
outcome, existing-run conflict and replacement failure. Assert zero start calls
before final confirmation and no automatic new calls on reconnect or auth.

Use deterministic providers through real HTTP for one Pack and one dynamic
start, including delayed `202`, lost response and cancellation/publication race.
Inspect browser storage/network and prove a private sentinel is sent only in
the confirmed transient request and never retained locally.

Run frontend tests/coverage and build/static sync; manually verify the
Spring-served UI at 360px and desktop, keyboard and browser Back. Run the exact
backend gate if server code changes. Keep rollout disabled. Mark 28.2 implemented
only when the complete start flow hands off a persisted run to the renderer or
its tested integration seam, then use the repository commit convention.
