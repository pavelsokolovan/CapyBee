# Spec 27.6 — Generated Cast, Quests, and Runtime Presentation

**Type:** Implementation specification  
**Parent:** Spec 27.5 — Generated Story Plan and Scene Continuity  
**Depends on:** Specs 24, 25, 26.1, 27.4, and 27.5  
**Baseline:** repository commit `b00c545`, plus the approved designs in Specs 27.4 and 27.5. The current `View`, `ViewBuilder`, `RunState`, objective evaluation, generated CAST/QUEST payloads, scene composition, session wire DTOs, TypeScript game contract, and console renderer were inspected while writing this specification. The build was not run.  
**Status:** Ready for implementation after Spec 27.5  
**Primary outcome:** Generated characters and quests become stable, player-visible parts of a full game. Dialogue shows character names instead of engine UUIDs. The current view exposes the story identity, discovered characters, and generated quest presentation. Objective state and all game effects remain controlled only by trusted pack rules.

---

## 1. Problem

The generation pipeline already creates CAST and QUEST artifacts, but the runtime uses them mainly as context for later generation.

Current player-visible problems:

- generated dialogue uses an engine-assigned actor ID as `Block.speaker`, so the CLI can print a UUID-like value instead of a name;
- generated character descriptions are not available in `View`;
- generated quest titles and descriptions are not connected to `ObjectiveItem`;
- the CLI shows authored objective labels even when a generated quest exists;
- there is no stable story title or premise in the runtime view;
- a host cannot distinguish known characters from characters not yet met;
- the wire view has no typed generated-story or character presentation fields.

The engine already has the correct trusted mechanical boundary. `ObjectiveDef.completeWhen` and `onComplete`, scene effects, conditions, and outcome rules control state. This specification adds presentation binding only. It does not let generated content control mechanics.

## 2. Current implementation findings

| ID | Finding | Consequence |
|---|---|---|
| F1 | `CastMember` contains trusted slot ID, engine-assigned actor ID, generated name, and generated description. | The engine already has enough data to resolve a speaker safely. |
| F2 | `GenerationPipeline.compose` currently creates `Block(SPEECH, actorId, text, ...)`. | The final player-facing block leaks an internal ID instead of resolved text. |
| F3 | `Block.speaker` is a string and the CLI prints it directly. | Resolving it before `View` fixes every text host without provider-specific logic. |
| F4 | `Quest` contains trusted objective ID, generated title, and description. | It can safely decorate an engine-owned objective. |
| F5 | `RunImpl.buildView` creates `ObjectiveItem` only from `ObjectiveDef.labelKey` and runtime state. | Generated quest presentation is currently ignored. |
| F6 | Objective state is stored as `Map<String, ObjectiveState>` and evaluated from trusted conditions. | Quest text can be added without changing state semantics. |
| F7 | `View` contains blocks, options, input, status, objectives, outcome, and places, but no story or character metadata. | A backward-compatible view extension is needed. |
| F8 | Session wire DTOs carry `View` directly and advertise `viewSchema = 1`. The UI declares `GameViewV1`. | Adding typed fields requires an explicit view-schema migration. |
| F9 | Generated artifacts already survive snapshot and resume. | Cast and quest presentation can be reconstructed without duplicating it in `RunState`. |
| F10 | The current full-game design makes every story scene a generated slot and gives slots trusted actor/objective allow-lists. | Discovery and current-scene presentation can be derived safely from trusted slots and accepted artifacts. |

## 3. Goals and non-goals

### 3.1 Goals

1. Require useful, complete CAST and QUEST artifacts for a declared full game.
2. Reference actor slots—not runtime actor IDs—in version-2 model output and fallbacks.
3. Resolve every generated dialogue speaker to a safe display name before returning `View`.
4. Expose story title, premise, and setting from the accepted story plan.
5. Expose discovered characters with stable IDs, names, descriptions, and discovery state.
6. Use generated quest title and description for trusted objectives.
7. Keep objective state, completion, effects, and events fully engine-owned.
8. Extend public and wire views with explicit backward compatibility.
9. Preserve authored packs and generation schema v1 behavior.
10. Prove restore and fallback produce the same presentation.

### 3.2 Non-goals

- Adding new runtime actor mechanics, stats, inventory, combat, relationships, or AI autonomy.
- Letting generated character descriptions change conditions or effects.
- Letting generated quests create objectives, completion conditions, rewards, or outcomes.
- Adding failed or optional objective states. Spec 27.7 may define result presentation.
- Adding CLI commands such as `/characters` or `/quest`; Spec 27.9 owns the command experience.
- Selecting endings or calculating success quality; Spec 27.7 owns resolution.
- Building the final web rendering; Spec 28 owns client presentation.
- Persisting a second copy of generated names or descriptions in `RunState`.

## 4. Decisions

| ID | Decision |
|---|---|
| D1 | Runtime actor IDs remain engine-assigned opaque IDs. The provider never supplies, chooses, or sees them. |
| D2 | Version-2 scene dialogue references trusted `actorSlot`, not `actorId`. This refines the provisional `PlannedScenePayload` in Spec 27.5. |
| D3 | Scene composition resolves `actorSlot → CastMember → display name`; the final `Block.speaker` is display-ready text. |
| D4 | Internal actor identity remains available through `CharacterItem.id`; it is not used as visible dialogue text. |
| D5 | A full-game CAST artifact contains exactly one member for every CAST template actor slot. No extra or missing member is accepted. |
| D6 | A full game has 1–12 trusted actor slots. Content-only schema-v1 packs retain their existing 0–12 behavior. |
| D7 | A full-game QUEST artifact contains exactly one quest item for every trusted objective ID declared by its QUEST template. |
| D8 | A full game has 1–12 generated quest objectives, and every scene-slot objective reference resolves to one of them. Internal authored objectives outside the template remain allowed and use authored presentation. |
| D9 | Generated quest text decorates trusted objectives only. `ObjectiveState` always comes from `RunImpl.objectives`. |
| D10 | Characters become discovered when a scene already entered by the run references their actor slot in trusted slot metadata or accepted dialogue. Discovery is derived from visited scenes and artifacts; it is not separately persisted. |
| D11 | The current scene’s characters are included before its `View` is returned, so a newly met speaker always resolves immediately. |
| D12 | `View` API schema becomes version 2. Legacy Java constructors remain. Session wire responses advertise `viewSchema = 2`; TypeScript accepts both v1 and v2 during migration. |
| D13 | Authored packs continue to return no story metadata and no generated characters. Their blocks, objectives, and console output remain unchanged. |
| D14 | Fallback cast and quest artifacts follow the same completeness and presentation rules as generated artifacts. |
| D15 | Generated presentation fields never enter logs or diagnostics. They exist only in generation artifacts, snapshots, and player-facing views. |

## 5. Full-game CAST contract

### 5.1 Payload

Keep the version-2 CAST payload shape from the existing artifact model:

```java
public record CastPayload(List<CastMember> characters) implements Payload {}

public record CastMember(
    String slotId,
    String actorId,
    String name,
    String description) {}
```

Provider output and fallback JSON contain only:

```json
{
  "characters": [
    {
      "slotId": "guide",
      "name": "Mara",
      "description": "A patient lantern keeper who listens before giving advice."
    }
  ]
}
```

`actorId` is absent from the provider schema. After validation, the engine assigns it through `IdSource` exactly once.

### 5.2 Validation

For a full game:

- exactly one member per CAST template actor slot;
- no unknown or duplicate slot;
- output order is normalized to trusted template slot order;
- name: 1–60 code points;
- description: 1–300 code points;
- names are unique after Unicode normalization and case folding;
- names and descriptions pass markup, PII, forbidden-content, and output-safety checks;
- names cannot look like UUIDs, internal identifiers, commands, or control codes;
- descriptions cannot assert mechanics, objective completion, rewards, or outcomes;
- assigned actor ID is non-blank, unique in the artifact, and no longer than the existing engine ID limit.

Schema-v1/content-only behavior remains unchanged.

### 5.3 Fallback CAST

Pack-load validation checks complete slot coverage and all display constraints. IDs are assigned only when a run accepts the fallback artifact, not during pack loading.

Given the same deterministic `IdSource`, fallback and generated cast assignment use the same slot-order algorithm.

## 6. Full-game QUEST contract

### 6.1 Trusted objective set

The QUEST template’s `objectiveIds` is the generated-presentation set.

For `FULL_GAME`:

- it contains 1–12 unique IDs;
- every ID resolves to an authored `ObjectiveDef`;
- every scene-slot objective ID from Spec 27.5 belongs to this set;
- every phase-plan objective ID belongs to this set;
- other authored objectives are allowed only as internal or authored-presentation objectives and cannot be referenced by generated slots or plans.

The pack may use internal objectives for implementation, but the player-facing full-game quest must include at least one generated objective.

### 6.2 Payload

Keep:

```java
public record QuestPayload(List<Quest> objectives) implements Payload {}

public record Quest(
    String objectiveId,
    String title,
    String description) {}
```

Provider output and fallback JSON contain exactly one item for each trusted generated objective.

### 6.3 Validation

- exact objective coverage; no missing or extra item;
- normalized trusted objective order;
- title: 1–80 code points;
- description: 1–500 code points;
- titles unique after normalization and case folding;
- output-safety and content-policy checks on both fields;
- no condition, effect, reward, state, completion flag, numeric progress, or outcome field;
- text cannot claim that an objective is already complete at run start unless the trusted initial state is complete;
- objective ID is data and must exactly match the allow-list.

The engine does not parse quest prose to determine progress.

## 7. Version-2 dialogue contract

### 7.1 Refinement to Spec 27.5

Replace `List<Dialogue>` inside `PlannedScenePayload` with `List<PlannedDialogue>`:

```java
public record PlannedScenePayload(
    String sceneId,
    String title,
    String narration,
    List<PlannedDialogue> dialogue,
    List<ChoiceLabel> choices,
    List<String> continuityFacts) implements Payload {}

public record PlannedDialogue(String actorSlot, String text) {}
```

The version-1 `ScenePayload` and `Dialogue(actorId, text)` remain unchanged for schema-v1 compatibility.

### 7.2 Request and response

A full-game scene request receives only the allowed actor slots with generated display information:

```json
{
  "allowedActors": [
    {
      "slotId": "guide",
      "name": "Mara",
      "description": "A patient lantern keeper."
    }
  ]
}
```

Do not send runtime actor IDs to the provider.

The response uses `actorSlot`:

```json
{
  "actorSlot": "guide",
  "text": "The light is weak, but it is not gone."
}
```

### 7.3 Validation and composition

- every dialogue slot is allowed by the current `SceneSlot.actorSlots`;
- every dialogue slot resolves to exactly one accepted cast member;
- maximum 8 lines, following existing scene bounds;
- dialogue text uses existing length and safety rules;
- missing, unknown, duplicated-as-control, or blank slot is invalid;
- repeated lines are allowed only when text differs;
- fallback scene dialogue follows the same slot contract.

During composition:

1. resolve `actorSlot` in the accepted cast artifact;
2. set final `Block.speaker` to the cast member’s display `name`;
3. preserve actor identity separately in the current-view character metadata;
4. never place actor ID, slot ID, or unresolved placeholder in visible text.

If resolution fails after pack/provider validation, use failure code `GENERATION_ACTOR_BINDING_FAILED` and do not commit the scene transition. Normal invalid provider output receives repair/fallback before this point.

## 8. Public view schema version 2

### 8.1 Story information

Add:

```java
public record StoryInfo(
    String title,
    String premise,
    String setting) {}
```

For a full generated game, values come from the accepted `StoryPlanPayload`. For authored and schema-v1 packs, `story` is `null` unless a later authored metadata contract supplies it.

### 8.2 Character information

Add:

```java
public record CharacterItem(
    String id,
    String slotId,
    String name,
    String description,
    boolean inCurrentScene) {}
```

`View.characters` contains discovered generated characters only, in first-discovery order. `inCurrentScene` is true when the current trusted scene slot allows the actor or the current composed blocks contain that actor’s dialogue.

The fields are presentation data. Hosts must not use them to construct commands or infer game permissions.

### 8.3 Objective information

Extend `ObjectiveItem`:

```java
public record ObjectiveItem(
    String id,
    String label,
    String description,
    ObjectiveState state) {
  public ObjectiveItem(String id, String label, ObjectiveState state) {
    this(id, label, null, state);
  }
}
```

For a generated quest objective:

- `label` is the accepted generated quest title;
- `description` is the accepted generated quest description;
- `state` comes only from trusted runtime objective state.

For an authored/internal objective:

- `label` keeps resolving `ObjectiveDef.labelKey` through pack strings;
- `description` is `null` in this specification;
- state behavior is unchanged.

### 8.4 View record

Extend `View` by appending fields:

```java
public record View(
    List<Block> blocks,
    List<Option> options,
    InputSpec input,
    List<StatusItem> status,
    boolean ended,
    EndReason endReason,
    List<ObjectiveItem> objectives,
    String outcome,
    PlacesView places,
    StoryInfo story,
    List<CharacterItem> characters) {}
```

Requirements:

- keep all current constructors as compatibility constructors with `story = null` and `characters = List.of()`;
- defensively copy characters;
- never return null lists;
- abandoned views may omit blocks but retain story, known characters, and objective presentation so a host can show a final summary later;
- short-reply views preserve story and characters instead of reconstructing a partial `View` that drops them.

### 8.5 Schema marker

Add a single public constant, for example:

```java
public static final int CURRENT_VIEW_SCHEMA = 2;
```

The session/server mapping uses this constant instead of literal `1` values.

## 9. Character discovery

### 9.1 Derivation

Do not add discovered character IDs to `RunState`. Derive them deterministically from:

- `RunState.visited` scene IDs in visit order;
- current scene ID;
- trusted scene-slot actor allow-lists;
- accepted composed dialogue artifacts.

For each visited/current story scene:

1. locate its trusted `SceneSlot`;
2. take slot actor IDs in trusted slot order;
3. add actor slots actually used by accepted dialogue, preserving dialogue order;
4. resolve them through the accepted CAST artifact;
5. add unseen actors to a linked set.

Slot allow-lists make a character discoverable even when the provider creates no dialogue for that character. This avoids different discovery behavior between generated and fallback scenes.

### 9.2 Current-scene flag

`inCurrentScene` is true when the actor slot is listed on the current scene slot. It does not mean the actor speaks.

### 9.3 Authored and utility scenes

- full-game utility scenes do not discover generated actors in contract version 1;
- authored packs keep current behavior and return no generated `CharacterItem` values;
- schema-v1 generated packs keep their existing blocks and do not gain inferred character lists.

### 9.4 Restore

Because discovery is derived from visited scenes, trusted slots, and accepted artifacts, the same snapshot produces the same character list after restart. No migration or extra snapshot field is needed.

## 10. Runtime binding

### 10.1 Generation pipeline indexes

After CAST and QUEST are accepted, build immutable indexes:

```text
actorBySlot: slotId -> CastMember
actorById: actorId -> CastMember
questByObjective: objectiveId -> Quest
```

Reject duplicate keys before storing artifacts. Restore builds the same indexes after complete artifact validation.

### 10.2 View construction

For each full-game `View`:

1. obtain the accepted story-plan, cast, and quest artifacts;
2. build `StoryInfo`;
3. build discovered `CharacterItem` values;
4. build objectives in trusted `Rules.objectives` order;
5. use generated quest presentation when `questByObjective` contains the ID;
6. use authored label and null description otherwise;
7. attach current trusted runtime state;
8. return resolved blocks whose speech speakers are names.

No provider call occurs during `view()`.

### 10.3 Objective evaluation

Keep the existing fixed-point objective evaluation unchanged:

- `completeWhen` decides completion;
- `onComplete` applies trusted effects;
- the engine emits existing events and issues;
- generated quest data is never consulted;
- rebuilding a view never applies effects;
- resume never replays objective completion.

### 10.4 Failure behavior

Missing or invalid startup CAST/QUEST artifacts should already have fallen back. If a full-game runtime nevertheless lacks a valid binding:

- starting the run fails safely with `GENERATION_REQUIRED_ARTIFACT_MISSING` before presenting a partial first view;
- restoring fails with the existing snapshot/artifact invalid path;
- a lazy scene with an impossible actor binding does not commit its transition;
- no internal ID is displayed as a fallback label.

## 11. Console rendering

### 11.1 Dialogue

The renderer continues to print:

```text
Mara: The light is weak, but it is not gone.
```

Because `Block.speaker` is now display-ready, the CLI does not need access to generation artifacts or an actor lookup.

For full-game speech blocks, a blank or unresolved speaker is a programming error and must have been rejected earlier. Do not print `null`, UUIDs, slot IDs, or `unknown` placeholders.

### 11.2 Story header

On the first rendered view of a console process, print the full-game title before scene blocks:

```text
The Lantern Road
```

Do not repeat title, premise, or setting on every turn. Session resume prints the title once when the console attaches, then the current scene.

Classic and session console loops own the “first render” decision; `ConsoleRenderer.render(view)` remains a pure rendering function and may expose a separate `renderHeader(view)` helper.

### 11.3 Objectives

For generated objectives, render one objective per line:

```text
Objectives:
  [active] Restore the Valley Lantern — Find a safe way to relight it.
  [done] Deliver the Sealed Letter — Bring it to the keeper.
```

Authored objective golden output remains unchanged unless the renderer is explicitly given view schema 2 generated descriptions. Do not show internal objective IDs.

### 11.4 Characters

Do not automatically print the full discovered-character list on every scene. The list is exposed in `View` for the later `/characters` command in Spec 27.9 and for other hosts.

## 12. Wire schema migration

### 12.1 `GameViewV2`

Add a TypeScript contract:

```ts
export interface GameViewV2 {
  blocks: Array<{
    kind: string;
    speaker?: string | null;
    text: string;
    refs: string[];
  }>;
  options: Array<{ id: string; label: string; enabled: boolean; hint?: string | null }>;
  input?: { mode: string; maxChars: number; prompt?: string | null } | null;
  status: Array<{ id: string; label: string; value: string }>;
  ended: boolean;
  endReason?: 'COMPLETED' | 'ABANDONED' | null;
  objectives: Array<{
    id: string;
    label: string;
    description?: string | null;
    state: string;
  }>;
  outcome?: string | null;
  places?: unknown | null;
  story?: { title: string; premise: string; setting: string } | null;
  characters: Array<{
    id: string;
    slotId: string;
    name: string;
    description: string;
    inCurrentScene: boolean;
  }>;
}
```

The v2 block contract uses the actual API meaning `speaker`; do not continue the current TypeScript-only `actorId` name mismatch.

### 12.2 Compatibility

- keep `GameViewV1` for decoding previously captured fixtures if needed;
- new server responses use `viewSchema: 2` and `GameViewV2`;
- TypeScript DTOs temporarily use a discriminated union of schema 1 and 2;
- current UI may ignore story, characters, and objective descriptions until Spec 28;
- server JSON tests and TypeScript contract tests cover both shapes;
- no HTTP endpoint or command request changes.

### 12.3 Scope boundary

This specification updates types and safe decoding only. It does not build final character or quest components in the web client.

## 13. Snapshot and restore

No new `RunState` fields are required.

Restore must validate:

- exact CAST slot coverage for a full game;
- unique engine actor IDs, names, and slots;
- exact QUEST objective coverage;
- actor/objective references in story plans and planned scenes;
- version-2 dialogue slot references;
- pack, version, locale, template, and artifact schema identity.

After restore:

- composed speakers have the same display names;
- discovered-character order is identical;
- story metadata is identical;
- objective labels/descriptions and runtime states are identical;
- no provider call occurs.

Do not copy generated presentation into separate snapshot fields. The accepted artifacts remain the single source of narrative truth.

---

## 14. Safety and privacy

- Names, descriptions, quest text, story metadata, and dialogue remain subject to the existing output safety policy.
- Provider-generated display text must not appear in normal logs, exceptions, metrics, debug lines, or diagnostic DTOs.
- Runtime actor IDs are not PII, but they are internal and must not be shown as names.
- Raw player input must not be copied into character or quest artifacts.
- Generated descriptions cannot include contact details, real-person claims, or instructions to leave the application.
- `toString()` for artifacts remains redacted.
- Wire views intentionally contain player-visible generated content; this is not an operational logging channel.

## 15. Error codes

Reuse existing generation, safety, fallback, and snapshot codes. Add:

| Code | Meaning |
|---|---|
| `GENERATION_CAST_COVERAGE_INVALID` | Full-game cast has a missing, extra, or duplicate trusted slot. |
| `GENERATION_CAST_NAME_INVALID` | Name is unsafe, duplicate, identifier-like, blank, or outside bounds. |
| `GENERATION_QUEST_COVERAGE_INVALID` | Quest has a missing, extra, or duplicate objective. |
| `GENERATION_QUEST_PRESENTATION_INVALID` | Quest title or description is unsafe or outside bounds. |
| `GENERATION_DIALOGUE_ACTOR_INVALID` | Planned dialogue references a disallowed or unknown actor slot. |
| `GENERATION_ACTOR_BINDING_FAILED` | Accepted/restored content cannot resolve a required actor binding. |
| `GENERATION_REQUIRED_ARTIFACT_MISSING` | A full-game view cannot be built because plan, cast, or quest is absent. |
| `VIEW_SCHEMA_UNSUPPORTED` | A wire consumer rejects an unsupported view schema. |

Repair context contains only the stable generation validation code and trusted allow-lists. It never includes rejected output.

## 16. Required tests

### 16.1 CAST validation

- exact slot coverage passes;
- missing, extra, and duplicate slots fail;
- invalid bounds, unsafe content, PII, markup, duplicate name, UUID-like name, and control-like name fail;
- provider-supplied `actorId` is an unknown-field failure;
- engine IDs are assigned in trusted slot order and are unique;
- fallback CAST follows the same rules.

### 16.2 QUEST validation

- exact trusted objective coverage passes;
- missing, extra, duplicate, and unknown objectives fail;
- title/description bounds and safety are tested;
- attempts to supply state, completion, effect, reward, or outcome fields fail;
- fallback QUEST follows the same rules;
- authored internal objectives remain valid and use authored labels.

### 16.3 Dialogue binding

- valid actor slot becomes a display-name speaker;
- runtime actor ID is absent from provider request and response schema;
- unknown or disallowed slot repairs, then falls back;
- fallback dialogue resolves through CAST;
- two actors with different slots produce correct names;
- no UUID, slot ID, null, or placeholder reaches a full-game speech block;
- schema-v1 dialogue behavior remains unchanged.

### 16.4 View construction

- full game exposes story info;
- authored and content-only packs expose null story and empty characters;
- discovered characters are ordered by first discovery;
- current-scene flags are correct;
- unvisited characters stay hidden;
- generated objectives use generated title/description and trusted state;
- internal objectives use authored label and null description;
- short replies preserve story and character metadata;
- abandoned and completed views retain summary presentation.

### 16.5 Objective integrity

- generated quest text cannot complete an objective;
- trusted condition completes it exactly once;
- `onComplete` effects and events remain unchanged;
- rebuilding views has no side effects;
- resume does not replay completion;
- fake quest text that claims success does not change runtime state.

### 16.6 Console

- generated dialogue golden output uses names, not IDs;
- story title prints once at start and once when attaching after restart;
- generated objectives render one per line with descriptions;
- authored console golden files remain byte-for-byte unchanged;
- no character list is printed automatically;
- no internal ID appears in a complete full-game transcript.

### 16.7 Wire schema

- session summary and command outcome report `viewSchema = 2`;
- v2 JSON contains `story`, `characters`, and objective `description`;
- blocks use `speaker` in the TypeScript contract;
- v1 fixture decoding remains covered where retained;
- TypeScript compilation accepts the schema union;
- current client does not fail when it ignores new fields.

### 16.8 Snapshot and fallback

- snapshot round-trip preserves cast and quest artifacts;
- restored view exactly matches pre-restart story, characters, speakers, and objectives;
- derived character discovery order is stable;
- no provider calls occur on restore;
- all-provider-failure run still shows fallback names and quest text and reaches an ending.

### 16.9 End-to-end full run

- scripted full game introduces at least three actors over several phases;
- undiscovered actors are hidden until their first allowed scene;
- all dialogue speakers are resolved names;
- one trusted objective completes and updates its generated presentation state;
- another objective remains active until a later trusted condition;
- final view has correct story info, discovered cast, quest states, and trusted outcome;
- transcript contains no generated artifact IDs or actor UUIDs.

## 20. Definition of done

Spec 27.6 is complete when:

- Every full game has a complete validated generated or fallback cast.
- Every full game has complete generated or fallback presentation for its trusted player-facing objectives.
- Providers use actor slots and never receive or return runtime actor IDs in v2 scenes.
