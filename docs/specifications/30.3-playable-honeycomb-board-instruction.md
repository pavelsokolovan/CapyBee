# Spec 30.3 — Playable Honeycomb Board

**Type:** Implementation instruction
**Intent:** [Illustrated Honeycomb RPG](intent/03-illustrated-honeycomb-rpg.md)
**Depends on:** [30.1](30.1-visual-design-and-svg-catalog-instruction.md), [30.2](30.2-public-presentation-contracts-instruction.md), 28.3–28.4
**Baseline:** `97c7a7c`, inspected 2026-11-15
**Status:** Draft — prepared for implementation

## Outcome and scope

Make the illustrated honeycomb the main navigation surface of the RPG. Show
Capy at the accepted current place, allow a legal neighboring destination to be
selected, and open that destination's authored encounter as part of the same
accepted move. The child must not need a second story choice after moving to
Mela, Borys, Luna or another destination to enter its moment.

Reuse the fixed SVG catalog, public presentation metadata, shared text renderer
and existing run controller/transport/queue. This part includes the minimal
universal movement contract needed to close the location/encounter gap. It does
not build companion portraits/party UI (30.4), illustrated encounter composition
or full text-mode controls (30.5), generated asset selection/prefetch (30.6), or
visual release certification (30.7). No new rewards, provider approval, live
generation enablement, competition, streaks or pressure to keep playing.

The RPG board remains separate from the personal activity `HoneycombMap` and
its daily cells. Visiting a game hex never creates or completes a real Mission,
friendship, memory or activity cell. Existing completion behavior stays intact.

## Repository baseline and chosen interaction

`GamePlaces` currently lives in a collapsed `ScenePanels` section, draws CSS
hexes and submits `MOVE`. `RunImpl.move` changes location/history and evaluates
objectives, but leaves the scene unchanged. Authored choices separately enter
encounters, sometimes with `GO_TO`. Simply painting SVG tiles would preserve
this split behavior and would not satisfy this specification.

Use **one existing `MOVE` command** with an authored destination-to-scene
binding evaluated inside the engine. Do not implement browser `MOVE` followed
by `CHOOSE`/`ADVANCE`, manufacture a choice ID from a place ID, or add a second
mutation endpoint. Location, encounter, discovered characters and party must
be consistent in one accepted revision, including replay and reload.

This is an explicit opt-in for a new Pack version. Existing place graphs and
saved versions retain location-only movement. `GO_TO` keeps its universal rule
semantics and never recursively invokes a destination's encounter binding.

## Versioned place-entry mechanics

Add support for `places.json` **schema version 2**, retaining schema 1 exactly.
Continue using the optional `PLACES` feature; illustration is not required for
the new mechanics. In v2, every place has a required `entry` object and the map
has a required navigation policy:

```json
{
  "schemaVersion": 2,
  "startPlace": "camp",
  "layout": {"kind": "HEX"},
  "navigation": {
    "allowedSceneIds": ["board", "visitor"],
    "unavailableHintKey": "navigation.choose-or-pause"
  },
  "places": [
    {
      "id": "river",
      "labelKey": "place.river",
      "position": {"x": 1, "y": 0},
      "entry": {
        "sceneId": "visitor",
        "requires": {"type": "FLAG_IS", "flag": "path-ready", "value": true},
        "unmetHintKey": "navigation.prepare-path"
      }
    }
  ],
  "links": []
}
```

The excerpt illustrates the new fields, not a complete loadable Pack.
`entry.requires` and its hint may be omitted together for an unconditional
entry. If `requires` is supplied, require a nonblank localized `unmetHintKey`.
Use the existing bounded condition DSL, reference validation and evaluator;
do not add JavaScript, arbitrary expressions, generated rules or a second
condition implementation. Bindings and navigation policy are mechanics data,
never presentation metadata or a permission derived from coordinates.

Limit bindings to the existing place/scene limits, with at most 128 allowed
scene IDs and no duplicates. Require target/source scenes and localized hint
keys in every declared locale. Validate condition references and bounds through
the same rules contract as scene choices. Reject missing entries, unknown
fields/schemas, dangling targets/flags/keys and duplicate entries/policy IDs.
Keep all domain records immutable, with source-compatible constructors/defaults
where existing API consumers need them. No product place IDs in engine code.

For v2, compute move eligibility from the same accepted state used to execute
the command: active run, different current/destination IDs, a declared direct
link, navigation allowed in the current scene, and the destination condition.
`availableMoves` must advertise exactly those destinations. Conditions are
evaluated before the move, not against speculative post-move flags or steps.
Reject unavailable moves before provider work or any state mutation.

## Atomic encounter entry

For an eligible bound destination:

1. Resolve its target scene through the existing authored/generated scene
   preparation path, including reviewed fallback. Do not expose or enter a
   future scene merely because its presentation was prepared.
2. Commit the destination/current-place and ordered visited-place state, enter
   the scene through the shared transition/effect/objective path, update entered
   scene history, and project the resulting public view.
3. Publish exactly one accepted command revision with the final location,
   narrative/actions, presentation, discovery and recruitment state together.

Stage preparation and commit so a missing/unusable target or unexpected failure
cannot leave a half-moved accepted run. An ordinary provider timeout/rejection
uses the authored scene fallback and completes the eligible move. Generation
usage accounting remains truthful: do not rewind paid call/token budgets when
an attempted preparation fails. Never reset the run or show a generation error
screen instead of an available authored fallback.

Scene `onEnter`, objective completion and ending effects execute once through
the existing machinery. Replaying an idempotent command returns the accepted
result without re-entering, regenerating or applying effects again. The ordered
place/scene histories have no duplicate visit entries, while legitimate revisits
still execute their authored entry behavior once per accepted command.

Selecting the current place is inspection, not another MOVE or a way to farm
entry effects. Opening the board, switching board/list, focusing/hovering a
cell and inspecting a place are read-only. No automatic pathfinding, multi-hop
movement, movement on hover or scripted sequence of browser commands.

The 30.2 discovery rule still depends on entered scenes. Schema-1 MOVE remains
location-only and reveals no new character metadata. Schema-2 MOVE may reveal
a hero because that same accepted command actually entered its scene. Client
inspection, layout and generation caches cannot reveal additional cast.

## Public view additions

Keep public view schema 2 and add optional, presentation-neutral fields:

- `PlaceView.moveBehavior`: `LOCATION_ONLY` or `ENTER_SCENE`.
- `PlaceView.moveHint`: nullable resolved text explaining a destination gate.
- `PlacesView.movementHint`: nullable resolved text for a scene-wide navigation
  restriction, such as an explicit Continue moment.

Advertise `place-entry-v1` in the existing capabilities `viewFeatures`. Do not
publish entry scene IDs, allowed-scene lists, conditions or flag names. Artwork
references continue through `View.presentation`; no new artwork schema is needed.

Extend TypeScript/decoders and shared wire fixtures in the same implementation.
Old absent fields remain valid; unknown move-behavior values use a generic move
label and make no encounter promise. Invalid optional hint text is omitted
without invalidating valid story/actions. Continue rejecting invalid core move
lists; optional artwork/layout degradation never authorizes a move.

React labels destination selection according to its public move behavior. For
`ENTER_SCENE`, explain that going there opens its moment; for location-only
maps, preserve the existing move wording. Hint precedence is pending/recovery
lock, scene-wide restriction, destination gate, then the generic unavailable
reason. All controls/copy use the existing EN/PL pattern, and Pack hints use
the story locale. No hidden-state inspection or Pack/version branches in React.

## React board and visible movement

For a valid public HEX layout with usable presentation metadata, render the
board prominently in `GameRun`, before the current moment's text/actions and
outside a collapsed details panel. Keep exactly one map instance. Refactor
`ScenePanels` accordingly; retain its unrelated objectives/characters/status
panels and the shared `SceneBlocks`/`SceneActions` renderer.

Reuse 30.1 pointy hex geometry, terrain art and state overlays. Resolve terrain
by public place ID and render one player marker from `presentation.playerAssetId`.
Remove the live marker's dependence on `GameTileArt`'s gallery-only hardcoded
Capy default: live rendering must accept the normalized player reference. Avoid
an embedded marker plus a second floating copy. Unknown art uses the existing
neutral fallback; absent player art keeps a readable current-location marker.

Keep axial relative positions and bound/sanitize the layout as in 29.3. Account
for label space and focus outlines so hex art never clips HTML labels or
controls. At 360px, the reference seven-place board must be usable without
horizontal page scrolling, forced panning or unreadable miniature targets.
Terrain remains recognizable at 64px width or larger; Capy's marker is at least
32px. Labels wrap in ordinary HTML rather than being drawn into SVG.
Do not carry the old blanket 28rem list-fallback threshold into the illustrated
board; choose fallback from the actual tile/label space so the seven-place map
can remain graphical at 360px and reflow safely when zoom leaves less room.

Use a single marker layer for the graphical board, positioned from rendered
cell centers. After an accepted location change, animate that marker to a
displayed neighboring cell in roughly 160–220ms. Keep movement visual only:
scene/actions and control availability follow accepted state, not an animation
timer. Reduced motion, initial load, reload, run replacement, layout/mode changes
and nonlocal authored relocation use the final position immediately. Never
animate through fabricated intermediate cells or infer a legal path from geometry.

While MOVE is queued/preparing/uncertain, keep the previous accepted location,
marker, scene and party; show a short pending status. Local focus/selection may
highlight a requested destination, but cannot mark it current/visited or reveal
its hero. Rejected, stale or failed actions keep/reconcile to server state
without speculative movement. Late responses for an old owner/run are ignored
by the existing controller, not a board-specific state machine.

Preserve a semantic place-list toggle and automatic list fallback for invalid,
duplicate, unsupported, oversized or impractical coordinates and narrow/zoomed
containers. The list uses the same legal destination controls, hints and entry
semantics, and shows the current player/location without requiring artwork.
Missing presentation metadata retains the existing text/map experience; generic
and dynamic public fixtures use the same source-neutral components.

## Focus, accessibility and recovery

Use semantic lists and native buttons, at least 44px targets, visible unclipped
focus, readable disabled explanations, `aria-current="location"` and textual
current/visited states. No color-only indicators, hearts or padlocks. Forced
colors must leave control boundaries, focus and all text usable when decorative
art disappears. Board/list controls have equivalent names and order.

Coordinate `GameRun`'s existing per-revision focus effect. An accepted user-origin
`ENTER_SCENE` move focuses the shared current-moment heading once, so keyboard
and screen-reader users can find the encounter. Location-only moves keep useful
map focus. Pending/rejected moves, background polling and idempotent replays do
not steal focus or re-announce the story. Mode switches preserve a corresponding
place focus; closing inspection restores its opener or a stable board heading.
Completed runs retain the existing result focus behavior.

Use a short polite accepted-location announcement, not an aria-live wrapper
around the whole board or dialogue. Inspecting a cell remains distinct from
going there; no read-only operation invokes generation. Full labels, choices
and navigation remain usable at 360px, 200% zoom and with SVGs hidden.

Keep 28.4 behavior for offline moves, original-revision retries, unsent intent
removal, account changes, two tabs and PWA recovery. Do not add a map-owned
queue, lock, flusher, story cache or localStorage persistence. Pause/back remains
available through the existing controls, with no forced timeout or penalty.

## Acceptance and required gates

- Engine: validate v1/v2 place files, all binding/policy/condition references,
  bounds and locales. Prove legacy MOVE and `GO_TO` semantics are unchanged.
  Test one-revision bound entry, shared on-entry/objective effects, conditional
  eligibility, navigation restrictions, rejection atomicity, terminal entry,
  repeated visits, current-place rejection and exact provider-disabled resume.
  A rejected ineligible move makes zero provider calls; failed scene generation
  uses authored fallback without a partially accepted location or budget reset.
- Contract: round-trip new optional fields through summaries, command outcomes,
  replay and old JSON. Verify public hints and behavior reveal no private entry
  IDs/conditions. Keep core view schema 2 and 30.2 metadata/discovery guarantees.
- Frontend: use a controller double that distinguishes pending and accepted
  revisions to prove a click sends only `{type:'MOVE', placeId}` once. No extra
  CHOOSE/ADVANCE follows it. Verify marker/scene synchronization, all tile states,
  accepted `GO_TO`, malformed/missing metadata and coordinates, neutral art,
  map/list parity, keyboard focus, long EN/PL labels and reduced/forced-color modes.
- Reference game: test a map-only route from the hub to a hero, then directly
  to an available neighboring hero; no extra travel choice is needed. Helping
  recruits only after its authored choice; moving away/declining does not.
  The crossing cannot bypass rail preparation. All three resolutions remain
  reachable. Current 1.3.0 and retained 1.0.0–1.2.0 routes stay playable and
  version-pinned.
- Integration: run the existing Spring/PostgreSQL browser suite against the
  production-built UI. Cover 360px/desktop, 200% zoom, reduced motion, forced
  colors, pending generation/fallback, offline replay, reload during an uncertain
  move, two-tab stale selection and account/run replacement. Assert accepted
  server destination, resulting encounter and revision, not merely a transient
  “Saved” status. Include authored and generated-fallback modes with deterministic
  providers; enabling a paid provider is not an acceptance step.
- Run standalone engine `clean verify`, the exact backend gate
  `mvn -B -f app/pom.xml -pl server -am verify`, frontend tests/coverage and the
  official PowerShell UI build/static sync. Compare both static directories to
  `dist/`; verify packaged current and retained Pack resources and cold CLI resume.
- Record screenshots of the real seven-place board, visible Capy, a pending
  destination and an accepted encounter, plus mobile/list/zoom/forced-color
  evidence. Store implementation, measured limits, Pack fingerprint, exact
  artifact verification and remaining release limits in
  `docs/game-honeycomb-board-acceptance.md`. Update the index and commit on `main`
  after required gates pass, using the repository's spec implementation format.
