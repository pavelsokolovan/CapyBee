# Spec 27.7 — Challenges, Consequences, and Generated Endings

**Type:** Implementation specification  
**Parent:** Spec 27.6 — Generated Cast, Quests, and Runtime Presentation  
**Depends on:** Specs 24, 26.1, and 27.4–27.6  
**Baseline:** repository commit `b00c545`, plus the approved designs in Specs 27.4–27.6. The current outcome definition, `END_RUN` effect, objective evaluation, scene transition order, event model, run state, view, and console ending behavior were inspected while writing this specification. The build was not run.  
**Status:** Ready for implementation after Spec 27.6  
**Primary outcome:** A full generated game contains trusted challenges with real consequences, reaches one of several trusted result classes, generates or falls back to an ending that reflects the final engine state, and presents a structured final summary. The model never decides the outcome, changes state, completes objectives, or invents consequences.

---

## 1. Problem

The engine can already:

- apply trusted option and scene effects;
- update counters, flags, sets, places, and objectives;
- end a run from an ending scene or `END_RUN` effect;
- store one trusted outcome ID;
- show final scene text and a simple outcome string.

That is enough for a small authored runtime, but not enough for a complete generated game:

- `OutcomeDef` has only an ID and no result class or label;
- a pack is not required to provide meaningfully different consequences;
- generated ending text can be prepared before the final option effects, target `onEnter` effects, and objective completion are known;
- there is no trusted, bounded list of important consequences for ending generation;
- the final view has no structured summary of result class, objectives, or consequence facts;
- an authored ending and an `END_RUN` effect can compete to choose the outcome;
- a player can finish, but the game does not clearly explain what happened and why.

Spec 27.7 adds trusted result metadata and an atomic transition-preview boundary. The engine computes the final state and outcome first. The generator receives only a safe summary of that trusted preview and writes presentation text for it. The state and generated ending are committed together.

## 2. Current implementation findings

| ID | Finding | Consequence |
|---|---|---|
| F1 | `OutcomeDef` contains only `id`. | The engine cannot present or classify success, partial success, or failure safely. |
| F2 | `Effect.EndRun` sets mutable `endRequested` and optional `requestedOutcome`. | Outcome selection can occur outside a declared ending and has precedence over the target scene outcome. |
| F3 | `RunImpl.choose` resolves/generates the target scene before applying option effects. | Generated destination text cannot reliably describe the selected consequence or final state. |
| F4 | `enterTarget` applies `onEnter`, evaluates objectives, then calls `finish`. | The accurate final objective/state snapshot exists only after target generation has already happened. |
| F5 | Scene routes and effects are trusted authored data. | The engine can preview them without asking the provider to decide mechanics. |
| F6 | `ObjectiveState` has `ACTIVE` and `DONE`. | Final summary can report completed versus incomplete without inventing a failure state. |
| F7 | `View.outcome` is only a string ID. | Keep it for compatibility but add structured result presentation. |
| F8 | Spec 27.5 adds story promises and continuity facts. | Ending generation can resolve narrative promises without receiving a transcript. |
| F9 | Spec 27.6 adds story, characters, and generated quest presentation to view schema 2. | The final result can reuse that view schema without exposing internal artifacts. |
| F10 | Prefetch may resolve a reachable scene before the player selects its incoming choice. | State-dependent resolution and ending scenes must not be prefetched without final arrival context. |

## 3. Goals and non-goals

### 3.1 Goals

1. Define trusted result classes and localized outcome labels.
2. Require at least two meaningfully different completion results for a full game.
3. Require trusted challenge choices whose routes or effects have observable consequences.
4. Define pack-authored result facts derived from trusted conditions.
5. Preview transitions without mutating the live run.
6. Generate resolution and ending scenes from bounded trusted post-transition state.
7. Commit state, events, objective updates, ending artifact, and run completion atomically.
8. Add a structured final `RunResult` to `View` schema 2.
9. Preserve provider-free completion through validated fallback endings.
10. Preserve authored and schema-v1 behavior.

### 3.2 Non-goals

- Letting the model score the player or choose the outcome.
- Parsing generated prose or continuity facts to infer state.
- Adding combat, dice, hidden random checks, health/death semantics, inventory items, or rewards.
- Adding a failed objective state to `ObjectiveState`.
- Generating new effects, conditions, counters, flags, sets, places, or events.
- Adding player setup or difficulty selection; Spec 27.8 owns setup.
- Completing the final CLI command system; Spec 27.9 owns commands and navigation.
- Adding long-term rewards or CapyBee-specific mission/honeycomb integration.
- Performing semantic quality scoring of ending prose; Spec 27.11 owns broader quality checks.

## 4. Decisions

| ID | Decision |
|---|---|
| D1 | The engine chooses the outcome only from trusted scene routing, effects, conditions, and authored outcome metadata. |
| D2 | Result classes are `SUCCESS`, `PARTIAL_SUCCESS`, and `FAILURE`. They describe the run result, not the player’s worth. Packs control calm, non-punitive display text. |
| D3 | A full game declares 2–8 outcomes, includes at least one `SUCCESS`, and includes at least one outcome with a different class. |
| D4 | Every declared full-game ending scene has `end: true` and a non-blank trusted `outcome`. Contract-version-1 full games do not use `END_RUN` to select completion outcomes. |
| D5 | `END_RUN` remains supported for authored and schema-v1 packs. It is rejected anywhere in a full-game contract v1 to avoid ambiguous result selection. |
| D6 | Full-game ending generation is state-dependent and always happens on entry, never through speculative prefetch. |
| D7 | Other scenes that need arrival consequences declare `generationTiming = ON_ENTRY`; ordinary context-independent scenes remain `PREFETCHABLE`. |
| D8 | The engine previews trusted effects and objective evaluation in an isolated state copy before generating an `ON_ENTRY` destination. |
| D9 | Provider output supplies ending presentation only. It cannot return outcome ID, result class, objective state, result facts, rewards, or events. |
| D10 | Pack-authored `ResultFactDef` conditions decide which important consequences are true in the previewed final state. |
| D11 | A final summary always contains trusted outcome/class, objective states, and matched result facts. Generated headline, summary, and objective notes are optional presentation layered over those facts. |
| D12 | If generation or repair fails, a validated ending fallback is composed using the same trusted final result. The run still completes. |
| D13 | If even the prevalidated fallback cannot compose because of runtime corruption, the live run remains at the previous scene and state. |
| D14 | `View.outcome` remains for compatibility. `View.result` is the authoritative structured result for view schema 2. |
| D15 | Abandonment has `EndReason.ABANDONED`, no trusted completion outcome, and `result = null`. It is not classified as failure. |

## 5. Rules schema version 2

### 5.1 Compatibility

`rules.json` schema version 1 remains supported unchanged. Full-game contract version 1 requires rules schema version 2.

Rules schema version 2 adds:

- outcome presentation and classification;
- trusted result facts.

Existing counters, flags, sets, objectives, effects, and conditions keep their semantics.

### 5.2 Outcome definition

Extend the outcome model:

```java
public record OutcomeDef(
    String id,
    ResultClass resultClass,
    String labelKey) {
  public OutcomeDef(String id) {
    this(id, ResultClass.PARTIAL_SUCCESS, null);
  }
}

public enum ResultClass {
  SUCCESS,
  PARTIAL_SUCCESS,
  FAILURE
}
```

The compatibility constructor is used only for rules schema v1. Schema-v1 runtime and output remain unchanged.

For a full game:

- ID follows existing outcome ID rules;
- `resultClass` is required;
- `labelKey` is required and resolves in every pack locale;
- labels are 1–80 code points after resolution;
- IDs and labels are unique;
- 2–8 outcomes;
- at least one `SUCCESS` and at least one differently classified outcome;
- every `runContract.completion.endings[].outcomeId` resolves here;
- every full-game outcome is used by at least one declared ending.

### 5.3 Trusted result facts

Add:

```java
public record ResultFactDef(
    String id,
    String labelKey,
    Condition when) {}
```

Extend `Rules` with `List<ResultFactDef> resultFacts` and keep a compatibility constructor that supplies an empty list.

JSON example:

```json
{
  "id": "guide-helped",
  "labelKey": "result.guideHelped",
  "when": {"type": "FLAG_IS", "flag": "helped-guide", "value": true}
}
```

Rules:

- 0–16 result facts;
- unique IDs following existing rule ID grammar;
- every label key resolves in every locale;
- labels are 1–160 code points;
- `when` uses the existing trusted `Condition` hierarchy;
- references validate at pack load;
- result facts have no effects and cannot mutate state;
- evaluate facts only for final/preview result construction;
- order in `rules.json` is presentation order;
- matched facts are true in the trusted final state; unmatched facts are omitted.

Result facts are the only authored narrative consequence data automatically sent to ending generation. Raw flag/set/counter IDs are not sent unless represented by a matched result fact or a displayed status item.

## 6. Full-game challenge contract

### 6.1 Challenge scenes

Spec 27.4 requires a `CHALLENGE` phase. Spec 27.7 adds meaningful-consequence validation.

At least one reachable scene in `CHALLENGE` must have two or more structurally available choices. Among those choices, at least two must differ by one or more trusted consequences:

- different destination scene IDs; or
- different effect lists; or
- different reachable ending outcome sets.

A label-only difference is not meaningful.

### 6.2 Observable consequence

At least one challenge choice on a valid route must affect one of:

- a displayed counter;
- a flag or set value referenced by a `ResultFactDef`;
- an objective’s eventual trusted condition;
- current or visited place;
- reachable ending outcome.

This is validated using trusted references and conservative graph analysis. The loader does not attempt full symbolic execution of arbitrary state. The minimal full-game fixture and every production full-game pack must additionally provide deterministic route tests proving the intended consequence.

### 6.3 Safe failure routes

A `FAILURE` result:

- still reaches a declared ending;
- still uses safe player-facing text;
- does not imply harm, punishment, blame, or loss outside the fictional run unless the pack’s audience/content policy explicitly permits the theme;
- cannot delete saves, consume external rewards, or trigger host-side penalties through engine behavior;
- is a completed run, not an engine error.

The universal engine enforces structural completion and content policy. Pack-specific tone requirements remain pack validation/test responsibilities.

## 7. Scene generation timing

### 7.1 Catalog field

Extend schema-v2 `SceneSlot` from Spec 27.5 with:

```java
GenerationTiming generationTiming
```

```java
public enum GenerationTiming {
  PREFETCHABLE,
  ON_ENTRY
}
```

Compatibility constructors use `PREFETCHABLE` for schema-v1/content-only slots.

Full-game rules:

- every `ENDING` slot is `ON_ENTRY`;
- every `RESOLUTION` slot that describes final state is `ON_ENTRY`;
- a slot whose narration must reflect incoming option effects is `ON_ENTRY`;
- shared converging slots should be `PREFETCHABLE` only when their text is valid for all incoming routes;
- utility scenes have no slot under contract version 1.

### 7.2 Prefetch behavior

`Run.prefetchCandidates()` excludes `ON_ENTRY` slots.

Session diagnostics and budgets otherwise remain unchanged. An excluded slot is not a prefetch miss and does not affect prefetch waste metrics.

Pack validation rejects an ending or state-dependent resolution slot marked `PREFETCHABLE`.

## 8. Transition preview

### 8.1 Purpose

Current transitions resolve the generated target before applying source option effects and target entry effects. State-dependent narrative needs the opposite information without weakening atomicity.

Add an internal transition-preview abstraction in engine-core. It is not a public command or pack API.

### 8.2 State carrier

Extract mutable runtime values into a copyable internal carrier, for example:

```java
final class RuntimeState {
  String sceneId;
  List<String> visited;
  Map<String, Integer> counters;
  Map<String, Boolean> flags;
  Map<String, LinkedHashSet<String>> sets;
  Map<String, ObjectiveState> objectives;
  String currentPlaceId;
  List<String> visitedPlaces;
  boolean ended;
  EndReason endReason;
  String outcome;
}
```

The exact class name may follow repository conventions. Requirements:

- deep copy all mutable collections;
- use the same clamp, condition, effect, objective fixed-point, place, and outcome logic for preview and commit;
- do not maintain two independent rule evaluators;
- preview cannot change timestamps, step, live events, artifacts, or the live state;
- commit replaces live runtime state once, after destination content is ready.

### 8.3 Transition preview result

```java
record TransitionPreview(
    RuntimeState state,
    List<Event> events,
    List<Issue> issues,
    String sourceSceneId,
    String targetSceneId,
    String selectedOptionId,
    List<ResultFactItem> matchedResultFacts,
    List<StatusItem> finalStatus) {}
```

`selectedOptionId` is trusted and nullable for `ADVANCE`. It is never derived from raw player text; free-text selection has already resolved to a trusted option ID.

### 8.4 Preview order

For `CHOOSE`:

1. validate the option and condition against live state;
2. copy live runtime state;
3. increment preview step bookkeeping as required by existing semantics;
4. apply source option effects to the copy;
5. set target scene and visited state in the copy;
6. apply trusted target `onEnter` effects;
7. evaluate objectives to fixed point on the copy;
8. if target is an ending, set `COMPLETED` and its trusted outcome;
9. evaluate result facts and displayed final status on the copy;
10. return preview without changing the live run.

For `ADVANCE`, omit option effects. For `MOVE`, keep current direct behavior in this specification because movement does not generate a new scene; if movement completes a full game through objective effects, the pack is invalid because full-game completion must occur in a declared ending scene.

### 8.5 Commit

After destination generation/fallback and composition succeed:

1. hold the scene and artifact in an immutable `PreparedScene` that is not yet visible through the generation cache;
2. verify the prepared artifact still matches the target slot and the live run is still at the preview source state;
3. replace live state with preview state and attach the prepared artifact in one non-throwing internal commit section;
4. increment the live step exactly once;
5. set `updatedAt` once;
6. return preview events and issues once;
7. build the view from committed state and accepted content.

Add a generation-pipeline seam equivalent to `prepareScene(sceneId, context)` plus `commitPreparedScene(prepared)`. Existing demand resolution may delegate to these two operations. Prefetch keeps its current separate accepted-artifact flow and never handles `ON_ENTRY` slots.

If content preparation fails without usable fallback, do none of these. The player remains at the source scene with original state, step, timestamp, events, objectives, and generation cache. A prepared artifact is discarded and is not included in snapshots, summaries, or diagnostics as an accepted scene.

### 8.6 Non-state-dependent scenes

Existing prefetched or already cached scenes do not need a provider call. Still use the same transition-effect evaluator so preview and commit semantics do not diverge.

## 9. Ending generation contract

### 9.1 Ending payload

Extend version-2 `PlannedScenePayload` from Specs 27.5–27.6 with nullable `EndingNarrative ending`:

```java
public record EndingNarrative(
    String headline,
    String summary,
    List<ObjectiveNote> objectiveNotes,
    String reflection) {}

public record ObjectiveNote(
    String objectiveId,
    String text) {}
```

Rules:

- `ending` is required for declared ending slots;
- `ending` is forbidden for non-ending slots;
- outcome ID, result class, objective state, result fact IDs, rewards, and events are not model fields;
- headline: 1–100 code points;
- summary: 1–700;
- reflection: 0–280, calm and non-commanding;
- exactly one objective note per player-facing QUEST objective, in trusted objective order;
- objective note text: 1–240;
- notes may describe trusted final state but cannot change it;
- all text passes normal output safety, markup, PII, and content-policy checks.

### 9.2 Ending request context

The ending scene request receives:

- trusted ending scene/slot ID and ending phase plan;
- story title, premise, themes, and story promises;
- trusted outcome ID, localized label, and result class;
- final generated objective titles/descriptions with trusted `ACTIVE` or `DONE` state;
- matched trusted result facts as localized labels;
- displayed final status items only;
- discovered character names and descriptions allowed by the ending slot;
- bounded visited continuity facts from Spec 27.5;
- selected incoming option ID and label when generation occurs on entry;
- current/final place label when places are enabled;
- the closed ending output schema.

It does not receive:

- raw flags, sets, hidden counters, or condition expressions;
- executable effects or routes;
- raw player input;
- unvisited content;
- internal actor/artifact IDs;
- provider diagnostics or credentials.

### 9.3 Truthfulness boundary

The request states that supplied outcome, objective states, result facts, and status are immutable facts to present. The output validator checks IDs and exact objective-note coverage but does not use generated prose to alter truth.

If prose contradicts trusted state in a way detectable through reserved state words or wrong objective coverage, repair once and then use fallback. Broader semantic contradiction detection belongs to Spec 27.11.

### 9.4 Fallback ending

Every ending slot fallback uses the same version-2 payload and contains an `EndingNarrative` valid for that ending’s trusted outcome class.

Because objective states may differ on routes to the same ending, fallback objective-note text must remain true for both `ACTIVE` and `DONE`, or the pack must use distinct ending scene IDs. Recommended full-game design uses distinct endings for materially different final states.

Fallback validation occurs at pack load. Runtime composition supplies trusted structured result data even when fallback prose is generic.

## 10. Structured run result

### 10.1 API types

Add:

```java
public record RunResult(
    String outcomeId,
    String label,
    ResultClass resultClass,
    String headline,
    String summary,
    List<ObjectiveResultItem> objectives,
    List<ResultFactItem> facts,
    String reflection) {}

public record ObjectiveResultItem(
    String id,
    String label,
    String description,
    ObjectiveState state,
    String note) {}

public record ResultFactItem(
    String id,
    String label) {}
```

All lists are immutable and keep trusted order.

### 10.2 View integration

Append nullable `RunResult result` to view schema 2 from Spec 27.6. Do not bump to view schema 3 because Specs 27.6 and 27.7 are the same not-yet-implemented v2 design sequence.

- active run: `result = null`;
- completed full game: non-null result;
- abandoned run: `result = null`;
- authored/schema-v1 run: null unless a later compatibility mapping explicitly supplies a result;
- `View.outcome` continues to contain `outcomeId` for compatibility.

Keep all prior `View` constructors and default `result = null`.

### 10.3 Trusted versus generated fields

Trusted:

- outcome ID;
- localized outcome label;
- result class;
- objective IDs, labels, descriptions, and states;
- result fact IDs and labels.

Generated or fallback presentation:

- headline;
- summary;
- objective note text;
- reflection.

If ending presentation is unavailable due to an impossible post-validation corruption, do not commit completion. Under normal provider failure, validated fallback always supplies these fields.

### 10.4 Snapshot derivation

Do not add `RunResult` as a second snapshot copy. Rebuild it from:

- saved trusted `RunState` outcome and objective states;
- rules outcome/result-fact definitions;
- accepted ending scene artifact;
- story/cast/quest artifacts.

Restore validates that the ending artifact’s ending presentation matches the trusted ending scene and exact objective IDs.

## 11. Outcome and completion invariants

For `FULL_GAME` contract version 1:

1. Completion occurs only by entering a declared ending scene.
2. Every declared ending has `end: true` and exactly one trusted outcome ID.
3. No full-game scene or objective uses `END_RUN`.
4. No movement command can complete the run.
5. Final outcome equals the ending scene outcome.
6. Final outcome resolves to one `OutcomeDef` and one `ResultClass`.
7. Final objective state is evaluated after option and ending-entry effects.
8. Result facts are evaluated after final objective fixed point.
9. Ending generation uses that final preview.
10. Live completion commits only after ending content is ready.
11. Completion events are emitted once and only from trusted effects.
12. Resume never replays effects, objective completion, result-fact evaluation side effects, or events.

Pack validation rejects any full-game content that violates these invariants before provider use.

## 12. Console presentation

### 12.1 Final scene

Render the composed ending scene normally, including named dialogue.

### 12.2 Final result

After the ending blocks, render:

```text
Result: Success — The Lantern Is Bright Again

The courier restored the light and delivered the letter safely.

Objectives:
  [done] Restore the Valley Lantern — You found a safe way to relight it.
  [done] Deliver the Sealed Letter — The keeper received the letter.

What changed:
  - The guide chose to help at the bridge.
  - The north lantern was repaired.

The road is quiet now. You can remember the brave first step.
  [end]
```

Rules:

- result-class display names are stable localized engine/pack strings, not raw enum names;
- do not print outcome IDs, objective IDs, fact IDs, internal state, or artifact IDs;
- omit empty facts or reflection sections;
- incomplete objectives display `[active]`, not `[failed]`;
- failure result text remains calm and does not blame the player;
- authored console goldens remain unchanged.

### 12.3 Script and exit behavior

A completed run exits 0 regardless of result class. `FAILURE` is a valid game result, not a process failure. Provider fallback also exits 0 when the run completes.

Live-smoke semantics remain about provider success, so a completed fallback ending may still cause live-smoke exit 4 under existing rules.

## 14. Safety and observability

- Ending presentation passes the same safety and PII checks as every generated scene.
- Failure outcomes must not produce insulting, shaming, hopeless, threatening, or manipulative text.
- Reflection text cannot direct a child to contact strangers, reveal information, spend money, or leave the application.
- Trusted result labels and fact labels are authored localized pack text and validated at pack load.
- Result context and generated ending text do not appear in logs, metrics, errors, debug output, or diagnostics.
- Diagnostics may report only outcome ID, result class, artifact outcome, call counts, latency, and stable failure codes.
- Raw hidden state is never sent to the provider.
- `RunResult` is player-facing and intentionally appears in view/wire output and saved accepted artifacts.

## 15. Error codes

### 15.1 Pack errors

| Code | Meaning |
|---|---|
| `PACK_RESULT_OUTCOME_INVALID` | Outcome metadata, label, class, coverage, or uniqueness is invalid. |
| `PACK_RESULT_FACT_INVALID` | Result fact ID, label, condition, or reference is invalid. |
| `PACK_RESULT_CHALLENGE_MISSING` | No reachable challenge has meaningfully different trusted consequences. |
| `PACK_RESULT_ENDING_INVALID` | Ending does not have exact trusted end/outcome behavior. |
| `PACK_RESULT_END_RUN_FORBIDDEN` | Full-game contract v1 uses `END_RUN`. |
| `PACK_RESULT_PREFETCH_INVALID` | State-dependent resolution/ending slot is incorrectly prefetchable. |

### 15.2 Runtime/generation errors

| Code | Meaning |
|---|---|
| `GENERATION_ENDING_INVALID` | Ending presentation shape or semantic references are invalid. |
| `GENERATION_ENDING_OBJECTIVE_MISMATCH` | Objective notes do not exactly cover trusted player-facing objectives. |
| `GENERATION_ENDING_STATE_CONTRADICTION` | Detectable ending text contradicts supplied trusted state. |
| `GENERATION_ENDING_BINDING_FAILED` | Ending artifact cannot bind to trusted outcome/objectives. |
| `TRANSITION_PREVIEW_FAILED` | Trusted state preview could not be computed safely. |
| `TRANSITION_COMMIT_FAILED` | Prepared preview cannot be committed due to an invariant violation. |

Provider errors, repair, budget exhaustion, and fallback continue to use existing codes and behavior.

## 16. Required tests

### 16.1 Rules parsing and validation

- Rules schema v1 remains compatible.
- Valid schema-v2 outcomes and result facts load.
- Missing label/class, duplicate IDs/labels, unused outcome, unknown ending outcome, and unresolved locale key fail.
- Full game with one outcome fails.
- Full game without `SUCCESS` or without another class fails.
- Invalid result-fact condition reference fails.
- `END_RUN` anywhere in a full game fails.

### 16.2 Challenge validation

- two label-only choices fail meaningful-consequence validation;
- distinct effects pass;
- distinct destinations with distinct reachable outcomes pass;
- challenge consequence connected to displayed counter, result fact, objective, place, or ending passes;
- no reachable challenge fails;
- deterministic route tests prove at least two different final summaries.

### 16.3 Generation timing

- ending must be `ON_ENTRY`;
- state-dependent resolution must be `ON_ENTRY`;
- `Run.prefetchCandidates()` excludes `ON_ENTRY` slots;
- exclusion does not increment miss/waste diagnostics;
- ordinary `PREFETCHABLE` behavior remains unchanged;
- schema-v1 slots keep current default behavior.

### 16.4 Transition preview

- preview applies option effects, entry effects, objective fixed point, outcome, and result facts in exact runtime order;
- live state, step, timestamp, events, and artifacts remain unchanged during preview;
- counter clamping and all condition/effect types match normal runtime behavior;
- preview and committed state are deeply equal after success;
- generation failure before fallback leaves live state unchanged;
- fallback success commits exactly once;
- repeated command/idempotency does not duplicate effects or events;
- preview failure returns a safe issue and does not end the run.

### 16.5 Ending request

- request receives final preview objective states and matched result facts;
- it receives no raw flags, sets, hidden counters, effects, routes, or raw input;
- selected trusted option is present for on-entry choice generation;
- story promises and bounded continuity facts are present;
- only allowed discovered characters are included;
- context limit trimming preserves mandatory trusted result data.

### 16.6 Ending parser and fallback

- valid ending narrative passes;
- missing ending data on ending slot fails;
- ending data on non-ending slot fails;
- unknown/duplicate/missing objective note fails;
- attempts to supply outcome, class, state, fact, reward, or event fields fail closed;
- unsafe or contradictory output repairs once, then falls back;
- provider failure goes directly to fallback;
- fallback ending composes for each declared outcome.

### 16.7 Structured result

- trusted outcome label/class are correct;
- objective states reflect final preview;
- matched result facts are exact and ordered;
- generated headline/summary/notes/reflection bind correctly;
- active and abandoned views have null result;
- completed full-game view has non-null result and matching legacy `outcome`;
- rebuilding view has no side effects;
- result survives snapshot/resume without provider calls.

### 16.8 Console and wire

- success, partial-success, and failure golden transcripts render correctly;
- all valid result classes exit process code 0;
- fallback completion exits 0 outside live-smoke;
- no internal IDs or raw enum names are displayed;
- `GameViewV2.result` JSON and TypeScript types match;
- authored and schema-v1 console goldens remain unchanged.

### 16.9 End-to-end routes

Use deterministic scripts for at least three routes:

1. success: all trusted objectives complete;
2. partial success: some objectives remain active and relevant result facts differ;
3. failure: the run still reaches a safe declared ending.

For each route:

- final outcome is trusted and expected;
- generated/fallback ending reflects the previewed state;
- objective effects run once;
- result facts differ as expected;
- save/resume immediately before and after the ending is identical;
- no repeated provider call occurs after completion;
- no hidden state or internal ID appears in transcript/log capture.

## 20. Definition of done

Spec 27.7 is complete when:

- Full-game outcomes have trusted localized labels and result classes.
- Every full game has at least two meaningfully different result paths.
- Challenge choices have trusted observable consequences.
- Result facts are derived only from authored conditions and final engine state.
- Full-game completion occurs only in declared ending scenes.
- Full-game contract v1 cannot use `END_RUN` to bypass the ending contract.
- State-dependent resolution and ending slots are generated on entry and never speculatively prefetched.
- Transition preview uses the same effect/condition/objective logic as commit.
- Provider/fallback preparation cannot partially mutate a run.
- Ending generation receives bounded trusted final state and cannot choose or change it.
- Every provider failure still reaches a validated fallback ending.
- A completed full game exposes a structured `RunResult` with trusted outcome, class, objective states, and result facts.
- Success, partial-success, and failure are valid completed runs and return CLI exit code 0.
- Save/resume before and after completion preserves the exact result without new calls or replayed effects.
- Authored and schema-v1 behavior remains unchanged.
- No hidden state, generated ending content, raw player input, or internal IDs leak into logs or diagnostics.
- Engine and application verification pass without network or credentials.

## 21. Handoff to Spec 27.8

Spec 27.8 will add player setup and personalization. It may provide sanitized, pack-declared inputs to THEME or SCENARIO generation and show the selected setup before provider use.

It must not:

- let setup input define mechanics, outcomes, result classes, or difficulty rules outside trusted pack configuration;
- persist or replay raw free text;
- allow player input to alter trusted result facts or objective definitions;
- weaken the atomic result and ending boundary established here;
- treat a failure result as a provider or process failure.

Personalization changes the story’s presentation. Trusted rules still determine what happens.
