# Spec 29.2 — Theme-first Generation and Safety

**Type:** Implementation instruction
**Parent:** [Spec 29](29-capybee-polish-game-and-product-integration-instruction.md)
**Depends on:** 29.1
**Baseline:** `967e1d9`, inspected 2026-11-14
**Status:** Draft

## Deliverable and boundaries

Add optional, Pack-declared generation to the Polish game: theme first, then
scenario, quests, cast and lazily generated dialogue/scene presentation, using
the existing generation catalog/templates/quality/fallback contracts. Author a
complete Polish fallback for every generated slot. Engine mechanics/routes
remain authored; do not silently substitute the generic dynamic profile or
create a CapyBee-only runtime fork. Discover existing support before adding any
small, universal schema extension; preserve old Pack/snapshot compatibility.

## Preparation and consent

Offer enumerated interests/tone and an explicit optional mood selection. A
current check-in may preselect only an allowlisted mood code, with a clear
editable control; do not send check-in notes, history, profile identity, age,
friendship data, precise location or names. No check-in is required to play.
Defaults must work without providing personal data.

The optional fictional wish is transient, at most 240 Unicode code points,
and disabled offline. Review shows only 'idea added', not its raw value.
Explain the third-party AI boundary, accepted-save behavior and possible
reviewed fallback in EN/PL before an explicit start. Preserve disclosure
revision/profile identity checks from 28.1–28.4. Re-review on changed terms;
never auto-start from mood/preference changes or an effect.

28.2 deliberately disables Pack free-text setup. Do not merely remove that UI
restriction: audit the Pack start request, `pending_start`, operation markers,
command rows, snapshot `startInputs`, provider envelopes and logs first. Raw
wish/check-in notes must not enter durable queue records, pending-start JSON,
snapshots, metrics, history/URL or logs. If the existing pipeline cannot satisfy
this, introduce a minimal transient preparation boundary with a body-free
operation identity before enabling the wish. Accepted generated content may
reflect the fictional idea, but is not permission to retain the raw body.

## Safe input and failure contract

Route wishes and gameplay text through the shared engine guard before any
provider call. Use existing safety contracts for ordinary scrubbing, blocked
PII, distress and emergency signals. The test plan must cover sadness, fear,
self-harm language, identifying information and instruction injection in Polish.
Do not use a browser keyword check or the story generator as the safety gate.
A distress route uses reviewed localized support copy and an optional trusted
adult/help step, without diagnosis, shame, forced contact or a claimed clinical
triage service. Do not infer permission to send distress text externally.

Review provider retention/child-audience terms and record an operator decision
before enabling live use. Deterministic tests and implementation do not grant
that approval or certify provider suitability. Keep generation disabled by
default. Apply existing per-run/per-child/global call/token budgets; no daemon
or always-on Fly worker. Timeout/rejection/quota exhaustion uses reviewed Polish
fallback without resetting call counts, deleting the accepted run or silently
retrying a paid start. Cancellation never promises reversal of cost.

## Acceptance

Deterministic generator/reviewer/guard doubles must prove theme dependency order,
strict slots, fallback completeness, no invented mechanics/IDs/assets, privacy
sentinel exclusion from every persistence/log boundary and zero provider calls
for blocked input. Prove one explicit attempt through 202/lost response/reload,
atomic replacement and exact provider-disabled restart after publication.

Run engine/backend/frontend coverage and static sync as affected, integrated
PostgreSQL/browser acceptance, and package/offline/compatibility checks for
changed Pack or public contracts. Paid live certification remains separately
opt-in and budgeted. Leave Missions/rewards and the graphical map to later parts.
