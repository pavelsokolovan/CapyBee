# Spec 29.3 — Accessible Hex Map and Encounter UI

**Type:** Implementation instruction
**Parent:** [Spec 29](29-capybee-polish-game-and-product-integration-instruction.md)
**Depends on:** 29.1; 29.2 only for generated variants
**Baseline:** `967e1d9`, inspected 2026-11-14
**Status:** Map UI implemented; authored Polish integration verified by 29.1

## Deliverable

Build a source-neutral graphical place map under the existing game component
boundary, consuming only the public `PlacesView`. Integrate the Polish Pack into
the Play entry without a second game controller, auth flow, mutation dispatcher
or story cache. The personal activity honeycomb (`HoneycombMap` and
`useHoneycombCells`) is a different feature; do not turn its cells into RPG
places or make the RPG map imply real-world progress.

Render an accessible hex arrangement for valid advertised coordinates/layout.
For absent, duplicate, unsupported or impractical coordinates, keep the 28.3
place-list fallback. Never compute legal moves from coordinates, drawn links,
visited state or visual adjacency. Only `availableMoves` authorizes a MOVE;
submit the original place ID through the existing controller/revision path.
Keep discovered characters/encounters in the shared scene renderer, not a
parallel mechanics/UI tree per Pack or source.

## Interaction and accessibility

Current and visited places need text and non-color indicators. Show only public
labels/descriptions; no hidden cast, blueprint, mechanics or snapshot inspection.
A map destination cannot act while a command is pending; leave the last accepted
map/scene visible without speculative movement. An informational place may be
inspected without provider calls or mutations. Returning from an inspection
restores focus; map opening does not advance the game.

Provide keyboard-accessible controls, readable disabled hints, at least 44px
targets, visible focus and a semantic list alternative. Long Polish/English
labels wrap at 360px and 200% zoom. Avoid forced panning/animation; respect
reduced motion and do not use sound or timed encounters. Announce only short
accepted-state changes, not the whole story/map at every poll.

On stale/late responses, offline selection, reload, account change or competing
tabs, use 28.4 recovery and server state. Do not add a second periodic flusher,
text persistence, map-owned optimistic state or custom localStorage lock.

## Acceptance

Test list/map parity for current/visited/legal/disabled places, malformed layout,
missing optional fields, unknown kinds, long labels, plain-text hostile strings,
keyboard focus and pending locking. Exercise an authored and a dynamic public
fixture through the same components; text-only games retain their renderer.

Run frontend coverage/build/static sync and the integrated Spring/PostgreSQL
browser suite with 360px/desktop, zoom, reduced motion, reload and two-tab stale
movement. Run engine/backend gates only for relevant public-contract changes.
No Mission creation, reward projection or production enablement belongs here.

## Implementation evidence

`GamePlaces` renders public HEX coordinates within the shared `ScenePanels`
boundary and retains the semantic list for unsupported/impractical layouts and
narrow containers. It uses only `availableMoves` and the existing controller.
Discovered encounters remain in `SceneBlocks`/`ScenePanels`; the Play catalog
and Pack start flow remain source-neutral.

See [acceptance evidence](../game-hex-map-acceptance.md) for verification and
limits. The original 29.3 baseline contained no Polish Pack;
[29.1 acceptance](../game-polish-authored-pack-acceptance.md) now verifies the
authored Polish Pack through the shared map/scene components. Current dynamic
profiles also prohibit places; public-view fixtures test rendering independently
of that capability. No generation/profile or production flag was enabled.
