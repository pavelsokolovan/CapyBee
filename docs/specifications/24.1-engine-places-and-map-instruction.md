# 24.1 — Engine Places and Map Runtime

## Purpose

Implement the optional `PLACES` feature in the universal engine: a pack-defined place graph, renderer-neutral map data in `View`, current/visited-place state, explicit movement commands, and the `GO_TO` effect plus place-aware conditions.

This is a **sub-spec** after spec 24, not a renumbering of the series. Specs 25–31 keep their existing numbers and scope. Spec 24 continues to own counters, flags, sets, general effects/conditions, objectives, outcomes, events, snapshot migration policy, and `RunStore`; this spec adds only the Places-specific types and behavior.

A pack without `PLACES` remains unchanged and does not need `places.json`. A pack with `PLACES` must ship and validate `places.json`, can be played and inspected through the console, and has deterministic place state saved in the ordinary run snapshot.

## Constraints

- **Universal:** no theme, genre, product, screen, or game-specific words in engine code, public types, ids, or tests.
- **Separate SDK:** changes stay under `app/engine/`, `.github/`, and `docs/`. Do not change `app/server`, database schema, HTTP endpoints, or deployment.
- **Headless and console-playable:** core returns data and accepts commands; only `app/engine/cli` reads or writes the console.
- **Deterministic:** no random movement, implicit path selection, wall-clock reads, or un-injected ids.
- **Pack-defined graph:** the engine validates declared places and links; it does not invent routes or infer links from coordinates.
- **Closed-world references:** every place, link endpoint, `GO_TO` target, and place condition must reference a declared id.
- **Optional feature:** packs without `PLACES` have no current place, empty visited-place state, no map in `View`, and no behavior change.
- **Independent concerns:** scene navigation (`next`, option `next`, `branches`) and place movement are separate. A `Move` command or `GO_TO` effect does not change the current scene. Use scene navigation for scenes and `GO_TO` when authored rules should also change the map position.
- Specs 25–31 retain their current numbering and scope.

### In scope

`places.json`; layout and place data; graph links; the `PLACES` feature contract; `PlaceMap` state; `Move`; `GO_TO`; `AT_PLACE` and `VISITED_PLACE`; `View.places`; snapshot defaults/migration; console map display and input; fixture and tests.

### Out of scope

Entities or entity-backed sets (25); stages/templates (25); generated maps or LLM generation (27); costs, path-finding, combat, random encounters, fog-of-war, map editing, animation, asset rendering (30), web persistence/integration (29), and CapyBee-specific content (31). There is no automatic scene-to-place binding in this version.

## 1. Vocabulary and feature ownership

| Term | Meaning | Owner after this spec |
|---|---|---|
| Place | A named node in the pack's place graph | 24.1 |
| Place link | A declared directed or bidirectional connection between two places | 24.1 |
| Place map | The immutable pack-level graph, layout kind, and start place | 24.1 |
| Current place | The place where the run is currently positioned | 24.1 |
| Visited place | A place entered during the run, recorded once in first-visit order | 24.1 |
| `PLACES` | Optional manifest feature that enables the place graph and movement | 22 defines the feature id; 24.1 defines its runtime contract |
| `GO_TO` | A rule effect that sets the current place to a declared place | 24.1 |
| `AT_PLACE`, `VISITED_PLACE` | Conditions over current/visited-place state | 24.1 |

`PackFeature.PLACES` already exists in the spec-22 vocabulary. Do not add a duplicate feature enum or invent a second map feature name. Once this spec is implemented, `PLACES` is a supported feature; it must no longer produce `FEATURE_NOT_AVAILABLE` solely because it is `PLACES`.

### Pack layout rules

- `places.json` is a single shared, locale-neutral file at the pack root. It must be listed in the manifest `files` array when `features` includes `PLACES`.
- If `PLACES` is declared and `places.json` is missing, normal `PackLayout.requiredFiles(manifest)` handling must report `PACK_REQUIRED_FILE_MISSING`.
- A pack whose manifest `files` array lists `places.json` but does not declare `PLACES` is invalid (`PLACES_FEATURE_REQUIRED`). The loader does not enumerate unlisted directory entries, so never claim to detect an unlisted file sitting on disk.
- Add `places.json` to `PackLayout.requiredFiles(manifest)` only when `PLACES` is declared. Do not make it globally required.
- `fixture-minimal` stays byte-for-byte unchanged. Upgrade the existing dungeon fixture in §10 instead of adding a new unrelated fixture pack.

## 2. `places.json` schema v1

The file is a JSON object with `schemaVersion: 1`, a start place, a layout kind, a list of places, and a list of links.

```json
{
  "schemaVersion": 1,
  "startPlace": "cell",
  "layout": { "kind": "GRAPH" },
  "places": [
    {
      "id": "cell",
      "labelKey": "place.cell",
      "position": { "x": 0, "y": 0 }
    },
    {
      "id": "corridor",
      "labelKey": "place.corridor",
      "position": { "x": 1, "y": 0 }
    }
  ],
  "links": [
    { "from": "cell", "to": "corridor", "bidirectional": true }
  ]
}
```

### 2.1 Fields and limits

| Field | Required | Rules |
|---|---:|---|
| `schemaVersion` | Yes | Must equal integer `1`. |
| `startPlace` | Yes | Valid place id; must identify one entry in `places`. |
| `layout.kind` | Yes | One of `GRAPH`, `GRID`, `HEX`, `FREEFORM`. `GRAPH` is the default recommendation. |
| `places` | Yes | 1–128 place objects; ids unique within this section. |
| place `id` | Yes | Existing id form `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`, max 48 characters. |
| place `labelKey` | Yes | Must resolve in `strings/<locale>.json` for every manifest locale. |
| place `descriptionKey` | No | If present, must resolve for every manifest locale. It resolves to plain text; no markup is introduced. |
| place `position` | No | `{ "x": integer, "y": integer }`; each coordinate is in `[-1000, 1000]`. Both coordinates are required together. |
| `links` | Yes | Array of 0–512 links. An isolated place is allowed but will generate a warning if unreachable from the start. |
| link `from`, `to` | Yes | Must each reference a declared place; a link cannot connect a place to itself. |
| link `bidirectional` | Yes | Boolean. `true` allows travel in both directions; `false` allows travel only from `from` to `to`. |

Unknown fields follow the existing `PACK_UNKNOWN_FIELD` warning convention. Invalid known values use `PLACES_FIELD_INVALID`. Do not use arbitrary JavaScript, expressions, scripts, unbounded numbers, or unvalidated custom movement rules in this file.

### 2.2 Layout semantics

`layout.kind` and optional `position` are renderer hints only. The engine passes them through without computing distance, geometry, adjacency, path-finding, or movement cost. Links alone determine legal movement.

For `HEX`, `position.x` and `position.y` are renderer-defined axial coordinates; for other kinds they are generic coordinates. This is descriptive metadata, not a rule that the engine interprets. Coordinates may be absent for any place, even when a layout kind is supplied.

### 2.3 Link semantics and order

Links are traversed in their declared direction, except a bidirectional link can be traversed either way. A second link with the same ordered `(from, to)` pair is a duplicate even if its `bidirectional` value differs. Opposite one-way links (`A → B` and `B → A`) are allowed, though one bidirectional link is preferred when both directions should be legal.

The order of `places` is meaningful for deterministic view output. The order of `links` is meaningful for serialization and diagnostics but does not override place order when listing available destinations. `availableMoves` is emitted in `places` definition order.

## 3. Validation and reference indexing

Add `PlacesSectionValidator` in `com.capybee.engine.places.json`; it implements the existing pure `SectionValidator` contract. Register it from `Engine.sectionValidators()` alongside—not instead of—`SceneSectionValidator` and `RulesSectionValidator`.

The validator must:

1. Require and parse `places.json` exactly when manifest feature `PLACES` is declared; report malformed JSON as a content issue, not an unchecked exception.
2. Validate schema version, field types, ids, limits, coordinates, duplicate ids/links, and `startPlace`.
3. Register all place ids through `ReferenceIndex.define("place", id, file, pointer)`.
4. Register `startPlace`, link endpoints, `GO_TO.place`, and `AT_PLACE` / `VISITED_PLACE` place ids as `ReferenceIndex.reference("place", id, file, pointer)`.
5. Register `labelKey` and `descriptionKey` with the existing `stringKey:<locale>` reference kind for every declared locale.
6. Use the shared final `ReferenceIndex.check()` for ordinary `PACK_DUPLICATE_ID` and `PACK_DANGLING_REF` reports. Do not duplicate these checks in a second bespoke pass.
7. Check reachability from `startPlace` by traversing legal link directions. Each declared place that cannot be reached is a `PLACE_UNREACHABLE` WARNING, not an error; disconnected subgraphs can be intentional.
8. Never depend on validator order. `RulesSectionValidator` and `SceneSectionValidator` may parse a reference before `PlacesSectionValidator` defines it; the shared index resolves references after all registered validators run.

| Code | Severity | Meaning |
|---|---|---|
| `PACK_REQUIRED_FILE_MISSING` | ERROR | `PLACES` is declared but `places.json` is not listed/present, through the existing required-file mechanism. |
| `PLACES_FEATURE_REQUIRED` | ERROR | `places.json` is listed or present while manifest feature `PLACES` is absent. |
| `PLACES_FIELD_INVALID` | ERROR | Invalid schema, field, id format, coordinate, range, duplicate link, or limit. |
| `PACK_DUPLICATE_ID` | ERROR | A duplicate place id, reported through the shared reference index. |
| `PACK_DANGLING_REF` | ERROR | A referenced place id does not exist, reported through the shared reference index. |
| `PLACE_UNREACHABLE` | WARNING | Place cannot be reached from `startPlace` following the declared directions. |
| `PLACE_UNKNOWN` | ERROR | Runtime `Move` target is not declared by the run's pack. |
| `PLACE_NOT_CONNECTED` | ERROR | Runtime `Move` target is declared but there is no legal link from the current place. |
| `PLACES_NOT_ENABLED` | ERROR | `Move` was submitted for a run whose pack has no `PLACES` feature. |

Malformed pack content must not throw from `PackLoader.tryLoad`. As elsewhere, `PackLoader.load` may throw its documented `PackValidationException` after collected errors are returned by the validation path.

## 4. Place state and public API additions

All place state belongs to a `Run`; the validated `PlaceMap` loaded from a pack is immutable and shared among runs. Keep public records immutable and defensively copy all collections.

### 4.1 `RunState` and snapshot

Extend the `RunState` defined in spec 24 with:

```java
String currentPlaceId;      // null when the pack has no PLACES feature
List<String> visitedPlaces; // empty when the pack has no PLACES feature
```

`visitedPlaces` is unique and preserves first-visit order. Do not sort it: order is part of the run history. A new run whose pack declares `PLACES` starts at `places.startPlace`; `visitedPlaces` initially contains only that id. A pack without `PLACES` has `currentPlaceId == null` and `visitedPlaces.isEmpty()`.

Keep `snapshotVersion = 1`. These are additive optional fields inside `state`, just like the fields introduced by spec 24. The snapshot codec writes `currentPlaceId` and `visitedPlaces` for a Places-enabled run and accepts their absence when reading an older snapshot. For a snapshot of a pack without `PLACES`, serialize `currentPlaceId` as `null` and `visitedPlaces` as an empty array, or omit both consistently if the existing codec's optional-field policy uses omission; do not vary the encoding between runs.

Example state after moving from `cell` to `corridor`:

```json
{
  "sceneId": "cell",
  "visited": ["cell"],
  "ended": false,
  "endReason": null,
  "counters": { "health": 10 },
  "flags": { "has-key": false },
  "sets": { "inventory": [] },
  "objectives": { "escape": "ACTIVE" },
  "outcome": null,
  "currentPlaceId": "corridor",
  "visitedPlaces": ["cell", "corridor"]
}
```

The scene fields and place fields are separate: after this movement, `sceneId` is still `cell`. This is intentional; this version adds no implicit scene/place binding.

### 4.2 `View.places`

Append one nullable field to the `View` from spec 24:

```java
PlacesView places; // null when the pack does not declare PLACES
```

`PlacesView` exposes current map state without requiring a host to parse pack files:

```java
public record PlacesView(
    String currentPlaceId,
    List<PlaceView> places,
    List<PlaceLinkView> links,
    List<String> availableMoves,
    List<String> visitedPlaceIds,
    String layoutKind // GRAPH | GRID | HEX | FREEFORM
) {}

public record PlaceView(
    String id,
    String label,
    String description,
    Integer x,
    Integer y
) {}

public record PlaceLinkView(String from, String to, boolean bidirectional) {}
```

Contracts:

- `label` and non-null `description` are fully resolved in the run's locale. Hosts do not translate them.
- `description`, `x`, and `y` may be `null` if omitted in the pack; `x` and `y` must be either both null or both non-null. The API exposes the position as scalar fields so it does not leak internal pack-model types.
- `places` and `links` preserve pack-file order. `availableMoves` follows place definition order. `visitedPlaceIds` follows first-visit order.
- A bidirectional link appears once in `links` with `bidirectional=true`; do not expand it into two links in the view. `layoutKind` is a string with one of the validated values `GRAPH`, `GRID`, `HEX`, or `FREEFORM`.
- `availableMoves` contains ids, not localized labels, to support `Command.Move` and host-side selection. Each id is resolvable through the `places` list.
- Build the view from immutable validated pack definitions plus current run state. No renderer-specific map layout, screen name, pixel unit, or asset is introduced.

Since `View` is a record, keep a source-compatible constructor with the full pre-24.1 spec-24 shape (including objectives and outcome) that delegates to `places = null`; also preserve the older six-argument spec-23 constructor if the implementation still uses it. Update all internal construction sites and snapshot/view tests.

## 5. Commands and effects

### 5.1 `Command.Move`

Add one command to the existing sealed `Command` interface:

```java
record Move(String placeId) implements Command {}
```

Rules:

- `Move` is available whenever a run is active and the pack declares `PLACES`, independently of whether the current scene normally accepts `Choose` or `Advance`. It moves on the map only; it does not choose an option or advance a scene.
- The target must exist and be directly reachable from `currentPlaceId` through a declared legal link. The engine does not calculate paths or auto-move through intermediate places.
- On success, set `currentPlaceId` to the target, append it to `visitedPlaces` if it has not appeared before, increment `step` exactly once, update `updatedAt` from the injected `Clock`, evaluate objectives under spec-24's accepted-step rules, rebuild `View`, and return an accepted `StepResult`.
- A rejected move does not change the view, current place, visited places, step, timestamp, objectives, events, or snapshot. Use `RUN_ENDED`, `PLACES_NOT_ENABLED`, `PLACE_UNKNOWN`, or `PLACE_NOT_CONNECTED` as appropriate.
- Moving to the current place is not a legal move unless there is a distinct valid link, and self-links are invalid, so it is rejected with `PLACE_NOT_CONNECTED`.
- A map move raises no event by itself and does not trigger scene `onEnter` effects. A later spec may add explicit movement events, but v1 must not manufacture event ids.
- `Abandon` continues to work as defined in spec 23. A command submitted after the run has ended is rejected with `RUN_ENDED`.

### 5.2 `GO_TO` effect

Extend the closed effect vocabulary from spec 24 with this exact shape:

```json
{ "type": "GO_TO", "place": "stairs" }
```

`GO_TO` is valid only if the pack declares `PLACES`, and `place` must reference a declared place. It sets the current place to the target regardless of adjacency; it is an authored state effect, not a player navigation command. It appends the target to `visitedPlaces` if this is its first visit. Applying it to the current place is a no-op for state/history.

Apply it in the list order defined by spec 24. It never changes `sceneId`, the `visited` scene list, or `RunState.endReason`. It does not interrupt the current effect list. If an option has both `effects: [{"type":"GO_TO", ...}]` and `next`, the effect runs first according to spec 24's step algorithm; scene movement then occurs as usual.

No `GO_TO` effect is allowed in a pack that lacks `PLACES`. A `GO_TO` target is a `ReferenceIndex` reference of kind `place`, not a `scene` reference. Scene navigation remains authored through existing `next` / `branches` fields.

### 5.3 Place-aware conditions

Add two leaf types to the condition vocabulary from spec 24:

| Type | Shape | True when |
|---|---|---|
| `AT_PLACE` | `{"type":"AT_PLACE","place":"stairs"}` | `currentPlaceId` equals the declared place id. |
| `VISITED_PLACE` | `{"type":"VISITED_PLACE","place":"armory"}` | The id is present in the unique `visitedPlaces` history. |

They work as children of `ALL`, `ANY`, and `NOT` with the same depth/node limits and deterministic evaluation as every other condition. They are invalid when `PLACES` is absent. Place references go through `ReferenceIndex` kind `place`, and malformed shapes use `CONDITION_INVALID` per spec 24.

## 6. Run semantics

### 6.1 Start

1. Validate pack, locale, start inputs, and features as defined by spec 23/24. `PLACES` is supported after this spec is implemented; `GENERATION` remains unavailable until its owning spec.
2. If `PLACES` is enabled, initialize `currentPlaceId` to `PlaceMap.startPlace` and `visitedPlaces` to `[startPlace]`. Otherwise initialize them to `null` and `[]`.
3. Initialize rule state and enter the authored start scene as described in spec 24. Scene `onEnter` effects may contain `GO_TO`; such an effect may move the current place away from the map's start place before the first `View` is returned.
4. Evaluate objectives and build the initial `View` using spec 24's order. `View.places` is non-null only for a Places-enabled run.

### 6.2 Accepted `Move`

For an active run with `PLACES` and a legal target:

1. Increment `step` once before evaluating any step-dependent conditions.
2. Update current place and first-visit history. Set `updatedAt` once via the injected clock after the accepted step has been applied.
3. Run objective evaluation using the existing spec-24 fixed-point algorithm, so `AT_PLACE` / `VISITED_PLACE` can complete objectives. No scene entry effects run because the scene did not change.
4. Perform the standard end check if objective effects request `END_RUN`.
5. Build the new view and return an accepted result. Events are returned in deterministic emission order.

### 6.3 Other accepted commands/effects

The spec-24 command algorithm remains authoritative. `GO_TO` participates wherever ordinary effects are applied (option effects, scene `onEnter`, and objective completion effects). It updates place state immediately in list order; objectives are evaluated at spec-24's defined point after the accepted operation. Any resulting view reflects the final current place after all effects in that atomic step.

Rejected commands follow the spec-23/24 invariant: no state, view, events, step, or timestamp changes. Do not catch programming errors by pretending a move succeeded.

## 7. Snapshot resume and pack-version compatibility

Preserve spec 24's pack-version policy: same-major pack versions can be migrated, while a different major version returns `SNAPSHOT_PACK_MISMATCH`. Do not create a second independent version policy for places.

- When either place field is absent or `currentPlaceId` is null for a Places-enabled pack, initialize it from that loaded pack's `startPlace` and initialize/repair `visitedPlaces` to include `[startPlace]`. This is the default for snapshots written before 24.1 and for additive optional fields omitted by older codecs; no warning is required just for missing fields.
- A pack without `PLACES` resumes with `currentPlaceId == null` and empty `visitedPlaces`. A snapshot containing non-empty place state for that exact pack version is `SNAPSHOT_INVALID`.
- For a same-major migration between different pack versions, a `currentPlaceId` that was removed falls back to the new `startPlace`, and unknown ids are removed from `visitedPlaces`; report `SNAPSHOT_STATE_PRUNED` WARNING. Ensure the fallback place is recorded in `visitedPlaces` if not already present.
- For an exact same-version snapshot, a non-null current place id or any visited-place id that does not exist, or any malformed place-state type, is `SNAPSHOT_INVALID`; do not silently repair corruption when there was no version migration.
- A different major version remains `SNAPSHOT_PACK_MISMATCH`. If the snapshot's stored scene is missing, spec 24's `SNAPSHOT_INVALID` behavior still applies; Places migration never remaps scene ids.
- Resume must not re-run scene entry effects, `GO_TO` effects, objective completion effects, or emit events again. Restore saved state after validating/migrating it.
- The `snapshotVersion` stays `1`; place fields are additive optional fields inside `state`. Do not add a separate places snapshot or storage port.

## 8. Console host changes

The console remains a host of the public API; it must not parse `places.json` or access internal `PlaceMap` types. Render only `View.places`.

### 8.1 Rendering

After the existing status/objective/outcome lines and before scene options, render the following when `View.places != null` and the run is active:

```text
Place: Cell
Moves:
  move corridor — Corridor
```

Use the resolved place label for `Place` and destination labels. If no move is available, render `Moves: none`. Render destinations in `availableMoves` order and show the command id exactly as `move <place-id>`. Do not render coordinate internals unless a future console spec asks for a map visualization. A pack without Places adds no output. In an ended view, render only `Place: <label>` and no movement choices; do not suggest commands that cannot be accepted.

The map block is informational and additive; keep scene blocks, status/objective/outcome formatting, option numbering, `[Enter]`, `[end]`, and `[abandoned]` semantics unchanged. Since `fixture-text-dungeon` will now have Places enabled, update its existing golden transcripts with the new `Place` / `Moves` lines at each active view. `fixture-minimal` golden output must remain unchanged.

### 8.2 Input

Accept `move <place-id>` and the short alias `m <place-id>` (case-insensitive command word; place ids retain their authored case-sensitive validity, though valid ids are lowercase). Convert either input to `Command.Move(placeId)`.

Keep existing input behavior: numbers choose options, option ids choose options, empty input advances, and `q` abandons. A command beginning with `move ` or `m ` must be recognized before generic option-id matching so a place id cannot be mistaken for a scene option. Unknown or illegal destinations flow through normal `StepResult.issues` rendering; do not add a second movement validator in the CLI.

- `ReferenceIndex` definitions and references must retain file paths and JSON pointers for actionable errors.

## 11. Testing and acceptance

All tests run under the existing engine Maven build and do not need Spring, database, Node, HTTP, an LLM key, or the application host.

### Unit and validator tests

- `places.json` parses; schema version, required/unknown fields, id formats, limits, duplicate place ids, duplicate link pairs, self-links, start-place errors, invalid coordinates, and unknown layout kinds.
- All locale label/description keys must exist. Missing key in any declared locale is an ERROR through the reference index.
- `PLACES` requires `places.json`; `places.json` without `PLACES` fails. A pack without either remains valid and unchanged.
- Link endpoints, start place, `GO_TO`, `AT_PLACE`, and `VISITED_PLACE` references resolve through the shared `ReferenceIndex`. Do not rely on validator order.
- Reachability respects direction and bidirectional links; unreachable places warn only.
- `Move` succeeds along a valid directed/bidirectional link; rejects unknown and disconnected targets; is independent of scene command mode; increments step once; updates time via injected clock; records each place once in first-visit order.
- Failed `Move` returns the expected issue and leaves `View`, events, state, timestamp, step, and snapshot byte-for-byte equivalent.
- `GO_TO` ignores adjacency, is list-ordered, appends first visits, is a no-op for the current place, and cannot be used without `PLACES` or with a missing target.
- `AT_PLACE` / `VISITED_PLACE` truth tables work as leaf and composite conditions, including objective completion following a `Move` or `GO_TO`.
- `View.places` resolves localized labels/descriptions, preserves stable ordering, lists only legal direct moves, and is null when Places is disabled.
- Snapshot round-trip; pre-24.1 missing-field defaults; current-place pruning and visited-place pruning on same-major migration; exact-version corruption invalidation; major version mismatch; resume does not replay effects or emit events.
- Console parser accepts `move <id>` and `m <id>`, rejects malformed/unavailable moves through ordinary issues, and preserves existing choice/advance/abandon behavior.

## 13. Decisions on Open Questions

No decisions remain open. The implementation uses these defaults:

1. **Should the map change the scene automatically?** In everyday terms, moving your marker on the map could also jump the story to a scene. Options: couple each place to a scene, or keep movement and story choices independent. **Decision used: independent.** `Move` and `GO_TO` change map position only; ordinary scene navigation continues through `next` / `branches`. A later spec can add an explicit binding if a concrete game needs it.
2. **Should every map edge be two-way?** Options: make every link bidirectional or mark direction explicitly. **Decision used: explicit `bidirectional` boolean**, so one-way routes are possible without a new schema later.
3. **Should the engine calculate routes or distances?** Options: infer movement from coordinates, or treat positions as drawing hints and links as the rules. **Decision used: links alone govern movement.** No path-finding, travel costs, or distance rules in 24.1.

## Notes

- The engine's coordinate/layout metadata is descriptive only. A host may render `GRAPH`, `GRID`, `HEX`, or `FREEFORM` differently, but the engine uses declared links—not positions—to determine legal movement.
- `Move` and `GO_TO` intentionally have different semantics: `Move` enforces an adjacent link; `GO_TO` is an explicit authored relocation and may target any declared place.
- Places are pack data, not a host screen. Console and web hosts receive the same resolved `PlacesView`.
- Verification expected for implementation: Maven and JDK 25 build, golden transcript execution, and Windows console checks must be reported after they are actually run. A document-level check is not a substitute for those tests.
