# Spec 26.1 — Generation Contracts and Runtime Integration

**Type:** Implementation specification  
**Parent:** Spec 26 — Generation Pipeline  
**Status:** Implemented (2026-10-14)
**Primary outcome:** A pack can run through a generated-game path in the CLI, use a configured real provider, and continue through multiple turns while the existing engine remains authoritative.

---

## 1. Context

The current implementation baseline, as described in the repository investigation, includes the provider-neutral `TextGenerator` port, an Anthropic adapter, pack loading and validation, the existing `Engine` / `Run` flow, authored `Scene` content, and input/privacy guard components.

The CLI currently plays authored scenes, but does not yet exercise a complete generated-game flow. The missing pieces include a versioned generation catalog, generation-pack validation, typed stage artifacts, the scenario/cast/quest/scene stages, semantic validation and repair/fallback behavior, lazy generated-scene resolution, and explicit CLI verification that distinguishes a real provider response from mock output or fallback content.

Spec 26.1 closes that implementation gap. It clarifies internal contracts between Spec 26 and the existing runtime without replacing the work reserved for Spec 27.

> **Roadmap note:** Existing specification documents may map some capabilities to different spec numbers. Do not silently renumber existing specs as part of this implementation. Update the roadmap/status documentation with a short reconciliation note and preserve the established Spec 27 boundary.

## 2. Goals

1. Provide a complete, runnable generated-game path from the CLI.
2. Validate all generation configuration and fallback resources before making provider calls.
3. Keep model output bounded to narrative/content fields defined by trusted pack templates.
4. Reuse the existing engine, run, rules, state, scene, and validation boundaries.
5. Support bounded repair and deterministic fallback behavior.
6. Generate scenes lazily as the player advances, instead of generating the entire game up front.
7. Resume a saved generated session without silently regenerating different content.
8. Test the pipeline comprehensively with a deterministic fake provider and provide an opt-in smoke test against an actually configured provider.
9. Preserve existing authored-pack behavior and keep provider-specific code outside engine core.

## 3. Non-goals

Spec 26.1 does **not** implement the full public Engine API, a new public session lifecycle, an offline queue, a client rendering layer, or the CapyBee Polish content pack. Those remain in their existing roadmap locations, including Spec 27 for API/session lifecycle concerns.

Do not replace the engine's state machine or create a parallel generated-game engine. Do not let model output define game rules, state transitions, conditions, effects, routes, objective-completion rules, trusted identifiers, or input/safety policy.

Do not require a live provider for ordinary unit or integration tests.

## 4. Core design rules

### 4.1 The engine stays authoritative

Generated content is data consumed by the existing engine, not a second source of game logic.

- The engine owns stable IDs, state mutations, conditions, effects, objective completion, legal choices, scene transitions, and snapshots.
- Templates declare the slots and choice/action keys which generated content may fill.
- Model output may supply bounded text and labels for those declared slots.
- Unknown IDs, new executable rules, arbitrary routes, undeclared choices, or model-supplied state changes must be rejected.
- A generated scene must be composed into the existing `Scene` representation, then validated through the existing validation/runtime boundaries before it can be used.

### 4.2 Pack validation precedes provider use

A generation-enabled pack is rejected before a provider request if its catalog, template references, stage configuration, locale configuration, fallback resources, or trusted engine references are invalid. Invalid fallback content must never be discovered only after generation has failed.

### 4.3 Fail safely and visibly

Each stage has an explicit result status. A fallback is a successful recovery path, but it is not reported as generated content. Provider failure, invalid model output, repair, and fallback are distinguishable in internal results and CLI diagnostics.

### 4.4 No partial state transition

If a choice requires a next generated scene, resolve and validate that scene before committing the choice's state changes and transition. If resolution fails, the run remains at its previous committed state. Follow the current runtime's transaction/snapshot pattern where possible; do not add a second independent mutation path.

### 4.5 Keep private content out of logs

Do not log API keys, full provider requests or responses, raw player free text, unredacted prompts, or generated narrative by default. Diagnostics should use stage names, status, stable error codes, elapsed time, provider/model identifiers where available, and usage/cost metadata where available.

## 5. Pack format and generation catalog

### 5.1 Catalog file

Add a versioned pack-level catalog at:

`generation/catalog.json`

The catalog is the entry point for generation-specific configuration. It must be parsed and validated by the pack-loading/validation path. Keep the existing locale-specific `prompts/<locale>/system.md` as pack instruction material; do not treat that file alone as a complete generation catalog.

The catalog must describe:

- catalog schema version;
- supported and default locales;
- enabled generation stages and their template IDs;
- stage ordering/dependencies;
- fallback resource references for every stage that can be invoked;
- limits or references to limits used by the pipeline;
- the trusted scene/choice/template definitions used to compose generated content.

The catalog should reference existing Spec 24 template definitions rather than duplicating their content in a second template system. Reuse existing pack conventions when they already provide an equivalent representation. If a required representation does not exist, introduce the smallest versioned addition and document it in the pack-format documentation.

### 5.2 Stage model

Support these logical stages:

1. `THEME` — optional, when configured by the pack.
2. `SCENARIO` — establishes the bounded narrative premise and scenario outline.
3. `CAST` — fills declared actor/character content slots.
4. `QUEST` — fills mission/objective presentation text that references existing trusted objectives.
5. `SCENE` — fills the next declared scene/beat template; invoked initially and lazily as required by play.

The enabled stages and dependencies must be explicit. Do not assume every pack needs a generated theme. `SCENE` must be available for lazy generation when a run reaches a declared generation slot.

### 5.3 Fallback resources

Every enabled stage must have a valid fallback defined by the pack. Fallback resources must be loaded and validated before the first provider call.

- The fallback must be represented in the same typed artifact contract, or be a reference to a fully validated authored resource that the runtime can use without model output.
- A scene fallback may reference an existing authored scene if the pack declares it as a valid fallback for that slot.
- A fallback cannot introduce trusted IDs, choices, effects, or rules that would be disallowed in generated output.
- If a required fallback is missing or invalid, pack validation fails before the run starts.

Use pack-relative paths or stable pack IDs consistent with existing loader conventions. Reject path traversal and references that escape the pack root.

### 5.4 Locale selection

Resolve locale in this order:

1. explicit CLI/run locale;
2. configured pack default locale;
3. existing product default, if one already exists.

The resolved locale must be supported by the catalog. Do not silently switch to another locale. If locale fallback is supported by the catalog, it must be explicit and validated at pack-load time.

### 5.5 Compatibility with authored packs

Packs without generation configuration remain playable through the existing authored-scene flow. The default CLI behavior must not unexpectedly invoke a provider. Generation must be explicitly requested or enabled through the documented pack/run configuration.

## 6. Typed artifact contracts

Represent each validated stage result as an immutable, typed artifact. Use the project's existing language and serialization conventions.

Every artifact must carry or be associated with:

- artifact schema version;
- pack ID and pack version;
- resolved locale;
- stage name;
- template ID;
- an engine-assigned artifact ID;
- stage outcome/provenance (`GENERATED`, `REPAIRED`, or `FALLBACK`);
- the validated content payload.

Do not accept an engine-assigned ID from model output. The engine assigns the artifact ID after validation. Include provider/model/usage metadata in separate execution metadata, not in player-facing content.

### 6.1 Scenario artifact

May contain only declared scenario fields, for example title, premise, setting description, tone, narrative constraints, and a bounded beat/slot outline.

It must not define game mechanics, arbitrary map topology, state variables, objective-completion criteria, or executable rules. References must resolve to declared template slots or trusted pack entities.

### 6.2 Cast artifact

May fill declared actor/persona slots with bounded descriptive text, display names, voice/style notes, and other template-approved narrative fields.

The set of actor slots and all runtime actor IDs are trusted inputs. The model must not add unbounded actors, invent runtime identifiers, or change actor stats/permissions. Enforce configured limits on names, descriptions, dialogue, and number of entries.

### 6.3 Quest artifact

May fill narrative titles, descriptions, hints, and presentation text for objectives already declared in the pack.

Every objective reference must resolve through the pack's trusted reference index. The artifact must not create new objective IDs, completion rules, state effects, dependencies, or rewards.

### 6.4 Scene artifact

May fill narrative slots in a trusted scene/beat template: scene title, narration, bounded dialogue entries, and labels for predeclared choices.

The trusted template supplies scene identity, actor references, choice/action keys, routes, conditions, effects, objective references, and input policy. Model output must not supply or alter those fields. A scene artifact is not usable until composed into the existing `Scene` shape and passed through applicable validators.

### 6.5 Closed schemas

Parse structured output using strict, versioned schemas:

- reject malformed JSON;
- reject unknown properties rather than silently ignoring them;
- reject missing required properties;
- validate string/count/length bounds;
- validate enums and all references;
- reject duplicate or conflicting entries;
- reject model content that attempts to supply control fields;
- apply the existing safety/privacy checks to generated text before it becomes player-visible.

Do not deserialize model output directly into trusted runtime/domain objects if that allows model output to set runtime-owned fields.

## 7. Pipeline and provider boundary

### 7.1 Provider-neutral port

Use the existing `TextGenerator` abstraction and request/result types. The pipeline should depend on the port, not directly on the Anthropic SDK.

- The core pipeline must be injectable with a `TextGenerator`.
- Provider adapters and credentials remain outside engine core.
- Keep deterministic fake implementations available for unit/integration tests.
- The provider configuration must never require a secret in command-line arguments or committed pack files.
- Missing provider configuration must produce a clear non-secret diagnostic and the configured fallback behavior.

### 7.2 Stage execution

For a new generated run, execute the configured stages in dependency order. At minimum, a generation-enabled flow must produce or fall back for scenario, cast, quest, and the initial scene. Generate later scenes on demand when the player reaches a declared generation slot.

Each stage should receive only the minimum data required: relevant pack instructions, trusted template/schema, validated prior artifacts, locale, sanitized user/player input when applicable, and bounded state/context. Do not send the entire run history by default.

Do not allow player free text to bypass the Spec 25 input/safety pipeline. Any player input sent to a provider must first pass the existing normalization, PII handling, and input guard path.

### 7.3 Validation, repair, and fallback

For each stage:

1. Build a bounded request from trusted pack/template data and validated prior artifacts.
2. Call the injected `TextGenerator` within the configured limits.
3. Parse and validate the response against the stage's closed schema and semantic rules.
4. Apply output safety/privacy checks.
5. If valid, accept the artifact with status `GENERATED`.
6. If output is invalid but the provider call itself succeeded, allow **at most one repair attempt** for that stage. The repair request should include concise validation error codes and only the minimum necessary sanitized context.
7. Validate the repaired response through the full validation path. If valid, accept with status `REPAIRED`.
8. If the provider is unavailable, a call fails, limits are exhausted, or the original plus one repair response remain invalid, use the validated fallback and mark the result `FALLBACK`.

Provider/network/authentication failures should not trigger a repair request to the same unavailable provider. They should go directly to the fallback path. Do not retry indefinitely. A fallback result must be distinguishable from generated output in logs, CLI summaries, test assertions, and run metadata.

If a required fallback cannot be used despite initial validation (for example due to an unexpected runtime corruption), fail the operation with a safe diagnostic and do not commit a partial state transition.

### 7.4 Budgets and limits

Add explicit, configurable limits for:

- total provider calls per run;
- maximum calls per stage;
- maximum output tokens or equivalent response size per call;
- maximum input/context size per call;
- maximum lengths/counts for generated fields;
- a repair limit fixed at zero or one, with the Spec 26.1 default set to one;
- optional cost budget when the provider supplies usage and a price configuration is available.

The pipeline must stop requesting content when a limit is reached and use the stage fallback. Limits must have safe defaults and be testable without a live provider. If usage or provider pricing is unavailable, report cost as unknown rather than inventing it. Cost accounting must not claim to be complete when data is missing.

The pipeline must expose a content-free execution summary: stage, status, call count, elapsed time, usage/cost when available, and stable validation/failure codes.

## 8. Runtime integration and lazy scene resolution

### 8.1 Reuse the existing runtime

Integrate generated content through the current `Engine`, `Run`, `Scene`, and rules/state model. Keep authored `SceneSet` or its current equivalent working as before. Prefer a small scene-resolution abstraction or equivalent seam over branching generated-game logic throughout the engine.

The resolver should return either a validated scene plus provenance metadata or a typed failure. It must not mutate run state while resolving content.

### 8.2 Lazy generation

A generated run must not need to generate every possible scene at start. It should generate the initial scene and then resolve a scene only when the player's chosen action/route reaches a declared generation slot.

Cache each accepted scene artifact for the lifetime of the run. Re-visiting a generated slot must reuse the same validated artifact unless the pack explicitly defines a different, deterministic versioned behavior. Do not silently regenerate content on every visit.

### 8.3 Atomic choice/transition

When a choice needs a generated destination scene:

1. Validate the selected choice against the current trusted scene.
2. Determine the trusted destination slot and required generation context.
3. Resolve, compose, and validate the destination scene without mutating run state.
4. Commit the existing engine choice/effects/transition only after destination resolution succeeds.
5. Record the scene artifact/provenance as part of the run's generated content state.

If resolution fails, the current run state and current scene remain unchanged. Do not apply choice effects twice when retries or fallback are involved.

### 8.4 Snapshot and resume

A saved generated run must resume with the same already accepted scenario/cast/quest/scene artifacts. It must not silently ask the provider to recreate content that was already shown to the player.

Use the existing snapshot mechanism where possible. Persist either the validated run-scoped artifacts themselves or a stable, durable, versioned reference to an artifact store. For this implementation, prefer including the bounded validated artifacts in the snapshot unless current project constraints make that impractical; document any alternative and its failure semantics.

Snapshot content must not include API keys or provider secrets. Ensure snapshot serialization/deserialization validates schema versions and artifact integrity. If a saved snapshot references an artifact version that cannot be loaded safely, fail with a clear recovery diagnostic rather than silently substituting different narrative content.

Spec 27 may formalize the public session lifecycle and external persistence API. Spec 26.1 must provide the internal artifact/snapshot contract and an integration test demonstrating continuity for the current CLI/runtime.

## 9. CLI integration

### 9.1 Modes

Preserve the current authored-pack command and behavior. Add a clearly documented explicit generated-play mode; use the existing CLI grammar and argument conventions where possible. The exact spelling of the new subcommand/flag may follow the current parser, but it must be unambiguous and covered by help text and tests.

The generated mode must accept a pack path and locale/configuration using existing CLI conventions. Provider selection/configuration must be injectable/configurable without placing credentials on the command line.

### 9.2 Output

The CLI should display:

- player-facing narrative and valid choices;
- a concise stage summary identifying `GENERATED`, `REPAIRED`, and `FALLBACK` results;
- a safe diagnostic if generation cannot continue;
- enough metadata to distinguish mock-provider tests from a real provider smoke test.

Do not print API keys, raw provider request/response bodies, raw free text, or full prompts. Detailed debugging may expose stable error codes but should not leak content.

### 9.3 Real-provider smoke test

Provide an opt-in command or mode that uses the actual configured provider adapter and real credentials from supported environment/configuration sources. Its name/help must make clear that it may incur provider cost.

A smoke test succeeds only when the live configured provider was actually called and all required stages for the smoke path—including at least one lazily generated scene—are accepted as `GENERATED` or `REPAIRED`. Fallback content, mock output, or a missing credential must not count as a successful live generation test. On failure, exit non-zero and state the failed stage/status without exposing secrets or content.

The smoke test must be opt-in and must not run during the default build/test lifecycle.

## 10. Error model and observability

Use typed failure categories or stable error codes. At minimum distinguish:

- invalid pack/catalog/template/fallback configuration;
- unsupported schema version or locale;
- provider not configured;
- provider unavailable/authentication/request failure;
- provider/budget limit reached;
- malformed structured output;
- schema validation failure;
- semantic/reference validation failure;
- output safety/privacy rejection;
- fallback selected;
- scene resolution failure;
- snapshot/artifact version mismatch.

Avoid using exception-message text as the only machine-readable signal. Provider response bodies may be useful for restricted local debugging, but must not be emitted in normal logs, returned to player-facing output, or persisted in snapshots.

Execution metadata should contain only what is needed for diagnostics and cost tracking. Any logging of generated narrative or player input must follow the privacy requirements of Spec 25 and be explicitly opt-in if the existing policy permits it.

## 11. Required tests

All deterministic tests must use a fake/scripted `TextGenerator` or adapter stub. Do not use real network calls in the normal test suite.

### 11.1 Pack/catalog validation

- Valid generation-enabled pack loads successfully.
- Missing/malformed catalog, unsupported catalog version, unknown template, unsupported locale, missing fallback, unsafe path, unresolved trusted reference, and invalid fallback all fail before the first provider call.
- A pack without generation configuration still follows the authored path unchanged.
- Existing pack/scene validation tests remain green.

### 11.2 Artifact and stage validation

- Each stage accepts valid output and rejects malformed JSON, unknown fields, missing fields, over-limit text/counts, invalid references, undeclared choices, and attempts to set trusted control fields.
- Output safety/privacy validation is invoked before content is accepted.
- Artifact IDs and provenance are assigned by the engine, not trusted from the model.
- Stage ordering and dependencies are tested, including the optional theme stage when enabled.

### 11.3 Repair, fallback, and budget behavior

- Valid first response yields `GENERATED`.
- Invalid first response followed by valid repair yields `REPAIRED`.
- Invalid first and repair responses yield `FALLBACK`.
- Provider unavailable/authentication failure yields `FALLBACK` without a repair request.
- Budget exhaustion yields fallback and does not exceed limits.
- Exactly zero or one repair request is made per stage; no unbounded retry loop is possible.
- Fallback results are never reported as generated.
- A fallback failure does not partially mutate the run.

### 11.4 Runtime behavior

- A scripted end-to-end test loads a generation pack, executes required initial stages, presents a scene, accepts a valid choice, lazily generates/resolves the next scene, and continues for several turns.
- The existing engine remains responsible for choice validation, effects, state, conditions, and objective progress.
- Repeated visits reuse the cached scene artifact.
- Failure resolving a destination leaves the run at the prior committed state with no duplicated effects.
- Snapshot/save-resume preserves accepted artifacts and continues without regenerating them.
- Existing authored-play and rules/state tests remain green.

### 11.5 CLI and live-provider distinction

- CLI help describes authored and generated modes and how provider configuration is supplied.
- CLI tests assert that stage status is visible and secrets/raw provider output are not printed.
- A fake provider can test a whole generated session without a network.
- The opt-in live smoke path cannot report success if credentials are missing, a fake provider is used, any required stage falls back, or no lazy scene was actually generated by the configured provider.
- The live smoke test is excluded from ordinary `verify`.

## 12. Implementation sequence

Implement in small, verifiable steps:

### Milestone A — Pack contract

1. Reconcile the roadmap/status documentation without renumbering specs.
2. Define `generation/catalog.json` against the current Spec 24 template model.
3. Add catalog parsing and pack-load validation for stages, templates, locales, fallbacks, safe paths, and trusted references.
4. Add a small generation-enabled fixture pack with validated fallback resources.
5. Prove invalid generation configuration fails before any provider call.

### Milestone B — Artifacts and pipeline

1. Add immutable versioned artifact types and closed-schema parsers.
2. Implement semantic/reference validation and output safety checks.
3. Implement stage orchestration via injected `TextGenerator`.
4. Implement one repair attempt, validated fallback, per-run/per-stage budgets, and content-free execution metadata.
5. Test every success, failure, repair, and fallback branch with scripted provider responses.

### Milestone C — Runtime and snapshots

1. Add a scene-resolution seam that supports both authored and generated content.
2. Compose validated scene artifacts into the existing `Scene` shape.
3. Implement lazy generation and per-run artifact caching.
4. Ensure choice/transition processing is atomic with respect to destination-scene resolution.
5. Extend existing snapshots or add a versioned snapshot contribution for generated artifacts.
6. Test save/resume continuity and no-partial-mutation behavior.

### Milestone D — CLI and end-to-end proof

1. Add an explicit generated-play mode while preserving authored-play defaults.
2. Wire a real configured provider adapter through dependency injection/configuration.
3. Add a scripted end-to-end multi-turn test.
4. Add an opt-in live-provider smoke path with strict pass/fail semantics.
5. Run the complete module verification and report which checks were mock-based versus live.

Suggested verification from the repository root:

```bash
mvn -f app/engine/pom.xml clean verify
```

Run the real-provider smoke test separately and only when explicitly requested/configured. The default build must remain deterministic and must not require credentials or network access.

## 13. Definition of done

Spec 26.1 is complete when all of the following are true:

- A valid generation-enabled pack can be selected in the CLI generated-play mode.
- The catalog, templates, locale, trusted references, and fallbacks are validated before provider use.
- A configured real provider can generate the initial content and at least one later scene.
- A player can make choices and continue through several turns using the existing app/engine/runtime.
- The engine, not the model, remains authoritative for all rules, state changes, legal choices, routes, and objective completion.
- Invalid output gets at most one repair attempt, then a validated fallback; provider failure goes directly to fallback.
- Budgets are enforced and the stage status makes fallback visible.
- No choice/state mutation is committed when required destination resolution fails.
- Saving and resuming preserves accepted generated artifacts.
- The authored-pack CLI path and existing tests remain unchanged and green.
- Unit/integration/E2E tests use deterministic providers and require no network.
- The opt-in live smoke test fails rather than passing through mock/fallback content.
- `mvn -f app/engine/pom.xml clean verify` passes.
- Documentation clearly marks the boundary between this internal generation/runtime integration and the public API/session lifecycle work in Spec 27.

## 14. Handoff notes for Spec 27

Spec 27 should build on the artifact and snapshot contracts established here. It may define the public API and supported external session lifecycle, but should not need to redesign the internal stage artifacts, fallback semantics, generated-scene resolution, or continuity guarantees.

If implementation reveals that the existing snapshot or runtime boundaries cannot support the required behavior, document the concrete incompatibility and propose the smallest compatible change before introducing a new parallel lifecycle.
