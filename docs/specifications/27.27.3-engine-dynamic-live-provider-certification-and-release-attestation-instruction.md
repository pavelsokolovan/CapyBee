# Spec 27.27.3 — Dynamic Live-Provider Certification and Release Attestation

**Type:** Implementation instruction
**Parent:** Spec 27.27 release readiness, following the atomic recovery completion in Spec 27.27.2
**Depends on:** Specs 27.17–27.27.2, especially trusted dynamic start, generator profiles, bounded blueprint generation and repair, semantic validation, compiled closed mechanics, dynamic snapshot v2, exact resume, Pack live certification, `DynamicCertificationCommand`, `CertificationCommand`, `AnthropicTextGenerator`, packaged profiles and offline certification
**Baseline:** Inspected clean local `main` at commit `ed6f015` on 2026-10-28. Dynamic offline certification starts a fixture-backed game, checkpoints it and finishes it in a second provider-disabled JVM. Pack certification already supports explicit live mode, pinned provider/model identity, reviewed pricing, call/cost admission, token accounting, redacted evidence directories and certificate expiry policy. Dynamic certification accepts only offline fixture inputs and writes one minimal JSON file; it has no live-provider path, pricing/cost guard, full evidence schema or release attestation. No network request or paid provider call was made while preparing this document.
**Status:** Ready for implementation
**Primary outcome:** Add an explicitly authorized, cost-bounded live certification path for the complete dynamic-game pipeline and produce privacy-safe evidence that attests the exact distribution, profile, provider/model, policy versions and restart behavior without storing generated prose, blueprints, prompts, setup text or credentials.
**Repository location:** `docs/specifications/27.27.3-engine-dynamic-live-provider-certification-and-release-attestation-instruction.md`

---

## 1. Purpose

The dynamic-game implementation is playable and deterministically certifiable offline, but its real provider boundary is not yet release-certified. The next release slice must exercise this exact path:

```text
explicit paid-operation confirmation
  -> zero-call local preflight
  -> validated packaged generator profile and public certification setup
  -> real structured provider calls through normal metering/review
  -> complete blueprint validation and trusted compilation
  -> atomic dynamic activation
  -> deterministic engine-guided play
  -> durable checkpoint and fresh provider-disabled JVM
  -> exact completion without blueprint regeneration
  -> redacted evidence and release attestation
```

This is certification infrastructure. It does not add a provider shortcut, weaken the dynamic trust boundary or turn live certification into an ordinary test/build action.

## 2. Scope

### 2.1 In scope

- Add `certify --mode live --dynamic` to the released CLI.
- Reuse the existing live provider configuration, pricing validation, call admission, cost accounting and bounded error vocabulary.
- Add a versioned dynamic live certification suite with public, non-sensitive setup presets and deterministic route policy.
- Exercise the normal trusted dynamic start rather than calling generation/compiler internals directly.
- Verify a real fresh-process resume with the provider disabled and zero calls after checkpoint.
- Produce schema-validated, checksummed and atomically finalized evidence.
- Bind evidence to the exact distribution, profile identity/fingerprint, provider/model, pricing digest and engine policy versions.
- Define canary versus full scope and the validity/expiry rules for a dynamic live certificate.
- Add deterministic fake-provider, adversarial, failure and redaction tests that run without network access.
- Update packaging, launcher help and certification documentation.

### 2.2 Out of scope

- Making a paid call during normal Maven verification, packaging or offline certification.
- Automatically running a paid call during implementation without separate explicit operator authorization.
- Adding another provider adapter, changing provider prices or embedding a pricing file in source control.
- Certifying arbitrary user profiles, free-text suggestions or private setup data.
- New blueprint fields, mechanics, rule types, snapshot/store versions or gameplay behavior.
- Treating creativity, prose style, fingerprint uniqueness or keyword matching as a deterministic pass/fail condition.
- Uploading evidence, signing certificates with an unmanaged key or creating a remote certificate service.
- Replacing the existing Pack live certificate or offline dynamic certificate.

## 3. Command contract

The authoritative live command is:

```text
java -jar bin/engine-cli.jar certify --mode live --dynamic --scope canary|full \
  --profile-dir profiles/generic-adventure \
  --suite certification/dynamic-live-v1/suite.json \
  --pricing-file <reviewed-pricing.json> \
  --max-provider-calls <positive-integer> \
  --max-cost-usd <reviewed-decimal-limit> \
  --evidence-dir <directory> \
  --confirm-live-provider-cost
```

The launcher may expose the same operation through `./dev.ps1 game-certify-live -- --dynamic ...`, but the shaded-JAR command is the compatibility contract.

Live dynamic mode:

- requires `GENERATION_PROVIDER_MODE=certification`;
- requires an explicitly pinned `GENERATION_MODEL_ID` matching the pricing document;
- reads the provider credential only from the provider adapter's approved environment variable;
- rejects `ANTHROPIC_DEBUG=true` and any provider debug/body logging;
- requires confirmation, pricing, maximum calls and maximum cost;
- rejects `--fixture-dir`, `--offline`, Pack arguments and ambiguous source options;
- never accepts suggestion text, prompts, API keys, model overrides or pricing values through generic setup arguments;
- validates all paths, schemas, limits, environment state and evidence destinations before the first call.

`--help` and all invalid/preflight paths make zero provider calls. Preserve exit semantics: `0` pass/help, `2` invalid/preflight, `3` local/evidence failure and `5` completed certification failure.

## 4. Certification scopes

### 4.1 Canary

Canary is diagnostic and never yields `live-certified` status. It performs one trusted dynamic start using a fixed public setup from the suite, verifies the accepted snapshot and applies at least one normal command. It records provider/model/usage/cost observations and all trusted fingerprints, then ends without claiming full restart coverage.

### 4.2 Full

Full certification performs at least two independent confirmed starts using two bounded public preset combinations and fixed suite seeds. Both must pass the normal input guard, blueprint parser/reviewer, semantic validator, mechanics binder, compiler, definition verifier, presentation materializer and atomic activation boundary.

For at least one run, certification must:

1. advance through the normal session command path to a declared checkpoint;
2. close the player and local store cleanly;
3. start a new JVM with provider mode disabled and no provider credential inherited;
4. reopen the same store and exact dynamic snapshot;
5. complete the game through the normal runtime within profile path limits;
6. prove the run ID, game/definition fingerprints, revision and provider-call total are continuous;
7. prove zero blueprint calls and zero accepted-artifact regeneration after restart.

The second run proves another valid independent generation/compilation path and may complete in one process. Fingerprint equality or inequality is recorded only as a diagnostic. It is not a creativity assertion and cannot fail an otherwise valid certificate.

All completed games may end in any engine-supported `ResultClass` reachable from their accepted definitions. Certification proves safety, validity and operability, not a predetermined story result.

## 5. Suite contract

Add a packaged `dynamic-live-v1` suite with a strict JSON Schema. It contains only public engine-owned data:

- suite/schema version and profile identity requirements;
- canary and full case IDs;
- locale, length preset, challenge preset and other public option IDs;
- deterministic seeds and checkpoint bounds;
- maximum accepted commands derived within profile ceilings;
- required certification capabilities and threshold profile ID.

The suite must not contain free-text suggestions, generated prose, expected keywords, prompts or provider output. Load the profile through `GeneratorProfileLoader`, resolve every case through `PreparationPresetResolver`, and reject stale/unknown preset IDs before provider construction.

Route execution must inspect the trusted materialized runtime view and select enabled options using one documented deterministic engine-owned policy. It must not parse narration, depend on model-authored choice labels or execute provider-produced commands. Enforce a hard command bound from the accepted profile and fail closed on cycles, missing choices, invalid endings or inconsistent revisions.

## 6. Provider and cost boundary

Use one shared observing/admission wrapper for Pack and dynamic live certification where practical. Every provider attempt, including parse repair and lazy scene generation, must:

- reserve one call and the configured conservative maximum cost before dispatch;
- be rejected before dispatch if the call or cost ceiling would be exceeded;
- use the exact configured provider and model;
- enforce the existing per-attempt deadline;
- require returned model identity, finish reason and token usage;
- account input, output, cache-read and cache-write usage with decimal arithmetic;
- reconcile reserved and actual cost without allowing negative or floating-point drift;
- expose only stable codes and numeric metadata to certification evidence.

Cancellation and timeouts stop future calls but do not claim that an already submitted request was free. Provider errors, missing usage, model mismatch, malformed output, exhausted repair allowance or budget denial produce a failed/inconclusive certificate and never fall through to a false pass.

The process used after the restart must remove provider credentials and provider-mode variables from its environment. A successful offline fallback scene after restart is acceptable only when it is the persisted definition's normal bounded presentation fallback; blueprint regeneration is always forbidden.

## 7. Trusted orchestration

Live certification must invoke the same `DynamicStartCoordinator`, `RunSessionService`, metered generator, output reviewer, semantic validator, compiler and session store used by normal dynamic play. Do not create a certification-only bootstrap that bypasses confirmation, safety review, budgets, atomic publication or exact resume.

The certification preparation capability is constructed from the validated public suite case and is never serialized. Every live attempt receives a unique request ID and run ID. Idempotent polling/replay may return the stored result but must not duplicate provider calls.

The checkpoint and completion phases use the normal session command transaction. A failed start must not create a playable row; a failed replacement must preserve the previous current run; and a failed evidence write must not alter the game result or masquerade as a certification pass.

## 8. Evidence format

Create versioned JSON Schemas for dynamic certification manifest, summary, per-attempt provider observations and per-run evidence. Write evidence to `<certification-id>.incomplete`, fsync/validate it, produce `checksums.sha256`, then atomically rename it to `<certification-id>` only after finalization.

The manifest binds at least:

- certification ID, mode, scope, result, start/end timestamps and expiry;
- distribution ZIP and CLI JAR SHA-256 digests;
- suite digest and threshold profile version;
- generator profile ID, version and fingerprint;
- provider ID, exact returned model ID and reviewed pricing digest/timestamps;
- blueprint schema, validator, output-reviewer, compiler, generated-rule and snapshot contract versions;
- Java/runtime identifier and restart process count;
- total attempts, calls, tokens, cache usage, actual estimated cost and configured ceilings.

Per-run evidence contains only bounded structural facts: run ID, seed identifier, preset IDs, accepted/repair counts, scene/actor/objective/mechanics counts, revisions, result class, fingerprints, checkpoint continuity and provider calls before/after resume.

Evidence must never contain:

- prompts, responses, canonical blueprints or materialized localized content;
- title, premise, narration, choice labels, actor names or outcome descriptions;
- suggestions, setup transcripts, terminal transcripts or store/snapshot JSON;
- credentials, request headers, provider request IDs when they can identify account activity, local absolute paths or environment dumps;
- raw exceptions or provider bodies.

Redaction tests must scan every finalized and incomplete evidence file, stdout and stderr using fixture secrets and recognizable generated phrases.

## 9. Attestation and validity

A passing full dynamic live certificate attests only this tuple:

```text
distribution digest
+ dynamic-live suite digest
+ generator-profile identity/fingerprint
+ provider and exact model
+ pricing digest
+ threshold/policy versions
```

It expires 14 days after completion and becomes invalid immediately when any tuple member changes. Canary, failed, incomplete or expired evidence never grants `live-certified`. Offline certification remains `offline-ready` and is not upgraded by the presence of credentials.

The attestation is integrity-checked by digests and checksums; do not describe it as cryptographically signed unless a separately specified managed signing system exists. Do not bundle operator-produced live evidence or pricing into normal source/release archives by default.

## 10. Failure behavior

Define stable bounded codes for at least:

- invalid/missing profile, suite, pricing or evidence destination;
- provider mode, credential, debug logging, confirmation or model mismatch;
- stale pricing and call/cost admission denial;
- provider timeout/error, missing usage and unexpected returned model;
- blueprint rejection, repair exhaustion, semantic/compiler/definition failure;
- atomic activation, command, store reopen or resume failure;
- post-restart provider call, identity drift or revision discontinuity;
- evidence schema, checksum, finalization or local process failure.

Failures preserve sanitized incomplete evidence when possible. They do not delete useful diagnostics, print generated content, disable normal Pack/dynamic play or rewrite prior certificates.

## 11. Tests and compatibility

Automated tests use deterministic fake/fixture providers only and must cover:

- live dynamic argument and environment preflight with zero calls;
- canary pass without a full-certificate claim;
- full two-start flow and real second-JVM provider-disabled resume;
- exact provider/model/usage/cost accounting across blueprint, repair and scene calls;
- admission denial before dispatch at call and cost boundaries;
- stale/mismatched pricing, missing usage, wrong model and timeout failures;
- invalid blueprint, rejected repair and compiler/definition failures;
- evidence schema validation, atomic finalization, checksum verification and expiry;
- exhaustive evidence/stdout/stderr redaction;
- cleanup/recovery of incomplete evidence without overwriting an existing certificate;
- unchanged Pack offline/live certification and dynamic offline certification;
- unchanged normal dynamic CLI start/resume and Willow Marsh routes.

No automated test may require network access or a real credential. Provider test doubles must fail the test if an unexpected call occurs.

## 15. Acceptance criteria

27.27.3 is complete when:

1. `certify --mode live --dynamic` has strict zero-call preflight and explicit paid-call confirmation.
2. Canary and full scopes are distinct, and only a passing full scope can issue a dynamic live certificate.
3. Full scope uses at least two trusted starts and includes a real second-JVM provider-disabled resume to completion.
4. Every live call, including repairs and lazy scenes, is admitted and accounted against exact call/cost limits.
5. Provider/model identity and usage are verified; missing or mismatched data cannot pass.
6. Dynamic start, persistence and gameplay use production trust/session boundaries with no certification bypass.
7. Evidence is schema-valid, checksummed, atomically finalized and free of prompts, generated prose, blueprints, suggestions, credentials and raw snapshots.
8. The attestation binds the exact distribution/profile/provider/model/pricing/policy tuple and enforces 14-day expiry.
9. Deterministic offline tests cover success, failures, limits, restart, redaction and evidence integrity without network access.
10. Pack live/offline, dynamic offline, normal CLI and Willow Marsh compatibility tests remain green.
11. `mvn -f app/engine/pom.xml clean verify`, packaging and all offline certification gates pass.
12. No real paid provider call is made without a separate explicit operator request.
