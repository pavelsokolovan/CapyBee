# Spec 27.9 — Complete CLI Play Experience

**Type:** Implementation specification  
**Parent:** Spec 27.8 — Player Setup and Safe Personalization  
**Depends on:** Specs 25, 26.1, and 27.1–27.8  
**Baseline:** repository commit `b00c545`, plus the approved designs in Specs 27.4–27.8. The current classic console, session console, CLI argument parser, renderer, local session store, run/session service, player `View`, pack manifest, scripts, and golden tests were inspected while writing this specification. The build was not run. Uncommitted implementation work already present in the worktree was not modified.  
**Status:** Ready for implementation after Spec 27.8  
**Primary outcome:** A player can launch a pack with one clear command, understand what game will start, complete interactive setup, play a full generated game from opening to ending, inspect useful game information, quit safely, and continue later. Normal play uses the durable session path. CLI utility commands never become engine commands and never change trusted game state.

---

## 1. Problem

The repository can already play a pack through the CLI, and session mode can persist a run. It is still an engineering console rather than a complete player experience:

- normal play requires knowledge of flags such as `--session`, `--store-dir`, `--generated`, and `--new`;
- the CLI loads exactly one pack directory but does not show a useful pack summary before starting;
- session mode silently resumes the current run instead of letting the player choose;
- `--new` deletes the previous run immediately;
- classic `q`/`quit` abandons a run, while session `/quit` merely closes the console;
- session `q` can mean a choice ID or abandon, depending on the current view;
- help text differs between classic and session modes;
- the main renderer repeats status, objectives, and map details after most turns, while there are no focused `/objectives`, `/characters`, or `/map` screens;
- `/status` currently reprints the scene instead of showing a concise run summary;
- generation progress is only a generic thinking message or a technical stage summary;
- recoverable command failures can look like fatal errors;
- save behavior is not explained to the player;
- debug and outbox-event commands are mixed into the player command loop;
- scripted play echoes every input even when future command kinds may contain private text;
- there is no single documented launcher command that proves a generated game is playable from setup through a trusted ending.

Spec 27.9 replaces these inconsistencies with one player command model and one canonical session-backed flow. It does not move game rules into the CLI.

## 2. Current implementation findings

| ID | Finding | Consequence |
|---|---|---|
| F1 | `ClassicConsole` owns direct `Run` play, snapshot import/export flags, numbered choices, text, movement, and live-smoke checks. | Preserve it for compatibility and test tooling, but stop treating it as the normal durable player path. |
| F2 | `SessionConsole` uses `RunSessionService`, revisions, idempotent command IDs, asynchronous generation polling, and a durable local store when `--store-dir` is supplied. | Make this the foundation for normal play. |
| F3 | Session mode without `--store-dir` uses `InMemorySessionStore`. | The normal launcher must not claim that a game is saved when storage is temporary. |
| F4 | `SessionPorts.RunRepository` exposes only `find`, `findCurrent`, and delete; it does not expose a general run browser. | Spec 27.9 supports the one current resumable run. Multi-run history belongs to Spec 27.10. |
| F5 | Accepted session commands save the new snapshot before their result becomes visible. | Normal play already has an autosave boundary; `/save` can report it without creating a second save system. |
| F6 | `RunSummary` contains status, revision, pack, locale, ending/failure, current `View`, and update time. | It is sufficient for a friendly current-run card and resume decision. |
| F7 | `View` exposes story, objectives, characters, places, status, legal choice options, input mode, and final result. | Focused player screens can be pure renderers over `View`; no generation artifacts need to leak into the CLI. |
| F8 | `Command` already covers choose, advance, text, move, and abandon. | Utility commands must remain local and must not be added to the engine command hierarchy. |
| F9 | The pack manifest has a plain `name` and optional `description`, plus version, locales, start inputs, and features. | Use these fields for the pre-start pack card without adding generation or a new pack schema. |
| F10 | Session start and scene generation may complete asynchronously. | The CLI needs bounded progress, interruption-safe detach behavior, and clear retry guidance. |
| F11 | Setup free text from Spec 27.8 is interactive-only and must never be echoed or persisted. | The new launcher and scripts must preserve the setup privacy boundary exactly. |
| F12 | The CLI currently prints provider IDs, token counts, events, and prefetch details in normal paths. | Keep technical diagnostics behind explicit developer mode. |

## 3. Goals and non-goals

### 3.1 Goals

1. Provide one canonical `play` invocation for a local pack.
2. Use persistent session play by default for the canonical invocation.
3. Show the pack and current-run state before a destructive or external action.
4. Give an explicit, friendly continue/start-over/cancel decision.
5. Preserve the complete Spec 27.8 setup and disclosure sequence for new runs.
6. Make numbered choices, Enter-to-continue, text, and movement predictable.
7. Add player commands for help, status, objectives, characters, map, redisplay, save status, quit, and abandon.
8. Keep `/quit` non-destructive and make `/abandon` explicit and confirmed.
9. Render generation waits and recoverable errors in player language without hiding stable error codes.
10. Make resume show exactly the saved current scene without replaying effects or provider calls.
11. Keep deterministic script mode suitable for full start-to-ending acceptance tests.
12. Preserve classic snapshot and live-smoke workflows during migration.

### 3.2 Non-goals

- Redesigning store durability, leases, migrations, crash recovery, multi-run history, archival, or corrupted-run repair; Spec 27.10 owns these.
- Adding a graphical terminal UI, cursor control, colors, animations, or external terminal libraries.
- Discovering packs across the whole machine or downloading packs.
- Adding web/server endpoints.
- Changing game rules, phase routing, choices, effects, objectives, outcomes, or result calculation.
- Parsing generated prose as commands.
- Adding arbitrary natural-language commands such as “go north” or “ask Mina”.
- Persisting CLI navigation history or player preferences.
- Exposing provider prompts, raw output, API keys, setup free text, or hidden state.
- Localizing pack manifest name/description beyond the existing manifest contract.
- Implementing multiple active runs for one local owner.
- Removing the classic `--load`, `--save`, or live-smoke compatibility path.

## 4. Decisions

| ID | Decision |
|---|---|
| D1 | The canonical `play` command uses `RunSessionService`; direct `Run` mode becomes an explicit compatibility/tooling mode. |
| D2 | Canonical play uses a durable local store by default. An explicit `--memory` option requests temporary play. |
| D3 | Exactly one current resumable run is presented for the local owner. General run listing is deferred to Spec 27.10. |
| D4 | A current run is never silently deleted. Starting over requires an interactive confirmation or explicit non-interactive flag. |
| D5 | `/quit` and EOF detach from the console without changing the run. `/abandon` is the only player utility that sends `Command.Abandon`. |
| D6 | Bare `q` is not a destructive shortcut. It may resolve an enabled choice whose trusted ID is `q`; otherwise it produces help. |
| D7 | All CLI utility commands begin with `/`. Unknown slash commands are never submitted as story text. |
| D8 | Utility commands read the latest accepted `View` and do not increment revision, append events, call a provider, or consume generation budget. |
| D9 | `/save` reports the autosave state. It does not invent a second persistence format in session mode. |
| D10 | The current scene renderer shows story content and immediate actions. Status, objectives, characters, and full map are rendered on demand, except short first-use hints and the final result. |
| D11 | Generated progress is player-friendly by default. Provider IDs, calls, tokens, events, revisions, and prefetch diagnostics appear only with developer diagnostics enabled. |
| D12 | Script syntax uses the same command grammar as interactive play, but interactive menus are resolved by explicit non-interactive arguments. |
| D13 | Script echo is allow-listed by parsed command kind. Free text is redacted, not echoed verbatim. |
| D14 | The CLI trusts only engine-provided option IDs, move IDs, input modes, and `View` data. Generated labels never become command identifiers. |
| D15 | Success, partial success, and trusted failure endings are successful play completion and exit with code 0. Infrastructure or contract failure uses a non-zero code. |

## 5. Canonical launcher

### 5.1 Command form

Add an optional `play` subcommand:

```text
java -jar engine-cli.jar play --pack-dir <directory> [options]
```

For one release cycle, the existing form beginning with `--pack-dir` remains accepted and maps to compatibility behavior. `--help` at the root shows the canonical form first.

Canonical examples:

```text
java -jar engine-cli.jar play --pack-dir ./packs/generated-adventure --generated
java -jar engine-cli.jar play --pack-dir ./packs/generated-adventure --generated --locale en
java -jar engine-cli.jar play --pack-dir ./packs/generated-adventure --generated --script ./play.txt --accept-generation-disclosure
```

### 5.2 Default storage

`play` resolves a platform-appropriate application-state directory through an injectable `ConsolePaths` port:

- Windows: `%LOCALAPPDATA%/CapyBee/cli` when `LOCALAPPDATA` is available;
- macOS: `~/Library/Application Support/CapyBee/cli`;
- Linux/other Unix: `$XDG_STATE_HOME/capybee/cli`, otherwise `~/.local/state/capybee/cli`.

Rules:

- `--store-dir <directory>` overrides the default;
- `--memory` uses `InMemorySessionStore` and clearly marks the run as temporary;
- `--memory` and `--store-dir` are mutually exclusive;
- tests inject a temporary path and never write to the real user directory;
- failure to resolve or create the default directory stops before setup or provider calls and prints how to use `--store-dir` or `--memory`;
- the resolved absolute store path appears only in `/status --technical` or `--debug`, not in normal output.

### 5.3 Compatibility modes

- Existing `--session` remains accepted as an alias for session-backed play.
- Existing classic mode is selected explicitly by `--classic`, `--load`, `--save`, or `--live-smoke` as required by current compatibility rules.
- `--classic` and `--memory`/`--store-dir` are mutually exclusive unless a current test requires the legacy form; such a test should migrate.
- Print a one-line deprecation warning only for ambiguous legacy invocation, never in golden script output unless the test opts in.
- Do not remove snapshot import/export or live-smoke behavior in this specification.

### 5.4 Packaging and repository helper

The CLI Maven build must produce one documented runnable artifact with `PlayMain` as its main class and all required runtime dependencies available.

Add a repository helper that delegates arguments without interpreting player input:

```text
./dev.ps1 game --pack-dir <directory> --generated
./dev.sh game --pack-dir <directory> --generated
```

If this repository does not support a Unix helper, document the Java command instead of adding an untested shell file. The helper must not read API keys, print secrets, or change provider configuration.

## 6. Startup state machine

### 6.1 Order

Canonical interactive play follows this exact order:

1. parse CLI arguments;
2. resolve interaction mode and store path;
3. load and validate the pack;
4. print the pack card;
5. inspect the current run for the local owner;
6. ask whether to continue, start over, or exit when needed;
7. for a new run, execute Spec 27.8 disclosure and setup;
8. submit or resume the session start;
9. wait for an active run with bounded progress;
10. print the story header and current scene once;
11. enter the command loop.

No provider call occurs before steps 4–7 complete.

### 6.2 Pack card

Example:

```text
CapyBee

Lanterns of Willow Marsh
A cooperative mystery about helping a wetland village.
Pack: generated-adventure 1.2.0
Language: English (en)
Story: generated, with an authored fallback
Saving: on
```

Requirements:

- manifest `name` is the heading; fall back to pack ID only when legacy validation permits no name;
- omit a blank description;
- show semantic pack version;
- show selected locale and a friendly locale label when known;
- distinguish authored, generated-content, and full generated game profiles;
- never promise live generation merely because `--generated` is present;
- say “authored fallback” when the provider is unavailable;
- show `Saving: temporary` in memory mode;
- do not show seed, paths, provider ID, token budget, or internal feature names by default.

### 6.3 No current run

Interactive output ends with:

```text
Press Enter to set up this game, or type /quit.
```

Enter continues to Spec 27.8 setup. `/quit`, EOF, or Ctrl+C before a start request creates no run and makes no provider call.

### 6.4 Current resumable run

Show a content-safe card:

```text
Saved game found
Story: Lanterns of Willow Marsh
Status: In progress
Last saved: 2026-10-21 18:42

1) Continue
2) Start over
3) Show details
/quit) Leave
```

- time is displayed in the host’s local zone with a stable, locale-aware formatter;
- details may show run ID, pack version, locale, and revision, but no hidden state or setup text;
- Continue attaches without rerunning setup or initial generation;
- Start over asks `Start over and abandon the saved game? [y/N]`;
- confirmation sends the normal abandon command when the run is active, waits for persistence, then begins setup for a new run;
- do not call repository `delete` as the normal start-over action;
- cancellation returns to the menu;
- a pack ID/version mismatch stops with a clear compatibility message and does not mutate the saved run.

### 6.5 Preparing run

If the current run is `PREPARING`:

- offer Continue waiting or Leave;
- do not offer Start over until the current start reaches a terminal state, unless Spec 27.10 adds safe cancellation;
- reconnect to the existing start job when possible;
- never create a duplicate start request;
- timeouts detach and preserve the preparing run for recovery.

### 6.6 Failed or ended current run

- A failed run prints its stable failure code and friendly next action. Recovery/deletion policy is deferred to Spec 27.10.
- An ended run prints the saved final result once if available, then offers Start new game or Leave.
- Reopening an ended run never replays its final command or provider generation.

### 6.7 Non-interactive startup

Script mode never waits on menus:

- `--continue` requires a compatible current resumable run;
- `--new` requires no current run;
- `--replace-current` explicitly authorizes confirmed abandon of an active run before starting new;
- `--run <uuid>` attaches to that owned run;
- if none of these resolves ambiguity, exit 2 with a concise instruction;
- `--replace-current` is valid only with a new-run request and is never implied by `--new`;
- Spec 27.8 preset input and disclosure-acknowledgement rules still apply.

## 7. Unified player command grammar

### 7.1 Parser contract

Add a CLI-only parser returning a closed type, for example:

```java
sealed interface ConsoleIntent {
  record ChooseIndex(int oneBasedIndex) implements ConsoleIntent {}
  record ChooseId(String optionId) implements ConsoleIntent {}
  record Advance() implements ConsoleIntent {}
  record SubmitText(String text) implements ConsoleIntent {}
  record Move(String placeId) implements ConsoleIntent {}
  record Utility(UtilityCommand command, String argument) implements ConsoleIntent {}
  record Invalid(String code) implements ConsoleIntent {}
}
```

The parser receives the current `View`, interaction mode, and developer-mode flag. It does not receive generation artifacts or pack files.

### 7.2 Player commands

| Command | Meaning | Mutates run? |
|---|---|---:|
| `/?`, `/help` | Show context-sensitive help. | No |
| `/look` | Reprint current scene and available immediate actions. | No |
| `/status` | Show story/run summary and visible status values. | No |
| `/objectives`, `/quests` | Show visible objectives. | No |
| `/characters` | Show discovered characters. | No |
| `/map` | Show known places, links, current place, and legal moves. | No |
| `/move <place-id>` | Request movement to an engine-provided available place ID. | Yes |
| `/text <words>` | Explicitly submit story text when current input mode allows it. | Yes |
| `/save` | Report latest autosaved revision and storage mode. | No |
| `/quit` | Detach and leave the run resumable. | No |
| `/abandon` | Confirm, then permanently end this run through `Command.Abandon`. | Yes |

Aliases are limited to those in the table. Do not add single-letter destructive aliases.

### 7.3 Developer-only commands

`/events [afterSeq]`, `/debug on|off`, `/diagnostics`, and technical status remain available only when the process starts with `--debug` or a test injects developer mode.

- Player help does not list them.
- Turning debug off during a process is allowed.
- Turning debug on from a normal player process is not allowed.
- Diagnostics must still redact provider secrets, input text, prompts, provider output, and setup attachments.

### 7.4 Resolution order

For each input line:

1. a leading `/` is parsed only as a utility command;
2. if an enabled choice list is present, an integer selects by displayed one-based position;
3. an exact case-insensitive trusted option ID selects that option for advanced/script use;
4. blank input becomes `Advance` only when the current engine input contract allows advance;
5. `/move` validates against `View.places.availableMoves` before creating `Command.Move`;
6. `/text` or remaining plain text becomes `SubmitText` only for `TEXT` or `CHOICE_OR_TEXT`;
7. otherwise return a local help error and make no engine call.

Disabled choices remain displayed but cannot be selected by index or ID. The CLI gives the option hint when available.

### 7.5 Slash and text safety

- Plain text beginning with `/` is reserved and is never sent to the engine.
- To submit story text that visibly begins with `/`, use `/text /...`; the argument after `/text ` is data.
- Do not trim internal whitespace from submitted text. Use engine normalization and validation.
- An empty `/text` is a local usage error.
- The parser never interprets generated labels, narration, character names, or descriptions as commands.
- Unknown commands print `Unknown command: /x. Type /help.` without echoing the rest of a potentially sensitive argument.

## 8. Rendering contract

### 8.1 Renderer split

Split the current all-in-one renderer into pure functions:

```java
renderPackCard(...)
renderScene(View view)
renderStatus(RunSummary summary, StorageMode storage)
renderObjectives(View view)
renderCharacters(View view)
renderMap(View view)
renderResult(View view)
renderHelp(View view, boolean developerMode)
renderIssue(Issue issue)
```

The exact class layout may differ. Rendering functions do not mutate, persist, generate, sleep, or inspect raw snapshots.

### 8.2 Scene

`renderScene` prints:

1. current blocks in order;
2. enabled and disabled choice labels with numbers;
3. a short text-input hint when applicable;
4. Enter hint only when advance is meaningful;
5. current place plus compact legal-move hint only when places exist.

It does not print the complete status, objective list, character list, map graph, generation diagnostics, or story premise after every turn.

### 8.3 Status

`/status` prints only player-visible data:

```text
Status
Story: Lanterns of Willow Marsh
Run: In progress
Saved: yes
Health 3  Courage 2
Current place: Reed Gate
Objectives: 1 active, 1 complete
Characters discovered: 3
```

- omit sections unavailable to authored packs;
- derive counts only from `View`;
- never reveal counters, flags, sets, hidden objectives, generation budget, or outcome candidates;
- in memory mode print `Saved: no — this run ends when the program closes`;
- developer mode may append run ID and revision in a separate Technical section.

### 8.4 Objectives

- Preserve `View.objectives` order.
- Show state, label, and optional description.
- Use friendly state labels: Active, Complete, Failed, or the exact future mapped value.
- Print `No objectives are visible yet.` for an empty list.
- Never display undiscovered or unexposed generated quest artifacts.

### 8.5 Characters

- Preserve `View.characters` order.
- Show name and description.
- Mark `Here now` from `inCurrentScene`.
- Do not show engine actor ID or slot ID in player mode.
- Print `You have not met any characters yet.` when empty.

### 8.6 Map

The v1 map is text-first and deterministic:

- list visited/known places in `View.places.places` order;
- mark current place with `*`;
- show description when present;
- show connections using localized labels and trusted IDs;
- show available destinations as `/move <id>` lines;
- do not expose an unvisited place unless it is already present in the player `View` contract;
- if coordinates and `layoutKind` can produce a stable small ASCII diagram, it may appear above the list;
- a list representation is mandatory and is the tested accessibility fallback;
- do not guess compass directions from coordinates.

### 8.7 Result

At a completed ending, print the trusted `RunResult` exactly once through the Spec 27.7 renderer, followed by:

```text
Game complete. Your final state has been saved.
Type /status, /objectives, /characters, /map, or /quit.
```

The ended-run loop accepts only read-only utility commands and `/quit`. `/abandon`, story commands, and movement are rejected locally. Script mode exits 0 immediately after printing the result unless a transcript assertion mode explicitly continues.

## 9. Generation progress and asynchronous commands

### 9.1 Progress phases

Use bounded player messages:

- initial start: `Creating your story…`;
- command/lazy scene: `Continuing the story…`;
- fallback selected: `The live story service was unavailable, so CapyBee used the prepared version.`;
- long wait: print at most one dot per configured interval on the same line;
- completion always terminates the progress line before rendering content.

Do not print stage names, provider ID, token use, raw failure messages, or retries unless developer mode is active.

### 9.2 While a command is processing

- retain the pending command ID;
- poll according to injected `ConsoleTuning`;
- `/status`, `/help`, and `/quit` remain available;
- `/quit` detaches without cancelling or resubmitting the command;
- other mutating input returns `A story action is still running. Please wait.`;
- after reconnect, query the pending command result before accepting another mutation;
- a polling timeout is not treated as command failure; print the run ID and resume guidance, then exit 3 in scripts or return to a safe interactive detach choice.

### 9.3 Interrupts

- EOF behaves like `/quit`.
- A normal interrupt during a prompt or wait makes best effort to print `Leaving the game. Your last completed action is saved.` and exits 130.
- Never translate interrupt, EOF, timeout, or terminal close into abandon.
- Never reuse a new command ID after an uncertain submission. Resume/poll the existing ID.

## 10. Save, quit, abandon, and resume semantics

### 10.1 Autosave boundary

For durable session play, a state-changing command is considered saved only after `RunSessionService.command` reports an applied/replayed result whose persisted revision matches the returned revision.

- Render the new scene only after this boundary.
- `/save` calls a read-only session/store verification method if one is required; it never re-applies a command.
- If persistence failed, do not print “saved”. Print the stable store error and detach guidance.
- `PREPARING` state and Spec 27.8 ephemeral setup attachment keep their existing special rules.

### 10.2 `/save`

Durable mode:

```text
Saved. Run 7f… is at revision 12.
```

Normal mode may shorten the run ID. `/status --technical` shows the full value.

Memory mode:

```text
This run is temporary and cannot be continued after the program closes.
Restart with --store-dir <directory> to enable saving.
```

Do not write an arbitrary snapshot file from session `/save`. Classic `--save <file>` remains separate compatibility behavior.

### 10.3 `/quit`

- immediate and confirmation-free;
- no engine command, revision, event, or provider call;
- prints whether the run can be continued and the canonical resume command;
- in memory mode warns that the run will be lost when the process exits;
- exit code 0.

### 10.4 `/abandon`

Prompt:

```text
Abandon this game? You will not be able to continue it. [y/N]
```

- default No;
- `yes`/localized affirmative submits one `Command.Abandon` with a fresh command ID;
- wait for the ended revision to persist;
- print the abandoned marker, not the success/partial/failure result summary;
- cancellation returns to the unchanged scene;
- script mode requires `/abandon --yes`; plain `/abandon` is an error and makes no mutation;
- repository deletion is not part of abandon.

### 10.5 Resume invariants

Resume must:

- restore the exact accepted snapshot and current `View`;
- not ask setup questions or provider disclosure again;
- not re-send setup inputs;
- not regenerate accepted theme, plan, cast, quest, scene, continuity, or ending artifacts;
- not replay entry effects, objective transitions, events, or final effects;
- not repeat earlier scene transcript, only the current view;
- preserve trusted option and move IDs;
- continue with the next revision and new command IDs.

## 11. Scripted full-game play

### 11.1 Script format

One UTF-8 command per line:

```text
# comments begin at column 1
1
/objectives
/characters
/map
/move village-square
/text I examine the lantern.
2
```

- blank lines are `Advance` only when the view permits advance; otherwise they are ignored with a script error in strict mode;
- `#` comments are allowed only when `#` is the first non-whitespace character;
- no variable interpolation, includes, shell execution, environment expansion, or conditional syntax;
- maximum 10,000 lines and 1 MiB;
- scripts cannot provide Spec 27.8 setup free text;
- preset start inputs remain command-line/config inputs, not script lines.

### 11.2 Echo

- choices, movement, and read-only utility commands may echo in canonical form;
- `/text` and implicit text print `> [text submitted]`;
- future sensitive command arguments default to redacted;
- comments are not echoed;
- the echo policy is based on parsed intent, not string-prefix guesses.

### 11.3 Strict deterministic behavior

Script mode is strict by default:

- invalid choice index/ID, invalid move, disallowed text, unknown command, unexpected menu, EOF before ending, or unresolved async command exits 4;
- every failure includes line number, stable code, and safe short hint;
- provider fallback is allowed for normal generated scripts and is reported;
- `--live-smoke` retains its stronger no-fallback/provider-call assertions;
- successful trusted ending exits 0 regardless of outcome class;
- a script can include read-only utility commands without changing expected revision count.

### 11.4 Golden end-to-end script

Add at least one deterministic full-game script for the minimal full-game fixture that:

1. starts with preset setup values;
2. accepts disclosure through the invocation flag when a provider double is configured;
3. views objectives, characters, and map;
4. exercises a legal movement when supported;
5. makes choices through every required phase;
6. observes one meaningful consequence;
7. reaches a trusted ending;
8. prints the final result;
9. exits 0;
10. proves the accepted command count matches story transitions and excludes utility commands.

Run the same route once with generated provider-double outputs and once with forced authored fallbacks.

## 12. Error presentation and exit codes

### 12.1 Error classes

| Class | Player behavior |
|---|---|
| Local input mistake | One-line hint; keep current view and prompt. |
| Engine command rejection | Friendly issue text; keep the returned/current view. |
| Revision conflict | Refresh once, show current view, ask player to choose again; do not auto-reapply. |
| Generation unavailable with valid fallback | Continue and explain fallback once. |
| Busy/processing | Preserve pending ID and poll or detach. |
| Store unavailable | Stop claiming persistence; give safe resume/retry information. |
| Pack/snapshot/contract invalid | Stop before play and print stable code. |
| Unrecoverable run | Stop mutation and hand off to Spec 27.10 recovery guidance. |

### 12.2 Output shape

Player mode:

```text
Could not make that choice.
That option is not available here. Type /look to see the current choices.
Code: COMMAND_REJECTED
```

- stable code is always present but visually secondary;
- no stack trace or exception class;
- no provider response or prompt fragment;
- no start free text or submitted story text;
- unexpected exceptions map to a stable safe code and log only content-free diagnostics.

### 12.3 Exit codes

| Code | Meaning |
|---:|---|
| 0 | Player quit, setup cancelled, or game ended normally with any trusted outcome class. |
| 1 | Pack source/load/validation failure. |
| 2 | CLI usage, startup ambiguity, or script syntax error. |
| 3 | Session, store, resume, or runtime infrastructure failure. |
| 4 | Strict script/live-smoke did not complete its required route. |
| 130 | User interrupt. |

Rejected in-game choices do not end interactive play and therefore do not directly select a process exit code.

## 13. Localization, readability, and accessibility

- All new player chrome uses a CLI message catalog keyed by locale; English is required for v1.
- Pack content continues to come from the selected pack locale.
- Missing CLI translation falls back to English and never blocks play.
- Tests compare normalized `\n`; runtime uses the host line separator.
- Default output is plain UTF-8 and readable without ANSI color.
- `--no-color` is accepted even if v1 produces no colors, allowing future compatibility.
- Prompts never rely only on color or punctuation.
- Choice numbers are one-based and stable for one rendered view.
- Map always has a list form.
- Lines should target 100 characters where practical, but pack narrative text is not destructively reflowed.
- Player commands remain ASCII and are not localized in v1; help descriptions are localized.
- Dates use local time but tests inject clock and zone.

## 14. Privacy and security invariants

1. Preserve every Spec 27.8 disclosure, transient-input, non-echo, and non-persistence requirement.
2. Start free text never appears in pack cards, run cards, status, save messages, scripts, diagnostics, errors, or logs.
3. Story text is not echoed in script mode and is not added to CLI diagnostics.
4. Provider credentials and environment values are never printed.
5. Store paths are normalized before use and are not built from pack/generated text.
6. Run IDs supplied by the user are parsed as UUIDs and ownership is checked by session service.
7. Pack names, descriptions, story titles, character names, and labels are display data only.
8. Escape or remove terminal control characters from every displayed pack/generated field before printing.
9. Generated text cannot emit a trusted slash command, auto-confirm abandon, select an option, or alter CLI mode.
10. Script files are read as data; lines are never passed to a shell.
11. Debug mode does not weaken input validation, ownership, consent, or redaction.
12. Utility commands do not enter the engine event log or command idempotency log.

## 15. API and module changes

### 15.1 Engine core

No new engine command, effect, condition, or generated payload is required.

Only make a core change if an existing `View` cannot expose already-player-visible data needed by a renderer. Any addition must be presentation-only, nullable/backward-compatible, included in the view schema/version process, and reflected in wire/TypeScript contracts.

### 15.2 Session module

Allowed small additions:

- read-only saved-revision/storage confirmation for `/save` if current `RunSummary` is insufficient;
- a content-safe current-run descriptor if constructing the menu from `RunSummary` is unsafe;
- an explicit abandon-and-wait orchestration helper if needed to avoid delete-based replacement.

Do not add general list/archive/recover APIs in 27.9. Do not expose raw snapshots merely for rendering.

### 15.3 CLI module

Add or refactor:

- `ConsoleCommandParser`;
- `PlayerConsole` or equivalent shared session player loop;
- `ConsoleMessages`;
- `ConsolePaths`;
- focused renderer methods;
- startup/menu coordinator;
- safe script reader/echo policy;
- signal/interrupt boundary where supported;
- optional `play` subcommand and compatibility routing.

Avoid duplicating the command loop in setup, classic, and session code. Shared parsing/rendering must not hide differences in persistence semantics.

### 15.4 Classic console

- Reuse unified command parsing and focused renderers where practical.
- Make `/quit` non-destructive there too.
- Keep explicit snapshot-save behavior.
- If a classic run has no persistent save target, say so before quitting.
- Preserve existing authored golden content unless the approved command-chrome migration intentionally changes it; record those diffs.

## 20. Definition of done

Spec 27.9 is complete when:

- one documented `play` command starts normal session-backed play;
- normal play is durable by default, and temporary play is clearly marked;
- the player sees the pack summary before setup or generation;
- an existing run produces an explicit continue/start-over/leave decision;
- start over never silently deletes an active run;
- Spec 27.8 disclosure and safe personalization remain unchanged;
- a player can complete setup and play every full-game phase using numbers, Enter, text, and movement as allowed;
- `/help`, `/look`, `/status`, `/objectives`, `/characters`, `/map`, `/save`, `/quit`, and `/abandon` behave as specified;
- utility commands make no engine call, revision, event, provider call, or budget use;
- `/quit`, EOF, and interrupt never abandon a run;
- `/abandon` requires confirmation and is persisted exactly once;
- scene output is readable and does not repeat every auxiliary panel;
- generated waits, fallback, rejection, and recoverable session errors have safe player messages;
- script text is redacted and setup free text remains absent everywhere required;
- quitting and resuming in a new process restores the exact current scene with no repeated generation or effects;
- provider-double and fallback scripts both reach a trusted ending and exit 0;
- authored, schema-v1 generated, classic snapshot, and live-smoke compatibility tests remain green;
- all standard verification passes without a live provider.

## 21. Handoff to Spec 27.10

Spec 27.10 owns durable session persistence and recovery beyond the single-current-run shell in this specification. It may add:

- run listing, archive, and multiple saved-run selection;
- store schema evolution and migration guarantees;
- atomic crash recovery for preparing and in-progress commands;
- stale lease repair and orphaned job recovery;
- corrupted snapshot quarantine and user-visible recovery choices;
- retention, cleanup, export/import, and storage limits;
- stronger process-restart integration tests.

It must preserve:

- the CLI command semantics and exit codes defined here;
- quit versus abandon behavior;
- command idempotency and revision safety;
- the exact accepted-artifact resume guarantees;
- Spec 27.8 transient free-text non-persistence;
- no silent deletion or replacement of a saved run.
