# Spec 27.23 — Blueprint Compilation and Materialized Game Definition

**Type:** Implementation instruction
**Parent:** Dynamic-game series, following Spec 27.22
**Depends on:** Specs 22–27.22, especially `SemanticallyValidatedBlueprint`, `ValidatedMechanicsPlan` and generated-rules-v1
**Baseline:** Inspected local `main` at commit `8746313` on 2026-10-25. Specs 27.18–27.22 are implemented. There is no `MaterializedGameDefinition`, dynamic compiler, trusted generated-ID mapping or non-Pack runtime definition boundary. Unrelated UI working-tree changes were present and must not be modified. No build or live-provider test was run while preparing this document; implementation must inspect current HEAD again.
**Status:** Ready for implementation; compiled definitions remain unstarted and non-durable until later specifications
**Primary outcome:** Deterministically compile one reviewed, semantically validated blueprint into an immutable `MaterializedGameDefinition` with engine-assigned local IDs, fully bound scenes and rules, planning content and final definition verification.
**Repository location:** `docs/specifications/27.23-engine-blueprint-compilation-and-materialized-game-definition-instruction.md`

---

## 1. Purpose

Spec 27.22 leaves the engine with a bounded, playable blueprint and a typed mechanics plan, but not executable engine state. Blueprint symbols are still model-proposed identifiers, mechanics still reference those symbols, and `DefaultEngine` can start only registered Packs.

This specification owns the deterministic trust transition:

```text
CandidateReviewed
  -> SemanticallyValidatedBlueprint + ValidatedMechanicsPlan
  -> deterministic compiler
  -> final materialized-definition verifier
  -> immutable MaterializedGameDefinition
```

Only the verified materialized definition may cross into runtime integration in 27.24. Compilation performs no gameplay, generation, persistence or host publication.

## 2. Scope and non-goals

### 2.1 In scope

- Define a versioned immutable `MaterializedGameDefinition` independent of Pack JSON.
- Accept only a reviewed candidate containing a genuine semantic wrapper and matching mechanics plan.
- Assign deterministic trusted local IDs for actors, objectives, scenes, choices, outcomes and state declarations.
- Rewrite graph, planning, condition and effect references to trusted IDs.
- Materialize existing `Scene`, `SceneOption`, `SceneSet`, `Rules`, state, objective and outcome types where compatible.
- Preserve reviewed story/actor/phase/scene planning content for 27.25.
- Create deterministic locale-bound string keys/content without interpreting prose.
- Verify the produced aggregate independently and return explicit success/failure.
- Preserve all authored Pack behavior.

### 2.2 Out of scope

- Starting/resuming a Run or changing `DefaultEngine`; 27.24 owns runtime integration.
- Generating prose, dialogue or final choice labels; 27.25 owns presentation.
- Durable codecs, fingerprints, migrations and storage; 27.26 owns persistence.
- CLI/setup exposure and released end-to-end play; 27.27 owns host release.
- Provider calls, review, semantic repair or a new repair allowance.
- Synthetic Packs, manifests, `rules.json`, catalogs or resource trees.
- Reinterpreting mechanic strings or adding operators.
- Run/session IDs, seeds, timestamps or global storage keys.

## 4. Compiler boundary

### 4.1 Input

The production entry point is conceptually:

```java
MaterializedGameCompilationResult compile(
    BlueprintGenerationResult.CandidateReviewed candidate);
```

Before allocation, verify:

- the candidate is reviewed, not pending;
- semantic wrapper/mechanics plan exist;
- reviewer and validator stamps are present;
- profile identity, locale and preset IDs agree;
- evidence contract equals `GeneratedMechanicsV1.CONTRACT_VERSION`;
- witnessed endings/objectives agree with the accepted blueprint.

Do not accept raw JSON, `ParsedGameBlueprint`, parser output, arbitrary `Rules` or a caller-supplied `validated=true` flag.

### 4.2 Purity

Compilation receives no clock, randomness, `IdSource`, UUID, Pack registry, filesystem, provider, guard, network port or mutable global cache. The same candidate and compiler version produce structurally equal definitions, IDs, order and evidence.

The definition has no global instance ID. 27.24 owns run/preparation identity and 27.26 owns durable content identity. Never derive identity from `hashCode`, time or provider request ID.

### 4.3 Result

Use explicit variants:

- `Compiled(definition)`;
- `InvalidAcceptedInput(code)` for stale/mismatched trust stamps;
- `CompilerFailure(code)` for internal mapping/verifier defects.

No partial definition is returned. Compilation performs no retry/provider call. If a new proposal invariant is discovered, move it into parser/semantic validation and reuse only the original 27.20 attempt allowance; do not create a compiler repair loop.

## 5. MaterializedGameDefinition v1

The immutable aggregate contains at least:

```text
definitionFormatVersion, compilerVersion, origin=DYNAMIC_BLUEPRINT
profileIdentity, locale, lengthPresetId, challengePresetId
blueprintSchemaVersion, generatedRulesContractVersion
semanticValidatorVersion, outputReviewerVersion
storyPlan, actors, phases, scenePlans
runtimeSceneSet, runtimeRules
localizedContent, idBindings, compilationEvidence
```

Requirements:

- `definitionFormatVersion` starts at 1; it is not the future codec version.
- Deep defensive copies and unmodifiable nested collections.
- Preserve blueprint declaration order with stable lists/insertion-ordered maps; do not depend on unspecified `Map.copyOf` order.
- Conditions/effects may be reused only after trusted-ID rewriting.
- Aggregate, bindings, plans and results have redacted `toString()`.
- The definition contains enough data for 27.26 to persist it without the original profile/provider, but this spec adds no codec.

## 6. Trusted local IDs

Blueprint symbols are lookup keys during compilation only. Runtime IDs are definition-local, engine-assigned and based solely on declaration order.

Freeze exact vectors such as:

| Kind | Example |
| --- | --- |
| Actor | `actor-001` |
| Objective | `objective-001` |
| Scene | `scene-001` |
| Choice | `choice-001-001` |
| Outcome | `outcome-001` |
| Counter | `counter-001` |
| Flag | `flag-001` |
| Set/member | `set-001`, `set-001-value-001` |
| Phase | `phase-opening` |

Actors/objectives/outcomes/state use list order; scenes use blueprint order; choices use scene plus local order; set values use declaration order; phases use `PhaseKind` order. Never sort by model text or hash.

Create immutable, namespace-separated bindings for source actors, objectives, scenes, scene-local choices, outcomes, counters, flags, sets and per-set members. No wrong-namespace fallback. Choice symbols may repeat across scenes. All runtime references use trusted IDs; source symbols may remain only inside redacted binding/provenance structures.

## 7. Planning and presentation data

Materialize the reviewed story title, premise, setting, tone tags and promises as inert content.

Each actor contains trusted ID plus reviewed name, role and description. Each phase contains stable ID/kind, goal/development/transition, trusted actor/objective IDs and trusted scene IDs derived from scene phases. Each scene plan contains trusted scene ID, phase, title/intent, actor/objective IDs and ordered trusted choice IDs/intents.

Choice intent is planning input, not a final label. The compiler does not embellish, translate or call a provider. Mechanical scenes may contain empty blocks and an explicit unresolved/internal label marker. Normal CLI/UI must not expose that form before 27.25 supplies validated presentation or definition-specific fallback. Do not hide English defaults such as “Continue” inside core.

## 8. Mechanical scene materialization

For each decision scene:

- trusted scene ID; start true only for mapped start;
- `end=false`, empty blocks;
- ordered options with trusted choice/destination IDs;
- rewritten requirement/effects from the matching mechanics plan;
- unresolved internal label, null unmet hint, `hideWhenUnmet=false`;
- null next/outcome, empty onEnter/branches, no input, maxChars 0.

For each ending:

- trusted scene ID; start false, end true;
- empty blocks/options and no outgoing behavior/input;
- trusted outcome ID.

Create one selected-locale `SceneSet` with the trusted start ID. Also retain a canonical ordered scene list because reusable `SceneSet` map ordering is not a canonical format. Add no utility scenes, places, branches, automatic edges or entry effects.

## 9. Rules materialization

### 9.1 State

- Counter: trusted ID, exact min/max/initial, display false, internal key; `maxDelta` is the largest absolute compiled COUNTER_ADD for that counter or null if unused.
- Flag: trusted ID and exact initial value.
- Set: trusted set ID, trusted member IDs in declaration order and rewritten initial subset.

Counter display remains false because blueprint v1 has no reviewed counter-label field.

### 9.2 Mechanics

Recursively rewrite typed mechanics-plan values:

- counter/flag/set references to trusted state IDs;
- set members to trusted member IDs in that set;
- visited scenes to trusted scene IDs;
- ALL/ANY/NOT structure and order unchanged;
- effect order unchanged.

Never reconstruct from blueprint discriminator strings. Unknown typed variants or contract mismatch are internal failures.

### 9.3 Objectives/outcomes

Create one ObjectiveDef per objective with trusted ID, deterministic label key, rewritten completeWhen and empty onComplete. Create one OutcomeDef per outcome with trusted ID, exact ResultClass and deterministic label key. Store reviewed titles/descriptions separately. Ending mapping remains one-to-one. Result facts are empty.

## 10. Localized content

The definition contains exactly the selected locale; do not synthesize translation or default-locale fallback. Generate stable engine-owned keys that contain no model symbols, for example:

```text
story.title
actor.001.name
objective.001.title
objective.001.description
outcome.001.title
scene.001.title
scene.001.choice.001.intent
```

Store key→reviewed text in deterministic order. No template interpolation or resource lookup occurs. The original suggestion, prompts, rejected attempts and provider envelope are absent; accepted reviewed prose may remain as game content.

## 11. Provenance and evidence

Retain content-free profile identity/fingerprint, locale/presets, blueprint schema, generated-rules contract, validator/reviewer/compiler versions, definition version, source/compiled counts and semantic min/max transition evidence.

A structural digest is optional only with a documented canonical encoding and must not be called the durable definition fingerprint; 27.26 owns persisted integrity. Do not retain model/provider IDs, request bodies, suggestion hashes or arbitrary provider metadata.

## 12. Final definition verifier

Verify the produced aggregate independently before success:

- supported versions and consistent provenance;
- trusted ID syntax/uniqueness and complete one-to-one bindings;
- exactly one start and matching SceneSet start;
- valid decision/ending shapes;
- resolving destinations and graph/count parity with semantic evidence;
- phase/scene/actor/objective/outcome coverage;
- only generated-rules-v1 mechanics with resolved trusted references;
- valid state bounds/set members;
- empty objective effects/result facts and no authored-only mechanics;
- one-to-one ending/outcome mapping and exact ResultClass;
- complete locale/content keys/planning slots;
- no Pack/place/event/input/external-resource dependency;
- evidence counts matching collections.

Do not construct a Pack or serialize/reparse for verification. Return bounded content-free codes, for example `MATERIALIZED_DEFINITION_VERSION_UNSUPPORTED`, `...PROVENANCE_INVALID`, `...ID_INVALID`, `...BINDING_INVALID`, `...SCENE_INVALID`, `...RULE_INVALID`, `...CONTENT_INVALID`, `...EVIDENCE_MISMATCH`. Pointers use field names and indexes, never source symbols/content.

## 13. Failure, privacy and compatibility

- Invalid input or compiler/verifier defect yields no definition and no model repair.
- Never publish partially compiled data or log prose, symbols, bindings, rule trees or exception payloads containing them.
- Metrics may contain version/status/count/duration only.
- Compilation creates no file, database record, Pack registration, session or snapshot.
- Authored Pack, registry/loader, DefaultEngine, RunImpl, snapshots, Willow Marsh and fixed-pack generated presentation remain unchanged.
- Do not add a fake DYNAMIC PackFeature, overload PackId or index definitions as Pack resources.
- No Spring, persistence, CLI or provider-SDK dependency enters engine core.

## 14. Required test matrix

| Group | Evidence |
| --- | --- |
| Trust boundary | CandidateReviewed compiles; pending/raw/forged/mismatched inputs do not. |
| Determinism | Repeat compilation gives equal structure, IDs, order, keys and evidence; no ports invoked. |
| IDs | Exact vectors for every namespace, repeated cross-scene choice symbols and maximum counts. |
| Variation | Independent EN and structurally different PL fixtures; no production scenario constants. |
| Graph | Start/routes/endings/outcomes preserve source topology after rewriting. |
| Mechanics | Every v1 condition/effect rewrites recursively; order preserved; no raw runtime symbols. |
| State | Exact counter bounds/initial/maxDelta/display, flags, sets and empty declarations. |
| Objectives/outcomes | Trusted IDs/keys, empty onComplete/resultFacts, exact classes/mappings. |
| Planning/content | Reviewed content preserved inertly; references trusted; deterministic keys, exact locale. |
| Scenes | Unresolved presentation and no next/branches/onEnter/input/places/events. |
| Verifier | Test-only mutations reject unknown IDs, missing bindings, swapped routes, authored effects, duplicate keys and evidence mismatch. |
| Immutability/privacy | Nested collections immutable; no content/symbol leaks in diagnostics or toString. |
| Compatibility | Existing Pack, Willow Marsh, semantic-validator and mechanics tests remain green. |
| Full gate | `mvn -f app/engine/pom.xml clean verify` passes without lowering gates. |

## 15. Implementation sequence

1. Reinspect HEAD/status, AGENTS/build guidance, Specs 27.17–27.22 and current domain types; preserve unrelated UI work.
2. Add immutable version/provenance/result/definition contracts without runtime integration.
3. Implement deterministic ID allocation and binding tables with vector tests.
4. Compile planning content and deterministic selected-locale keys.
5. Rewrite mechanics references and materialize state/rules/objectives/outcomes.
6. Materialize mechanical scenes/SceneSet with unresolved presentation.
7. Add independent final verifier and explicit failures.
8. Add determinism, adversarial, privacy, immutability, variation and compatibility tests.
9. Update engine README/spec index to mark compilation available but startup/persistence/CLI unavailable.
10. Run focused tests and `mvn -f app/engine/pom.xml clean verify`; fix implementation failures without lowering gates.
11. After complete implementation, commit only 27.23 changes to main as `spec 27.23 is implemented - <short description>`.

No live provider test is required. Do not implement 27.24 or 27.26 implicitly.

## 16. Acceptance criteria and handoff

27.23 is complete when only a reviewed semantic candidate compiles; compilation is pure/deterministic; every model symbol becomes a trusted definition-local ID; the immutable definition contains complete mechanics and downstream planning; typed mechanics are rewritten without reparsing strings; final verification returns no partial success; private source material is absent from diagnostics; authored paths stay compatible; and nothing is started, persisted, registered or exposed through CLI.

**Next: 27.24 — Dynamic Game Bootstrap and Runtime Integration.** It adds a definition-aware start boundary, assigns run/preparation identity, publishes the definition atomically and starts it through existing `RunImpl` behavior without fabricating a Pack or creating a second gameplay engine.
