# Spec 30.1 — Visual Design and SVG Catalog

**Type:** Implementation instruction
**Series:** Spec 30 — Illustrated Honeycomb RPG (user-provided roadmap)
**Intent:** [Illustrated Honeycomb RPG](intent/03-illustrated-honeycomb-rpg.md)
**Depends on:** Existing 28.3 renderer and 29.1–29.3 foundations; no new runtime contract prerequisite
**Baseline:** `473e96f81022bce26a72217d6bd74b6475790fc5`, inspected 2026-11-15
**Status:** Implemented — catalog v1, 2026-11-15; [acceptance evidence](../game-visual-catalog-acceptance.md)

## Outcome and scope

Settle the visual language and deliver a fixed, reusable SVG catalog for the
Honeycomb Board, Befriend & Recruit characters and Hive Expedition backdrops.
Produce finished local artwork, a typed React rendering boundary and a preview
gallery that shows the intended experience with synthetic fixtures. The catalog
must work without network access, a provider, canvas or a game engine library.

This part owns artwork and presentation primitives only. Public character
traits/needs, asset references and companion membership belong to 30.2; playable
board movement and automatic encounter entry belong to 30.3; recruitment UI to
30.4; live scene composition and accessible text-mode controls to 30.5; generated
asset selection and bounded prefetch to 30.6; release certification to 30.7.
Do not change Pack routes, public API DTOs, saves, recruitment rules, generation
profiles, production flags or the existing game controller in this part.

## Fixed art direction

Use a flat storybook diorama: broad rounded silhouettes, warm dark outlines,
two or three large color regions per object, sparse environmental detail and
generous empty space. Characters are more saturated than scenery. Detail comes
from recognizable ears, tails, wings, reeds and lanterns, rather than texture.
No photorealism, pixel art, 3D/isometric camera, heavy lighting effects or new
font is required. Keep Inter/system typography in HTML outside the SVG.

| Token | Value / use |
|---|---|
| `game-paper` | `#FFFDF7`, surrounding surface |
| `game-cream` | `#FDF6E3`, panels and dialogue surface |
| `game-ink` | `#2E2413`, text and primary outlines; existing app ink |
| `game-muted` | `#6C5A3A`, secondary text; existing app muted |
| `game-honey` | `#F2B233`, accents and Capy's scarf; existing app accent |
| `game-focus` | `#765321`, visible focus, on an opaque cream backing |
| `game-sage` | `#A8BEA0`, meadow/foliage fills |
| `game-water` | `#B5D5D8`, water fills |
| `game-lilac` | `#C9BED9`, moth and quiet distance fills |
| `game-earth` | `#C79A70`, Capy/beaver/wood fills |

Scope tokens to the RPG; reuse existing root tokens where equivalent. Pastels
are illustration fills, not text or sole indicators of an interactive state.
Verify WCAG AA text contrast (4.5:1 normal, 3:1 large) and 3:1 for meaningful
control boundaries/focus against their actual adjacent surface. Place controls
on opaque panels, never directly on variable scenery.

Capy is a recognizable capybara: rounded rectangular muzzle, small round ears,
short legs, warm tan body and a small honey scarf. Keep the same proportions
and identity in portrait and full-body views. Use the existing Capy assets as
an identity reference during implementation and record the reference used.
Do not embed a raster image inside an SVG to satisfy this requirement.

Mela has a round striped body, soft translucent-looking solid-fill wings and
short antennae. Borys has a broad muzzle, small ears and a clearly visible flat
tail. Luna has broad rounded wings and soft antennae, with no eye-like threat
markings. Characters remain animals, without human bodies or hands. Expressions
are neutral, attentive and gently pleased. None implies that the child's mood
is a score or determines whether a companion likes them.

The Old World is represented by a softly glowing lantern, with a solid pale
halo rather than a filter. Both old and new places are welcoming. Do not make
the Old World dark, broken or something to unlock. Across this catalog and its
preview: no human figures, hearts, padlocks, health/affection bars, trophies,
streaks, rankings, urgency badges, confetti or competitive cues.

## Geometry, composition and states

Use pointy-top hexes, with a shared `viewBox="0 0 120 140"` and vertices
`60,2 118,36 118,104 60,138 2,104 2,36`. This orientation matches the existing
axial visual placement relation (`2*x+y`, `y`); the current CSS polygon is a
placeholder and its eventual replacement belongs to 30.3. Terrain and state
overlays share this exact silhouette and clipping geometry.

Leave the central 48% of each tile uncluttered for a marker. Labels are HTML
outside the clipped artwork. Design tiles to remain recognizable at 64×74.7px
and larger; Capy's marker at 32px, portraits at 40px and 64px, and figures at
96–160px. A tiny portrait is accompanied by a readable character name.

Tile state treatments are trusted React/CSS composition, not model-selected
assets. Provide gallery samples for current, visited, available, unavailable,
selected, keyboard focus and pending. Current uses Capy plus a double outline;
visited adds a check plus text; available uses a solid boundary plus a move
label; unavailable uses a subdued dashed boundary plus a reason; selected adds
a distinct inset boundary. Focus is an outer 3px outline with a 3px separation,
never clipped by the hex. Pending keeps the last accepted tile/marker with a
nearby text status, without pulsing. State combinations must remain legible:
current+visited, available+focus, selected+focus and current+pending.

Artwork does not authorize movement. Do not add drawn links, speculative
locations or encounter badges that disclose hidden encounters. Selection is
not a claim that the server accepted a move or recruited a hero.

Backdrops use a `640×360` viewBox and opaque base fill. Use background, middle
distance and ground groups; no parallax or animation. Keep the middle 60% of
the width and lower half sparse for figures. Essential landmarks remain in
the central 70% of the width and upper 65% of the height. Preserve aspect ratio;
mobile may letterbox instead of cropping essential landmarks. Dialogue and
choices sit in a separate opaque HTML panel below the illustration.

The gallery must include a mobile and desktop composition with Capy, one
companion, a backdrop, a character name, trait/need text and two ordinary
choices plus a pause option. Also show three recruited portraits with names
and an empty party. These are fixture demonstrations, with no controller,
persisted state or recruitment effects. Actual choice counts come from public
content in 30.5. Companion slots must not resemble locked collectibles or a
completion checklist. Long text increases layout height without truncation.

## Asset and React boundary

Place source artwork under `app/ui/src/assets/game/` and reusable renderers
under `app/ui/src/components/game/art/`. Include a catalog manifest and short
art guide documenting each ID, kind, variants, dimensions, safe area, fallback,
source/provenance and catalog version. Keep one canonical ID list; derive
TypeScript unions from it rather than independently maintaining duplicate
lists. Export serializable catalog metadata separately from React components
so 30.2/30.6 can consume or package an allowlist without importing browser code.
Do not add engine/backend dependencies to React in this part.

Suggested local API (names may follow repository conventions):

```tsx
<GameCharacter assetId="character.mela-bee" variant="portrait"
  expression="attentive" decorative />
<GameTerrain assetId="terrain.water" decorative />
<GameBackdrop assetId="backdrop.reed-bank" decorative />
```

Expose only bounded ID/variant/expression/orientation enums and accessibility
props. Position, tile states, sizing and layout belong to trusted UI code.
No arbitrary SVG markup, paths, CSS, component names, URLs, filenames or color
strings may come from content or generation. The runtime AI never draws; no
image-generation or remote illustration API belongs in the game pipeline.

Resolve assets through explicit registry entries/static imports. Never derive
an import path from a received string. Use React SVG elements or build-time
trusted SVG imports; no `dangerouslySetInnerHTML`, runtime SVG parsing, scripts,
event attributes, `foreignObject`, embedded raster images, remote references,
external fonts, SMIL, filters or external styles. Local clip paths/gradients are
allowed only when necessary and their DOM IDs must be unique per instance.
Ordinary solid fills are preferred.

Unknown, absent or wrong-family IDs resolve to `character.abstract-guide`,
`terrain.neutral` or `backdrop.neutral` according to the receiving component.
Invalid variants/expressions use that character's neutral supported default.
An unknown motif is omitted. A rendering fallback makes no provider request,
throws no user-visible error and does not change text or mechanical state.
Display public character names rather than replacing them with the fallback's
catalog name. Catalog labels are not alternate story dialogue.

Treat v1 IDs as stable. Future additions are additive; never repurpose an ID
for a different species/place meaning. Record `catalogVersion: 1` in metadata.
Public version negotiation, persistence and old-save projection belong to 30.2;
do not add a catalog version to snapshots in 30.1.

## Accessibility and calm behavior

Art is decorative when adjacent text already supplies its meaning: mark the
SVG `aria-hidden="true"` and keep it unfocusable. If an illustration supplies
unique meaning, require a caller-provided localized accessible name using
`role="img"` and a unique title ID. Do not expose raw catalog IDs to assistive
technology or announce every SVG subpath. Board location, speaker, trait, need,
joined state and choices must be available as HTML text in the previews.

The gallery's buttons/controls use visible focus, at least 44×44px targets,
keyboard operation and EN/PL copy. Provide a text-only preview with equivalent
fixture content and order. It must remain usable with SVGs hidden, at 360px
width and 200% zoom, and in forced colors. Decorative art may be suppressed
in forced colors; meaningful control borders/focus must remain visible.

Artwork is static. No idle bouncing, flashing, sound or timed dismissal.
A later board implementation may move Capy's container after an accepted
server transition; it must respect reduced motion and retain a static final
position. No animation is required or introduced by 30.1. Pause/skip wording
must convey that leaving is allowed without losing affection or a streak.

## Deliverables and implementation sequence

1. Inspect current Capy references and app tokens; record the chosen identity
   reference and this art direction in `docs/game-visual-art-guide.md`.
2. Author all catalog v1 artwork and the manifest, including neutral fallbacks.
   Document provenance and any license/attribution obligations per source.
3. Implement typed, side-effect-free renderers and shared hex state styling.
   Keep assets bundled locally; deduplicate common geometry and lazy-load the
   gallery through the existing build pattern. No new runtime dependency is
   needed solely for SVG rendering.
4. Provide a development/test-only gallery through the existing preview pattern
   (or a development-only entry if none exists). Do not add a production
   navigation item. Show every ID, variant, expression and required state,
   plus mobile/desktop board, encounter and party fixture compositions.
5. Add the 30.1 and intent links to the specifications index. Record validation,
   screenshots and limits in `docs/game-visual-catalog-acceptance.md`.

Set a budget of 20 KiB uncompressed per character's combined artwork, 8 KiB per
terrain/motif and 30 KiB per backdrop; keep all catalog artwork and metadata
within 500 KiB uncompressed, excluding gallery code and screenshots. Record
measured totals. Simplify excess detail before adding compression or effects.
No external asset fetch is permitted; verify the built application loads the
gallery and art with provider access disabled and network unavailable after
the app shell/assets have been cached. Full PWA update certification is 30.7.

## Acceptance and verification

The implementation is complete only when:

- All specified assets exist as actual SVG artwork, are recognizable at their
  target sizes and share one coherent visual language. No placeholder emoji,
  raster wrappers or missing seven-place coverage remain.
- Gallery coverage includes every registered combination, all tile states and
  specified combinations, all seven settings, three companion portraits, empty
  party, text mode, long EN/PL labels and a neutral unknown-character example.
- Focus and controls remain outside clipped art; labels, trait/need text and
  choices wrap without horizontal page overflow at 360px and 200% zoom. Content
  is still understandable with all artwork hidden.
- Registry checks cover unique IDs, valid kinds, complete variants, nonempty
  provenance and local resolvable references. Focused renderer tests cover
  missing/unknown/wrong-family IDs, invalid variants, decorative/named semantics
  and multiple SVG instances without clip/title-ID collisions. Validate source
  SVGs for the prohibited constructs above, and measure actual asset sizes.
- Inspect mobile/desktop, reduced motion, forced colors and text-only gallery
  states. Record screenshots for Capy on a board, each companion, lantern grove,
  encounter and recruited party. Record contrast measurements for UI states;
  visual review is required in addition to passing automated checks.
- Run affected frontend tests/coverage, production build and static sync under
  `.github/instructions/build-workflow.instructions.md`; inspect the Spring-served
  UI for static asset correctness. Run backend/engine gates only if their code
  or contracts were actually affected. Do not enable live generation to verify
  a fixed artwork catalog.
- Existing game play still uses the existing controller, legal-move source and
  text renderer. No changes to Pack fingerprints, old saves, companion flags,
  runtime presentation DTOs or personal activity honeycomb are introduced.

Report the exact catalog inventory/version, measured sizes, screenshots,
verification performed and any outstanding visual review. Passing this part
establishes reusable art and its React boundary; it does not establish playable
movement-to-encounter flow, recruitment integration or visual release readiness.
